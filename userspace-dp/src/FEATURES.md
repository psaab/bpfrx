# userspace-dp/src/ — feature modules

The single-file feature modules sit at the crate root and are
consumed by the per-worker hot path in `afxdp/`. They're intentionally
flat: each owns one feature's lookup tables and decision logic, with
no internal sub-modules. Test layout is mixed: most feature modules
have a sibling `<feature>_tests.rs` (`nat`, `nat64`, `nptv6`,
`policy`, `screen`, `prefix_set`); some keep their tests
inline (`fairness`, `slowpath`, `protocol`, `prefix`); and a few have
neither (`state_writer`, `xsk_ffi`).

## Stages mirroring the BPF pipeline

These mirror the BPF-side stage modules in `bpf/xdp/` and `bpf/tc/`.
The table is a simplified map of feature areas — the actual order
the worker hot path runs them in is interleaved across the
session-hit and session-miss branches in
`afxdp/poll_descriptor.rs`. Read that file for the authoritative
ordering.

| File | Stage | What it does |
|------|-------|--------------|
| `screen.rs` | screen | Pre-session attack-protection checks (land, TCP SYN+FIN, no-flag, FIN-without-ACK, WinNuke, syn-frag, ping-of-death, teardrop, ICMP frag, IP source-route, plus rate-limits). Mirrors `bpf/xdp/xdp_screen.c`. **#2215 parity fixes:** `ping-of-death` now ports the #893 IPv4 fragment-reassembly formula — any IPv4 fragment where `((frag_off & 0x1FFF) << 3) + ip_total_len > 65535` drops (the prior userspace port was an ICMP-only `pkt_len > 65535` predicate that is structurally unsatisfiable on a `u16`, so fragment ping-of-death went undetected); `land` now drops on `src_ip == dst_ip` alone for IPv4/IPv6 (the prior port additionally required `src_port == dst_port`, admitting same-IP different-port spoofed frames the BPF screen dropped). **#3119:** `teardrop` now screens IPv6 as well as IPv4 — a non-first IPv6 Fragment-header fragment whose data contribution (`ip_payload_len - frag_data_off`, saturating) is `< 8` bytes drops, mirroring the #2293 dual-family `ping-of-death` coverage and the #3027 zero/under-length IPv4 case; the prior port gated `teardrop` on `AF_INET` only, so IPv6 teardrop fragments bypassed the screen. Also contains the #1374 userspace SYN-cookie runtime: deterministic cookie mint/validate, fixed-size validated-client admission table, session-miss ACK validation with current/previous/next wall-clock epoch tolerance and standby prefilter/rate-limiting, bounded SYN-ACK/RST reply enqueue, snapshot-published key derived from cluster-synced root encrypted-password material, and per-binding sent/valid/invalid/bypass/budget counters. The Go `syn-cookie` capability gate admits active SYN-cookie screen profiles only after secret material exists; missing secret material fails closed and remaining #1374 work is live HA/flood evidence before BPF source removal. |
| `policy.rs` | policy | Zone-pair → permit/deny + forwarding-class + DSCP-rewrite + filter chaining. `ZonePairKey` is a `u32` (`from_id << 16 \| to_id`); `JUNOS_GLOBAL_ZONE_ID = u16::MAX` is the sentinel for the global zone. Zone ids are a **stable name-hash** (`config.StableZoneID`, FNV-1a folded into `[1, ZONE_ID_RESERVED_MIN-1] = [1, 65533]`, a pure function of the zone NAME) carried on the event-stream wire as **u16** (#3075 widened the former u8 chokepoints — the event-stream SessionOpen/SessionClose delta, the forwarding-snapshot zone table, and the fabric zone-encoded MAC — to u16; this SUPERSEDES the #2391 u8 count cap, so `MaxUsableZoneID` is now `ZONE_ID_RESERVED_MIN-1` and a commit-time collision gate rejects two zone names that fold to the same id). `SnapshotIntegrityError::InterfaceUnknownZone` fails the snapshot CLOSED when an interface names a zone absent from the zone table instead of collapsing it to zone 0. **#2410 (validated narrowing newtypes):** the forwarding-build conversion (`afxdp/forwarding_build/validated.rs` — `VlanId`/`TunnelTtl`/`QueueId`, decoded ONCE with a checked `try_from_snapshot`) fails the snapshot CLOSED on an out-of-range integer at the second trust boundary instead of narrowing it with an unchecked `as` cast: a VLAN id > 65535 (`InterfaceVlanOutOfRange`) no longer wraps to a different L2 domain, a tunnel TTL > 255 (`TunnelTtlOutOfRange`) no longer wraps 256→0 (blackhole), and a CoS forwarding-class queue id outside 0..=255 (`CosQueueIdOutOfRange`) is no longer silently dropped from `class_to_queue`. **#2409 (fail-silent drop):** an interface address that fails `IpNet` parse (`InterfaceAddressUnparseable`) and a CoS scheduler-map entry referencing a forwarding-class absent from the class-to-queue table (`SchedulerMapUnknownClass`) now fail the snapshot CLOSED instead of `continue`-ing — the pre-fix skips lost connected-route material or partially installed a scheduler while the apply still succeeded. All five are helper-boundary backstops to the Go commit-time gates, consistent with the #2173/#2212/#2240/#2391 fail-closed family; the apply preflight catches the Err and keeps the previous live forwarding state. **#3367/#3711 (malformed-address fail-closed):** every address parse path REPORTS an unparseable token and fails the snapshot CLOSED instead of silently dropping it — legacy `source_addresses`/`destination_addresses` (`UnrepresentableLegacyAddress`, #3367), v3 `source_literals`/`destination_literals` (`UnrepresentableV3Address`, #3711), and address-book `prefixes_v4`/`prefixes_v6` (`UnrepresentableAddressBookPrefix`, #3711). Silent-drop is a fail-OPEN: a v3 side / book collapses to `MatchNone` (a `deny` then matches nothing and falls through to default-permit), and the legacy empty→`MatchAny` path widens a deny to match-all. `UnrepresentableAddressBookPrefix` also ENFORCES the declared family (M02 — a wrong-family token is rejected, not routed to the other family's set). The `__unsupported_address__` sentinel preflight (`UnrepresentableAddress`, #3261) is checked first so its more-specific diagnostic wins. **#3771 (route/neighbor wire-struct integrity):** `populate_routes`/`populate_neighbors` (afxdp/forwarding_build/fib.rs) are now fallible and fail the snapshot CLOSED on self-contradicting metadata — a route whose non-empty `family` disagrees with its parsed destination prefix (`RouteFamilyMismatch`, M4), a route with a negative `preference` that would sort ahead of every route in the `sort_routes` tie-break (`RoutePreferenceOutOfRange`, L1; Go primary gate = `schema_routing.go` `ValidateInteger(0, i32max)` on the route `preference` leaf), and a neighbor whose non-empty `family` disagrees with its parsed `ip` (`NeighborFamilyMismatch`, M11). An EMPTY `family` is unconstrained (parse-only). Separately (M12) `neighbor_state_usable`/`classify_neighbor_state` (afxdp/forwarding/mod.rs) became an ALLOWLIST (`reachable`/`stale`/`delay`/`probe`/`permanent`/`noarp`): `failed`/`incomplete` are skipped silently, and an empty/`none`/future/corrupt state is skipped AND counted by the `NEIGHBOR_UNKNOWN_STATE_SKIPPED` diagnostic atomic (the pre-fix denylist installed every unrecognized state carrying a parseable IP+MAC). |
| `nat.rs` | NAT44 | Source / destination / static NAT decisions. `NatDecision` carries `rewrite_src` and `rewrite_dst` Options the TX path consumes. **#2394:** the DNAT table (`nat/destination.rs`) matches a rule on `(protocol, dst_ip, dst_port)` AND its `match source-address` constraint — a source-scoped DNAT (`DnatEntry.source_v4/source_v6`, CIDR or bare-host /32 /128) fires only for packets whose source IP falls in a configured prefix. `DnatEntry.source_constrained` distinguishes an UNSCOPED rule (no `source-address` -> match any source, unchanged behavior) from a SCOPED rule whose entries all failed to parse (-> match NOTHING, fail closed — never match-any). Before #2394 the source constraint was dropped at the Go->Rust snapshot boundary, so a source-scoped DNAT became destination-only and published the internal service to every source (fail-open). **#2398 (SNAT sibling):** the SNAT match logic (`nat/source.rs`) gets the same fail-closed treatment for BOTH its source AND destination match sets. `SourceNatRule.source_constrained`/`destination_constrained` (derived at decode from the snapshot match list being non-empty — no wire field) drive `nets_match_v4`/`nets_match_v6`: no match set -> match any (unscoped, unchanged); a non-empty match set whose prefixes ALL fail to parse -> match NOTHING (fail closed). Match prefixes also parse a bare host IP -> /32 (v4) or /128 (v6). Before #2398 an empty parsed list collapsed to match-any, so a SNAT rule whose match prefixes were all typo'd silently translated all traffic in the zone pair (fail-open broadening). |
| `nat64.rs` | NAT64 | RFC 6052/7915 IPv4↔IPv6 translation. `Nat64Prefix` is the 96-bit + IPv4-pool config; `Nat64ReverseInfo` carries the original IPv6 tuple for reverse translation. **No per-packet heap alloc on the transit path (#2211):** `write_v6_to_v4_into`/`write_v4_to_v6_into` translate directly into a caller buffer with a streamed pseudo-header checksum; the frame builders make exactly one output allocation (`TxRequest.bytes`). **Fail-scoped config parse (#2212, refined by #3888):** `from_snapshots` is INFALLIBLE (`-> Self`) and SKIPS the offending NAT64 rule (logging a loud one-line warning naming the rule + reason) on a bad prefix or a non-host pool address, publishing the remaining NAT64 rules AND every other rule type. The whole rule is dropped all-or-nothing — a single bad pool entry drops its rule rather than silently NARROWING the pool (preserving #2212's intent) — mirroring the sibling `DnatTable`/`StaticNatTable`/source-NAT skip-and-continue posture (#1960 lenient-load doctrine). Pre-#3888 the fallible `try_from_snapshots` returned `SnapshotIntegrityError::Nat64UnparseableRule` that propagated via `?` out of `build_reconcile_forwarding`, so ONE bad NAT64 rule (from a mixed-version HA peer-sync or a corrupt snapshot — paths the Go gate doesn't cover) froze the ENTIRE control→dataplane pipeline, blocking every other rule type + every later commit. The Go #2173/#3886 commit-time gate remains the primary defense; this is the helper-boundary backstop, now scoped to a NAT64-only degradation. NPTv6 (`nptv6.rs`) intentionally stays fail-CLOSED (abort-all) — its #2241 overlap rejection is order-dependent so a blind per-rule skip would be ambiguous (flagged follow-up). **RFC 7915 fragment translation (#2488):** v6→v4 derives the IPv4 MF/offset/Identification (low 16 bits of the 32-bit id) from the IPv6 Fragment Header when present (`ipv6_fragment_header`), falling back to the `no-v6-frag-header` atomic-datagram policy only when absent; v4→v6 inserts an 8-byte IPv6 Fragment Header (next-header 44) for a fragmented IPv4 input, copying offset/MF and zero-extending the 16-bit id. A first-fragment TCP/UDP checksum is adjusted incrementally for the v4↔v6 pseudo-header address delta (RFC 1624) since the full payload is absent; a v4 UDP fragment with a zero checksum is dropped (cannot synthesize the mandatory v6 checksum). **Non-first fragment traversal (#2562):** a stateful fragment-association cache (`Nat64FragAssoc`, port-free key `(family, src, dst, ip_id)`, bounded LRU + ~2s TTL, cross-worker via the shared `Arc<ForwardingState>`, NOT HA-synced) lets a non-first TCP/UDP fragment INHERIT the first fragment's translation and translate L3-only (`write_v6_to_v4_nonfirst_into`/`write_v4_to_v6_nonfirst_into` — payload verbatim, no L4 checksum, IPv4 ident = low-16 of the v6 ident / v6 ident = v4 ident zero-extended) so the whole datagram reassembles: the FIRST fragment installs the association on the cold path, and a non-first fragment consults it on the flowless arm. The FORWARD (v6→v4) direction is wired end to end; the REVERSE (v4→v6) translator + frame-builder are in place with the reverse-reply install/consult a follow-up. A non-first fragment with NO association (reorder / orphan / eviction / cross-node failover) still drops fail-closed (#4617, `nat64_frag_dropped`) — never forwarded to a wrong source. Fragmented ICMP/ICMPv6 stays dropped both directions (below); true IP reassembly (`force-ip-reassembly`) remains a separate feature. **#5689 — ordinary same-family NAT / NPTv6 fragment consistency (SAME cache):** `Nat64FragAssoc` is deliberately generic — its port-free key `(family, src, dst, ip_id)` and full `SessionDecision` value are family-agnostic — so an ORDINARY same-family SNAT / DNAT / static-NAT / NPTv6 forward flow now installs a fragment association too (`nat_install_forward_fragment_assoc`, called at the cold-path forward-commit point where the composed NAT decision is final) and its non-first fragments consult it on the flowless arm (`nat_consult_forward_fragment_assoc`, tried after the NAT64 consult, for BOTH IPv4 and IPv6). A hit inherits the first fragment's permitted verdict + egress resolution and the forward-build path applies an ADDRESS-ONLY L3 rewrite (`apply_nat_ipv4` / `apply_nat_ipv6` already SKIP the L4-checksum + port rewrite for a non-first fragment, #1852), so the whole datagram reassembles TRANSLATED at the receiver. Before #5689 a non-first fragment of an ordinary-NAT'd flow resolved `NatDecision::default()` on the flowless arm and was forwarded UNTRANSLATED (leaking the internal source / pre-DNAT destination). The `nat64` flag on the cached decision keeps NAT64 and ordinary-NAT associations from aliasing (a given datagram installs exactly one entry; the ordinary consult filters out `nat64` entries and vice-versa), and the shared `build_generation` guard — which advances on EVERY config commit (`snapshot.generation`), not only NAT64 changes — invalidates a stale ordinary-NAT association after a SNAT / DNAT rule change. FORWARD-only, mirroring the NAT64 forward-first wiring (the reverse-reply association is a deferred increment). Pinned by `flowless_non_first_fragment_inherits_ordinary_snat_translation_5689`. **#2562 fail-closed ICMP fragment drop + counter:** a REAL fragment (Fragment Header present with MF=1 OR a non-zero offset) carrying ICMP/ICMPv6 is now DROPPED both directions — the ICMP checksum covers the WHOLE datagram, so `translate_icmpv6_message_to_icmpv4` / `translate_icmpv4_message_to_icmpv6` over a single fragment's bytes would emit a FIRST fragment with a wrong checksum the receiver discards (the pre-#2562 behavior). An ATOMIC fragment (MF=0, offset 0 — RFC 6946) carries the complete message and still translates; a first-fragment TCP/UDP keeps its incremental-checksum translation. The fail-closed drop — the today-silent non-first-fragment drop AND the new ICMP-fragment drop — is now OBSERVABLE: `nat64::frame_is_nat64_fragment_drop` (the SSOT predicate mirroring the translator guards, `v6_to_v4_is_fragment_drop`/`v4_to_v6_is_fragment_drop`) attributes a NAT64 `build_nat64_forwarded_frame`-returned-`None` at the TX dispatcher to a new per-binding `nat64_frag_dropped` counter (`BatchCounters::record_nat64_frag_dropped`, wired through the #4520 plumbing — live atomic, snapshot, wire `BindingStatus`, summed as the `NAT64 fragment drops` row in `format/status.go`). This is the observable-drop half of #2562; the stateful frag-association cache that lets real TCP/UDP fragments traverse end-to-end (the #3291 stage-4 principled fix) is now built — see **Non-first fragment traversal (#2562)** above — with fragmented ICMP staying the fail-closed drop (the ICMP checksum covers the whole datagram). **RFC 6146 BIB — stateful port/identifier translation (#4381):** NAT64 is a many-to-one (v6→v4) translation, so two IPv6 clients behind ONE pool v4 address that share a TCP/UDP source port or ICMP echo identifier would otherwise produce an identical reverse (v4→v6) 5-tuple and the server's replies would be mis-associated. Each `Nat64Prefix` now owns a `PortAllocator` — the SAME pool-mode SNAT allocator (`nat/allocator.rs`) — and `Nat64State::allocate_source` hands every admitted forward flow a UNIQUE `(pool v4 address, translated source port / ICMP identifier)`. `forward_decision` carries the translated value in `rewrite_src_port`; the frame builder (`afxdp::frame::build_nat64_forwarded_frame`) rewrites the L4 SOURCE via the same-family `apply_nat_port_rewrite`/`apply_nat_icmp_identifier_rewrite` (incremental checksum) on the forward path, and `NatDecision::reverse` restores the ORIGINAL client port/id on the L4 DESTINATION on the reverse path. The reverse session key therefore keys on the TRANSLATED value (what the server replies to). Allocation is deferred to the Permit branch (a denied flow consumes no pool port) and rolled back on every install-failure exit; the reaped/purged forward entry frees the port via `release_nat64_allocation` alongside `release_source_nat_allocation`. The pool exhausting (no free translated port) fails CLOSED (drop). **#4520 counter split:** the drop reason carried on `allocate_source`'s `Err(SourceNatFailureReason)` is now attributed distinctly — transient `AllocatorExhausted` (pool full under load → add capacity) bumps `nat64_pool_exhausted`, while a config/empty/missing pool (the classify-time `MatchUnavailable`, plus any non-exhaustion allocate error → fix config) keeps `nat64_no_source_pool`, mirroring source-NAT's `pool_empty`/`pool_exhausted` separation so the two opposite-remedy cases are distinguishable on `show ... status` (`BatchCounters::record_nat64_source_failure`, both surfaced per-binding through the wire `BindingStatus` and summed in `format/status.go`). BOUNDARIES: the allocator is rebuilt fresh on every config commit (like the pre-#4381 round-robin `pool_index` reset), so live reservations do not survive a snapshot rebuild — a bounded overlap window until pre-reload sessions age out (preserving allocations across reload, à la source-NAT `reuse_pool_allocator`, is a follow-up); and (pre-#4565) `Nat64ReverseInfo` was NOT HA-synced, so a standby could not reverse-TRANSLATE a promoted NAT64 session. **#4512 port-reservation sync:** the translated-port carriage already rides `NatDecision` (which IS synced), and the standby now RESERVES that port in its local NAT64 allocator when the forward session is peer-synced (`reserve_synced_nat64_allocation`, called from `handle_upsert_synced`, mirroring #4388's `reserve_synced_source_nat_allocation`), freed by the same `release_nat64_allocation` on reap/purge/delete-sync — so a post-failover local flow can no longer `allocate_source` a `(snat_v4, port)` still owned by an in-flight synced session (the cross-node analog of #4518's same-node reload durability). Pinned by `nat64_4512_synced_session_reserves_translated_port`. **#4565 reverse-BIB sync (completes the HA story + ARMS #4512/#4564):** a peer-PROMOTED NAT64 session can now reverse-translate its v4→v6 replies after failover. The KEY realization: the original v6 src/dst ARE the synced forward v6 session key (`key.src_ip`/`key.dst_ip` == `orig_src_v6`/`orig_dst_v6`, since a NAT64 forward flow is keyed on the original IPv6 5-tuple and no DNAT/NPTv6 composes with it), and `dst_v4` is the RFC 6052 /96-embedded low 32 of the key dst — so the ONLY datum the standby cannot reconstruct is the translated pool source `snat_v4` (chosen by `allocate_source`, not in the key). A single new tag-matched wire field carries it: FLAG_NAT64 (event-stream open frame) + a trailing `snat_v4` → `SessionDeltaInfo.Nat64`/`Nat64SnatV4` → `SessionValueV6.Nat64SnatV4` (a length-gated trailing field on the cluster sync payload, riding alongside the #3301 fields) → `SessionSyncRequest.nat64_snat_v4` (Go+Rust, self-signaling — the protocol_wire_v1.json / cross-language contract field). On the standby `build_synced_session_entry` rebuilds the forward NAT decision (`nat64 = true`, `rewrite_src = snat_v4`, `rewrite_dst = dst_v4`; the translated port already rides `nat_src_port`) and stamps `metadata.nat64_reverse` from the v6 key; `build_reverse_session_from_forward_match` inherits it onto the synthesized reverse companion, and `reverse_session_key` then derives the correct v4 `(server → snat_v4)` reply tuple. Because the pre-#4565 synced entry set `nat64: false`, #4512/#4564's `reserve_synced_nat64_allocation` (gated on `nat.nat64`) was a silent no-op on the real HA path — #4565's `nat64` flag is what ARMS it. Pinned by `nat64_synced_entry_rebuilds_reverse_bib_4565` (Rust) + `synthesized_synced_reverse_entry_inherits_nat64_reverse_4565` + the Go `TestSessionWireRoundTripNat64SnatV4_4565` / `TestBuildSessionSyncRequestV6CarriesNat64SnatV4_4565` / `TestDecodeSessionEventNat64_4565`. **#5606 reverse info on the LIVE TX request (local, non-HA path):** the reverse `Nat64ReverseInfo` lived only on `SessionMetadata`, but the live-forwarding `PendingForwardRequest` — the descriptor the TX dispatcher hands `build_nat64_forwarded_frame` — hard-coded `nat64_reverse: None`. So a server's IPv4 reply to a NAT64 flow reached the AF_INET (v4→v6) branch of the frame builder with no reverse info, which returns `None` (fail-closed) and DROPPED the reply / could not translate an embedded ICMP error. `build_live_forward_request_from_frame` now takes a `nat64_reverse` parameter that its poll-loop callers thread from the matched reverse-companion session's metadata (`resolved.metadata.nat64_reverse` on the session-hit resolve): the reverse companion of a NAT64 flow is installed keyed on the translated v4 reply tuple with `metadata.nat64_reverse = Some(orig_v6_src/dst)` and `decision.nat.nat64 = true`, so the reply's session-hit supplies exactly what the builder needs. Only this LIVE path needs it — the embedded-ICMP (`try_reverse_embedded_icmp_error`) and generated-time-exceeded (`icmp.rs`) constructors build PREBUILT frames with a `NatDecision::default()` (non-NAT64) decision, so the dispatcher enqueues their bytes directly and never calls `build_nat64_forwarded_frame`; their `nat64_reverse` field is inert (they translate internally). Non-NAT64 flows keep `None` (the common IPv4/IPv6 same-family path is byte-identical). The threading is uniform across every `build_live_forward_request_from_frame` caller — slow-path transit, cluster-peer-return, and flow-cache fallback — even though NAT64 is excluded from the flow cache (`FlowCacheEntry::should_cache`) and the peer-return metadata is always `None`, so the invariant "request.nat64_reverse mirrors its driving session metadata" holds everywhere. Pinned by `build_live_forward_request_threads_nat64_reverse_info_5606` (constructor threading + non-NAT64 control) + `nat64_5606_reverse_frame_requires_reverse_info_or_drops` (consumer: `Some` → correct IPv6 reply, `None` → drop). **RFC 6146 §3.5 source eligibility (#5623):** the forward IPv6 path now gates on the SOURCE address BEFORE any allocation/translation. `Nat64State::source_within_pref64` flags a source whose high 96 bits match ANY configured Pref64 — a looping/synthesized "already-translated" source (the §5 hairpin construction), which subsumes the degenerate lower boundary `<prefix>::` (embedded v4 `0.0.0.0`), the upper boundary `<prefix>::ffff:ffff` (embedded v4 `255.255.255.255`), and any source whose embedded v4 is non-global (still inside the prefix). `Nat64State::classify_ipv6_packet(src, dst)` runs that check ahead of the unchanged `classify_ipv6_dest`, returning the distinct fail-closed `Nat64Match::IneligibleSource`; the pre-routing NAT64 arm in `poll_descriptor` drops it with `BatchCounters::record_nat64_ineligible_source` (→ `BindingLiveState.nat64_ineligible_source`, wire `BindingStatus.nat64_ineligible_source`, the `NAT64 ineligible-source drops` row in `format/status_sections.go`) BEFORE route lookup, policy, or `allocate_source`, so a spoofed/looping source mints NO session, BIB, or allocation state. The scan is one bounded, allocation-free pass over the small prefix list (identical shape to `match_ipv6_dest`), safe on the session-miss hot path, and an eligible global-unicast source outside every Pref64 falls through to translate exactly as before (no over-reject). Pinned by `nat64_5623_source_{lower,upper}_pref64_boundary_rejected` / `nat64_5623_source_looping_synthesized_rejected` / `nat64_5623_eligible_global_unicast_source_translates` / `nat64_5623_eligible_source_non_nat64_dest_still_routes`. **RFC 7915 §5.1 translation-eligibility gate (#5625):** the v6→v4 forward translators (`write_v6_to_v4_into` / `write_v6_to_v4_nonfirst_into`) now REJECT (fail-closed drop) — BEFORE resolving the terminal L4 — a packet carrying an Authentication Header (51), an ACTIVE Routing header (43 with Segments Left > 0), or a Mobility (135) / HIP (139) / Shim6 (140) header, via the `nat64_v6_translation_ineligible` chain walk. | `nptv6.rs` | NPTv6 | RFC 6296 stateless IPv6-to-IPv6 prefix translation. Each rule maps an internal /48 or /64 to an external prefix; a precomputed adjustment value keeps the L4 checksum neutral so no checksum update is needed after rewrite. **Fail-closed config parse (#2240):** `try_from_snapshots` rejects the whole snapshot (`SnapshotIntegrityError::Nptv6UnparseableRule`) on an unparseable / unsupported / mismatched-length prefix rather than silently `continue`-ing past the bad rule (the pre-fix skip let the Go compiler's `DeleteStaleNPTv6` tear down a working translation on a typo — a fail-open in a retired-eBPF world); helper-boundary backstop to the Go #2240 commit-time gate (`pkg/config/compiler_nat.go`). **Overlap rejection (#2241):** because the runtime resolves a match by FIRST hit in insertion order with no longest-prefix-match, `try_from_snapshots` also rejects the whole snapshot (`SnapshotIntegrityError::Nptv6OverlappingPrefix`, carrying the two rule names + the offending `direction`) when two rules have overlapping prefixes in the same direction — internal/outbound or external/inbound, including a /48 that nests a /64 and identical prefixes. Without it a broad prefix configured before a more-specific one would shadow it and reordering the same rules would change the translation identity; rejecting keeps translation deterministic and order-independent. The Go commit-time gate (#2241, `validateNPTv6Strict` in `pkg/config/compiler_nat.go`) is primary; this is the helper-boundary backstop. The lenient load path (#1960 doctrine) downgrades both #2240 and #2241 violations to warnings so a pre-gate or peer-synced config still boots, and the helper preflight (not the validator) is what keeps the previous forwarding state until the rule is corrected. |

|------|--------------|
| `slowpath.rs` | TUN device injection for firewall-local packets (TCP retransmits, ICMP errors). Built on `io_uring` for batched submit. Rate-limited with `DEFAULT_RATE_LIMIT_PACKETS_PER_SEC = 1_000_000` and `DEFAULT_RATE_LIMIT_BYTES_PER_SEC = 4 * 1024 * 1024 * 1024` (4 GiB). |
| `fairness.rs` | Pure functions for the fairness-regimes contract (`compute_cstruct`, `compute_observed_cov`, `starved_flow_count`). Consumed by the `fairness-eval` binary and by the contract's pinned worked-example tests. See `docs/fairness-regimes.md` and `docs/per-5-tuple/state.md`. |

## Lookup-structure helpers

## Wire / transport / state

| File | What it does |
|------|--------------|
| `protocol.rs` | Control request / response and snapshot schema types shared between the control socket server (`server/`) and the AF_XDP coordinator. The JSON tags ARE the wire contract — changing them without updating the Go side (`pkg/dataplane/userspace/protocol.go`) breaks the helper. |
| `state_writer.rs` | Crash-safe writer for the daemon's state snapshot file. Each write goes to a PRIVATE temp path `<dest>.<pid>_<starttime>.<seq>.tmp` (process-instance identity = pid + `/proc/<pid>/stat` start time, plus a process-global monotonic counter), created `O_EXCL`, so two writers — even overlapping helper processes during a restart/upgrade handover — can never open/truncate/write the SAME temp and publish crossed bytes under a successful rename (#2705). Both the `io_uring` transport and the sync fallback route through one durable finalizer (`finalize_durably`): fsync temp file → atomic rename → fsync parent dir (#2147); a failed write removes its unique temp so nothing leaks. A best-effort orphan sweep (once per destination) removes temps from crashed writers, keyed on pid **and** process start time so a recycled pid can't make a stale orphan look live-owned (#2957). |
| `xsk_ffi.rs` | Drop-in replacement for `xdpilone` using libxdp's XSK helpers via a C bridge. Provides the same type names (`Umem`, `UmemConfig`, `UmemChunk`, `IfInfo`, `Socket`, `DeviceQueue`, `RingRx`, `RingTx`, `ReadRx`, `WriteTx`, `WriteFill`, `ReadComplete`, `XdpDesc`) so the rest of the crate compiles unchanged. |
| `test_zone_ids.rs` | Test-only zone-id constants used across `_tests.rs` files. |
| `main.rs` / `main_tests.rs` | Crate `main()` — argv handling and dispatch into `server::lifecycle::run()`. Tests live next door. |

## Where these are called from

The worker poll loop drives the per-packet stages from
`afxdp/worker/lifecycle.rs::poll_binding` and the per-descriptor
dispatch in `afxdp/poll_descriptor.rs`. The stages above approximate
the "session-hit" fast path; the real session-miss order interleaves
DNAT, NPTv6 inbound, NAT64, FIB / forwarding resolution, policy, and
SNAT decisions across multiple branches in `poll_descriptor.rs`. Read
that file for the authoritative order — the tabular pipeline above is
intentionally simplified.

`fairness` is an auxiliary surface consumed by the `fairness-eval`
binary. (Flow export — NetFlow v9 / IPFIX — is NOT a dataplane module:
it is owned entirely by the Go control plane `pkg/flowexport`, driven by
SESSION_CLOSE events. The dead Rust `flowexport.rs` exporter was removed
in #2130; the dataplane emits no flow records.)
