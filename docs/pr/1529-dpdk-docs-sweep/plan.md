# #1529 — DPDK Docs Sweep (Phase 4 of #1525)

**Status:** DRAFT v2 — addressing Codex r1 PLAN-NEEDS-MAJOR
findings. Antigravity r1 PLAN-READY with two minor recommendations
incorporated.

## Issue framing

#1525 retires the DPDK dataplane. The sibling Chain A issue #1531
rewrites the two architectural design docs that recommend DPDK as a
live backend (`docs/dataplane-decision-dpdk-vs-vpp.md`,
`docs/dpdk-dataplane.md`). The mechanical removal of `dpdk_worker/`,
`pkg/dataplane/dpdk/`, `Makefile` targets, config schema, and canary
allowlist entries happens later in #1528 / #1527.

This PR (#1529) is the **broad documentation sweep** — every other
top-level repo doc that still describes DPDK as a live, secondary, or
forward-looking backend. After this PR merges, a new operator reading
the repo from `README.md` outward must not be able to conclude that
DPDK is currently in scope.

The PR is pure-text. No code is touched. No source files (`*.rs`,
`*.go`, `*.c`, `*.h`, `Makefile`, `debian/*`) are modified. The diff
is bounded to `*.md` files under the repo root and `docs/`, plus
`CLAUDE.md` and `README.md`.

## Honest scope / value framing

This is documentation correctness work. The win is operator clarity
and removal of contradictions between docs and runtime behavior once
#1525 Phase 1 (commit-time rejection of `system dataplane-type dpdk`)
ships. There is no perf or memory win. The risk is leaving stale
"DPDK is recommended" language in any doc an operator might read,
or over-editing historical PR/issue records and rewriting history.

If reviewers conclude the doc churn is too speculative or too broad
(e.g., touching files better left alone until #1528 actually deletes
the code), PLAN-KILL is an acceptable verdict. The alternative is to
defer this sweep entirely until after #1528 lands, on the theory that
edits to docs that reference paths about to be deleted are wasted
churn.
