Not a kill. The direction is right, but this plan is not implementation-ready.

**Findings**

1. **A4 validation is overclaimed and partly wrong.**  
   The plan says a Secure-Boot-capable profile makes “#1930 A4 boot-path work … live-validatable” ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:55)), but its actual validation only exercises A4 “if V2/baked-image” ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:260)). Default V1 does not stage `/etc/grub.d/09_xpf`, `xpf-uefi-slots`, `xpf-kernel-promote`, or A/B ESP dirs; bake.py does that explicitly ([bake.py](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/scripts/image/bake.py:330), [bake.py](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/scripts/image/bake.py:339), [bake.py](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/scripts/image/bake.py:351)).  
   Worse, the plan repeatedly says `grub-reboot`, but the actual A4 path uses `efibootmgr --bootnext <inactive-slot>` ([kernel.go](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/pkg/upgrade/kernel.go:17)). EFI varstore validation must prove BootOrder/BootNext persistence, not grubenv behavior.

2. **The kernel gate is necessary but not sufficient.**  
   The plan gates on `uname -r >= 6.18` ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:84)) and proposes only `dpkg --compare-versions` ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:136)). That prevents a too-old verifier kernel, but not a VM missing the real dataplane driver set. Production bake installs `linux-generic` ([bake.py](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/scripts/image/bake.py:219)) and hard-asserts Mellanox modules exist ([bake.py](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/scripts/image/bake.py:226)). The kernel-upgrade code says omitting `linux-modules-extra` can boot a candidate that “cannot drive the dataplane NICs” ([kernel_linux.go](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/pkg/upgrade/kernel_linux.go:203)). Add module/driver assertions.

3. **Package delta audit is incomplete.**  
   The plan says only `golang` and `linux-perf` are at-risk and that `host` is identical ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:154)). Current scripts install `host` and `linux-perf` ([setup.sh](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/test/incus/setup.sh:281)); cluster also installs `frr-pythontools` and `ethtool` ([cluster-setup.sh](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/test/incus/cluster-setup.sh:459)). Ubuntu resolute has `golang-go`, `linux-tools-generic`, and `bind9-host` as the obvious package names, not proof that plain `golang`, `linux-perf`, or `host` are safe defaults. Sources: Ubuntu package list shows `golang-go` lines 8561-8562, `linux-tools-generic` lines 3199-3200, and `bind9-host` lines 193-198. The plan must simulate the exact full standalone and cluster package lists.

4. **The GRUB drop-in fix is directionally right but incomplete.**  
   Bake’s `GRUB_DROPIN` appends `init_on_alloc=0` and also sets `GRUB_DISABLE_SUBMENU=y` ([bake.py](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/scripts/image/bake.py:77)). The plan says to delete the kernel reboot loop ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:131)), but current setup’s reboot is also what applies the GRUB cmdline after `update-grub` ([setup.sh](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/test/incus/setup.sh:303)). If you keep `init_on_alloc=0`, keep a post-GRUB reboot or explicitly accept that it is inactive until the next reboot.

5. **Cluster validation does not validate the cluster image change.**  
   The plan says for C1: `make cluster-deploy` plus fast smoke ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:265)). But `IMAGE_VM` is consumed only during VM creation ([cluster-setup.sh](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/test/incus/cluster-setup.sh:334)); `cluster-deploy` only builds and pushes binaries ([Makefile](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/Makefile:256)). Also, smoke really is on the loss userspace cluster ([CLAUDE.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/CLAUDE.md:85)). Either scope cluster out explicitly, or require a locked recreate/rolling replace plus smoke.

6. **Pinning is right, but the plan contradicts itself and breaks rollback.**  
   It says `make test-vm` should match bake.py with “default auto-latest” ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:44)), then proposes pinned `26.04` ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:112)). Pinning the test VM is the right call for this issue, but say that consistently. Also the proposed `IMAGE_VM="..."` assignment is not env-overridable, yet rollback claims `IMAGE_VM=images:debian/13 make test-vm` works ([plan.md](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/docs/research/1943-ubuntu-test-env-parity/plan.md:282)). Use the cluster pattern: `IMAGE_VM="${IMAGE_VM:-...}"` ([cluster-setup.sh](/home/ps/git/bpfrx/.claude/worktrees/1943-research-ubuntu-parity/test/incus/cluster-setup.sh:85)).
