# #6846 — CoS `transmit-rate remainder` and `buffer-size temporal` were accepted-but-inert

- **Timestamp**: 2026-08-27
  - **Action**: resolved both forms, the last two of #4228 Gap 2's four
    sub-items. Both parsed, committed and stored a typed value that nothing
    consumed — each carrying a commit advisory naming itself as the residual,
    so the gap was self-documented in the shipping artifact and still live.
  - **Premise re-verified before starting**, by the check that settles it —
    not "does the cited line still exist" but "does anything downstream consume
    the field". `TransmitRateRemainder` was written at
    `compiler_class_of_service.go:488` and read only by a strict validator and
    a warning; `BufferSizeTemporalUS` at `:503`, read only by a warning.
    Neither reached the dataplane. The issue's contrast held: `percent` DOES,
    so there was an existing seam to extend rather than one to invent — which
    is what kept this M rather than L.
  - **`remainder` is a PRE-PASS, and that is the whole difficulty.** It means
    "whatever the interface shaping rate has left once every SIBLING queue on
    the scheduler-map resolves", so it cannot be computed inside the
    per-scheduler helper the way `percent` can. `cos_remainder_rate_bytes` runs
    once per interface before any queue is materialized; computing it inside
    the materialization loop would give each remainder queue a different
    PARTIAL sibling set depending on iteration order.
  - **The sibling sum is over RESOLVED siblings only.** A sibling that is
    itself `remainder` contributes ZERO (it claims the leftover, not a share of
    it); one with no rate contributes zero (no guarantee to subtract).
    Summing an unresolved sibling yields a leftover that looks right and is not.
  - **`Some(0)` and `None` are different answers**, and the narrowed advisory
    depends on the difference: over-subscription RESOLVED, to zero (legal to
    express, so rejecting it would break configs that commit today — but a
    silently starved queue looks configured, so commit warns); no shaping rate
    did not resolve at all.
  - **No shaping rate stays inert, measured rather than assumed.**
    `InterfaceSnapshot` carries no link-speed field at all, and
    `contributes_usable_cos_state` already treats a zero shaping rate as "no
    usable CoS state". There is no base to take a remainder of and none
    available to substitute; plumbing an ethtool/netlink read onto the Rust
    wire would change what EVERY CoS knob means on an unshaped interface,
    which is a different change.
  - **The split FLOORS by decision, not by `/`.** An indivisible leftover
    loses up to `count - 1` bytes/sec — noise against any shaping rate a
    remainder is meaningful on. Ceiling would make the remainder queues
    jointly claim MORE than the leftover they came from; distributing the
    slack would make the result depend on WHICH queues come first,
    reintroducing the map-order dependence the pre-pass exists to avoid.
  - **`temporal` resolves after the rate**, including after `remainder` when
    both are set on one queue — that combination is LEGAL, because temporal is
    well defined once remainder resolves and a strict gate refusing a
    combination the model supports would break valid Junos.
    `cos_temporal_buffer_bytes` returns `None` for a zero rate: a queue with no
    drain speed has no byte value for a microsecond target, and returning 0
    would be a blackhole dressed as configuration.
  - **Cells shaped so a weaker fixture cannot pass them.** The two-remainder
    split uses an INDIVISIBLE leftover (999 across two queues), because an
    evenly-divisible one returns the same number under floor, ceil, and
    distribute-the-slack — and also catches a `leftover`-not-`leftover/n`
    implementation. The resolved-sibling cell carries a PERCENT sibling,
    because an absolute-only fixture cannot tell "resolve percent" from
    "ignore percent". Order-independence is asserted rather than hoped for.
  - **Incidental**: adding two additive wire fields broke 71 exhaustive
    `CoSSchedulerSnapshot` literals across five test files. Mechanically given
    `..Default::default()`, which is what they should have carried — an
    exhaustive struct literal in a test turns every additive wire field into a
    compile break in code that does not care about the field.

  message was right and the predicate was wrong
  - **Measured, not argued.** A probe drove `build_cos_state` with a shaped
    interface (10_000_000 B/s) and a scheduler carrying ONLY
    `buffer-size temporal 1s` — no absolute rate, no percent, no remainder —

    `default_cos_burst_bytes` would give. So temporal DID convert, on a queue

    A queue with no guarantee still drains at the interface shaping rate, so a
    microsecond target against it still has a byte value. "No resolvable
    transmit-rate" and "no drain rate" are different questions, and I had used
    the first to answer the second.
  - **The advisory TEXT already named the right condition** — "no absolute
    rate, and no scheduler-map binding to an interface with a root
    shaping-rate". The message and the predicate disagreed and the message was
    right; `cosSchedulerTemporalResolves` now implements what the message says.
  - **The F3 subtest was flipped, and it was my own reasoning that was wrong.**
    "remainder with a ZERO leftover still warns" asserted a temporal advisory on
    the reasoning that the queue has no rate. The queue has no GUARANTEE, which
    is not the same thing. The remainder advisory still fires for that shape —
    `TestRemainderAdvisoryTracksTheLeftover6846` asserts it — so the operator
    still gets the signal that matters, about the knob that is actually inert.
  - **A row was added that keeps the predicate honest**: bound to an UNSHAPED

- **Timestamp**: 2026-08-27
- **Action**: Mirror the Rust percent rounding on the Go side (review F6)
  - **The duplication I flagged as a risk had already diverged.** Rust
    `cos_percent_buffer_bytes` CEILS, clamps to at least 1, and returns `None`
    outside `(0,100]`. My Go mirror was an inline
    `uint64(float64(shaping) * pct / 100.0)` — truncating, unclamped,
    unguarded.
  - **Reachable, and measured before fixing.** `percent 33.3333333` +
    `percent 66.6666667` on `shaping-rate 1g` compiles with the fractional
    percents intact: Go claimed 124_999_999 and answered "resolves" with a
    leftover of 1; Rust claims 125_000_001, saturates the leftover to zero and
    declines. Silent at commit AND inert at runtime — F3 arriving through the
    mirror instead of the predicate.
  - **My own agreement test could not see it.** Every row used an INTEGRAL
    percent, where ceil and truncate are equal by construction. The fixture
    varied the right axis and sampled only the point where the two sides agree
    — the same trap as the lone-remainder 100m fixture, one round later.
  - **Fix**: `cosPercentRateBytes` as a named shared helper carrying all three
    rules, plus `cosSaturatingAdd` for the accumulation Rust does in `u128`. A
    fractional-percent row and an out-of-range-sibling cell now bind the axes
    the old fixtures could not reach.
  - **Verified claim**: `SchemaValidate` really does reject `percent 150`
    ("percent out of range (0,100]"), so the domain guard is defense-in-depth
    for the lenient load path rather than the primary gate — stated that way
    rather than implying it is the gate.

- **Timestamp**: 2026-08-27
- **Action**: Consolidate onto the package's existing percent resolver (review
  follow-up to F6)
  - **The helper I added in the F6 fix was a duplicate of a function that
    already existed in the same package.** `resolveCoSPercentRateBytes`
    (`compiler_class_of_service.go`) has mirrored the Rust rounding since
    #4228, and its doc comment already said "mirrors the Rust
    `cos_percent_buffer_bytes` resolution EXACTLY". Had I found it, F6 would
    have been a one-line fix — call it — instead of a new function.
  - **Why I missed it**: my search for other Go percent computations grepped
    for the ARITHMETIC SHAPE (`float64` … `/ 100`) in non-test code. That
    finds inline expressions and misses a well-named function that does the
    same job. Searching for the shape of the bug finds other instances of the
    bug; it does not find the correct implementation you should have called.
  - **The fix for a rule that drifted cannot be a third copy of the rule.**
    F6 was caused by two implementations of one rule diverging, and the fix
    left three (two Go, one Rust). A divergence between the two Go ones would
    always be a bug, so by the same reasoning they are a consolidation
    candidate, not a pair to bind with a test. Reviewer differential-tested
    them at 128 input pairs and found zero divergences today — so this is a
    structural fix, not a defect fix.
  - `> 0` is an exact substitute for the `(bytes, ok)` pair: a usable result is
    always at least 1 because of the min-1 clamp, and 0 is returned only for an
    unknown base or an out-of-range percent.
  - The F6 reasoning moved into `resolveCoSPercentRateBytes`'s doc, since that
    is now the single statement of the rule. Its float-boundary comment (the
    `>=` against `float64(^uint64(0))`, because MaxUint64 is not float64-exact)
    was better than mine and is what survived.
