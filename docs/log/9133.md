# #9133 — BER OID sub-identifiers were platform-width signed int with no RFC 2578 bound

- **Timestamp**: 2026-09-06
  - **Action**: bounded OID sub-identifiers to RFC 2578 §7.1.3's
    `0..4294967295` at the DECODER, and changed `berEncodeSubID`'s parameter to
    `uint32` so the out-of-range case is unrepresentable rather than checked.
  - **File(s)**: `pkg/snmp/agent_ber.go`,
    `pkg/snmp/ber_oid_subid_bound_9133_test.go` (new),
    `pkg/snmp/agent_test.go` (the existing `TestBerEncodeSubID` table's `val`
    field follows the parameter type), `pkg/snmp/README.md`

    Three symptoms, ONE modelling choice. `berDecodeOID` accumulated
    `val = (val << 7) | int(data[i]&0x7f)` over an unbounded continuation run;
    `berEncodeSubID`'s `if val < 0x80` fast path is true for every NEGATIVE
    value and returned `byte(val)`; `oidCompare` compares components with a
    signed `<`. The fix is at the decoder because that is the only entry point
    from the wire: with it bounded, no out-of-range component can reach either
    of the other two sites, and `oidCompare` is correct as written.

  - **`oidCompare` is deliberately NOT changed, and that is a claim, so it is
    tested.** `TestOIDOrderingHoldsOverTheWholeLegalRange9133` walks an
    ascending ladder across `math.MaxInt32` — the boundary a 32-bit `int` would
    wrap at — and then re-derives every rung through the codec, so the ordering
    claim is about values the agent can actually hold rather than about
    literals.

  - **The "platform-width" half of the title needed a compile-time guard, not a
    runtime one.** Components are carried as `[]int`. On amd64/arm64 `int` holds
    4294967295 fine; on a 32-bit target `int(val)` would wrap every large
    sub-identifier negative, which is this defect restored by the back door.
    `const _ uint = uint(^uint(0)>>1) - maxOIDSubIdentifier` is a compile error
    there and a no-op here.

  - **What was deliberately left alone, with the reason.** The first two arcs
    are folded into one octet by X.690 §8.19.4, and `berDecodeOID` reconstructs
    them as `data[0]/40` and `data[0]%40` — so a first octet above 0x77 yields a
    first arc above 2, technically invalid ASN.1 that round-trips byte for byte.
    Bounding it would replace a faithful echo of the client's own OID with an
    empty one, which is worse for the client and is not what this issue is
    about. `TestTheFoldedFirstArcsAreLeftAlone9133` is the guard.

  - **Found while fixing, not in the issue: a varbind ARITY violation.**
    `decodePDUFields` SKIPS (`continue`) a varbind whose OID fails to decode
    rather than failing the PDU. MEASURED: a two-varbind v1 GET with one
    undecodable OID returns a `noError` response carrying ONE varbind, which
    violates RFC 1157 §4.1.2 (the response's variable-bindings must name the
    same variables). It is PRE-EXISTING and not a #9133 regression — the same
    skip is reachable at master through the function's other error, which the
    vector `06 02 2b 80` triggers there and here alike, and that vector is in
    the pinning cell precisely so the claim is measured rather than argued.
    What #9133 changes is that an overflowing sub-identifier now takes this path
    instead of being echoed as malformed BER. Pinned by
    `TestAnUndecodableVarbindIsSkippedNotRejected9133` and filed as #9333: the
    remedy is a decision about all five `continue` arms in that loop (bad tag,
    bad length, short body, empty OID, decode failure), not about OID bounds,
    and making one of the five behave differently would be the worse outcome.

  - **Mutation table** (`go test -count=1 ./pkg/snmp/`; each mutant confirmed
    BUILT and APPLIED before scoring):

    **Q2 SURVIVED, and the honest reading is that my comment was overstated, not
    that the test is weak.** With a `uint64` accumulator a post-shift check is
    equally correct: seven more bits cannot wrap 64, so the check fires at the
    fifth significant octet either way. The pre-shift form is still the one to
    keep — it bounds `val` below 2^25 so the shift *cannot* overflow regardless
    of the accumulator's width, removing a reasoning step rather than relying on
    it — and the comment now says that instead of claiming the post-shift form
    is wrong. Recorded as a survival rather than quietly dropped from the matrix.

    **Q7 is the row that justifies the folded-arc exclusion.** Bounding the
    first two arcs is the "obvious" extra hardening; it reds a SHIPPED cell
    (`TestWireVarbindByteFloors_6551`) as well as the guard written for it.

    `TestAnUndecodableVarbindIsSkippedNotRejected9133`'s two sub-cases split
    under Q1 exactly as claimed: `overflowing-subidentifier` reds (that vector
    only reaches the skip path because of #9133) and `truncated-continuation`
    stays green (it reaches it at master too). That split is the measurement
    behind the "pre-existing" claim in the follow-up issue.

    The compile-time `int`-width guard has no mutant: it either compiles or it
    does not, and there is no 32-bit target in the tree to build it against.

  - **`go test ./...` gate**: green except ONE red,
    `TestV2cTrapIsUnaffectedByTheTargetMove9123`, which is a PRE-EXISTING FLAKE
    unrelated to this change. Diagnosed by mechanism rather than by re-running:
    `buildLinkTrapV2` draws `requestID := rand.Int31()` and
    `berEncodeIntegerValue` emits the minimum number of octets, so the encoded
    request-id is 4 octets for a value >= 2^23 and shorter below it — and the
    cell asserts that three independently-built packets have the SAME length.
    MEASURED at 20,000 iterations in-tree: `MISMATCH 216/20000 = 1.080%`,
    lengths `{129: 2, 131: 215, 132: 59783}`. Nothing in #9133 touches
    `math/rand` or `berEncodeIntegerValue`, and the earlier
    `go test ./pkg/snmp/` run of the same tree was green. Filed as #9335 with
    the measurement and three candidate remedies; the cell's own comment records
    that byte-identity was abandoned for this exact cause, so the replacement
    changed the symptom and kept the mechanism.
