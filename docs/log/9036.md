# #9036 — a superseded remote failover ACKed `applied` with no demotion

- **Timestamp**: 2026-09-06 (lane-8388)
  - **Action**: restored #5640's invariant by resolving the fence barrier with a
    verdict instead of deleting it.

    **Four correct steps composed into a two-owner window:**

    1. `pkg/cluster` returns `FailoverSuperseded` before the SecondaryHold
       write — correct (#5246): the reset is the operator's newer intent.
    2. the daemon wiring **disarmed** the fence barrier — correct in isolation
       (#8000): nothing will ever actuate it, and leaving it armed makes the
       applied-ack burn the fence timeout and blame the fencing path.
    3. `waitFailoverActuated` returns nil when no barrier is armed — correct,
       and the reason step 2 chose disarming.
    4. `sync_failover.go` sends `failoverAckApplied` when the wait returns nil
       — correct (#5640): a clean fence means the peer may promote.

    > **#8000 removed the only thing on the wire that distinguished "fenced"
    > from "never happened"**, and the typed `FailoverSuperseded` that could
    > have carried the distinction was collapsed to `nil` at the callback
    > boundary.

    Fix: `failFailoverActuation` resolves the barrier with
    `cluster.ErrFailoverSuperseded` and LEAVES it for the waiter to consume, so
    the ack downgrades to `failed` and the peer holds. Per-**request**, not
    per-RG: `resolveFailoverActuation` fans a demotion EVENT out across every
    in-flight request because the event answers all of them; a supersede is a
    fact about ONE request's generation check, and failing a sibling's barrier
    would discard the identity discipline #6177 enforces.
