## Premise check at `origin/master` (`f7128bc1b`)

Not stale, and it did not need re-measuring from scratch: the issue's own last
verification pass landed
`fabric_ingress_return_traffic_is_denied_on_the_lan_node_7770`, which drives a
session-less `wan -> lan` fabric-ingress return through the real poll loop and
asserts `PolicyDeny reason=5 policy_id=4294967295 ingress_zone=wan
egress_zone=lan` with `missing_neigh=0`. It is green at master, so the premise
is executable rather than narrative.

The quantifier in the title checks out structurally too. The session-miss policy
+ install block in `poll_descriptor` is entered only for
`ForwardingDisposition::ForwardCandidate`; a `FabricRedirect` resolution reaches
neither, so the punting node evaluates nothing and installs nothing, for every
new flow, for as long as the split lasts. That is the "first packet of EVERY new
flow" and the "does not self-heal" in one place.

## The design question, and why B/C/D collapse to one answer

The thread left three standing options and the last comment ranked D (a punt
record) over B (synchronous sync), naming two things it had not established.
Both resolve against the code, and together they collapse the set:

**1. The verdict bit cannot ride a `META_FLAG`.** The last comment proposed
stamping the peer's permit/deny verdict on the return frame using a spare
`META_FLAG_*` bit from `bpf/headers/xpf_common.h`, and flagged "whether the
fabric redirect path preserves meta flags across the fabric hop" as the thing
that would make or break it. It does not. `meta_flags` is a field of
`UserspaceDpMeta`, the XDP metadata area the shim writes for the LOCAL
userspace pass; the fabric hop transmits an Ethernet frame and the receiving
node's shim writes fresh meta. The only wire-carried metadata on that hop is the
synthetic source MAC, and all six bytes are spoken for
(`[0x02,0xbf,0x72,MAGIC,zone_hi,zone_lo]`). A second `MAGIC` value would be
additive room — so the idea is implementable, just not by the proposed carrier.

**2. It is not needed, because the record does not have to be bespoke.** D's
cost was "adding a record adds per-flow state on a node that deliberately holds
none, and its lifetime, cap and eviction are exactly the kind of thing that
turns into its own issue". The session table already answers all three. So the
punt record IS a session — which is option C, the one ruled dead on the grounds
that the punting node "never evaluates policy for the flow, so it would be
minting sessions for traffic it never authorised". That is a statement about the
current code, not a constraint on it. Add the evaluation and C's objection is
answered, D's state question disappears, and the peer's verdict stops mattering:
the authorisation is this node's own.

## What landed

`should_seed_fabric_punt` (three conditions: the resolution is a
`FabricRedirect`, the packet did NOT ingress on the fabric, the flow carries no
ingress translation) and `fabric_punt_seed_metadata` (evaluate the flow's REAL
zone pair, `None` on anything but a permit), both in
`afxdp/forwarding/fabric.rs`; an arm in the session-miss block of
`poll_descriptor` that installs a `SessionOrigin::FabricPuntSeed` session when
they agree.

The real zone pair comes for free: `from_zone_id`/`to_zone_id` are computed at
the top of the miss arm from the PRE-redirect resolution, so `to_zone_id` is
still the flow's true egress zone rather than the fabric parent's. Reading it
off the redirected resolution instead resolves the unzoned sentinel 0 and seeds
nothing — which is one of the mutations below.

## Direction of the change, stated because this is a security-adjacent path

**No new drop site.** The arm never touches the packet's disposition. A deny, an
unresolvable zone pair, an ingress translation, or a full session table all
leave the punt exactly as it is today, with the peer adjudicating it as it does
today. Nothing permitted today becomes denied.

**One new admit, and what bounds it.** A fabric-ingress `wan -> lan` packet
matching the reverse of a punt seed is now forwarded instead of denied. The seed
is only creatable by a packet that (a) ingressed on one of THIS node's own
non-fabric interfaces and (b) passed THIS node's own zone policy. So the
admitted flow is the reply direction of a flow this node itself adjudicated —
not a privilege the requester did not already hold — and an attacker on the
shared fabric segment cannot manufacture the record, which is the difference
between this and the "skip policy for fabric-ingress packets" option the thread
ruled dead on #6458's forgeable-stamp residual.

**What fraction of traffic takes the "exceptional" path.** Zero on a healthy
single-primary cluster: `FabricRedirect` requires the egress RG to be
peer-active, and the backup receives no transit traffic. During a split it is
EVERY cross-RG transit flow. So the path is exceptional in TIME, not in
fraction — which is also why the state cost below is proportionate rather than
marginal.

**State cost, named.** During a sustained split the punting node holds one
session per punted flow where it held none, bounded by the same `max_sessions`
cap and idling out on the admitting application's window. Same order as the
session count the peer already holds for those flows. Punt seeds are excluded
from the per-IP session-limit count (they are transient seeds), which is
unchanged from today: those flows were uncounted on this node before, because
they created nothing.

## The mutation that ESCAPED, and what it changed

The `!fabric_ingress` condition — the one carrying the security property —
was originally inline in the poll-loop arm, and deleting it **reds nothing**.
`finalize_new_flow_ha_resolution` refuses to redirect a fabric-ingress packet
back onto the fabric, so `FabricRedirect && fabric_ingress` is unreachable
through the loop and no end-to-end cell can reach it.

That is an unbindable guard on the most important line of the change. The gate
was extracted into `should_seed_fabric_punt` so it can be driven directly, and
`should_seed_fabric_punt_binds_each_condition_7770` now binds all three
conditions individually. The three re-run mutations each red it by name.

A second escape was found and fixed the same way: the first version of the Go
filter test looped over `transientLocalSeedOrigins` itself, so deleting
`fabric_punt_seed` from the list deleted the assertion about it and the test
stayed GREEN. A per-member check cannot see a MISSING member. The membership is
now pinned by `TestTransientLocalSeedOriginsLockstepWithRust7770`, which parses
the helper's own `is_transient_local_seed` + `as_str` arms rather than restating
the strings — a constant written down twice is two constants.

## Why the delta must not leave the node, and the belt for it

`SessionOrigin::is_transient_local_seed` covers `FabricPuntSeed`, so
`install.rs`'s `counted` gate emits no Open delta and the owner-RG bulk export
skips it. That is not tidiness: #6599 measured what a FabricRedirect-disposition
Open delta does when it reaches the peer — it overwrites the owner's
authoritative session family under latest-generation-wins — and a punt seed is
the worst shape of that class, right disposition and no NAT. The Go daemon
already filtered `missing_neighbor_seed` for the same reason; `fabric_punt_seed`
joins it, and the lockstep test holds the two languages' sets together.

## Harness

`test/incus/test-private-rg.sh` creates and HOLDS the RG1/RG2 split and probes
inside it — the thread's earlier "no smoke ever creates and holds a split" was
corrected on the issue — but read `ping -c 3` as a BOOLEAN, and `ping` exits 0
if any reply arrives, so one lost first packet was a PASS. The gate entered the
state under test and reported the healthy value from inside it.

It now also sends three SEPARATE `ping -c 1` probes while the split is held.
Each invocation picks its own ICMP identifier, so each is a distinct flow and
each exercises the first-packet case; `-c 1` leaves no later packet to mask it,
so the exit status is the measurement and there is nothing to parse — which is
deliberate, because a parse that matches neither branch is how a gate ends up
emitting nothing while summarising "0 failed".

The previous comment on the issue declined to land this "because turning it into
a counting probe today would red a gate on a known, unfixed defect — it should
land with whichever remedy is chosen". This is that landing.
