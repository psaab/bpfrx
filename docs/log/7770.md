# #7770 — LAN/WAN redundancy-group split drops the first packet of every new flow

- **Timestamp**: 2026-08-27
  - **Action**: characterized the defect end to end. The dropped packet is the
    **REPLY**, not the request: the deny log reads
    `src=<wan target> dst=<lan host> ingress_zone=wan egress_zone=lan
    policy_id=4294967295` (no-match default deny). The request egresses fine and
    the WAN-owning node creates the session; the reply returns in ~1-3ms, the
    LAN-owning node has no session for it yet, and refuses it as unsolicited
    inbound. Counter-diff with a no-split control: `Policy deny +1` on the LAN
    node in both split probes and neither control probe.
  - **File(s)**: none (measurement)

- **Timestamp**: 2026-08-27
  - **Action**: bounded it, refuting my own escalation. I predicted the ~1s
    session-sync sweep, which implies a faster probe loses more packets. Ten
    packets at 1.0s / 0.5s / 0.2s intervals lost **1 / 1 / 1**, always
    `icmp_seq=1`. A 1s window would have cost ~5 at 0.2s. So this is one packet
    per flow, not a one-second hole in every connection — the originally filed
    title is correct and the escalation was wrong. Recorded because the test was
    worth running: it could have changed the severity.
  - **File(s)**: none (measurement)

- **Timestamp**: 2026-08-27
  - **Action**: corrected an earlier wrong reading of my own counters. I first
    reported the drop as the LAN node's OUTBOUND evaluation. `Sessions created`
    moving on the WAN node and never on the LAN node reads as "the LAN node
    refused the outbound"; it actually means "the LAN node was never told about
    the flow, so it refused the INBOUND". The counters could not distinguish
    those — the deny log's `src`/`dst` is what settles it.
  - **File(s)**: none (correction, posted to the issue)

- **Timestamp**: 2026-08-27
  - **Action**: documented the instrument hazard that nearly produced two wrong
    answers, in the testing guide rather than only in an issue comment.
    `tcpdump` on `ge-*-0-1` / `ge-*-0-2` cannot see forwarded traffic (native XDP
    + AF_XDP consumes packets in userspace before the AF_PACKET tap), and it
    fails in the dangerous direction: a low frame count reads as packet loss on
    an investigation that is about dropped packets. Measured: 4-14 frames across
    four hops against 15 echo requests, all of them the cluster's own probes.
    Added a table of what does and does not observe this traffic, including that
    `show security policies hit-count` reported 0/0 on every row including live
    permit policies.
