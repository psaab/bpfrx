# #7342 — enforce security flow tcp-session initial/closing/time-wait timeouts

- **Timestamp**: 2026-08-30 (`fix/7342-tcp-session-timeouts`)
- **Action**: split the TCP close state into CLOSING and TIME_WAIT, carried the
  three `security flow tcp-session` timeout leaves on one additive wire bump,
  and flipped the #6539 enforcement table.

## Why the split had to come first

`session_timeout_ns` split a TCP close only into RST and not-RST, so
`closing-timeout` and `time-wait-timeout` had ONE window between them. Mapping
either onto it was a guess and mapping both was impossible, which is why #6539
could only record that neither was enforced. `initial-timeout` alone would have
been a small additive field — it maps 1:1 onto `tcp_opening_ns` — but doing the
three together is one protocol change, one cluster smoke and one release note
instead of two of each.

## The discriminator, and the one that looked right and was not

A FIN per DIRECTION. Forward and reverse are independent entries, so each knows
whether its own direction FINed; `propagate_tcp_state_to_companion` mirrors that
as the companion's peer-side FIN. One FIN is CLOSING, two is TIME_WAIT, a RST
short-circuits both.

`SessionEntry.observed_tcp_flags` looks like the same thing already exists and it
does not: `account_packet` OR-folds BOTH directions' flags onto the forward entry
deliberately (#2749, so NetFlow's `tcpControlBits` reports the whole flow), so
`observed_tcp_flags & TCP_FIN` is true after ONE fin. A TIME_WAIT detector built
on it would have put every half-closed session straight into TIME_WAIT, and every
single-FIN test would still have passed.

## Compatibility

Both new windows default to the one every post-FIN close already used, and `0` on
the wire means unset, and the three fields are `omitempty` / `serde(default)`. So
an operator who sets neither leaf, a Go binary that predates the change, and a
helper that predates it all produce byte-identical reaping. Each of those three is
pinned by its own cell.
