# #7230 — a zero-length WireGuard keepalive did not roam its peer on a multi-peer interface

- **Timestamp**: 2026-08-27
  - **Action**: `try_decap` returned the authenticated zero-length keepalive as
    `Err(DecapError::MalformedInner)`, discarding the peer identity; the caller
    recovered it with `single_peer_pubkey()`, which is `None` on any multi-peer
    interface, so a keepalive-only roaming peer never roamed its endpoint and was
    blackholed until its next handshake (~120–180 s — bounded, so degraded rather
    than an outage). The comments justifying this claimed multi-peer attribution
    was ambiguous; it was not, and that is why it survived. `try_decap` demuxes
    the session from `hdr.receiver_index` BEFORE any AEAD work, so
    `session.peer_pubkey` is in hand at the exact site that throws it away. Added
    `DecapError::Keepalive(peer_pubkey)`, routed through `count_decap_err` whose
    exhaustive match forces an observability arm. The record is still not
    deliverable and still exits as an `Err`, so the no-TUN-write contract is
    unchanged — only attribution is added. Inverted two green tests deliberately,
    each carrying why the old expectation was wrong; the second's justification
    ("external error contract unchanged") was the bug wearing the clothes of a
    contract. New cell uses TWO peers with an anti-vacuity floor asserting
    `single_peer_pubkey()` is `None`, because a single-peer version passes against
    the defect. Retracted the `docs/wireguard-interop.md` S5 claim that keepalive
    endpoint learning had shipped (true single-peer, false multi-peer). Scoped OUT
    and filed as #7686: the same discard on the malformed-but-authenticated inner
    path, measured at 13 assertion sites and anomalous rather than continuous
    traffic. Owed smoke is BLOCKED, not skipped — `cluster-deploy` fails its
    primary reassert on clean `origin/master` too; filed as #7688.
