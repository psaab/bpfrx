# #9038 — a nil `ResetFailover` on the abort path was treated as confirmed failback

- **Timestamp**: 2026-09-06 (lane-8388)
  - **Action**: filed as an UNRESOLVED validation task ("should be closed by
    evidence either way"). Measured the reachability question first, found it
    reachable, and fixed the claim rather than the state.

    ## Reachability, on the REAL cluster.Manager

    `ResetFailover` clears `ManualFailover` and re-runs the election. Whether
    this node reclaims the RG depends on the **peer's** position, so:

    ```
    peer alive, peer OWNS the RG at the stronger position
      ResetFailover()  -> nil
      IsLocalPrimary() -> false
    ```

    Reproduced with `cluster.NewManager` plus a `PeerGroupState` showing the
    peer primary — **not** a fake driver. Three shapes were tried before it
    reproduced (solo manager, lower local priority, peer-alive-without-peer-
    state), and all three restored primary; only a peer that genuinely OWNS
    the RG produces the nil-with-no-effect ACK. Recording the negative
    attempts because "it reproduces" is much weaker than "it reproduces under
    exactly this condition and not the three neighbouring ones".

    ## The finding is narrower than the issue's severity guess, and that matters

    The resulting STATE is correct HA behaviour — the peer owns the RG, there
    is one owner, no outage — and it is what the failover smoke asserts as
    right (*"fw0 rejoined as secondary for every redundancy group (no
    auto-preempt)"*).

    > **The defect is not the state. It is the abort path's CLAIM about the
    > state:** *"aborted WITHOUT cutting (node still forwarding)"* when the node
    > is not forwarding for at least one RG.

    So this is a WRONG-DIAGNOSTIC defect, not a stranded-node defect. The
    issue's "could leave a supposedly recovered node demoted and reduce
    redundancy" is right about the operator's belief and wrong about the
    mechanism; the redundancy reduction is the drain the operator asked for.

    ## Fix

    Read back with the SAME predicate the rejoin path already trusts
    (`LocalRejoinComplete`), **once and without polling** — an abort must not
    become slower or able to hang. Applied to BOTH abort branches, because
    `RejoinAndConfirm` in the same package already said a nil reset is not
    proof and the two abort paths were the ones taking the weaker reading.

    ```
    M1  DELETE the rolling readback call   1 -> 0 sites, COMPILES (rc=0)
        -> rolling/nil-reset-did-NOT-restore      RED
           rolling/readback-ERROR                 RED
           (kernel cell and must-survive cell stay GREEN)

    M2  DELETE the kernel readback call    2 -> 1 sites, COMPILES (rc=0)
        -> kernel_drain/same-defect-same-fix      RED  (only)
    ```

    Independently bound. The **mutant that must survive** — a nil reset that
    DID restore must still report "still forwarding" — stayed green under
    both: a fix that reported every abort as stranded is as useless as one
    that reported none.

    `make test-failover` PASS 21/0, `exe_check=MATCH`, 20.6 Gbps. The first
    attempt came back `exe_check=MISMATCH` because the source had moved since
    the last deploy; the harness voided it rather than letting a 20/1 read as
    a result. Second time today that check stopped me quoting a gate about a
    different binary.
