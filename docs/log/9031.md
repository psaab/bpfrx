# #9031 — embedded ICMP quote keys erased the GRE discriminator

## Defect

Every quoted-packet lookup key set `discriminator: Default::default()` —
`TunnelDiscriminator::None`. A live GRE session carries `Unkeyed`, `Keyed(k)` or
`Pptp(handle)`, and `SessionKey` derives `Hash/PartialEq/Eq` **including** that
field (#7188), so every exact index probe for a GRE quote missed.

Consequence: an ICMP error for a translated accelerated GRE tunnel finds no NAT
state, the outer destination and quoted source cannot be restored, and no usable
signal reaches the endpoint. GRE carries bulk payload — small probes stay healthy
while large traffic stalls after an MTU reduction, and ordinary
unreachable/traceroute signalling is lost. HA-imported sessions inherit the same
mismatch, because sync correctly preserves the discriminator.

#8103 threaded the discriminator through the five TRANSFORM helpers and pinned
them. Those cover transforms of an EXISTING key; this is a key **produced from a
quoted packet**, which is the gap.

## Fix

Both embedded parsers now read the quoted GRE discriminator with
`gre_transit_discriminator` — the SAME extractor the transit path uses, reused
rather than re-spelled, because a second parser for one wire format is where two
readings of the same bytes silently diverge.

Bounded by `inner_declared_end`, the QUOTED datagram's declared end, not the
backing frame: the #2361 rule the extractor already enforces for transit, applied
to the quote. And **fail-closed by construction** — every failure path returns
`Unparseable`, a distinct class from `Unkeyed`, equal to no live session's
discriminator, so a malformed quote MISSES rather than wildcarding. That is met
by the type rather than by a check anyone could forget.

`nat64_match.rs` is deliberately left at `None` and says why: NAT64 translates
the protocol across families, so a quoted GRE header on one side names no tunnel
identity the other side's session carries.

### M3-M5 are the finding, and they survived TWICE

#9031's acceptance says plainly: *"reverting any one constructor to
`Default::default()` must red"*. My first cell set (parser + reply key) did not.
So I built the end-to-end cells on the real
`try_embedded_icmp_nat_match_from_frame` harness — and **they still survived.**

The reason is a property of the session table, not a gap in the fixtures:
`install_with_protocol` publishes a REVERSE COMPANION, and `embedded_reply_key`
— which IS wired — matches that companion. So every fixture that resolves at all
resolves through the reply key, and the forward key is never the deciding
lookup. Two rounds of better fixtures could not change that.

The forward key is still not redundant: an AS-IS hit and a REPLY-KEY hit produce
different direction bookkeeping (#6474 `outbound_snat`), so a forward key built
with `None` silently shifts which branch classifies the error — a real behaviour
change with **no match/no-match signal**. That is what a structural guard is
for, and the guard carries that reasoning rather than being an unexplained
grep. It also carries a non-vacuity count (M7), because a scan that reads
nothing reports no offenders.

Recorded rather than smoothed over: I wrote two rounds of behavioural cells
before concluding the behavioural route could not reach these constructors, and
I verified that by mutation each time instead of asserting it.

PPTP is fail-closed today (`Unparseable` → miss, never a wildcard), which meets
the safety half. Resolving the call ID through the worker association table is a
separate piece: the handle is deliberately locally derived, not taken from the
packet, because the Call ID names the peer and differs per direction (RFC 2637
§4.1), so an embedded parser cannot compute it from the quote alone.
