# #9322 — a 64 MiB response truncation was reported as "the helper rejected it before replying"

- **Timestamp**: 2026-09-06
  - **Action**: made the control-response cap DISTINGUISHABLE from a helper that
    died mid-write, named it at all three `boundedResponseReader` call sites,
    and corrected the false in-source premise that the cap is unreachable.
  - **File(s)**: `pkg/dataplane/userspace/socket_trust_9003.go`,
    `pkg/dataplane/userspace/process_control.go`,
    `pkg/dataplane/userspace/boot_probe.go`,
    `pkg/dataplane/userspace/socket_trust_9003_test.go` (census extended),
    `pkg/dataplane/userspace/response_cap_diagnostic_9322_test.go` (new)

    `io.LimitReader` ends at the cap with a plain `io.EOF`, which `json.Decoder`
    turns into `io.ErrUnexpectedEOF` for a partial body — byte-identical to a
    peer that died mid-write. `limitedResponseReader` records which one
    happened, and `responseCapError` says so.

  - **The premise the old comment rested on is false, and I corrected it rather
    than deleting it.** It said the cap "being reached at all is not a reachable
    state for the real helper (it is bounded by the same MaxControlRequestBytes
    ceiling on what it can be asked to produce)". `MaxControlRequestBytes`
    bounds what can be ASKED. `export_owner_rg_sessions` is asked with ~60 bytes
    and answered with the unbounded owner-RG session set.

  - **The reader must not be wrong in the other direction either.** A response
    that ends EXACTLY at the cap is COMPLETE, and reporting it as truncated
    would be the same class of wrong diagnostic pointed the other way. The
    budget-exhausted arm therefore does a one-byte probe on the underlying
    reader — data still there means truncated, clean EOF means the body simply
    ended at the boundary. Costs one read, on an error path only.

    **My cell for that arm was VACUOUS and the matrix is how I know.** Mutant S2
    (set `truncated` unconditionally once the budget is spent) SURVIVED the
    first version, which drove a cap-sized body through `json.Decoder`: with a
    complete object the decoder already holds the closing brace when the budget
    runs out and never calls `Read` again, so the `remaining <= 0` arm — the
    entire subject of S2 — is never entered. The property was real and the
    fixture could not reach it. The cell now exercises the READER'S CONTRACT
    directly (read exactly the cap, then read once more) on both sides of the
    boundary, which enters that arm deterministically; S2 is killed by the
    `body ends exactly at the cap` sub-case. The decoder-level cell is kept
    beside it as the end-to-end statement.

    That survival is also a fact about production, and it is why the probe is
    worth having anyway: through `json.Decoder` the false-positive S2 would
    introduce is largely unreachable, so the probe is defence for the reader's
    CONTRACT rather than for today's only caller — and the cell that binds a
    contract has to be at the contract's level.

  - **What was deliberately NOT changed.** The session-socket truncation keeps
    its `errSessionHelperUnreachable` wrapper. That error gates
    takeover-readiness (#5247), and reclassifying a truncation as healthy is a
    #6785-shaped decision with HA blast radius — this change NAMES the cause, it
    does not re-decide the classification. Mutant S7 (drop the wrapper) is
    killed by an explicit `errors.Is` assertion, so the non-change is bound
    rather than merely intended.

  - **An existing content-scanning census fired on my change, correctly.**
    `TestEveryHelperResponseDecodeIsBounded9003` requires every
    `json.NewDecoder(...)` argument at four enumerated sites to mention
    `boundedResponseReader` or `io.LimitReader`. Binding the reader to a local
    (necessary — the caller has to INSPECT `bounded.truncated`) made all three
    sites read `json.NewDecoder(bufio.NewReader(bounded))` and the census failed
    them. Extended rather than loosened: an identifier is accepted ONLY when the
    same file assigns it from `boundedResponseReader`/`io.LimitReader`. Matching
    on the bare word "bounded" would have accepted any variable anyone chose to
    name that; mutant S9 feeds a decoder from an untraceable identifier and the
    census still refuses it.

  - **Criterion 4 — "decide the export's real bound" — is answered by
    MEASUREMENT and filed as #9344, because neither of the issue's two stated
    options survives contact with the numbers.**

    Per-delta size, derived from `SessionDeltaInfo` by reflection rather than
    sampled: zero-value 83 B, **worst case 1424 B** (43 fields; every string a
    full-width IPv6 text address). The issue's 577 B was a typical IPv4 delta —
    the worst case is 2.5x that, and a bound must use the worst case.

    | workers | theoretical max response | vs. the 64 MiB cap | cap crossed at |
    |---:|---:|---:|---:|
    | 1 | 178 MiB | 2.8x | 47,127 sessions/worker |
    | 6 (loss cluster) | 1068 MiB | 16x | 7,854 |
    | 16 | 2848 MiB | 44x | 2,945 |

    So "raise the cap above `DEFAULT_MAX_SESSIONS * workers * bytes-per-delta`"
    is **not a number** — it is a number per box, linear in a runtime quantity
    whose only source is the helper's own status. Sizing an allocation bound
    from a value the bounded party supplies is not a bound, and any constant
    large enough for a 16-worker box reopens #9003.

    That leaves paging, and paging is **not expressible** against today's helper
    — a fact the issue does not contain and one that would have cost the next
    person a wasted attempt, because the protocol already carries `max` and
    "just call it repeatedly" looks like it should work. It does not:
    `drain_session_deltas_fair` DRAINS the per-binding buffers, and a second
    export re-kicks phase 1, so repeated capped calls yield duplicates from two
    different instants rather than pages of one window — exactly the harm
    `daemon_ha_userspace_export.go:83-84` warns about.

    The primitive is already there and thrown away: `drain_session_deltas_fair`
    computes `overflow` (budget spent AND deltas still pending) and the owner-RG
    call site discards it into `_overflow`. That is the has-more bit a paging
    protocol needs.

  - **The 3 s deadline against a 15 s helper ack ceiling** (the issue's adjacent
    fact 1) moved to #9344 with the paging design, not because it is unimportant
    but because raising this verb's floor to ~18 s changes what a stop can be
    holding, which is pinned by the #8526 shutdown census and the #7675
    reachable-bound cell. That analysis belongs with the design, not with a
    diagnostic fix.
