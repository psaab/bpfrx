# #9008 — ipsec proposal `lifetime-seconds`: rejected at commit, silently accepted on every other channel

- **Timestamp**: 2026-09-05
  - **Action**: closed the tolerant-path hole on the IKE (Phase-1) and IPsec
    (Phase-2) proposal `lifetime-seconds` leaf. Both leaves already carried
    `validator: ValidateIntegerMin(1)` in `setSchema`, but `SchemaValidate` is
    invoked ONLY from `compileTreeStrict`, so the floor was enforced on the
    `Store.Commit -> compileTree -> compileTreeStrict` channel and NOWHERE
    else. `compileTreeLenient` — which backs `Store.Load` (daemon boot,
    reading back the persisted active config) and the HA `SyncApply` path —
    downgrades schema findings to `slog.Warn`, and the compiler then dropped
    the offending token with no diagnostic at all.

    Measured at master `b8b0636a1` before the fix, naming both channels:
    `SchemaValidate` REJECTed `lifetime-seconds -5`
    ("integer must be at least 1"), while `CompileConfigLenient` returned
    ACCEPTED with **0 warnings** and a compiled proposal carrying
    `lifetime=-5`. A negative was therefore worse than dropped:
    `strconv.Atoi("-5")` succeeds, so it was STORED and carried on into the
    swanctl renderer.

    The compiled int cannot express either failure — a non-numeric leaves 0,
    which is indistinguishable from "not configured" — so both compiler loops
    now RECORD the raw token in `LifetimeSecondsInvalidSpec` and
    `validateIPsecProposalLifetimesStrict` reads it. Wired through
    `opts.lenientIPsecProposalLifetime`: hard reject on commit, `cfg.Warnings`
    on the tolerant path, per the #1960 fail-closed-on-load doctrine —
    `Store.Load` may gain a new WARNING but never a new REJECTION, or a
    downgraded binary strands the box on an unreadable active config. The
    only non-test caller of the strict `config.CompileConfig` is
    `compileTreeStrict` itself, so no tolerant path gains a rejection.

    The guard drives all three channels (`SchemaValidate`, `CompileConfig`,
    `CompileConfigLenient`) x both phases x {3600, -5, 0, abc}, with 3600 as
    the accepted-control. Seven PRODUCTION mutants, all killed, chosen so
    every assertion arm has a mutant that REACHES it: dropping the recording
    and removing the gate both die on the strict arm, so they do not exercise
    the tolerant-silence assertion that expresses the actual defect — M6
    (strict still rejects, tolerant branch swallows the warning) and M7
    (warning emitted but not naming the proposal) were added to kill that arm
    specifically, and M5 (recorded but ALSO stored) covers the
    not-carried-to-the-renderer arm.

    Docs: `docs/config-schema.md` credited `ValidateIntegerMin(1)` with fixing
    "0/garbage" WITHOUT naming the channel — the same defect in prose. It now
    states which channel the bound covers and which one the compiler gate
    covers.
