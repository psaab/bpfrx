## The defect

Admission evaluates zone policy on the POST-translation destination
(#2345/#2358) — `policy_dst_ip` / `policy_dst_port`, whose own comment says they
carry "the correct post-translation tuple for all inbound destination
translations (DNAT/static-DNAT/NPTv6/NAT64)". The #8356 re-derivation evaluated
`flow.dst_ip` / `flow.forward_key.dst_port`, i.e. the WIRE tuple, because the
forward session is installed on the wire key. The two sites asked DIFFERENT
questions about the same session.

The dominant direction is **fail-CLOSED and needs no crafted config**: a
published service whose permit names the real server is revoked and its packet
dropped on the first flow-cache miss, with the policy completely unchanged —
because the rule admission matches (`dst 10.0.61.102`) is exactly the rule the
re-derivation cannot match against the VIP, so it fell to `default_policy: deny`.
The fail-OPEN direction exists too: a deny narrowed against the real server is
missed because the VIP still matches a broader permit.

## Why the trigger is not "an operator commit"

- `PublishRouteOverlaySnapshot` bumps the config generation for a ROUTE-ONLY
  publish (`pkg/dataplane/userspace/manager_overlay.go`), and the rtnetlink route
  listener calls it on kernel route changes (`pkg/daemon/daemon_route_listener.go`,
  coalesced to at worst one per 3 s). A generation bump invalidates every
  flow-cache entry. So ordinary BGP/OSPF churn was enough.
- Independently, a session installs with `policy_revalidated_gen: 0`
  (`session/install.rs`), which is never the live generation, so an ordinary
  flow-cache eviction sufficed with no generation change at all.

## Remedy: the entry's own `decision.nat`, and why it is the SAME quantity

`decision` is already a parameter. Only `.resolution` is re-resolved on a session
hit (`session_glue/mod.rs` mutates `decision.resolution` and nothing else), so
`.nat` is the translation the flow was ADMITTED with — exactly what admission
folded into `policy_dst_ip`. Verified per translation kind at this base:

| translation | admission's `policy_dst_ip` / `_port` | entry `decision.nat` | equal? |
| --- | --- | --- | --- |
| pre-routing DNAT / static-DNAT | `pre_routing_dnat.rewrite_dst.unwrap_or(resolution_target)` / `.rewrite_dst_port.unwrap_or(wire)` | `decision.nat = nptv6_nat.or(pre_routing_dnat)` → the same two fields | yes |
| NPTv6 inbound | `IpAddr::V6(internal_dst)` / wire port | `nptv6_nat { rewrite_dst: Some(V6(internal_dst)), rewrite_dst_port: None }` | yes |
| NAT64 | `IpAddr::V4(dst_v4)` (the extracted target) / wire port | `Nat64State::forward_decision` → `rewrite_dst: Some(V4(dst_v4))`, `rewrite_dst_port: None` | yes |
| none (incl. source-NAT-only) | `resolution_target`, which is `parse_packet_destination_from_frame(...).unwrap_or(flow.dst_ip)` = the wire dst | both `unwrap_or` arms collapse to the wire values | yes — byte-identical to pre-#9382 |

The SOURCE deliberately stays pre-translation (`flow.src_ip`) in both places:
Junos evaluates policy after destination NAT and BEFORE source NAT.

## Why the shipped #8356 cells could not see it

Every cell installs `NatDecision::default()` AND writes
`destination_addresses: vec!["any"]`, so the pre/post-translation destination is
unobservable twice over. The survival cell even asserts it is "preserving NAT" in
a fixture that has no translation to preserve.

## Acceptance table

All six cells are TWO-PHASE and driven through the REAL poll body. Phase 1
ADMITS the translated flow through the production path (session MISS -> policy ->
NAT -> forward+reverse install) and is asserted (`tx == 1`, 2 sessions) so a
phase-2 assertion can never be vacuous on a flow that was never admitted. Phase 2
drives one more packet of the SAME flow on a FRESH binding — an empty flow cache,
which is what a generation bump leaves behind and what makes phase 2 reach the
session-hit path. `session_hit == 1` is asserted in every cell.

| translation | phase-2 policy | expect revoked | expect sessions | base (fix absent) | branch |
| --- | --- | --- | --- | --- | --- |
| DNAT (`172.16.80.8:443` -> `10.0.61.102:8443`) | **identical** to the admitting permit | 0 | 2 | **FAIL, revoked 1** | PASS |
| DNAT | permit now names an unrelated host — **the load-bearing control** | 1 | 0 | PASS | PASS |
| DNAT | DENY on the REAL server + trailing permit-any | 1 | 0 | **FAIL, revoked 0** | PASS |
| DNAT | DENY on the VIP ONLY + permit on the real server | 0 | 2 | **FAIL, revoked 1** | PASS |
| NPTv6 (`2602:fd41:70::/48` -> `fd35:1940:27::/48`) | identical, names the INTERNAL prefix | 0 | 2 | **FAIL, revoked 1** | PASS |
| NAT64 (`64:ff9b::808:808` -> `8.8.8.8`) | identical, **mixed-family** destination set | 0 | 2 | **FAIL, revoked 1** | PASS |

Read the third and fourth rows together: they fail in OPPOSITE directions before
the fix (`revoked 0` where 1 is required, `revoked 1` where 0 is required), which
is what pins the evaluated tuple exactly rather than merely showing that
something changed. No constant satisfies both.

The DNAT fixture translates BOTH the address AND the port
(`172.16.80.8:443` -> `10.0.61.102:8443`), so a fix that carried the translated
address but left the wire port would not pass.

The NAT64 cell uses a MIXED-FAMILY destination set on purpose. The v4-only shape
passes today for the WRONG REASON: a destination set with no IPv6 member compiles
to IPv6-match-any (the legacy address-set convention), so the synthetic v6 wire
destination matches on the match-any path and the broken derivation looks correct.
Adding a v6 member that does not cover `64:ff9b::/96` removes that accident, and
the rule then names the real IPv4 server — exactly what #2358 tells operators to
write.
