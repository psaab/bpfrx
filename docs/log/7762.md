# #7762 — the peer boot epoch reaches the connection classifier

- **Timestamp**: 2026-09-03
- **Action**: Plumbed the heartbeat boot epoch to `installConn` as an injected
  callback rather than by widening `clusterRuntime`, and classified the
  EMPTY-alternate-slot peer reboot on it.
- **File(s)**: `pkg/cluster/{heartbeat,heartbeat_manager,sync,sync_conn}.go`,
  `pkg/daemon/daemon_ha_sync.go`, plus two new test files.

## Shape: NOT `clusterRuntime`, and the reason is a category error

The issue proposed extending `clusterRuntime`. That is the wrong interface, and
not merely because it is broad.

`clusterRuntime` is the DATAPLANE-BACKEND surface — `Sessions()` + `Telemetry()`,
implemented by `*dataplane.Manager` and `*userspace.LegacyDataPlaneAdapter`, with
its own doc warning that additions give SessionSync a new runtime dependency. The
boot epoch is cluster-Manager state on a different axis: `d.cluster`, not
`d.dataplane()`. So widening asks every dataplane backend a heartbeat question it
cannot answer — **both production implementors would return 0, and 0 is exactly
the silent fail-open this classification must not have.** Nineteen types implement
that method set, seventeen of them test doubles: seventeen new sites defaulting to
"no reboot" that no reader would recognise as a classification input.

The narrow shape was already in the same struct. `SessionSync` carries six
injected callbacks; two are wired by the daemon at `daemon_ha_sync.go` as
closures over `d.cluster`. `PeerBootEpochFn` joins them.

## Two values, not one

`func() (epoch uint64, latched bool)`. An unlatched floor reads 0, and 0 is a
legal floor ("none accepted yet"), so a single `uint64` collapses "the peer has
not proved it emits epochs" into "no reboot happened" — silently. With the nil
check there are THREE states and each is named: not wired, race window, usable.

## The promotion question, answered rather than deferred

`peerEpochFloor`/`peerEpochLatched` are documented "Diagnostics and tests only".
That is a statement about consumers, not a ceiling; what a correctness consumer
needs is a safe update path, and it is:

- both writes happen in `admitAuthed` under `s.mu`, and the read takes the same
  mutex — no torn or half-updated pair;
- the floor is monotonically non-decreasing (sole assignment guarded by
  `epoch > s.highEpoch`; the `<` case writes nothing);
- the latch is one-way (`epochSeen = true` is the only production assignment,
  nothing sets it false, and `hbAuth` is an embedded value that survives
  heartbeat restart, VRF rebind and UpdateConfig).

A new `peerBootEpoch()` reads both under ONE acquisition. Two separate locks
could interleave with `admitAuthed`'s single critical section and yield
(floor=0, latched=true) — an incoherent pair a classifier would misread.

NOT promoted: `peerEpochLatched`'s warning that it is "A FACT ABOUT THIS STATE,
NOT ABOUT CURRENT ENFORCEMENT" stands. It is used only as a validity flag for
the floor, which is the fact it does assert.

## A defect I reasoned my way to, then measured before believing

The #6910 boot-id prime path (`applyPeerIncarnationSwitchLocked`) also retires an
incarnation, and it does not go through `installConn`. Left alone it would keep
the OLD floor as the baseline, so the peer's SECOND fabric coming up afterwards
would read a raise already consumed, advance the incarnation again, and **evict
the connection the prime just established** — a healthy second fabric evicting
the first, which is precisely what installConn's comment says must not happen.

I wrote the cell first and it FAILED, which is the order that matters: the
reasoning was right but the test is what makes it a fact. Fixed by rebasing the
baseline inside `applyPeerIncarnationSwitchLocked`, so whichever reboot signal
observes the event first consumes it.

## Guards, and one that was wrong

Four cells. The headline one asserts the CHOSEN FABRIC (the issue's stated
acceptance criterion — the stamp is the mechanism, the choice is the property);
a nil-source control proves the fixture does not retire the corpse on its own,
so the others' passes come from the epoch signal.

**The middle-state cell was wrong first, and a mutation caught it.** Its first
draft drove the behaviour with a third install — but with both slots occupied any
third install SUPERSEDES a live connection, which retires the incarnation by
itself. It passed, and then survived the mutation that moves the record above the
`!latched` return: it was measuring the supersession path, not the baseline. It
now asserts the baseline field directly, with the reason recorded in the cell so
the next reader does not "fix" it back into a behavioural assertion.

The daemon wiring is bound separately, and that separation is the point:
deleting `ss.PeerBootEpochFn = ...` from `startClusterComms` reds the daemon cell
while EVERY cluster cell stays green.
