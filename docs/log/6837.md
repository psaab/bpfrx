# #6837 — portless protocols bypass the flowless path via the metadata fallback

- **Timestamp**: 2026-08-27
  - **Action**: made `metadata_tuple_complete` answer the question its name
    asks. It returned true for any protocol as soon as both addresses were set;
    it now returns true only for the protocols the XDP shim actually resolves an
    L4 identity for (TCP, UDP, ICMP, ICMPv6). Everything else carried the
    `Some((l4_offset, 0, 0, 0, 0))` placeholder the shim's `parse_l4` catch-all
    stamps, and that placeholder was overriding the frame side, which had
    already refused those protocols.
  - **Measured, before deciding**:
    - The defect reproduces: a GRE (47) and an ESP (50) transit descriptor each
      installed **2 sessions** (forward + reverse companion) with `src_port: 0,
      dst_port: 0`, against a TCP control that also installed 2. Paired, with
      protocol the only variable.
    - "Stranding" is false. `tx=1` on both sides of the change for GRE, ESP and
      OSPF — a flowless packet FORWARDS. What is lost is stateful return
      admission and `show security flow session` visibility, not reachability.
      #6923's comment asserted the opposite without taking the measurement.
    - The issue's own impact claim #2 ("does not receive the flowless-arm
      treatment: `evaluate_non_pbr_input_filter`, the ingress route-table
      override, the L3-aware policy evaluation") is **false as stated**. Both
      arms call those same three helpers — `poll_descriptor/mod.rs:1264` vs
      `:3440`, `:1347` vs `:3496`, `:2100` vs `:3613` — and
      `evaluate_policy_result_with_icmp` (`policy.rs:2664`) is a thin wrapper
      over `evaluate_policy_result_l3_aware` (`policy.rs:2695`) differing only
      in `l4_present`. The flow-backed arm applies MORE, not less (active reject
      replies, `PbrRejectSink`). The real distinction is stateful-once vs
      stateless-per-packet.
    - The genuine enforcement argument runs the other way and is worth more than
      the one the issue made: flowless evaluates with `l4_present = false`, so
      port-bearing terms fail closed (`policy.rs:3494`/`3538`, inert when
      `l4_present == true` per `policy.rs:3505`). Today a portless protocol is
      evaluated as a resolved L4 flow carrying fabricated port 0, so a
      port-bearing DENY term simply does not match it.
  - **#6923 conflict, resolved rather than overridden**: two tests pinned the
    opposite contract, not the one the parent named. `inspect_tests.rs`'s sweep
    and `tests_shim_ext_parity.rs`'s over-reach guard (legs a, b AND c) both
    asserted portless tuples stay complete, justified by the "would strand
    ESP/GRE/ICMPv6" rationale. #6923's REAL property — a traversable
    next-header value is refused on IPv6 — survives, anchored on the strictly
    stronger row that #6837's rule cannot explain: refused **even when the tuple
    carries real ports**. Its set-equality guard
    (`refused_protocol_set_equals_the_shim_traversable_set`) is untouched and
    still pins `ipv6_ext_header_is_traversable` against the shim's `eh_class`.
  - **Note on the ext-header branch**: inside `metadata_tuple_complete` it is
    now subsumed — every value in the traversable set is portless, so `_ =>
    false` would refuse them anyway. It is kept as defence in depth (it fires
    again the moment any traversable value enters the resolved set) and its
    independent guards live in `refused_protocol_set_equals_the_shim_traversable_set`
    and `server/helpers/session_sync.rs:34`.
  - **Rescued**: two measurement probes from an abandoned attempt at
    `.claude/wt-a6837` (uncommitted, never run to a recorded answer). One was
    broken — it never set `meta.flow_src_addr`, so it exercised the
    unspecified-address early return and would have reported "GRE seeds no
    session" against UNFIXED code, i.e. the exact inverse. Pairing it with a
    TCP control is what exposed that. The abandoned worktree was not modified.
