## The issue's OWN first question, answered from shipped code

> how does a packed run get into a persisted tree at all, if commit rejects it?
> … If neither is real, these 18 are unreachable and this issue closes as such.
> **Answering that question is the first task here, before any fix.**

It needs no new measurement, because the tree already carries two SHIPPED
migrations whose only reason to exist is exactly that situation:

- `rewriteRetiredDataplaneType` (#1373/#1525, `store_persist.go`) — *"a node may
  boot with `system dataplane-type ebpf` persisted from before the
  retirement-strict validator landed"*.
- `SanitizeTreeControlChars` (#1798, `store_persist.go`) — *"a persisted free-text
  value carrying control characters committed before the strict commit-time gate

And `compileTreeLenient`'s own doc comment states both of the issue's candidate
mechanisms as design premises rather than hypotheses: *"a persisted config written
by an older binary (pre-gate, or before a leaf's range was typed/tightened)"* and
*"a config pushed from a possibly-un-upgraded cluster primary"*. Every container
in this change got its schema declaration in some commit; a tree written before
that commit carries the packed spelling and boots through the lenient path today.
**The rows are reachable.** Checking whether the code already answered it was
cheaper than measuring it.

## TWO of the eighteen rows are NOT lenient-only — the issue's premise is partly false

Measured with REAL instance names at `SchemaValidateWithDefinitions`:

say — the more severe #9088 class, not the "fidelity question, not a security one"

**The census mislabelled them, by the mechanism #9265 names.** The #8939 census
synthesises the instance name as the literal token `arg1`, so the fixture it hands

a valid IPv6 prefix, so the typed KEY validator rejects the fixture, and
`flatSetAdmittedAnyOrder` reads any rejection as "the packed spelling is refused",
i.e. lenient-only. The row scored rejected because its NAME was invalid, not
because its BODY was checked — the `xpfarg` hazard #9265 warns a census owes a
control for, observed here on a shipped column rather than predicted.

Both are fixed by this change, and the channel is now recorded PER ROW and
asserted in both directions, so a row silently becoming operator-reachable (a
severity increase) reds.

## Three EXISTING cells went red, and each was a prior decision speaking

None was a stale test. All three were found by `go test ./...` over the whole
tree — a package-scoped run on `-run 9235` saw none of them, which is the reason

### 1. `TestBracedPackedUntouchedWithoutOptIn8886` — the subject moved, not the gate

> an un-opted container split its packed run (high-watermark=90). The split must
> stay gated on packedStatements.

#8886's contract is that splitting a packed run is a per-container OPT-IN. The
cell used `security flow aging` as its un-opted control, and this change makes
that container split.

**There are TWO splitting mechanisms and the opt-in governs only one.** Measured
on a container that has never opted in:

```
security { flow { tcp-session { closing-timeout 10 established-timeout 20; } } }
  -> closing=10 established=20        with packedStatements=false
```

`packedStatements` gates the schema-level brace-elision FOLD
(`splitBracedPackedChildren8886` / `splitPackedStatements8768`). A COMPILER READ
that calls `expandFlatRun` / `hoistAndSplitRun8939` splits a packed run on its own
by a keyword-delimited scan of the node's Keys, and has done since #8939 at a
dozen containers. So `aging` was a valid subject only because it was un-opted AND
not reached by a compiler-read expansion, and this change removes the second
property. The cell's own `t.Skip` anticipated the container opting in and said to
pick another.

Re-anchored onto `class-of-service schedulers <s>`, which has BOTH properties —
measured, `schedulers s1 { priority high buffer-size percent 20; }` keeps
`priority` and DROPS the buffer-size. A positive control on the FIRST statement
was added, because "the second did not land" is otherwise satisfied by a fixture
that compiled nothing. The assertion is unchanged; the replacement `t.Skip` now
says that being un-opted is NOT sufficient.

### 3. `TestSchemaSpellingDifferentialGate` — three leaves became ASKABLE, and are not lists

The three `security flow aging` thresholds report `A=drop B=keep … F=keep`. The
precedent is in that gate's own `notAValueList`, written for #8939's filter-term
`then` actions, and it is the same situation word for word: the leaves *"became
comparable to this gate for the first time when `packedStatements` was declared …
previously a run sat unsplit on the node's Keys and the gate could not reach the
individual actions at all. So the gate is asking a question here that was never
askable before, and the answer is that none of these is a value list."*

Each threshold is `args: 1` with a `smallint` value pair — exactly ONE value.
VERIFIED WHERE THE EXTRA TOKENS LAND, as that map's contract requires:

```
aging { early-ageout 10 20; }       early=10   20 DISCARDED
aging { high-watermark 90 95; }     high=90    95 DISCARDED
aging { low-watermark 60 65; }      low=60     65 DISCARDED
aging { early-ageout [ 10 20 ]; }   early=10   20 DISCARDED
aging { early-ageout { 10; 20; } }  early=0    the block form is not read at all
```

and the typed schema walk REJECTS every one of those spellings, so no operator can
author a two-element list here; the tolerant path compiles one value and warns,
naming the leaf. A second threshold is not a second value of the same setting — it
is malformed input — which is precisely what `notAValueList` exists to record.
Registered with the measurement, not with the arity.

### 4. `TestSchemaSpellingGateCoverageIsGated_7484` — the coverage floor, lowered with an argument

Registering the three thresholds in `notAValueList` EXCLUDES them from the gate's
enumeration, so `compared` falls 743 -> 740 and the floor reds. That is the same
mechanism the floor's own #9416 paragraph records for `snmp client-list` /
`client-list-name` ("registered in notAValueList and are therefore excluded from
the enumeration rather than added to it, which is why the floor moves by ONE and
not by three").

A LOWERING NEEDS A STRONGER ARGUMENT THAN A RAISE, and it is this: the regression
this floor exists to catch is a leaf that STOPPED COMPILING — it could still
exhibit the #2419 class and now carries no verdict, so the class has more room to
hide. These three cannot exhibit it at all, because the class is "a two-element
LIST authored in one spelling compiles differently from the same list in another"
and each leaf is `args: 1` with a `smallint` value pair. There is no list, the
schema walk rejects every multi-value spelling, and they became comparable only
because this change expanded the run that previously hid them. The floor is
returning to a population that never included them, not shrinking past one that
did. Lowered to 740 with that reasoning recorded beside the constant.

### The survivor pair, and three wrong accounts of it

"Compiling must not rewrite the authored tree" is protected by TWO independent
mechanisms and no single mutation can expose it. Getting that stated correctly
took three measurements, and the first two accounts were both wrong:

1. I wrote that `expandRun9235`'s clone protects the tree. The cell I wrote for it
   used `security flow aging`, which reaches the SLICE helper and never constructs
   a node — so it could not have failed. A cell named for a function it does not
   reach reports coverage for the one property nothing else here would notice.
2. Re-anchored onto two fixtures that DO reach the node helper, the in-place
   mutation survived anyway. The reason is `compileConfigWithOpts`'s opening
   `tree = tree.cloneForExpansion()`, a deep copy taken before any reader runs. So
   I rewrote the claim as "`cloneForExpansion` is the mechanism".
3. That is also not killable alone: discarding `cloneForExpansion` survives,
   because the local clone covers it.

Only the CONJUNCTION reds the cell. The two are kept because they are redundant on
today's fixtures and NOT redundant in scope — `cloneForExpansion` is total (every
compiler reader) while the local clone is what keeps a future caller outside the
compile path honest. Both the cell and the helper's doc comment now state the
measured matrix instead of a hypothesis. The third subtest (`security flow aging`)
correctly does not red under the double mutation: `expandRunChildren9235` returns a
fresh slice and never writes through to the parent, so it has no in-place variant.
