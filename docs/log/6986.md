- The `pendingXSKStartup` branch is in `applyCompiledSnapshot`, not lexically in

- `persistResolvedFabricsLocked` now lives in `manager_fabric_sync.go:72`, not

## The defect

`applyCompiledSnapshot`'s `pendingXSKStartup` branch stores `m.lastSnapshot`
**without publishing it** — the publish is deferred, not skipped — leaving
`publishedSnapshot < lastSnapshot.Generation`. That inequality is the
level-triggered predicate the 1s status tick uses (`process_status.go:221`) to
drive `syncSnapshotLocked` once the XSK-startup window ends.

Two other producers advanced `m.generation`, `m.lastSnapshot.Generation` and
`m.publishedSnapshot` **in lockstep** after their own push, neither of which is
an `apply_snapshot`:

| writeback | what it sends | file:line at master |
|---|---|---|
| `RegenerateNeighborSnapshot` | `update_neighbors` | `manager_neighbor.go:131-141` |
| `persistResolvedFabricsLocked` | `update_fabrics` | `manager_fabric_sync.go:80-85` |

```
before:  lastSnapshot.Generation = 10   publishedSnapshot = 7   (gen 10 NEVER sent)
regen:   generation++ -> 11; lastSnapshot.Generation = 11; publishedSnapshot = 11
after:   publishedSnapshot == lastSnapshot.Generation  ->  the tick's gate is FALSE
```

The deferred generation's policies, routes, interfaces and NAT were never
`apply_snapshot`'d. The helper had only the neighbor replace or the fabric
update. The manager's bookkeeping said it was published.

**Complete writer census.** `publishedSnapshot` is an unexported `Manager` field,
so package `userspace` is the whole universe. Nine writers: five follow a real
`apply_snapshot`; two advance without a send but are GATED ON EVIDENCE (the
helper's own reported generation at `process_status.go:18`, and the content hash
at `:77`); one resets to 0 on helper teardown. **Exactly two advance
unconditioned** — the two above. The issue's claim was exact.

**Reachability, and it is worst where it hurts.** `RegenerateNeighborSnapshot` is
driven by the daemon's `RTM_NEWNEIGH`/`DELNEIGH` listener plus a 60s safety tick.
A link DOWN/UP flushes the kernel neighbor table for that link, so the diff is
non-empty and it publishes — during exactly the RETH MAC link cycle whose #6871
lease suppresses the status tick that would otherwise have serviced the pending
publish.

## The second kill — the part that makes a generation-only fix useless

The premise check turned up something the issue only flagged as "needs a look":
**both writebacks also refresh `m.lastSnapshotHash`**, and that is an
INDEPENDENT suppression.

`syncSnapshotLocked` re-hashes `m.lastSnapshot` and returns without sending when
it matches (`process_status.go:77-80`). Both writebacks recomputed the hash from
`m.lastSnapshot` *after* mutating it, so the stored hash became the hash of the
deferred, never-sent content. Even with the generation gate open, the dedup would
have swallowed the publish.

So a fix that addressed only `publishedSnapshot` would test green on the
bookkeeping and still lose the config. Cell **Q2** is that fix, and it reds.

## The fix — unrepresentable, not narrower

Both writebacks route through one shared helper
(`advanceGenerationAfterPartialUpdateLocked`, `manager_generation.go`) that
samples "was the full snapshot already published?" **before** the bump and
advances `publishedSnapshot` only from a value that already equalled the
high-water mark:

```go
fullSnapshotWasPublished := m.publishedSnapshot >= m.lastSnapshot.Generation
m.generation++
m.lastSnapshot.Generation = m.generation
if !fullSnapshotWasPublished {
    return          // gate stays open; hash stays stale-but-TRUE
}
m.publishedSnapshot = m.lastSnapshot.Generation
if h, ok := snapshotContentHash(m.lastSnapshot); ok {
    m.lastSnapshotHash = h
}
```

`publishedSnapshot` can therefore never leapfrog an unpublished generation, on
any interleaving. **There is no residual window to state** — this is not a
narrower race, it is the absence of one. Both fields are gated by the same
condition, so the hash half is closed with it; left un-refreshed, the hash
correctly describes the last content the helper actually received.

Single-sourced rather than duplicated. These are the only two writebacks that
advance `publishedSnapshot` after a partial update, so a divergence between them
is a bug by construction — one would swallow a deferred publish and the other
would not, and the difference would surface only as a lost config on a loaded
box.

## Tests assert the END property, not the bookkeeping

Each arm seeds the swallow window (deferred generation 10 carrying a marker zone
that exists ONLY there, `publishedSnapshot = 1`, `lastSnapshotHash` describing
the generation-1 content the helper really has), runs the partial update, checks
the gate is still open, then drives `syncSnapshotLocked` and requires an
`apply_snapshot` **carrying the marker zone**.

That last step is what catches the hash half. It also means the assertion is on
the RECORDED WIRE REQUEST rather than on `syncSnapshotLocked`'s error — which is
both necessary (the post-publish `applyHelperStatusLocked` needs BPF maps a unit
test does not load) and stronger, since a publish that never happened records
nothing.

`buildNeighborSnapshots` returns nil for a config with no interfaces, so the
neighbor arm's diff is deterministic with no netlink dependence.

## Adjacent inaccuracy, not fixed here

`process_status.go:88-89` and `:109-112` assert that the deferred branch is the
sole producer of an unpublished `lastSnapshot`. `BumpFIBGeneration`
(`manager_generation.go:71-72`) also does `m.generation++;
m.lastSnapshot.Generation = m.generation` with no `publishedSnapshot` advance, so
it produces the same state. That is a comment inaccuracy adjacent to this fix,
not one of the issue's claims, and it does not change the mechanism above —
recorded so the next reader does not trust the absolute.
