## Re-verification at the base commit

Still live, identical to the issue and to its re-measurement comment:

```
AST:
  [group G]
    [type external]
    [peer-as 65001]
    [neighbor 10.0.2.2]
    [neighbor 10.0.2.2]
      [import PS]

neighbors=2
  [0] addr=10.0.2.2 group="G" peer-as=65001 import=[]
  [1] addr=10.0.2.2 group="G" peer-as=65001 import=[PS]
```

The mechanism, measured rather than assumed: `SetPath` does not reuse a node it
has already marked `IsLeaf`, so the BARE declaration and the later sub-leaf
become siblings. Two sub-leaf lines with no bare declaration produce ONE node
(`[neighbor 10.0.2.2] > [import PS] [import PS2]`) and compiled to one entry
even before this change — so the trigger is specifically a bare declaration
beside an extended one.

Rendered, before:

```
neighbor 10.0.2.2 remote-as 65001
neighbor 10.0.2.2 remote-as 65001
 neighbor 10.0.2.2 activate
 neighbor 10.0.2.2 route-map PS in
```

after:

```
neighbor 10.0.2.2 remote-as 65001
 neighbor 10.0.2.2 activate
 neighbor 10.0.2.2 route-map PS in
```

## Remedy

Find-or-create on `(GroupName, Address)` within a BGP instance
(`findBGPNeighbor9192`), mirroring the #8436 OSPFv3 area-interface merge that
already lives forty lines below it. Group defaults are applied on CREATE only:
re-applying them for a later node would wipe the per-neighbor overrides an
earlier node set, which is the drop the merge exists to prevent — measured, the
`props-then-bare` order keeps `description=D`.

`neighborOwnExport` / `neighborOwnImport` moved from per-NODE locals to
per-NEIGHBOR state (`ownExport9192` / `ownImport9192`, scoped to the BGP
instance). They implement #5277 most-specific-LEVEL-wins and were correct while
one node meant one neighbor; with several nodes per neighbor a per-node flag
makes the SECOND node's first `export` wipe the FIRST node's own list, turning
the union this change exists to produce back into a last-node-wins drop.

## Collateral, named rather than absorbed

- **`TestDuplicateBlockConservationIsPinned8436`** reported that
  `protocols bgp group xpfname neighbor` "now CONSERVES but is still listed".
  It is: two `neighbor <ip>` blocks under one group now merge into one peer
  carrying both blocks' statements, which is a stronger conservation than the
  strict-commit refusal the entry recorded. The line is DELETED from
  `dupConservationInventory8436` rather than re-homed, because a stale entry
  hides the next regression at that site.
- **`TestTouchedFileCrossedModularityThreshold`** reds when a file the branch
  TOUCHES crosses 1500 LOC, and `compiler_protocols.go` sat at 1499. Rather than
  record an acceptance for a file none of the three "When NOT to refactor" cases
  describes, the per-neighbor property loop moved to
  `compiler_bgp_neighbor_merge_9192.go` as `applyBGPNeighborProps9192`. That
  split IS the change rather than tidying beside it: the loop used to run
  exactly once per neighbor because the caller built a fresh struct per node,
  and it now runs once per NODE onto a SHARED neighbor — which is why its
  own-export/own-import flags became pointers into the caller's per-neighbor
  state. `compiler_protocols.go` 1499 -> 1384.
