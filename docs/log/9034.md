# #9034 — twice-NAT source-NAT matched on the PRE-DNAT destination port

- **Timestamp**: 2026-09-06
  - **Action**: `SessionFlow::with_destination` now takes the post-translation
    destination PORT as a required parameter and writes it into
    `forward_key.dst_port`, so a composed DNAT -> source-NAT evaluates the
    source-NAT rule against the full post-DNAT destination.

    It previously took the address alone and carried `forward_key.dst_port`
    over unchanged, so the matcher saw the post-DNAT ADDRESS with the PRE-DNAT
    PORT — a tuple that existed on no wire. `SourceNatRule::l4_matches`
    (`nat/source/mod.rs:998-1008`) tests `dst_port` against `match_dst_ports`,
    so a rule scoped to the real service port did not match, and one scoped to
    the external port matched when it should not have.

    The correct derivation was already in the file: `policy_dst_port`
    (`poll_descriptor/mod.rs:1543-1546`), whose comment records that it
    "carries the correct post-translation tuple for all inbound destination
    translations (DNAT/static-DNAT/NPTv6/NAT64)". POLICY matching used it;
    source-NAT matching was the consumer left behind. The call site now reuses
    that binding rather than re-spelling the expression, so the two cannot
    drift.

    The port is REQUIRED rather than optional deliberately: the whole defect
    was that a caller could omit it and still compile. Making it mandatory
    immediately surfaced a THIRD call site — `tests_bind_forward.rs:2234`, a
    twice-NAT cell that asserts `rewrite_dst_port == Some(8443)` two lines up
    and then dropped that port on the floor. It now passes it and asserts the
    flow handed to the matcher carries 8443.

    **HA wire: nothing moves, and this was measured rather than assumed.**
    `nat_match_flow` appears 10 times in `poll_descriptor/mod.rs` and NONE is
    an install, publish or sync site — installs use `&flow.forward_key`, the
    untouched original. Its `forward_key` is cloned only into
    `source_nat_release_key`, a local consumed by
    `rollback_source_nat_allocation_for_worker` within the same invocation that
    made the allocation, so allocation and rollback always agree on the key
    even across a rolling upgrade.

    **The call site was UNBOUND before this change, and the mutation proved
    it.** Mutating `poll_descriptor` to pass `flow.forward_key.dst_port`
    instead of `policy_dst_port` compiled (0 errors) and survived the ENTIRE
    suite. The unit cells on `with_destination` bind the function; only the two
    end-to-end cells added here — which drive `txn_run_descriptor` ->
    `poll_binding_process_descriptor` with a source-NAT rule scoped to
    `match_destination_ports 8443` — bind the caller that chooses the port.
    Re-run after adding them, the same mutant reds both.

    Mutants, each verified to BUILD before scoring: M1 (`with_destination`
    ignores the port) reds the function cell and both end-to-end cells; M2 (the
    call site passes the pre-DNAT port) reds both end-to-end cells and
    correctly leaves the unit cells green, which is what distinguishes a
    function binding from a wiring binding. The paired end-to-end rows are a
    discriminator, not a smoke test: the second asserts a rule scoped to the
    PRE-DNAT port must NOT match, so a "match any port" fix fails it.
