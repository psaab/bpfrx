# #9140 — `then routing-instance` + `then next term` renders a terminating accept

## Summary

`then { routing-instance <x>; next term; }` committed cleanly and then rendered a
TERMINATING `accept` in both the kernel lo0 nft mirror and the Rust userspace
evaluator, so every later term in the filter went dead for that term's match set.
On `lo0` — the host control-plane filter — an SSH deny written after a PBR
classification term was silently unreachable.

The two runtimes AGREE with each other and are correct as written: a
routing-instance term takes its own forwarding decision and is not a
fall-through. The defect is the missing commit gate. #5142 already rejects
"terminating action + `next term`", but it tested only
`len(term.TerminalActions) > 0`, and `compileFilterThen` records the FBF steer on
`term.RoutingInstance` instead. Fixed at the gate.

- **Action**: correct the mechanism attribution in the source report. The
  external review claimed a boolean-precedence slip in the two Go renderers and
  proposed changing them to
  `if term.NextTerm || (term.Action == "" && term.RoutingInstance == "")`.
  That fix is HARMFUL: `userspace-dp/src/filter/compiler.rs:1195` sets
  `continue_term: snap.action.is_empty() && snap.routing_instance.is_empty()`
  deliberately and in writing, so the Go change alone would make nft fall through
  while the Rust evaluator still terminates — a kernel-vs-userspace divergence on
  a shape the tolerant load / peer-sync path can still deliver, contradicting the
  mirror contract stated at `daemon_nft_term_lower.go:483-490`. Neither runtime
  was changed.

## Files

- **File(s)**: `pkg/config/compiler_validate_strict_filter.go`
  - `validateFilterTerminalConflictStrict`: the `next term` arm now derives the
    term's terminating action from `TerminalActions[0]` when present and from
    `"routing-instance " + term.RoutingInstance` otherwise, and rejects the
    combination naming it. Precedence is TerminalActions-first so an explicit
    `accept`/`reject`/`discard` is still the reported terminal.
  - The function's doc comment previously listed `routing-instance` among the
    "non-terminating modifiers". That is the misconception that produced the
    defect; corrected in the same change, with the two runtime citations that
    make it checkable.
- **File(s)**: `pkg/config/firewall_ri_nextterm_9140_test.go` (new) — inet and
  inet6 rejection cells, the `CompileConfigLenient` no-brick leg, and three
  controls: bare `then routing-instance` still commits, `routing-instance` +
  `accept` still commits (and + `next term` is still rejected by the #5142 arm
  naming `accept`), modifier-only `next term` still commits.
- **File(s)**: `pkg/daemon/lo0_ri_nextterm_mirror_9140_test.go` (new) — pins that
  the renderer still terminates this shape, mirroring Rust, so the one-sided
  "fix" reds; plus the end-to-end payload showing the shadowed deny.
- **File(s)**: `docs/config-schema.md`, `pkg/daemon/README.md` — both carried the
  same false claim about `routing-instance` being non-terminating; corrected and
  extended with the gate's new behaviour.
