# #8898 — master-password PRF selector dropped when the system brace is elided

- **Timestamp**: 2026-09-05
  - **Action**: two fixes, and the first alone did nothing.
    1. Admitted `system master-password` to `compactNormalizeInScope`. The
       inner pair `master-password pseudorandom-function` had been admitted all
       along and INERT, because the fold reaches a child only after
       `system -> master-password` creates the container — the #8858 shape.
    2. **Folded at the SCAN SITE.** `effectiveMasterPasswordPRF` walks the RAW
       tree, so it never sees the normalizer, which runs inside the compiler.
       The selector still resolved to nothing after the scope entry landed.
       `config.NormalizeCompactForScan` (clone-safe) is now called before the
       scan. This is #8867's shape with a different consumer: **the fold is a
       property of the compile path, and every reader outside it must opt in.**
  - **Consequence fixed**: the config DB was encrypted with
    `defaultMasterPasswordPRF` while `show configuration` rendered the selector
    the operator wrote — display and enforcement disagreeing silently, which is
    what makes it a security defect rather than a config-loss defect.
  - **The fixture value is deliberately not the default**, with a guard
    (`TestFixtureIsNotTheDefault8898`) that reds if it ever becomes one. The
    first measurement of this defect used `sha256`, which IS the fallback, so
    losing the selector produced the same effective value as keeping it and the
    row measured clean while fully broken.
  - **Validation**: unwiring either half reds the cells, so both are proven
    necessary. A display/enforcement cell asserts the rendered config and the
    enforced PRF agree, with a liveness check that the render mentions the
    selector at all. A mutation cell asserts the scan does not mutate the
    caller's tree, which configstore persists.
