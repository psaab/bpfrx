# #6937 — struct-heterogeneity signal for the modularity audit

- **Timestamp**: 2026-08-27
  - **Action**: established that the issue's proposed metric is the wrong
    one, BEFORE building it. Censused 1095 named top-level Go structs via
    `go/ast`: a `fields >= 100` rule flags seven and **four are false
    positives**, with the top hit `xpfCollector` (347 fields, 334 of them
    `*prometheus.Desc`, one per metric) ranked ABOVE `Daemon`, the target
    the issue was filed about. A gate whose first row is a false positive
    gets ignored. The discriminating property is HETEROGENEITY: `Daemon`'s
    most common type is `sync.Mutex` at 27 of 255 — twenty-seven
    independently-locked concerns — against a 109-type tail, while
    `xpfCollector` has 11 distinct types and drops out of the ranking.
  - **File(s)**: none (measurement)

- **Timestamp**: 2026-08-27
  - **Action**: implemented the signal on DISTINCT FIELD TYPES.
    Floors `[WATCH] >= 20` / `[REFACTOR] >= 40` chosen from the measured
    distribution (16 and 7 structs, 1.5% and 0.6% of 1095; the LOC heatmap
    lists 50 rows). Calibrated with the pair astride the floor rather than
    the extremes: `eventengine.Engine` (25 fields, 20 types) flags and
    `dataplane.CompileResult` (30 fields, 19 types) passes — Engine has
    FEWER fields and MORE concerns, which is the whole argument for the
    metric in one comparison. A modal-share filter was deliberately NOT
    added: at these floors it changes exactly one verdict, so it would be
    fitted to that point rather than calibrated.

- **Timestamp**: 2026-08-27

    output against the issue's independently-stated ground truth rather
