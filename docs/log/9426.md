# #9426 — `check_teardrop` drops a legal 1-7 byte last fragment

## The defect

Every IP fragment except the LAST must be a multiple of 8 bytes; the last one
may be any size. `check_teardrop` dropped ANY non-first fragment carrying 1-7
bytes, so an IPv4 datagram whose length mod 1480 lands in 1-7 produced a legal
last fragment the firewall dropped — and the receiver's reassembly then times
out, so the whole datagram is lost. No attacker required.

The discriminator was already in the struct and unused: `ip_frag_off` is
documented as the raw field, so MF (v4 `0x2000`; v6 the Fragment header's low
bit) is in hand at this check. The fix gates the `< 8` arm on MF=1.

The `<= hdr_len` / zero-contribution arms stay UNGATED: a non-first fragment
that contributes no data is malformed whatever MF says — a last fragment with
nothing in it is not a legal tail. #3027 and its IPv6 analogue are preserved,
and `teardrop_zero_payload_last_fragment_still_drops_9426` is the cell that
catches the over-correction.

## The shipped cell that pins the mistaken premise — re-anchored, not deleted

`teardrop_v6_tiny_non_first_fragment_drops` built an explicitly **trailing**
(M=0) IPv6 fragment carrying 4 bytes and asserted DROP, justifying it as "a tiny
data contribution (< 8 bytes) IS the IPv6 teardrop signature". That is a factual
claim about IP, and it is false.

Its stated reason was read first, and it splits cleanly:

- **#3119's actual claim — "the IPv6 arm exists at all"** (pre-#3119
  `check_teardrop` was `AF_INET`-only) — is STILL TRUE and still fail-on-revert.
  Deleting the `AF_INET6` branch still reds this cell. **Kept verbatim.**
- **The FIXTURE's `more: false`** is what was wrong. Corrected to `more: true`,
  which is a genuinely malformed non-last tiny fragment.

The legal case the old fixture actually described is now asserted, as a PASS, by
`teardrop_v6_last_fragment_tiny_payload_passes_9426`. So nothing the cell
established is lost, and the shape it mis-classified is now covered on the other
side of the boundary.

## Cells

- `teardrop_last_fragment_tiny_payload_passes_9426` / `..._v6_...` — SWEPT over
  1..7, not sampled: a fix that admitted only one size would pass a
  single-value cell.
- `teardrop_non_last_fragment_tiny_payload_still_drops_9426` / `..._v6_...` —
  the companion. Without the pair the fix is indistinguishable from deleting the
  `< 8` check outright, which would lose a real malformed-fragment defence.
- `teardrop_zero_payload_last_fragment_still_drops_9426` / `..._v6_...` — the
  #3027 arm must NOT be gated on MF.
- `teardrop_eight_byte_fragment_passes_either_way_9426` — the boundary control
  retained.
- `flowless_legal_last_fragment_tiny_payload_is_forwarded_9426` — END TO END on
  the live flowless path, which IS the production path for a non-first fragment
  (#2344). Its two legs differ in ONE bit and the MF=1 leg is the positive
  control, so the MF=0 PASS is a real admission rather than a screen that
  stopped running.

## Scoped out, deliberately

The BYPASS half — that this is not an overlap detector — is structurally true
but is a design limitation of a stateless screen, not a coding defect. The only
fragment-state module (`fragment_assoc`) says in its own doc that it ASSOCIATES
rather than RFC-reassembles. Recorded in `docs/feature-gaps.md` §9, where the
code comment previously asserted the opposite.
