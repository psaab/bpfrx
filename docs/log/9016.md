# 9016 — the multiport WireGuard advisory denied the one difference that matters

- **Timestamp**: 2026-09-06
- **Action**: correct the commit-time multiport advisory to state the
  steered/unsteered SECURITY asymmetry, and invert the cell that required it be
  denied.
- **File(s)**: `pkg/config/compiler_validate_wireguard_multiport.go`,
  `pkg/config/wireguard_multiport_advisory_text_9016_test.go`.

## What was already fixed, and what the fix broke

`921028959` correctly retracted the advisory's claim that the unsteered tunnel
was "dead while appearing configured / no handshake ever completes". It is not
dead: the host-inbound filter admits every configured listen-port and each
tunnel binds its own socket.

But the replacement text added a NEW claim:

> Note this is about STEERING only: no WireGuard tunnel's decapsulated plaintext
> is zone-adjudicated today, steered or not — see the separate tunnel plaintext
> advisory, which covers every tunnel in this config.

**That is false at HEAD**, and it points the same way the retracted claim did:
away from the bypass. The first said "don't worry, it's dead". The second says
"don't worry, there's no difference".

## The evidence, three independent in-tree statements

1. `userspace-xdp/src/lib.rs`, the #8274 step 3 arm — *"a WireGuard
   TRANSPORT-DATA record for a configured local listener is NOT local delivery
   any more — the worker decaps it and adjudicates the inner packet under the
   tunnel's logical ingress zone."*
2. `userspace-dp/src/afxdp/poll_descriptor/mod.rs` at the `stage_wg_decap` call
   — *"Everything downstream then sees the INNER packet — flow parse, screen,
   session, policy, NAT, forward build ... instead of being written to the wgN
   TUN for the kernel to forward with no zone policy at all."*
3. `maps_sync.go` — `userspaceCtrlFlagWgRx` is set iff at least one WireGuard
   tunnel is configured, so that gate is armed exactly when this advisory can
   fire.

So:

```
steered port    transport data -> worker decap -> zone/session/policy/NAT
unsteered port  transport data -> kernel -> control thread -> wgN TUN
                                -> kernel forwards, no zone policy
```

`wg_worker_claim` requires `parsed.flow_dst_port == ctrl.wg_listen_port`, one
scalar, so a second port never matches and falls to the generic
local-destination arm. #9016's original framing is correct.

## Where the false claim came from

It was inherited, not invented. It cites the #5618 advisory
(`compiler_wireguard_plaintext_warn.go`) as authority — and that file still
describes the pre-#8274 world in its own opening paragraph: *"The XDP shim
deliberately steers inbound UDP on the configured WireGuard listen port to the
KERNEL (#5582)."* #8274 replaced that for transport-data records and nothing
re-checked the advisory built on it. The correction then cited the hollowed
advisory in good faith.

That advisory fires for EVERY WireGuard tunnel, including a single steered one
whose plaintext is now adjudicated. Filed separately rather than changed here —
suppressing a security warning on my own reading is the change where being wrong
is both expensive and silent, whereas a false "you are unprotected" costs only
unnecessary work.

## The cell that would have kept it

`TestMultiportAdvisoryDoesNotClaimTheTunnelIsDead9016` asserted:

```go
// It must NOT imply the steered tunnel is adjudicated. No WireGuard
// tunnel's plaintext is, steered or not
if !strings.Contains(text, "zone-adjudicated") { ... }
```

A cell requiring the denial. It is now inverted to require the asymmetry, with
the three sources above written into it, so the next person to reach for "steered
or not" has to argue with the evidence rather than with a preference.
