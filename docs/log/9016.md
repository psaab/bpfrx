# #9016 — the multi-port WireGuard advisory told the operator a LIVE tunnel was dead

- **Timestamp**: 2026-09-06
  - **Action**: corrected three copies of a false, security-relevant claim and
    bound each to the mechanism it describes. **Scope: the claim half only.**
    Multi-port steering itself (#1434 Increment 2) is NOT implemented here.

    **Reachability, measured first, because it gates the severity.** The schema
    DOES express two wireguard tunnels on distinct listen-ports; the real commit
    gate (`configstore.CheckText`) ACCEPTS the shape at `e10d4c28f` with two
    warnings, and `WireGuardListenPorts()` returns BOTH ports. So the
    configuration is reachable and the kernel accept is installed for both.

    **The issue's headline is overstated, and the correction matters.** It
    frames the second port as "the #8274 bypass" — inner plaintext forwarded
    with no zone adjudication. Measured across four topologies, that is NOT
    differential: no WireGuard tunnel's decapsulated plaintext is zone-
    adjudicated, one tunnel or two, zoned or unzoned, and the product already
    says so loudly for every tunnel via the #5618 advisory. What IS real is the
    false wording.

    En route I made and caught a measurement error worth recording: my first
    probe grepped only for the heading `NOT ZONE-ADJUDICATED` and I read its
    absence on a zoned tunnel as "zoning suppresses the safety warning" — a
    finding I was about to report. There are TWO headings; a zoned tunnel gets
    the ACUTE variant (`ASSIGNED A ZONE THAT IS NOT ENFORCED`). The absence was
    an artifact of my predicate, not of the product. An absence claim from a
    grep needs a positive control, and this one did not have it.

    The three copies of the false claim, all saying the unsteered tunnel is
    dead / never handshakes:
      - `pkg/config/compiler_validate_wireguard_multiport.go` — the commit
        warning, which reads as authoritative;
      - `pkg/daemon/daemon_nft.go` — "that second rule is currently a no-op at
        the kernel (nothing steers that port up)";
      - `docs/wireguard-interop.md` — the same paragraph and a verbatim copy of
        the warning text.

    All three are false the same way: the host-inbound filter admits EVERY
    configured listen-port (the production NETLINK installer, not just the nft
    text renderer) and the helper binds a socket per wireguard endpoint, so the
    unsteered port receives transport and decapsulates — on the KERNEL path.
    "Unsteered" means not on the AF_XDP fast path, not inert. Nothing in the
    tree bound any of these strings, which is how a false claim survived in a
    warning operators are meant to act on.

    Five PRODUCTION mutants, all killed, one per arm: M1 (advisory reverts to
    the "dead" wording), M2 (advisory drops the not-adjudication sentence, so a
    reader infers the steered tunnel is policed), M3 (advisory fires for a
    single port — the control arm), M4 (steering picks the LAST port, reddening
    the mechanism cell that the advisory's wording depends on), M5 (host-inbound
    admits only the first port). M5 is the coupling: if only the steered port
    were admitted, the OLD wording would have been correct, so the two cells pin
    the same fact from opposite sides.
