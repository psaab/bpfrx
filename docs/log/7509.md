## Premise check, before any design

The issue body's table was verified at `origin/master` (81b4b95fb), from the
code, not from the issue:

| direction | resolved | mechanism |
|---|---|---|
| ingress | `vpnb` | `ifindex_to_zone_id` — the `st0` BASE row's inherited zone |
| egress | `0` | `ifindex_unambiguous_zone_id` — the #6722 gate |

It HOLDS, with one correction to the issue's own mechanism note: the ingress
answer comes from the BASE ROW's direct insert (`st0` arrives carrying `vpnb`
from `InterfaceZoneMap`'s fan-UP), not from the child→parent propagation. The
propagation is a second path to the same answer and is refused separately;
fixing only one arm leaves the other handing out the sibling's zone.

## What the issue said was impossible, and why it is not

Both #6727 and #8407 recorded that separating a base row whose zone was
AUTHORED from one that merely INHERITED a sibling's needs a fact "not on the
wire", because "a zoned row plus an unzoned row on one ifindex" is the same
shape as a trunk parent legitimately inheriting its single child's zone
(#921/#3618).

The two shapes are distinguishable. The fact is not on the ROW; it is in the
row's UNIT SIBLINGS on the same ifindex:

- `InterfaceZoneMap` fans a BARE `security-zone <z> interfaces <ifc>` reference
  DOWN onto every configured unit ⇒ an AUTHORED base has unit rows carrying its
  zone.
- It fans a unit-suffixed reference only UP ⇒ an INHERITED base has unit rows
  that do not.
- The #921/#3618 propagation case has NO unit row on the parent ifindex at all.

Measured from the Go side in `zone_unit_provenance_7509_test.go`: two configs
whose `st0` base rows are byte-identical (`Zone == "vpnb"`, ifindex 42) differ
only in `st0.0`'s row (`""` vs `"vpnb"`), and a trunk with no unit 0 puts no
unit row on the parent ifindex — with the positive control that declaring
unit 0 does.

## The change

`populate_interfaces` computes `unit_zone_claims` (ifindex → `Agreed(zone)` /
`Disagree`) in a pre-pass, and both write arms consult `unit_rows_admit` before
inserting. An ifindex whose logical-unit rows do not unanimously name one
nonzero zone takes no zone from a base row and none from a propagation. Scoped
to ifindexes that CARRY a unit row, so #921/#3618 is untouched by construction.

Reported twice, never silently: a commit-time advisory naming the interface and
the units, and a per-build runtime warning naming the ifindex.

## Cluster exposure

`docs/ha-cluster-userspace.conf` is UNAFFECTED: no base ifindex on either node
carries an unzoned logical-unit row beside a zoned sibling. `reth0`'s units are
both `wan` and both tagged (own netdevs); `reth1.0` is `lan` via a bare `reth1`
reference (fan-down, so base and unit agree); `gr-0/0/0.0` is the only unit of
its tunnel. The smoke is therefore a no-regression check, not an exercise of
the new path — the new path is exercised by the unit cells, which drive the
real `build_forwarding_state` on Go-measured row shapes.
