# #7559 — the image-roll election window

- **Timestamp**: 2026-09-03
- **Action**: Closed the #7559 window by NOT STARTING THE ELECTOR rather than
  by holding it. The issue's three recorded designs all put a hold inside
  `xpfd` on the recreated node, and were bounded by the framing "closing it
  needs a signal that survives the disk wipe". Verified the premise first at
  `origin/master`: `daemon_run_bringup.go:179` runs
  `holdSecondaryIfKernelCandidateArmed()` before `:181 UpdateConfig(cc)`,
  `UpdateConfig` elects (`group_state.go`, `electSingleNode`), and
  `election.go:121`'s fresh-boot guard is `!rg.Preempt && !m.peerEverSeen &&
  rg.State == StateSecondary && m.controlInterface != ""` — so a `preempt` RG
  (and a cluster with no `control-interface`, which is committable) falls
  through to `electLocalPrimary`. The premise holds as written.

  The reframing: the election is run by a DAEMON whose start the deploy driver
  already controls end to end, and the #5075 identity gate is evaluable with
  that daemon DOWN — `xpfd protocol-versions` is a pure binary invocation
  (`cmd/xpfd/main.go` `cmdProtocolVersions`) and `/etc/xpf/node-id` is a `cat`.
  So the driver asks the recreate hook to keep `xpfd` from auto-starting on the
  recreated node's first boot, proves identity, and starts the daemon only
  then. A node that fails the gate is left inert instead of merely detected.
  This is also the only candidate that covers the case #5075 was filed for — a
  hook that relaunched the OLD image — because an image that predates any
  in-`xpfd` hold simply ignores it.

  Not enforced by default: every hook written before this leaves `xpfd`
  auto-starting, so an unheld daemon is REPORTED (the #6759 detector stays the
  net) and `--require-daemon-hold` makes it a refusal. The daemon state is a
  THREE-way classification (`held` / `running` / `pending`-`unknown`) read from
  one `systemctl show` round trip; `is-active` alone cannot tell a masked unit
  from a node still booting.

  Two defects found by a hostile design review and fixed before commit, both
  verified against `origin/master` rather than taken on report:

  1. **The hold is backend-gated.** `scripts/image/bake.py` purges cloud-init
     and deletes every netplan / `interfaces.d` file, so xpfd's bootstrap
     lifeline is the ONLY thing that addresses `fxp0`. That is what makes a
     held node inert — and it is why `--backend ssh` cannot use the hold: the
     driver reaches the node by IP, so a held xpfd would make the node
     unreachable, time out the poll, and strand it masked and console-only.
     `incus exec` goes through the baked incus-agent and is unaffected. So the
     hold is requested on incus, skipped on ssh (bit-identical to today), and
     `--require-daemon-hold` forces it for an operator whose platform addresses
     the node independently of xpfd.
  2. **"Ready" is not "systemd active".** `xpfd.service` is `Type=simple`, and
     `RejoinAndConfirm` calls `ResetFailover()` OUTSIDE its retry loop — one
     un-retried gRPC dial with a 5s timeout — while the gRPC listener comes up
     only after the four startup phases. Waiting on `ActiveState` would have
     failed the roll on a cold daemon. The wait now requires the unit running
     AND `show chassis cluster status` to answer with a redundancy-group block.

  A third review finding (driver death leaves the node held with no
  self-recovery) was checked and is NOT a loss: `startKernelSelfRecovery` gates
  on `LocalDrained()`, and a recreated node is not drained — the recreate wiped
  the in-memory drain with the disk — so that path is a no-op with or without
  the hold.

  Validation: 16-mutation table over the driver, all killed, no survivors
  (release moved before the gate; release deleted; still-booting classified as
  held; both `require` gates removed; hold probe neutralised; readiness verdict
  ignored; falsy `expect_node_id` guard; held-before-running ordering; unknown
  folded to held; hook env; hold supported on every / no backend; readiness =
  systemd-active only; `_daemon_cli_ready` accepting any answer; ssh override
  removed). Full `scripts/deploy` unittest suite + `make selftest` +
  `make test` + `make test-failover` on the loss userspace cluster.
