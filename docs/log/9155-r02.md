# 9155 R-02 — authPriv on one `set` line committed as authNoPriv

- **Timestamp**: 2026-09-06
- **Action**: hoist the flat-run body at the SNMPv3 USM user level.
- **File(s)**: `pkg/config/compiler_system.go`,
  `pkg/config/snmpv3_packed_run_r02_test.go` (new).

## The defect

```
set snmp v3 usm local-engine user alice \
    authentication-sha256 authentication-password A \
    privacy-aes128 privacy-password P
```

committed clean and compiled to `authProto="sha256" privProto=""`. The operator
configured **authPriv** and the agent served **authNoPriv**.

`SetPath` builds a flat-set line as a **nested chain**, not a packed run on one
node, so the privacy stanza landed as a *grandchild*:

```
[user alice] > [authentication-sha256] > [authentication-password A]
                                          > [privacy-aes128 privacy-password P]
```

`compileSNMPv3Users` iterates the user's own children and never reached it.

## Why #9155's gates could not catch it

Both gates read the **compiled config** and key on a protocol being NAMED —
`PrivProtocol != "" && PrivPassword == ""`, and `PrivProtocol != "" &&
AuthProtocol == ""`. Neither can fire when the privacy protocol was **discarded
before the gate ran**.

> **A gate downstream of a dropping compiler is blind to exactly what it drops.**

That is why this fix belongs in the compiler and not in a third gate, and it is
the general reason the #9155 family needed a compiler fix as well as validators.

## Three wrong sites before the right one

Worth recording, because two of them looked correct and one *built cleanly*:

1. **`parseSNMPv3UserKeys`** — I rewrote it to walk a whole packed run. Plausible,
   and wrong: this input is not a packed run. Reverted rather than kept, since a
   change that fixes nothing still has to be maintained.
2. **`expandFlatRun`** — the right family, wrong member. It leaves body-owning
   leaves alone *by design*, and `authentication-sha256` legitimately owns a body
   (its declared `authentication-password` child).
3. **`hoistAndSplitRun8939`** — the member that exists for exactly this shape: a
   run nested *under* a body-owning leaf.

The schema already declares every cut point — `user` names all five protocol
children, each with its `*-password` — so no per-container shim was needed, only
the call.

**I found the site by dumping the AST, after assuming it twice.** The probe that
settled it printed the tree; the two failed attempts each looked right on
inspection.

## Behaviour change, stated because it is one

A config that compiled as authNoPriv now compiles as authPriv, so the #9155
runtime floor will refuse authNoPriv requests naming that user. **That is the
configured level being enforced, not a regression** — serving below the
configured level is the defect #9155 closed — but a deployment polling such a
user at the wrong level will notice at the moment of upgrade.
