# 9161 — the hybrid-apply guard was blind to the secrets the helper CAN see

- **Timestamp**: 2026-09-07
- **Action**: fix + acceptance table + mutation score
- **File(s)**: `pkg/dataplane/userspace/manager_overlay.go`,
  `pkg/dataplane/userspace/hybrid_guard_secret_9161_test.go`

## The defect

`configsContentEqual` decided whether a published config differed from the one
the helper already holds by comparing `json.Marshal` output. `config.Secret`
renders **REDACTED** in that encoding, so a WireGuard key rotation — a change of
`WgLocalPrivkeyHex`, or of a peer's `PresharedKeyHex` — marshalled to identical
bytes and compared **EQUAL**.

The consequence is not a missed diff, it is a false success: the #5680
hybrid-ACK refusal did not fire, the snapshot was marked applied, and the
operator was told the rotation had landed **while the tunnel kept running on the
previous key material**.

## Why the existing comment did not stop this

The function carried a long justification for the coarsening, ending in an
explicit instruction not to restore the former `DeepEqual`. Overriding a
deliberate prior decision needs its premise checked, so it was:

> the helper ALWAYS receives the redacted JSON encoding — it never sees raw
> secrets

That premise is **false**, and its own list gave the tell: it named strongSwan,
FRR, vrrp and cluster as the secret-bearing subsystems that apply on separate
paths. **WireGuard is not on that list, and does not apply on a separate path.**
`pkg/dataplane/userspace/protocol_tunnels.go` declares `WgLocalPrivkeyHex` and
`WgPresharedKeyHex` as plain `string` with json tags, and
`pkg/dataplane/userspace/tunnels.go:137,149` fills them with `.Reveal()`. The
helper receives raw WireGuard key material in the very snapshot this guard
governs.

## The fix

The coarsening is kept — the comment's *other* half is still true, and a
secret-only change the helper cannot observe genuinely is not a route-overlay
hybrid. Only the secrets that demonstrably reach the helper are added back:

```go
if !bytes.Equal(ab, bb) { return false }
// #9161: the redacted marshal cannot see a secret the helper CAN see.
return helperVisibleSecretDigest9161(a) == helperVisibleSecretDigest9161(b)
```

`helperVisibleSecretDigest9161` walks `config.EmitTunnelEndpointNames` — the
same enumerator `buildTunnelEndpointSnapshots` uses, so the digest's population
is the snapshot's population by construction, not by a parallel list that can
drift — and hashes the revealed tunnel privkey plus each peer's revealed PSK,
peers sorted by public key exactly as the snapshot builder sorts them.

The comment was rewritten rather than deleted: it now records the refuted
premise, preserves the over-strictness reasoning that is still valid, and
forbids the *new* failure mode — widening the digest to secrets the helper never
receives.

## Acceptance table

`pkg/dataplane/userspace/hybrid_guard_secret_9161_test.go`, shaped as the issue
asked ("a cell that changes only a secret … with a non-secret change and a
no-change case as the two controls"):

| Cell | Asserts |
|---|---|
| `TestSecretOnlyRotationIsADifference9161` | the defect: a privkey rotation is a difference. Carries a **precondition** check that the two configs' REDACTED marshals are identical — without it the cell could pass without exercising secret-blindness at all |
| `TestPresharedKeyRotationIsADifference9161` | the per-peer PSK is the second revealed secret; a tunnel-level-only digest passes the cell above and fails this one |
| `TestIdenticalConfigsStillCompareEqual9161` | control: no change still compares EQUAL. Without it, "report everything as different" satisfies the rows above and refuses every route-only publish |
| `TestASecretTheHelperNeverSeesStillComparesEqual9161` | control: an SNMPv3 password change still compares EQUAL — the coarsening survives, i.e. this is not a re-introduced `DeepEqual` |
| `TestPeerOrderDoesNotChangeTheDigest9161` | peer authoring order does not move the digest, and a real peer-set change does |

The last cell drives `helperVisibleSecretDigest9161` **directly**, not through
`configsContentEqual`. Through the guard it would be **vacuous**: the marshal
comparison runs first and already reports a reorder as a difference, so the
digest is never consulted and a mutation dropping the sort survives. Extracting
the input rather than writing a comment excusing an unreachable guard is the
#9123 rule.

D is the direction-of-error control: it is the mutation that makes the fix *too*
strict, and it is caught by the coarsening control rather than by a rotation
cell. Each mutation was confirmed APPLIED by occurrence count before scoring,
and each run was bounded so a hang would score VOID rather than as a kill.

B was first attempted by deleting the `sort.Slice` call outright. That orphaned
the `"sort"` import and **did not build**, which is VOID, not survived — a
mutant that does not compile has measured nothing. Neutering the comparator
instead keeps the import live and leaves the order unchanged, which is the
behaviour the mutation is meant to model.
