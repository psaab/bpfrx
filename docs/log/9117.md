# 9117 — the fourth shape, and the issue located it one step downstream

## What the issue asked for, and its own split

The issue is explicitly split: the originating report's MECHANISM and FIX are
REFUTED (reordering the share publication would compare the just-ended epoch's
grants against the NEW epoch's share and break the only gate that pairing
feeds), and a narrower claim SURVIVES. I took the surviving half and the fix
direction it prefers — exclude the newcomer for one epoch rather than fail the
whole class open.

## The issue's own location is one step downstream, and the probe proved it

> A worker whose flow buckets were empty at rotation N … IS admitted past the
> `prev_grants[id] == 0` skip at `:116`, reaches `:130`, and trips
> `UnsampledActiveWorker`.

I implemented the carve-out at that `prior_share == 0` check and the cell still
failed, reporting:

```
reason=UnsampledActiveWorker excluded=0
```

`excluded=0` means my branch never ran: **the class was already disarmed before
that check was reached.** The fail-open fires in the FIRST loop's participation
arm (`publish_equal_flow_epoch_v8.rs:88`), not the second loop's share check. A
mid-epoch newcomer has `demanded`/`prev_grants` set but
`sampled_active_flows_by_worker == 0`, because the sampler snapshot was taken at
the rotation — before it woke. So it is not "a participant we failed to sample";
it is **a participant that did not exist yet**.

That is the fourth shape, and it is absent from the module's own three-case
enumeration.

## The fix

At the real site: a participant whose share was **published as 0** is excluded
for one epoch, exactly as the idle-at-rotation case on the next line already
does, and for the same reason — a worker we cannot fairly compare is left OUT of
the comparison rather than used to disarm it. Its next epoch is fully sampled
and it rejoins.

`None` vs `Some(0)` is kept distinct, where `unwrap_or(0)` had collapsed them:
None means the id is outside the published vector — an inconsistency between the
worker set and the share table, which still fails open.

The exclusion is **counted** (`newly_active_excluded_count`, with an accessor)
rather than left as a local. A local that is assigned and never read is a claim
written into inert code; more practically, a flat fail-open count beside a
climbing exclusion count is exactly what "the fix is working" looks like from
outside.

## What it cost before

`fail_open` resets `valid_streak` and `smoothed_target_per_flow`, and
`EQUAL_FLOW_VALID_STREAK_REQUIRED = 2`, so ONE mid-epoch activation suppressed
enforcement for ~3 epochs **across the whole class** — one lease serves every
worker on it. Bounded (~600 µs at `EPOCH_DURATION_NS = 200_000`, opt-in via
`equal-flow-enforcement`, and it fails in the SAFE direction) but entirely
avoidable.

## Mutation matrix, including the one that SURVIVED

| # | Mutation | Verdict |
|---|---|---|
| M1 | restore the unconditional fail-open | **FAIL** — the subject cell |
| M2 | exclude EVERY unsampled participant, not just the newcomer | **SURVIVED** |

M2 is recorded in the test file as a known coverage bound rather than left for
someone to rediscover. It would delete the genuine case-2 safety fail-open, so
the gap is real. The cell that closes it needs an ESTABLISHED worker (non-zero
share) that is ACTIVE but UNSAMPLED, and **that state is not constructible
through this API**: `rehydrate_worker_active_count(id, 0)` clears
`active_by_worker` as well as the sampled count, so such a worker is skipped by
the `!active_by_worker[id]` guard before it reaches the participation arm — the
attempt produced `reason=None` with enforcement ON, i.e. the shape never
occurred. Closing it needs a seam that sets the sampled flow count independently
of the active flag: a production-type change for a test's benefit, which I did
not make unilaterally.

The cell that could not assert its subject was DELETED rather than left green —
a cell that cannot construct its own precondition asserts nothing while looking
arranged.

## The pair, and why the control is load-bearing

Kept as the issue requires. Without the control, "not enforced" is the state at
every early epoch, so the subject would pass against code that never enforces at
all. The subject also asserts its PRECONDITION directly — worker 1's published
share is 0 while worker 0's is not — so a future change that stops constructing
the shape fails loudly instead of passing vacuously.
