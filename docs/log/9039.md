## The asymmetry

`vrrp-group <id> advertise-interval` (seconds) is gated by
`validateVRRPGroupTimersStrict` (#8483). `chassis cluster
reth-advertise-interval` (milliseconds) reaches the SAME 12-bit centisecond wire
field by the same route and had no compiled-Config gate at all — admission is a
bare `strconv.Atoi`, and the only bound was the schema's
`ValidateInteger(10, 40959)`.

`duration_bound_8642.go` already states why that is not the same thing:
`compileTreeLenient` downgrades a typed-leaf violation to a warning on the
tolerant `Store.Load` / `Store.SyncApply` ingress, so a schema ceiling stops an
operator's commit and does not stop a config arriving from disk or from an HA
peer. **The bound has to be at the conversion.**

## Two halves, and the second is not redundant

1. **`validateRethAdvertiseIntervalStrict`** — hard-rejects at commit,
   downgraded to a warning on the tolerant path like every sibling gate in that
   file (#1960 no-brick). Its own cell asserts the warning is actually emitted:
   downgrading a rejection to *silence* is not the no-brick posture, it is the
   defect.
2. **A saturating clamp at the wire conversion.** Precisely because the gate is
   lenient on the tolerant ingress, an out-of-range config still reaches
   `pkg/vrrp` — warned about, and applied.

**The ceiling is 40950, not the schema's 40959.** 40959 ms is one millisecond
short of 4096 cs and encodes as 4095 cs only because integer division truncates,
so everything in 40950..40959 lands on the same wire value. Rounding down to the
last exact multiple keeps "what you configured" and "what the peer is told"
equal, which is the property the gate exists for. The gate also rejects a value
that is not a whole centisecond for the same reason.

## Saturate, not alias

```
700000 ms -> 70000 cs -> uint16(70000) = 4464 -> & 0x0FFF = 368 cs = 3.68 s
```

The instance advertises every 700 s while telling the peer to expect one every
3.68 s. Note 40960 ms is worse: `4096 & 0x0FFF = 0`, i.e. "expect an advert
immediately".

Saturating is the safe direction and aliasing the dangerous one. Too LARGE a
value on the wire makes a peer notice a real failure late — recovered by the
next advert. Too SMALL a value makes it declare a live master dead. Between
"converges late" and "fails over against a healthy peer", the first is the one
to pick when the config is already out of range.

A second cell states the invariant independently of any input: whatever reaches
`packet.go` must already fit in 12 bits, so the `0x0FFF` mask is a no-op rather
than a silent rewrite.

## Severity, kept honest

Low-to-Medium, not High, and the issue's own analysis is why: `masterAdverFloor()`
is `max(the RECEIVER's own interval, minLearnedMasterAdverInterval)` (#4548), and
12-bit aliasing can only produce a value BELOW the configured one — so on a
config-synced pair the receiver clamps the bogus value straight back. What
survives is the explicitly-supported MISMATCHED-interval case, where the alias
turns a genuinely slow master into a false fast one.

## The reference arm earned its place

The first run of the commit cell failed on its *admit* rows: the fixture had no
`chassis cluster authentication-key`, so the PSK gate was rejecting every case —
and **every "must reject" row was passing for the wrong reason**. Without an arm
asserting that an ordinary value still commits, this would have shipped as a
gate that appeared to work and had never once been the thing doing the
rejecting.
