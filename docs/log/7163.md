# #7163 — Noise session-sync transport

Vector B of #5078: the session-sync proof carried no role, identity or
transcript, and the frame-key derivation canonically SORTED its two nonces, so
both directions of a connection shared one key.

## Scope finding — why this could not be a narrow fix

`sync_auth_upgrade.go` (#6628, in-place PSK upgrade) **shared both defective
primitives** — `syncAuthProof` at `:290`/`:413` and `syncDeriveFrameKey` at
`:323`/`:373`/`:438`, the last two with the SAME two nonces, so it was undirected
there too. Fixing only the connect handshake would have left a second admission
path with the identical oracle — and it would have become the one an attacker
picks, because it is the one that still accepts.

The upgrade path could not be deleted instead. #6628 exists so a committed key
reaches a READ-ONLY secondary, where `EnterConfigureSession` returns
`ErrClusterReadOnly` and config-sync over the established connection is that
node's only writer.

## What shipped

**Both** admission paths run Noise_NNpsk0 from `github.com/flynn/noise` v1.1.0
(chosen over nyquist on evidence: nyquist has no tagged release, defeating "pin
an exact version" and CVE tracking, and carries 4 production deps to flynn's 1).

- `sync_auth_noise_7163.go` — one `newSyncNoiseState` builder for both paths.
  The prologue binds construction version, a PHASE byte, cluster id,
  ROLE-ORDERED node ids and the fabric index. `syncNoiseSplitKeys` maps the two
  CipherStates onto this side's read/write.
- Connect handshake: role from the TRANSPORT (dialer = initiator), a source the
  peer cannot assert.
- In-place upgrade: role from NODE ID (lower id initiates), *not* from the nonce
  comparison `upgradeIAmResponder` used — a nonce is peer-supplied, and role must
  not be an attacker-chosen input to our own key derivation.
- `syncAuthProof`, `syncCheckPeerNonce`, `syncDeriveFrameKey` and their tags are
  DELETED, not left unreferenced.
- `SessionSyncWireVersion` 1 → 2 (NOT `CurrentHAProtocolVersion`).

## The measurement that changed the design

The handover brief carried two contradictory claims about Noise_NNpsk0's first
message: that it "carries no payload and so no tag" (which forced a four-frame
upgrade exchange) and, elsewhere, that "under psk0 the FIRST message already
carries a tag, so a wrong PSK is refused at msg1".

Measured against flynn/noise v1.1.0 rather than reasoned about:

```
msg1 len=48                                    (32-byte ephemeral + 16-byte tag)
responder split at msg1 = false                (splits when it WRITES msg2)
WRONG-PSK       responder read msg1 -> chacha20poly1305: message authentication failed
WRONG-PROLOGUE  responder read msg1 -> chacha20poly1305: message authentication failed
ChannelBinding  32 bytes, equal on both ends after msg2
cs1 != cs2                                     (independent directional keys)
```

So the responder AUTHENTICATES the initiator before it answers, and the fourth
frame — whose only stated purpose in #6628 was that "the responder has proven
nothing when it switches" — has nothing left to do. The upgrade exchange is
three frames:

```
I (node 0)                        R (node 1)
-- Hello{msg1} --------->         reads msg1 => key equality proven
                        <-- Proof{msg2} --   then R installs writeKey
reads msg2 => installs readKey
-- Confirm{MAC} -------->         then I installs writeKey
                                  verifies MAC => installs readKey
```

`TestUpgradeMsg1IsAuthenticated7163` pins the measurement, paired (wrong PSK
refused AND right PSK accepted) so "refuses everything" cannot pass it. If it
ever stops holding, the three-frame shape is unsafe and that test says so.

## Switch-point discipline with TWO keys per direction

`Split()` returns two independent keys where `syncDeriveFrameKey` returned one
shared value, so there are two install points per direction rather than one.
They cannot land out of order: each is anchored to exactly one frame, the WRITER
installs immediately after writing it inside the `writeMu` section, and the
READER installs while processing it. TCP orders frames within a direction.

Two consequences that are easy to get wrong and are now tested:

- The boundary frame must be UNSEALED when it crosses a boundary that has not
  moved yet, and the writer's install must not happen at all if that frame did
  not go out (`TestUpgradeInstallPointsAreAnchoredToTheirFrames7163`, both
  sub-cases, the second forced by killing the socket before delivering msg2).
- The two COMPLETING frames (Proof at the initiator, Confirm at the responder)
  are deliberately **not** gated on the live control-link key, and `authPSK` is
  stamped with the round's key rather than the live one. A key rotated or
  cleared between the Hello and one of them would otherwise make this node
  refuse a frame whose peer has ALREADY switched — leaving the peer sealing into
  a reader that never moved. That is the one desync the mechanism promises never
  to cause.

## The hazard the three-frame shape introduced, and how it is closed

Committing at msg2 buys a frame and costs a guarantee, and the cost was found by
asking what a hostile peer does rather than by re-reading the happy path.

A msg1 is 48 bytes of CLEARTEXT on a not-yet-sealed stream — the only stream an
in-place upgrade ever starts on — and its AEAD tag covers the prologue and the
initiator's ephemeral, neither of which changes on a replay. So a captured Hello
RE-VERIFIES. Traced end to end:

1. R answers Hello_1 and installs `writeKey = r2i_1`.
2. An attacker replays Hello_1. R mints a second round and installs `r2i_1'`.
3. I completes round 1, installs `writeKey = i2r_1`, sends Confirm_1.
4. R checks Confirm_1 against round 1' — MAC fails — R never installs a read key
   while I is already sealing.
5. Both directions desync. The connection DROPS.

#6628 was immune because its round state was set-once NONCE state a second Hello
could not clobber. Noise handshake state is not, and replacing `ac.upgrade`
wholesale on every msg1 is what lost the property.

**The four-frame variant does not avoid this**, and that was checked before
reaching for it. Moving R's commitment to an Ack only moves the exposure: I's
write install at the Confirm is still unilateral, and R still needs un-clobbered
round state to honour it. Someone commits first either way. The fix is that the
state a commitment depends on cannot be taken away:

- the RESPONDER refuses a msg1 while `answeredAwaitingConfirm()`;
- the INITIATOR never supersedes an incomplete round, not even for a rotation;
- the RESPONDER stays silent — no Request — while awaiting a Confirm.

Two escapes keep the second guard from stranding a rotation forever against a
peer that never answers, and neither is a timer: a Request from the peer, and a
round that COMPLETES under a retired key re-triggering itself at the end of
`handleAuthUpgradeProof`.

### The same hazard through a forged Request

A Request carries no MAC — on a not-yet-sealed stream there is nothing to key one
with that a replay would not also carry — so an attacker can inject one. Minting
a fresh round on it discards the handshake state an in-flight msg2 needs: the
same drop from the other side. So a Request for a round still outstanding under
the SAME key RE-SENDS that round's Hello byte for byte. The test asserts byte
equality rather than frame type, because a fresh round carries a different
ephemeral and a type-only assertion passes either way.

**Residual, stated rather than hidden.** A forged Request arriving while a round
for a DIFFERENT key is outstanding still starts a fresh round and can strand a
msg2. Closing it needs per-round state pinning and buys nothing: the
precondition is frame injection on an unauthenticated session-sync stream, where
the same attacker can already send `syncMsgFence` and disable every redundancy
group the victim owns. That is #6628's existing residual, not a new one; on an
authenticated stream (a rotation) every frame is sealed and none of it is
reachable. The NEVER DROPS paragraph in `sync_auth_upgrade.go` carries the
qualifier.

## Mutation evidence

Pre-redesign matrix: **10 of 11 cells RED**, tree CLEAN after restore. Full
`pkg/cluster` + `pkg/daemon` suite per cell, `-count=1`, no `-run` filter, each
edit asserted landed against the tree (`git diff --stat` non-empty) between the
edit and the run.

The single ESCAPE was an INERT MUTATION, not a coverage gap, and the finding is
load-bearing. Deleting the responder's msg1 error check changes nothing:
`flynn/noise`'s `ReadMessage` calls `s.ss.Rollback()` on an AEAD failure and
leaves `shouldWrite` false, so the following `WriteMessage` returns "unexpected
call to WriteMessage should be ReadMessage". The responder CANNOT answer a msg1
it did not authenticate even with the check removed — the guarantee comes from
the library's state machine rather than from an `if` we wrote, which is exactly
what the three-frame shape rests on. The cell was replaced by one that binds the
real premise: `syncNoisePSK` ignoring its input, so every node derives the same
PSK and a wrong control-link key authenticates.

## Defects found by running, not reading

- **Noise mandates a 256-bit PSK**; `ControlLinkAuthKey` is an arbitrary-length
  config string, so every real cluster would have failed the handshake.
  `syncNoisePSK` derives 32 bytes via labelled SHA-256 (not truncation, which
  collapses keys sharing a prefix; not zero-padding, which leaves most of the
  PSK constant).
- The happy-path connect fixture gave both ends node id 0, so their role-ordered
  prologues differed and the handshake failed. That was the identity binding
  **working**; the fixture was wrong. The same trap bit the upgrade fixtures:
  two ends with the same node id both believe they are the initiator.
- The upgrade prologue needed a PHASE byte. Without it a connect msg1 — which
  travels in cleartext on a fresh TCP connection — is also a well-formed upgrade
  Hello: replay it into an established unauthenticated stream and the responder
  answers, switching its write direction to a key derived from an ephemeral
  nobody holds. The peer can then read nothing and the connection DROPS, which
  is the one thing the in-place upgrade promises it never does.
  `TestUpgradePhaseSeparationRefusesAConnectMessage7163` is paired.

## Anti-vacuity work

- `TestInPlaceUpgradeWithMismatchedKeysSwitchesNothing6628` had NO anti-vacuity
  guard: every assertion in it says "nothing switched", which a completely
  broken exchange satisfies as well as a correctly refusing one. Since #7163
  changes the handshake underneath it, that was a live vacuum. A positive
  control was added — the same pump sequence with MATCHING keys must produce a
  msg2 and complete — and it is checked at the msg2 step, not only at the end,
  because the mismatch is now refused one frame earlier.
- The directional-key assertion binds VALUES, not the existence of the fields,
  and `TestInPlaceUpgradeInstallsDirectionalKeys7163` goes further: it asserts
  the CONSEQUENCE (a node's own sealed `syncMsgFence`, echoed back at it, is
  refused) with a positive control that the same frame verifies at the peer.

## Residual, unchanged by this work

A HOSTILE stream admitted before the commit still declines the upgrade by
staying silent, and a decliner is indistinguishable from a legitimate
not-yet-keyed peer. Closing it needs a bounded drop window — the mechanism #5078
shipped and then removed, for three reasons any replacement must answer. Not
attempted here.
