# #9323 — `routing-instances <name>` was open-world, so a nested subtree committed clean and compiled to nothing

- **Timestamp**: 2026-09-06
  - **Action**: added `validateRoutingInstanceChildTokensAST`, a SCOPED prewalk
    gate on the keywords directly under `routing-instances <name>`, and
    declared the four routing-instance keywords the compiler admitted and the
    schema did not.
  - **File(s)**: `pkg/config/compiler_routing_children_9323.go` (new),
    `pkg/config/schema_routing.go`, `pkg/config/compiler_prewalk.go`,
    `pkg/config/compiler_opts.go`,
    `pkg/config/routing_instance_closed_world_9323_test.go` (new),
    `docs/config-schema.md`

  - **The issue's criterion is "decide the world", and the decision is: a
    scoped gate, NOT `closedWorld: true`.** Both options were tried; the
    measurement is what chose.

  - **The whole-suite measurement said `closedWorld` was safe, and it was
    WRONG.** `go test ./...` with the flag armed on the routing-instance
    wildcard rejected ZERO configs — a clean board across the entire corpus.
    A targeted over-reach cell then found

        set routing-instances VRF-A protocols bgp group g1 neighbor 10.0.0.1 peer-as 65001

    REJECTED, because the per-instance `protocols bgp group` subtree does not
    declare `neighbor` while the shared compiler (`compileProtocols`, copied
    into `ri.BGP`) handles it fully. **No fixture in the tree configures a BGP
    neighbour inside a routing instance**, so the green was evidence about the
    CORPUS, not about the change. `closedWorld` INHERITS, so arming it exposes
    every incompleteness in the per-instance protocol grammar — an unbounded
    tail, and exactly the failure mode that backed the same flip out at the
    config root (9 of 10 shipped configs) and at `firewall family` (#9017).

    The scoped gate is therefore the honest bound, not a narrowing: it closes
    precisely the level the defect is at and inherits nothing.

  - **Found while building that guard, filed as #9351**: the same schema gap
    SILENTLY DROPS a per-instance `neighbor <ip> local-address <ip>` in the
    flat-set form while the identical GLOBAL spelling compiles correctly.
    Measured — the configured case and the never-configured case are
    byte-identical, on a clean commit. `SetPath` breaks nodes by walking the
    schema, so an undeclared child cannot be broken out and the tokens are
    PACKED onto the neighbour's own Keys, where the compiler's child-form
    reader never sees them. `peer-as` fails CLOSED only because a separate
    validator demands it; everything else fails open.

  - **Four keywords declared BEFORE the gate, because gating without them is a
    regression the suite cannot see.** `description`, `vrf-target`,
    `vrf-table-label` and `route-distinguisher` are admitted by
    `isRoutingInstanceKeyword8787` and `description` is compiled into
    `RoutingInstanceConfig.Description`; the schema declared four of the
    compiler's eight. With the gate armed and those four undeclared,
    `go test ./...` rejects nothing — no fixture writes any of them. A targeted
    probe found it. `TestRoutingInstanceSchemaAndCompilerAgree9323` now holds
    the two sets equal in BOTH directions, which is the drift the #8787 note
    beside that helper warns about in prose and nothing enforced.

  - **The permitted set is read from the schema** (#9017's rule), so a new
    routing-instance keyword is permitted automatically and there is no second
    place to remember.

  - **#1960 split**: strict commit / commit-check rejects; Load / SyncApply
    warns and boots. Asserted in ONE cell with both halves, because either
    alone is satisfiable by the wrong thing — a lenient-only cell passes for a
    gate that never rejects, and a strict-only cell passes for a gate that
    bricks the boot.

  - **MY OWN GATE FALSE-REJECTED VALID CONFIG, and the probe that found it was
    the packed-vs-braced coverage question.** The first version read BOTH a
    node's `Keys` tail AND its `Children` as instance keywords. In the
    BRACE-ELIDED spelling those are not the same thing: `VRF-A routing-options
    { static { … } }` parses to `[VRF-A routing-options] > [static]`, where the
    keyword is on the Keys tail and the Children are THAT KEYWORD'S BODY.
    Measured:

        VRF-A routing-options { static { route 0.0.0.0/0 next-hop 10.0.0.1; } }
          -> REJECTED: "static" is not a routing-instance keyword
        VRF-A protocols { ospf { area 0.0.0.0 { interface ge-0/0/1.0; } } }
          -> REJECTED: "ospf" is not a routing-instance keyword

    Both are valid configuration. A commit gate that refuses valid
    configuration is a WORSE defect than the silent drop #9323 fixes, and
    "consistency" is satisfiable by a gate that rejects everything — which is
    why the fix is pinned by REFERENCE ARMS that must ACCEPT, not only by
    rejection arms.

    The same shape also made the gate name the WRONG TOKEN on a genuine
    rejection: `VRF-A security { nat { … } }` reported `"nat"` (the body) rather
    than `"security"` (the keyword). Both directions are now cells.

    The two sources are EXCLUSIVE, not additive: a node whose Keys carry a tail
    is a packed/elided instance keyword and its Children belong to that keyword;
    only a bare `[<name>]` node has Children that are instance properties. This
    is #9055's lesson, which the COMPILER already learned at the sibling site —
    the gate had to learn it separately because it splits the node itself.

  - **Spelling coverage is now STATED, not inferred from what the tests happen
    to contain.** `TestTheGateCoversAllThreeSpellings9323` pins all three —
    flat-set chain, ordinary braced, brace-elided — in both directions, with the
    two false-reject arms as reference.

    the defect it had to fix.

    T7 survived the entire suite until a white-box cell swapped the schema node
    out for the duration. A decline arm that no production path can reach is
    still worth having — refusing every routing instance on a lookup failure is
    a total commit outage — but it is only worth having if something asserts it.

  - **THE ADMISSIBLE SET IS NOT DERIVABLE FROM EITHER SOURCE — it had to be
    MEASURED, and three separate false-reject classes proved that before the
    gate was right.** In order:

    1. `closedWorld: true` on the wildcard — rejected
       `protocols bgp group <g> neighbor <ip>`. Found by a targeted over-reach
       cell; the whole suite was green.
    2. The gate reading a brace-elided node's Children — rejected
       `VRF-A routing-options { static { … } }` naming "static", and
       `VRF-A protocols { ospf { … } }` naming "ospf". Found by probing the
       three AST spellings.
    3. The gate's permitted set taken from the schema + the compiler helper —
       rejected `set routing-instances dmz-vr interface-routes rib-group inet
       dmz-leak` (the shipped #2226 contract) and
       `routing-instances { apply-macro M { k v; } RI { … } }` (#7029, a Junos
       statement permitted at ANY hierarchy point). Found by `go test ./...`.

    Only after enumerating the CORPUS did the set close. Measured occurrences
    of a keyword appearing directly under a routing instance across every
    `.go`, `.conf` and `.md` in the tree:

        instance-type 129, interface 66, protocols 36, routing-options 29,
        interface-routes 6, description 2, vrf-target 1, vrf-table-label 1,
        route-distinguisher 1

    — plus the universal meta statements (`apply-groups`,
    `apply-groups-except`, `apply-macro`), which are skipped via the same
    three-keyword set and the same reasoning as
    `zoneInterfaceApplyMetaKeyword` (#7029): the latter two SURVIVE group
    expansion as live nodes, so they reach a gate verbatim.

  - **The schema/compiler agreement guard asserted a FALSE claim and was
    corrected.** Its first form asserted schema == `isRoutingInstance
    Keyword8787` in BOTH directions. That helper is not the admissible set — it
    is only where a PACKED multi-value run stops — and `interface-routes` is the
    measured counterexample: shipped, declared, and absent from the helper. The
    guard now asserts only the direction that must hold (every keyword the
    packed reader admits must be declared, or the gate rejects it), and says why
    the converse must not be asserted.

  - **Two ratchets tightened with named reasons, not slack**: the #7484
    spelling-gate `gateCoverageFloor` 715 -> 716 (declaring `interface-routes`
    made one already-read spelling comparable — the same movement #9151
    recorded) and `gateBlindUnreachable` 132 -> 137 (the four accepted-and-inert
    keywords cannot change output BY CONSTRUCTION, so the differential can never
    move them out of `unreachable`; that is a property of the leaf, not a gap in
    the instrument).

  - **Three ratchets/registries moved, each updated with a named reason rather
    than loosened**: #7484 `gateCoverageFloor` 715 -> 716 and
    `gateBlindUnreachable` 132 -> 137 (above), and the #8921 multisite-admission
    registry, where declaring `interface-routes` under the wildcard gave three
    recorded admissions a THIRD declaring site
    (`routing-instances/*/interface-routes` and its two `rib-group` children).
    That registry stores site PATHS rather than a count precisely so a
    substitution cannot hide; the three rows now name the new site.
