# #9009 — the Go and Rust binding-plan keys disagreed six ways

## The reframing that made it tractable

The two keys are **never compared to each other**. Each side compares its own
key across consecutive snapshots. So byte-equality is not the property and
making the tuples identical is not the goal — they must **move together**. That
is why Go keeps hashing `LogicalOnly` although Rust has no such field: the flip
cannot occur alone, so the extra field never moves Go's key by itself.

**Rust is authoritative** for every divergence closed here, and not by default:
its filters and rx_queues resolution mirror `replan_queues`, the function that
builds the layout, and the #2915 invariant is that the key must move whenever
the layout would.

Both directions matter, asymmetrically:
- **Go under-detects** → a real plan change is called "same plan" and published
  through the pending-XSK-startup window while the helper rebuilds bindings.
- **Go over-detects** → `!samePlan` reaches `stopForNewGenerationLocked` →
  `stopLocked` + `ensureProcessLocked`: a full AF_XDP teardown and rebind, and
  inside the XSK window the snapshot is not published at all. A forwarding
  interruption, not wasted CPU.

## The six

| | divergence | direction | fix |
|---|---|---|---|
| D1 | orphan VLAN child: Rust hashes the PARENT's queue count, Go hashed the child's | tracking two different numbers | `planKeyRXQueues` |
| D2 | refused fabric parent: Rust drops the row, Go's fabric loop had **no filter at all** | Go under-detects | `refused.refusesNetdev` |
| D3 | refused bind target: Rust filters, Go had the predicate and did not apply it | Go under-detects | `planKeyBindingTargetRefused` |
| D4 | `shared_umem` list ORDER: Rust sorts, Go joined authored order | Go over-detects | sort a copy |
| D5 | `logical_only` Go-only, justified by a **false** reason | none (conclusion held) | corrected comment |
| D6 | fabric rx_queues fallback + `.max(1)` | Go under-detects | `planKeyEffectiveRXQueues` |

D1 deserves the note the issue makes: #8901 dismissed the rx_queues class as
"not a config commit, and this key is about config snapshots". **That does not
cover the orphan case** — the two sides hash different numbers responding to
different stimuli, so the divergence persists across commits rather than being
one number sampled at two instants.

D5's finding is that the recorded reason was false. It claimed *"Rust excludes
the row upstream via `include_userspace_binding_interface`"*; that function
tests zone-empty, `local_fabric_member`, `userspace_unbindable_netdev` and
mgmt/control, and `logical_only` appears nowhere in `userspace-dp` (the wire
value is discarded by a serde struct with no such field). The *conclusion*
survives — a `LogicalOnly` flip also swaps the row's ifindex, which both sides
hash — so the field stays and the reason is now true. A false rationale that
licenses a real difference is worse than none: it is inherited as established
and reasoned from.

## The #8901 guard had to be repaired, not just extended

Its Go-side extractor took the source text from `"iface=` to the **first `)`**
and matched `iface\.([A-Za-z]+)`. That works only while every argument is a bare
field selector. Routing rx_queues through `planKeyRXQueues(...)` put a `)`
inside the window, which **silently truncated it** and dropped four fields —
reported as *"hashed by Rust and not by Go"*. An instrument break, misattributed
to the code under test, in the direction that reads as a real defect. Rebuilt on
`go/ast`.

Its "WHAT THIS GUARD DOES NOT CHECK" section named the VALUE and POPULATION
classes as open. They are now closed, so that text was corrected rather than
left to rot the way the `logical_only` adjudication did. **The guard still
cannot see either class** — it compares names — which is exactly why the new
cells execute the hash.

## Cells

Four, one per named acceptance item, each a **baseline/perturbed pair**
asserting moved or not-moved. A single key proves nothing about movement.

Each also carries an attribution guard: D2 and D3 assert the row is present in
the baseline key, so "the key moved" cannot be satisfied by a key that never
mentioned the row; D4 asserts membership changes still move the key, so the
sort cannot be satisfied by dropping `shared_umem` entirely.

### M2 was void in a way the build check does not catch

It built, it ran, and it reported a survivor — but the `perl` matched the
**first** occurrence of that filter in the file, which is a **pre-existing** one
in `buildUserspaceIngressIfindexes`, not the one in `snapshotBindingPlanKey`.
The mutation was applied to a function the cells were not about, so "survived"
was a statement about the wrong code.

An occurrence count (2 → 1) proved it applied; it did not prove it applied *to
the right site*. Re-scoped to the function body, it kills. **The lesson beyond
"check it built": a whole-file text splice needs the SITE verified, not just the
edit.**

Following it up rather than moving on: removing that pre-existing filter reds
**five named cells** (`TestOwnerlessFabricParentIsRefused`,
`TestSkewedFabricSampleKeepsIngressAndAllowlistAgreed`,
`TestFabricParentVerdictSurvivesACanonicalAlias`,
`TestAFabricVoteCannotOverturnAnOwningRow`,
`TestFabricLoopCannotReadmitARefusedMember`), so it is well covered. Checked,
because "my scoped run didn't fail" is not evidence about coverage.

M5 is the over-broad-fix detector: applying the orphan re-key to every VLAN
child would satisfy the orphan assertion and break the normal case.

## Not closed here

The issue's deeper observation stands: there is still **no shared SSOT** — no
codegen, no shared fixture, no golden digest across the two planes. Six
divergences were found by diffing two hand-transcribed functions, and nothing
structurally prevents a seventh. The cells added here execute the Go hash only;
a genuine cross-plane conformance suite (shared snapshot fixtures, both sides
asserting the same movement verdicts) remains the architectural fix.
