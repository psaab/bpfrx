# 9121 — the config-sync endpoint is the set #8965/#8987 should have been keyed on

## The instruction that shaped this

> Establish which set is authoritative before changing either.

There are **three** sets in this daemon, and they answer three different
questions. Naming which one is authoritative *for the preflight* is the whole
finding; the code change follows from it.

| Set | Question it answers | Authoritative for |
|---|---|---|
| `clusterTransportKey` — 6 fields incl. fab1 (`daemon_ha_sync.go:1354`) | "does step 20 RESTART cluster comms?" | step 20. Correctly wide. |
| the HEARTBEAT pair `{ControlInterface, PeerAddress}` via `Manager.HeartbeatPeerAddr` / `HeartbeatControlInterface` | "is the heartbeat running, and where?" | #8965 / #8987 as written |
| `clusterSyncTransport`'s SELECTED PAIR (`daemon_ha_comms_wiring.go:104`) | "which endpoint carries the CONFIG PUSH?" | **this family** |

A partition strands the **push** (`pushCommittedConfigToPeer` →
`syncConfigToPeer` → `QueueConfig`), so the third is the authoritative one. The
heartbeat pair is a PROXY for it — exact in control-link mode, and control-link
mode is the only shape the shipped fixtures configure
(`docs/ha-cluster-userspace.conf`, `test/incus/loss-userspace-cluster.env`), so
nothing measured the divergence.

## Verified at head (d766d902a), each claim read rather than inherited

- `clusterSyncTransport` falls back to `{FabricInterface, FabricPeerAddress}`
  when **either** control field is empty.
- `daemon_ha_sync.go:882` starts the heartbeat only when **both** are set. So in
  fabric mode `HeartbeatPeerAddr()` and `HeartbeatControlInterface()` are BOTH
  empty, both sibling gates take their `have == ""` arm, and **both return nil on
  the commit that partitions the pair.** The gate misses twice.
- `clusterTransportKey` includes fab1, and step 20 restarts comms on a fab1
  change — correct for the restart question.
- **fab1 is a REDUNDANT secondary sync path**: `NewDualSessionSync` takes it as
  a second dial target beside fab0 and `sync_conn.go:837` logs "secondary fabric
  listen failed, using primary only". A fab1-only change therefore does NOT
  strand the push.
- `#8987` was already CLOSED (15:28:46Z today) by another lane —
  `clusterControlInterfaceCommitPreflight` is on master and wired at all three
  apply paths. The queue item is done; reported to team-lead.
- `d.activeTransport()` takes `clusterCommsMu`, which is not held on the commit
  path (grep: no `clusterCommsMu` in `daemon_apply_commit.go`). Safe to call
  from the preflight.

Including fab1 is an **over-gate**: it would refuse a commit that partitions

## What landed

`clusterSyncEndpointCommitPreflight` compares resolved **endpoints**: it runs
`clusterSyncTransport` over the running `clusterTransportKey` and over the
candidate config and refuses when the selected endpoint moves. Using the same
selector on both sides is structural, not stylistic — a hand-copied fallback
rule would drift from the one that actually picks the transport, and drift is
this family's whole history.

Free consequence, not in the issue: a transport-**TYPE** switch (adding or
removing a control link on a running cluster) moves sync while the peer stays
put — the same durable partition, invisible to both siblings because their
running value is empty on one side of it. Covered without a fourth gate.

A control-link→control-link move is deferred to #8965/#8987 by an explicit arm,
so the decision stays total rather than relying on call ordering.

Wired at all THREE apply paths (`commitAndApply`, `syncAndApply`,
`commitConfirmedAndApply`), as #8987 item 4 requires.

### Methodology note — `go vet` is not a compile check

The first attempt at M1 inserted `return nil` at the top of the function and
scored it **VOID (does not compile)** on a `go vet` failure. That was wrong:
unreachable code is a *vet* diagnostic; the mutant BUILDS and runs fine. Scoring
it VOID would have silently dropped the most important arm of the matrix from
the record. Re-run with `go build` as the gate, it kills six cells. **Use `go
build` to decide VOID; `go vet` answers a different question.**
