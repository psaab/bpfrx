# #7899 — the fragment-association cache becomes its own component

- **Timestamp**: 2026-09-03
- **Action**: Moved the fragment-association cache out of `nat64.rs` into
  `userspace-dp/src/fragment_assoc/`, then dropped the `Nat64` prefixes it was
  mislabelled with. Two commits: motion, then renames.
- **File(s)**: `userspace-dp/src/fragment_assoc/{mod,key}.rs` (new),
  `userspace-dp/src/nat64.rs`, `userspace-dp/src/nat64_tests.rs`,
  `userspace-dp/src/main.rs`,
  `userspace-dp/src/afxdp/{mod.rs,coordinator/status.rs,poll_descriptor/frag_assoc.rs,tests_nat64_tunnel.rs}`,
  `userspace-dp/src/FEATURES.md`, `docs/feature-coverage.md`.

## The seam was verified before anything moved

The issue argues the split is justified because the data model is already
shared. That is a checkable claim and it is the whole justification, so it was
checked first.

**Confirmed as stated:** `FragKey` is family-agnostic (`addr_family`, `src`,
`dst`, `ident`, `protocol`, `authority` — nothing NAT64-specific), and the
entry's only NAT64-typed field is `reverse: Option<Nat64ReverseInfo>`.

**The stated REASON is wrong, and the correction strengthens the case.** The
issue says the field is optional "precisely because the same-family NAT arm
leaves it `None`". Measured: BOTH arms leave it `None`. There is no `Some(..)`
in any `frag_assoc.install(..)` call anywhere in the tree — production or test
(positive control: the pattern returns 0 matches, and it does match when a
`Some` is present) — and both `lookup` consumers bind `_reverse` and discard
it. The field is optional because the reverse (v4→v6) direction is a documented
deferred increment.

So the entry carries no LIVE NAT64-specific content at all. The move
concentrates a property that was already true and mislabelled, which is the
test a split has to pass, and it passes more cleanly than the issue argued.

**The `reverse` field was NOT reclaimed.** It is a placeholder for deferred
work, not accidental dead code: `Nat64ReverseInfo` is live elsewhere (session
sync), and #6386 — where the consumers acquired their leading underscore — was
itself a pure move that decommissioned nothing. Deleting a field that exists
for a designed-but-unbuilt case is the failure mode where a fix is correct for
every case that EXISTS and wrong for the pending one.

## A false comment was load-bearing for the design argument

`frag_assoc.rs` claimed cross-family NAT64 "has its own install (which also
stamps the reverse info)". It does not and never did. That sentence is where
the issue's premise came from — so a stale comment had been propagating into a
design decision. Corrected in place with the measurement recorded beside it.

## What was deliberately NOT done

- **The cache INSTANCE stays on `Nat64State`**, so call sites remain
  `forwarding.nat64.frag_assoc`. Re-homing it is a lifecycle change, not
  motion: the Arc is threaded across config reloads inside
  `from_snapshots_with_previous` so in-flight datagrams keep translating.
  Mixing that into a relocation is what makes a relocation unreviewable.
- **The 55 fragment tests stay in `nat64_tests.rs`.** They are interleaved with
  119 non-frag NAT64 tests across 7000 lines. Extracting them has its own
  failure mode — an insertion between a doc comment and its `fn` steals the
  `#[test]` attribute and silently decommissions the guard — and it belongs in
  its own change.
- **Two counters keep their `NAT64_FRAG_` names.** They ARE the shipped
  Prometheus series `xpf_userspace_nat64_frag_{cross_domain,protocol_alias}_misses_total`,
  so the identifier is the grep path from an alert to the code. Renaming them
  would break a real workflow to make a module read tidier.

## The exact non-motion delta

Eight visibility widenings, all private → `pub(crate)`, none wider:
`FRAG_SHARDS`, `FRAG_CAP_PER_SHARD`, `FRAG_TTL_NS`, `frag_shard_index` in the
new module; `Ipv6FragInfo`, its four fields, and `ipv6_fragment_header` in
`nat64.rs` (which keeps them — it still has four other uses). They exist
because `nat64_tests.rs` reached these through `use super::*` while they lived
in `nat64.rs` and now sits in a sibling module.

Renames: only the misleading `nat64` token was dropped. `frag` was kept where
the bare name would collide — `shard_index` and `SHARDS` already name unrelated
sharded structures in `flow_cache.rs`, `sharded_neighbor.rs` and
`cos/token_bucket_tests.rs`, and taking those names would be legal per-module
while making a grep for either ambiguous.

## Validation

"Pure move" is exactly the claim that gets taken on trust, so it was measured:

- The moved text was diffed against the original region at `origin/master`.
  `key.rs` is **byte-identical** (100/100 non-blank lines); the cache body
  differs on exactly **8 lines**, all listed above.
- The full test inventory (`cargo test -- --list`) is **byte-identical** before
  and after both commits — 5257 entries — so no test was lost, added, renamed
  or duplicated. Post-rebase it differs by exactly one entry, a test master
  added in its own commit. Scoped duplicate checks on `fragment_assoc::` and
  `nat64` are both 0; **scoped**, because the unfiltered form reports 22 false
  positives from modules compiled into two binaries.
- Full `cargo test` green (5118 unit tests), `go build ./...` rc=0, full Go
  suite rc=0, touched-file modularity gate passes.
- `nat64.rs`: 4537 → 3824 LOC.
