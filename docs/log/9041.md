# 9041 — clearPeerSessions ghost clear, and the held session-walk slot

## Part 1 — `clearPeerSessions` on `context.Background()` (FIXED)

### Reachability, established before the fix

The issue's defect only matters if something cancels. Two independent
cancellers, both found in the callers rather than assumed from "gRPC cancels
contexts":

- `pkg/api/sessions.go` calls `svc.ClearSessions(r.Context(), ...)` — an
  in-process call carrying the HTTP request context, which `net/http` cancels
  when the client disconnects.
- `cmd/cli/shared.go` supplies `cmdCtx`, declared as
  `cmdCtx context.Context // per-command context, cancelled by Ctrl-C`
  and built with `context.WithCancel`.

So an operator pressing Ctrl-C on a clustered clear, or an HTTP client hanging
up, cancels the handler context. On `context.Background()` the caller returned
immediately while the peer clear ran to completion — a ghost clear.

Why that is not merely untidy: #5882/#2468 built the `clearErrors` /
partial-success apparatus precisely because partial clears are normal and must
be REPORTED. A ghost clear is the one outcome it cannot represent, because the
work happens after the reporter has gone.

### The fix

`clearPeerSessions` gained a `ctx` parameter and derives its 5s peer-RPC
deadline from it. Both call sites pass the handler's context. That makes the
site identical to its five siblings (`fetchPeerSessions`,
`proxyPeerSessionSummary`, `proxyPeerZonePairSummary`, `proxyMonitorInterface`,
`proxyPeerSystemAction`), which all already derived from the caller.

### Why the guard is structural

Binding this behaviourally needs a live `cluster.Manager` with `PeerAlive()`
plus a real authenticated peer dial — the same limit
`peer_fanout_attach_6851_test.go` states for its sibling. So the WIRING is
bound instead, which is the half a behavioural test could not reach anyway.

`TestClearPeerSessionsDerivesCallerContext_9041` asserts three things, and the
third exists because the first two are not sufficient:

1. the function TAKES a `context.Context` — before this it did not, so it
   structurally could not honour one however the call site was written;
2. its timeout is not rooted at `context.Background()`;
3. every call site passes a context AND does not pass `context.Background()`
   explicitly. Arity alone is satisfiable while still dropping the cancel.

Mutation-verified, each by its own branch: reverting the body reds with "roots
its peer-RPC timeout"; removing the parameter reds with "takes no context";
a call site passing `context.Background()` — which satisfies the arity check —
reds with "passes context.Background()". The third mutant is why check 3 was
strengthened from an arity test after the first version let it through.

## Part 2 — four handlers hold the session-walk slot across the peer RTT (OPEN)

NOT fixed here, and #9041 is deliberately left open for it.

`GetSessions`, `GetSessionSummary`, `GetZonePairSummary` and `ClearSessions`
each acquire `sessionWalkLimiter` with `defer release()` covering the whole
handler body, and dial the peer INSIDE that region. With
`MaxConcurrentSessionWalks = 4`, a peer RTT (up to 4s dial + 3-5s RPC) holds a
slot that bounds LOCAL walks while doing no local walking.

The remedy is to release the slot before the peer leg in each of the four, once
the local walk is complete. That is a concurrency change across four handlers
touching a DoS bound, not a one-line derivation, and it deserves its own change
with its own reasoning about double-release and about whether the peer leg can
re-enter the limiter. Landing part 1 alone is not a close.
