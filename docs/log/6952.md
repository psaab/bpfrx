# #6952 — the parallel `cargo test` wedge is a single-thread RwLock self-deadlock

- **Timestamp**: 2026-08-28
  - **Diagnosis before fix, with the prediction recorded first.** The issue
    proposed a lock-ordering inversion or a shared static in the WG engine test
    harness, with `wg_engine_test_serial_grants_exclusive_access` as the natural
    first suspect. I recorded a different prediction before running anything:
    that the three named tests were ONE staller plus TWO innocent parkers on the
    shared `wg_engine_test_serial` mutex, that no two-lock cycle could form
    (only `reconcile_lock` is on the trajectory; `load_table` is lock-free), and
    that the stall was MUTEX STARVATION of the bounded installer thread by
    `reconcile_churn_until`'s unbounded loop. I also recorded the discriminator
    up front: sample `utime+stime` on the wedged pid — non-zero means spinning,
    zero means everything is parked.
  - **The starvation prediction was REFUTED; the discriminator settled it.**
    Measured `utime+stime` delta over 5s on the wedged process: **0 ticks**.
    Every thread parked. Both racing threads had already been JOINED and were
    absent from the thread list, so starvation was not merely unproven, it was
    impossible. The one-staller/two-parkers structure was confirmed exactly.
  - **Reproduction rate, and a VOID cell caught.** HEAD `f0a1d3b25` did not
    wedge in 32 full-suite runs (12 unconfined 16-thread, 18 on 4 CPUs, 2 on 2
    CPUs), so a control at the issue's own base was the only way to make any
    statement interpretable. At base `40344ab05` it wedged on **run 7 of 7**
    unconfined. The first base attempt was VOID and had to be discarded: it ran
    the release *bin* rather than the unittest binary and exited rc=1 in 2s with
    `missing value for argument --test-threads=16` — twelve runs that measured
    nothing and would have read as twelve clean runs.
  - **Root cause — a shadowed lock-guard rebind.** In the tail of
    `install_session_serializes_with_reconcile_removal`:

        let by_index = engine.sessions_by_local_index.read().unwrap();  // (A)
        ... asserts ...
        engine.reconcile_peers(&[]);                                    // (B)
        let by_index = engine.sessions_by_local_index.read().unwrap();  // (C)

    (C) SHADOWS the binding from (A) but does not drop its guard — a shadowed
    value lives to the end of the enclosing BLOCK, not to its last use. So at
    (B) the thread still held a READ guard on `sessions_by_local_index`, and
    `reconcile_peers` takes the WRITE guard on that same `RwLock`.
    `std::sync::RwLock` is not reentrant: the thread deadlocks against itself.
    gdb confirmed it directly — `RwLock::write_contended <- reconcile_peers <-
    install_session_serializes_with_reconcile_removal`, with no other thread
    alive to hold the lock.
  - **Why it was intermittent — the exact window.** `reconcile_peers` takes the
    demux write lock only `if !dropped_indices.is_empty()`, i.e. only when the
    peer being removed still owns a live `current`/`previous`/`next` session.
    `reconcile_churn_until` always ends its cycle on the RE-ADD, and a removal
    drops the `Arc<Peer>` (the `existing` branch of `reconcile_peers` reuses a
    peer only when the pubkey is still present, so remove-then-re-add builds a
    FRESH one). So a reconciler that runs even one more full cycle after the
    installer's last successful install leaves a sessionless peer, and the sweep
    never reaches the write. The deadlock needs the reconciler to observe `stop`
    with ZERO further cycles while the peer it last re-added still carries that
    install. CPU contention deschedules the reconciler and widens the window,
    which is why the wedge tracked machine load — it reproduced at load ~13 and
    not at load ~2. Nothing about scheduler FAIRNESS is involved, which is why
    the #6157 serialization guard (a correct fix for a different wedge) did not
    remove this one.
  - **`--test-threads=1` is a rate reducer, not a guarantee.** The two racing
    threads are spawned by the test body, not by libtest, so serial mode does
    not serialize them; it only shifts CPU availability and therefore the odds.
    `docs/testing-procedures.md` previously attributed the flag solely to the
    `__skb_wait_for_more_packets` socket-test hang — that hang is real and the
    flag is kept for it, but it was not this defect. (7 idle `neigh-monitor`
    threads were parked in exactly that `recv()` at wedge time, which is how the
    two get conflated.)
  - **Fix and fail-on-revert.** The post-condition sweep moved into
    `assert_no_orphan_demux_entries`, with the first read guard explicitly
    SCOPED. A new test `orphan_demux_sweep_does_not_self_deadlock_6952` arranges
    the deciding precondition deterministically — install one session on the
    only peer and assert the demux map is non-empty — so removing the scope reds
    on every run instead of one in six. Both call sites run the sweep through
    `run_bounded`, which asserts completion against a loose 30s liveness
    backstop: a reintroduced self-deadlock now fails BY NAME rather than wedging
    the binary at rc=124, which was the issue's actual complaint (an
    uninterpretable mutation cell).
  - **Sweep for the class.** A scope-aware pass over every `.rs` in the crate
    for "a lock guard still in scope when the same lock is taken again" returned
    exactly 3 candidates; 2 are false positives (a temporary guard dropped at
    end-of-statement in `server/tests.rs`, and a ring reader named `read` in
    `xsk_ffi_tests.rs`). The third is this defect. Production is clean: the only
    other live `sessions_by_local_index` read guard,
    `handshake_session::reserve_pending_locked`, never calls anything that takes
    the write on that lock.
  - **Not fixed here (recorded for a separate look).** 7 live `neigh-monitor`
    threads were parked in `recv()` at wedge time with no coordinator test
    thread left running. `coordinator/neighbor_manager.rs` documents the
    opposite ("none of them LEAKS one (every spawner stops it)"). Off the
    deadlock path, so out of scope for this change.
