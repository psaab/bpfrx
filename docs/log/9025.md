# #9025 — two blocking I/O sites on the EventStream reader goroutine

## Why the goroutine matters

The EventStream reader is not a logging goroutine. The same `switch` loop also
handles `EventTypeSessionOpen/Update/Close` (**HA session sync**),
`EventTypeDrainComplete` (the **ISSU drain signal**) and
`EventTypeFullResync`. Stalling it stalls those.

The contract was already in-tree and it named this collateral by name.
`pkg/flowexport/routemask.go` (#3743) moved FIB lookups off this exact path
because they *"stall the event reader and every other callback behind it
(including the trace writer)"*. That precedent moved a different blocking call —
**the trace writer it named as a victim was itself still blocking.**

## Site 1 — UDP syslog had no deadline, and the exemption was a false comment

TCP/TLS route through `streamWrite`, which arms a 4s deadline. UDP did a bare
`conn.Write`, on the strength of a comment repeated twice:

> UDP is connectionless and never blocks on Write, so these do not apply to it.

**This tree refutes that verbatim**, in `pkg/flowexport/transport.go` (#4423 H07):

> A connected-UDP Write is normally instantaneous, but it **can block
> indefinitely on a full socket send buffer** (ENOBUFS / a congested or down
> egress path parks the goroutine in the netpoller until the buffer drains).

Two modules in one tree held opposite beliefs about the same syscall; one armed
a deadline and one did not. **UDP is the default protocol**, so the unbounded
path was the common one.

The comment was the proximate cause, not a side note — a false rationale
re-justifies itself every time someone checks. Deleting it was as much of the
fix as arming the deadline.

`datagramWrite` is a **separate function from `streamWrite`**, deliberately: the
two differ in exactly what matters, PARTIAL WRITES. A stream write can leave a
truncated octet-counted frame that permanently desyncs the collector's length
parser (hence #3874's conn teardown); a datagram is atomic. Sharing one function
would have carried the stream's teardown into a path that cannot need it — how a
correct-looking generalisation acquires a wrong branch.

A deadline expiry is **counted** as a drop. Arming a deadline without counting
would trade a silent stall for a silent drop, and a silent drop is worse: it is
indistinguishable from success. Only the timeout case is counted, so pre-existing
UDP error accounting is untouched (the acceptance requires #3478's accounting
unchanged).

## Site 2 — audit disk writes ran inline

Both writers now hand the line to a bounded queue drained by one dedicated
goroutine, dropping and counting on overflow — the #3478 shape, reused.

Three decisions worth recording:

**`LocalLogWriter.Send` was NOT made async.** Its error reports the write
result, and #3478 M04 made that deliberate ("the error is also returned to the
caller"). That contract and "the write does not happen on your goroutine" cannot
both hold — an async `Send` returns nil for a line that later fails, silently
voiding a guarantee several callers and cells rely on. Existing cells red'd when
I first tried it, and that was a **prior decision speaking**, not stale tests. So
only the one caller that cannot afford to wait — the event reader — moved, via
`SendFromEventReader`.

**A retired writer must REFUSE.** My first version regressed this: after
`Close`, the queue still had room, so post-close events were accepted into a
channel with no reader and silently lost — with no drop counted. That is
strictly worse than the synchronous nil-file drop it replaced, and it was caught
by an existing #3478 cell rather than by me. `stopped` now makes the enqueue
fail so the loss is counted.

**`Close` drains the queued tail**, before taking `mu` (the writer goroutine
takes `mu` itself, so stopping under the lock would deadlock). Discarding the
tail would lose exactly the audit records around whatever caused the shutdown.

## Site 3 — trap writes

`sendTrap` bounded the DIAL and not the WRITE. The trap worker is single and
serial, so one backpressured target head-of-line-blocks traps to every healthy
target, and `Stop()` waits on `trapWG`. The write now carries the same 2s bound
as the dial.

### M4 kills by hanging, which needed the harness fixed first

A blocking-enqueue mutant does not fail — it **deadlocks**, and my first matrix
run simply timed out and took the remaining mutants with it, leaving the mutant
applied in the tree. A hang IS a kill, but only if the runner bounds it: an
unbounded runner just looks stuck, and the natural reaction ("something's wrong
with my harness") is exactly the wrong conclusion.

The matrix now runs each mutant under both `timeout` and `go test -timeout`, and
scores a timeout as KILLED-by-hang explicitly. The applied-check (`grep` for the
mutated construct) is what showed the tree was still mutated after the
interruption.

That is the third distinct harness defect today, after the Go build-failure
reads-as-survival case and the cargo test-failure reads-as-void case.
