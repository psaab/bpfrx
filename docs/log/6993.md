# #6993 — TestRetiredLegNeverGainsARotatedCredential_5561 intermittent red

- **Timestamp**: 2026-08-28
  - **The assertion is identified, and it was already on record.** #6993 asks
    for the failing line before anything is fixed. #7667 — the same flake, same
    test, same direction, filed separately — captured it verbatim:

    ```
    listener_retiredauth_5561_test.go:124: secret-a still authenticates on the
    retired listener — a retiring leg must still honour a revocation
    immediately (#5561 round 7)
    ```

    That is the round-7 revocation PROPERTY, not a precondition guard. #6993's
    observation (branch head `e17de05f1`, 2026-08-13) predates the #7667
    fixture work (`cd72696ff`, 2026-08-26) by thirteen days.
  - **Reproduction attempted and NOT achieved, stated plainly**: 30 iterations
    of `go test -count=1 -shuffle=on ./pkg/api/` at pristine `origin/master`,
    `GOTMPDIR=/dev/shm/t` (so the 108-byte `sun_path` hypothesis in the issue is
    excluded), in a worktree nobody was editing — no failure. That matches the
    recorded history: 1 in ~19 under `./...`, never package-scoped. The
    reproduction that DID work is the one #7667 names, and it is a forced
    condition rather than an observed one.
  - **The probe, and what it found.** Forcing `retired.drained.Store(true)`
    immediately before `ReplaceAuth` at current master still failed at the
    round-7 assertion (`:200`), NOT at #7667's `!drained` precondition. The
    precondition samples `drained` at ONE instant and the window that matters
    runs from there to `ReplaceAuth`, so a drain landing inside it is invisible
    to the guard and is reported, again, as a revocation defect.
  - **Second residual, same half**: the hold waited 50 ms after WRITING the
    request rather than for the handler to have been ENTERED.
    `http.Server.Shutdown` waits for requests it has already dispatched; one
    written but not yet dispatched is not among them, so the leg could still
    drain — and drain after the precondition had been sampled.
  - **Fix**: the `/hold` handler signals on entry and `startHeldRequest7667`
    waits for that signal (an edge, not a sleep, and a named failure if it never
    arrives); and the round-7 assertion re-reads `drained` at the failure, via
    `retiredRevocationFailure6993`, so the classification is TOTAL whenever a
    drain wins from any cause.
  - **Disposition**: #6993 is the same flake as #7667. The assertion is
    identified and it was MISCAST — the message accused a security property for
    a fixture race. Both residuals in #7667's fix are closed here. What is NOT
    established, and is not claimed: that the drain-wins mechanism is what
    happened in the observed `./...` failure. #7667's own commit says the
    condition did not arise naturally in 80 attempts, and it did not arise in
    30 more here.
  - **Not done, deliberately**: no timeout was raised and no sleep was added.
    The assertion was not loosened; the round-7 message is still produced for a
    leg that is genuinely still retiring, and a cell asserts that so the
    classification cannot be bought by deleting what it classifies.
