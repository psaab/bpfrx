## 2026-08-27 — what actually remained

- **Action**: found the real gap by asking which DIRECTION each guard covers.
- **File(s)**: `pkg/config/compiler_cos_inert_advisory_silence_6850_test.go`
- **All five guards are positive-only.** Every one is `if !hasWarning...` —
  "the advisory fires when the knob is set". None asserts the advisory stays
  SILENT when the knob is absent. So dropping the presence gate on any of the
  five (`sched.CodelTargetNS > 0`, `len(cos.EXPRewriteRules) > 0`, …) makes
  that advisory fire on every config, and all five pre-existing guards stay
  green.
- **Why that is the cohort's own harm by the opposite route**: an advisory
  warning about a knob the operator never configured is how the single signal
  they get becomes noise they scroll past. Same end state as the knob being
  silently inert.
- Added a PAIRED table — 5 knobs, SET-fires and ABSENT-silent. The negative
  row alone would pass if the advisory were deleted outright; the positive row
  alone is what already existed.
- Each negative fixture deliberately builds the ENCLOSING entity (a
  traffic-control-profile with only a shaping-rate, a second scheduler with
  only a transmit-rate, a dscp rewrite-rule in place of an inet-precedence
  one) and omits only the knob. A fixture omitting the whole stanza would
  leave the advisory's enclosing block unexecuted, so deleting the presence
  gate would change nothing and the cell would be a false green.
