# 9087 — made the leak visible in ONE run, and the leak is NOT fixed

## Headline, stated first because it is the part that matters

**The proxy-ARP leak is NOT fixed by this change.** What landed makes it fail
**within a single run** instead of only on the next one, and replaces the
issue's hypothesis with a measurement. #9087 stays OPEN.

## The instruction that shaped this

> A cell that passes once and fails on a repeat is carrying state between runs;
> find what it leaves behind rather than making it tolerant.

What it leaves behind is a kernel `NTF_PROXY` entry on the node that was primary
during the crash phase. That is now measured rather than hypothesised.

## What the issue hypothesised, and what is actually true

The issue proposed that "demotion does not remove the NTF_PROXY entry (or
removes it late)" and said explicitly it was "a hypothesis, not a conclusion —
it has not been confirmed by reading the demotion path."

Measured on the live cluster, three ways:

1. **It is a permanent LEAK, not a 30-second window.** With fw1 in
   `secondary-hold`, `ip neigh show proxy` reported `fw0=1 fw1=1` long after
   the 30s re-assert cadence had run many times. Sampled again at +20/+40/+60/+80s
   with the fix deployed: `1/1` throughout.
2. **The ownership decision is CORRECT and the sweep is what fails.** fw1 logs
   `proxy-arp: suppressing responder for an interface this node does not own
   iface=reth0.80 issue=#8297` every 30 seconds — the predicate fires, every
   time — while the kernel entry survives. So the defect is downstream of the
   gate, not in it.
3. **At the instant of failback the state is `fw0=0 fw1=1`** — the NEW owner has
   not installed yet and the OLD owner has not cleared. That is not a duplicate
   answerer; for that window the ONLY answerer is the wrong node. The issue
   describes the two-answerer shape and does not name this one.

## The harness change — the part that is proven

The acceptance's first bullet:

> Re-read `ip neigh show proxy` on **both** nodes **after** each ownership
> change, not only in the preflight — the current single observation point is
> what makes the leak invisible to a clean run.

The check is extracted into `check_proxy_arp_ownership <phase>` (body preserved
verbatim, including its deliberate three-state reasoning and the "do not
collapse this branch" comment) and called twice: at the preflight and after the
full crash-failover + manual-failback cycle.

**It worked on the first run.** Run 1, on a fresh deploy, previously green:

```
PASS  only the RG owner answers proxy-ARP for 172.16.80.7 (preflight, before any failover)
FAIL  the RG OWNER does not answer proxy-ARP for 172.16.80.7 after the crash
      failover AND the manual failback (fw0=0 fw1=1)
Failover test: 21 passed, 1 failed
```

`exe_check=MATCH exe_scope=both`, verdict FAIL. A defect that took two runs and
a cross-run comparison to notice now fails once, in the run that caused it, and
the message names WHICH transition leaked.

## The two code changes, and what they are NOT

**Neither fixes the leak.** Both are real, both are small, and I am labelling
them accurately rather than letting them read as the fix.

1. **The misleading diagnostic.** `pkg/dataplane/proxyarp.go` logged
   `proxy-arp: interface not found` for an interface that WAS found and was
   deliberately suppressed by the #8297 ownership gate. A reader chasing a
   "not found" warning on a healthy standby is chasing the wrong thing.
   Verified fixed: the WARN is gone from fw1's log with the new binary running,
   which also confirms the deployed build is mine.
2. **A one-shot sweep window.** `proxyARPIfaceMapFiltered`'s doc says a
   suppressed entry "must be actively torn down by the reconcile sweep rather
   than retained", and the sweep can only reach an interface present in
   `ifaceMap` or `priorIfaceMap`. A suppressed interface is in neither after the
   FIRST suppressed pass, because that pass stores an `enabled` set with the
   interface gone. So the teardown had exactly one chance, on the pass that runs
   during demotion — when `programRethMAC`'s link DOWN/UP makes the netdev
   hardest to resolve. `retainSuppressedProxySweepTargets` keeps it swept.

   Unit-pinned and mutation-checked, and **deployed to the cluster, where the
   entry still did not clear.** So this gap is real and is NOT the cause.

## What the next person should look at

The gate fires and the entry survives, so the remaining suspect is the delete
itself: whether `ReconcileProxyARP`'s sweep resolves the same netdev the entry
is installed on. The entry is installed via `cfg.ResolveKernelIfName`
(`reth0.80` → the local physical member's VLAN netdev) while the prior-set is
resolved by `ifaceIndexByName` on the REMEMBERED Linux name — if those two
names disagree on the standby after a role change, the sweep manages an ifindex
the entry is not on. That is the next measurement, not another hypothesis.

## Validation

- `go test ./...`: 73 packages, EXIT=0.
- Three unit cells for the retention, including the control that keeps it
  distinct from #6536's retention (which protects a LIVE responder — the
  opposite intent).
- Live: `make cluster-deploy` then `make test-failover` on a fresh deploy,
  `exe_check=MATCH exe_scope=both`. The run FAILS, correctly, at the new
  observation point.

## Why this is not closed

The acceptance has three bullets. The first is done and proven. The second —
"fix the demotion side if the hypothesis holds, with a cell that fails on
revert" — is not: the hypothesis holds in outcome but not in mechanism, and the
mechanism is still open. Closing on the harness half would retire the question
while the defect ships, which is the #9052 shape.
