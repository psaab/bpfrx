# 9044 — the exe-provenance attestation covered one node of a two-node gate

## The defect, and why only one direction of it matters

`harness-result.sh`'s executable-provenance readback read **node 0 only**, with
the single-node assumption written into the code as its own justification:

> And it reads NODE 0 only -- both nodes carry the same build after a
> `cluster-deploy`, so one readback is the attribution point for the run.

That is a property of one way of *invoking* the deploy, not of the system.
`Makefile`'s `NODE ?= all` is a plain override and `cluster-setup.sh deploy
[0|1|all]` accepts the scope, so `make cluster-deploy NODE=0 && make
test-failover` is two ordinary lines. The failure is asymmetric:

| Deploy scope | fw0 | fw1 | Row before this change |
|---|---|---|---|
| `NODE=1` | old | new | `MISMATCH` → VOID. **Fails safe.** |
| `NODE=0` | new | old | **clean `MATCH`** for a gate that failed over onto the unattested node. |

An HA smoke fails over BY DEFINITION, so the node the attestation skipped is
the node the result depends on. This is a rationale hollowed by a fact nobody
re-checked: the comment's premise was true of `NODE=all` and of nothing else.

## Which of the issue's two fix directions, and why both

The issue offered: read both nodes' hashes, **or** record the deploy scope. I
did both, because they answer different halves and only one of them is
self-contained.

- **Reading both nodes** is the DETECTOR, and it needs no cross-process state.
  A deploy-scope marker would have to be written at deploy time and read at
  gate time, which can go stale, and it only catches divergence a marker
  predicts — not a node manually restarted onto an old binary, a failed push,
  or a stale sbin symlink (#2162/#1917 shapes). Reading both catches all of
  them. The cost is one extra post-gate readback, no lock, read-only.
- **`exe_scope`** is the HONESTY field, and it is what the issue correctly
  called the real gap: the row "cannot express *I attested one of the two nodes
  this gate used*". It matters precisely when the peer cannot be read, where
  the detector has nothing to say.

## The asymmetry inside the fix, which is the part to review

A peer running a DIFFERENT build → `MISMATCH` → VOID, by the same #2176 rule as
a local mismatch.

A peer that is UNREADABLE is **not** a void. `test-ha-crash`,
`test-chained-crash` and `test-double-failover` force-stop a node and may
legitimately leave it down when the gate ends. Treating an unreadable peer as
`UNAVAILABLE` would VOID exactly the gates whose job is to kill a node — a loop
layer breaking the gates it measures, the same mistake the existing
exit-status rule refuses to make. That case records `exe_scope=local-only`.

## A bug my own trace caught, after three wrong hypotheses

The first version redded 6 selftest cells with `exe_check=NOT-APPLICABLE` and
"the smoke aborted before reaching its summary". I formed three explanations
(mode clobbered by the arg parser, `cluster-env.sh` aborting the parent under
`set -e`, a function-name collision) and none was right. One trace gave it in
one line:

    harness-result.sh: line 787: peer_node: unbound variable

The run wrapper executes under `set -u`, and I had written `local peer_node
peer_running_exe_sha exe_scope` with no values — the existing locals all
initialise to `""` for exactly this reason. Cost of measuring instead of
reasoning: one 5-second script.

## Regression cells (`test/incus/harness-result-selftest.sh`, hermetic)

The mock answers **per node** — the only shape in which a one-node and a
two-node readback give different verdicts. A mock returning one sha for every
node would pass under both the old and the new code.

- **10d** the finding: node 0 matches, peer runs a different build → VOID +
  `MISMATCH`, the peer's sha is on the row, and the void reason names the peer.
- **10e** the control that matters: both nodes on the build under test → still
  a clean `MATCH`/`PASS`, `exe_scope=both`. A guard that voided every cluster
  gate would satisfy 10d perfectly and be worthless.
- **10f** peer unreadable → still `PASS`/`MATCH`, `exe_scope=local-only`. This
  is the arm that proves the change does not red the crash gates.
- **10g** `harness_exe_scope` as a table.

## Mutation matrix

Each mutant `bash -n`-checked; restore verified byte-identical (`diff -q`).

| # | Mutation | Cells that red |
|---|---|---|
| M1 | never read the peer back | 10d (all four assertions) |
| M2 | never fold the peer into `exe_check` | 10d verdict + void reason |
| M3 | treat an UNREADABLE peer as a mismatch | 10f — "this reds every gate that force-stops a node" |
| M4 | `harness_exe_scope` always returns `both` | 10f scope + two 10g rows |

**M4 was initially scored SURVIVED and that scoring was false.** The anchor
never applied (shell quoting inside the mutation helper), the helper's assert
failed, and the loop still printed a verdict line for an unmutated file — the
"a mutation reported exit 0 and did nothing" shape, in the scoring harness
rather than the mutation. Re-run with a verified anchor (`grep -c MUTANT` = 1
before scoring) it kills three cells.

## Not done, deliberately

No `Makefile` or `cluster-setup.sh` change. The issue lists them as affected
consumers on the assumption that the deploy would have to communicate its scope
to the harness. Reading both nodes removes that requirement — the harness
observes the fact instead of being told it, which is also why it catches
divergence no deploy-scope marker would predict.
