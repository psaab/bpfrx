# 9110 — one real defect fixed, one flake NOT reproduced, and a real red found in passing

## What the issue asked, in priority order

1. make the two tests not flake; 2. failing that, mark them; 3. record the rule
that already works (gate in a dedicated worktree).

## The reproduction the issue said nobody had run

> A sweep would be `go test -count=N ./...` under deliberate parallel load,
> which nobody has run.

Run, in three shapes, on the two named tests:

| # | Load shape | Iterations | Failures |
|---|---|---|---|
| 1 | target test alone, 48 busy loops on 16 cores (3x oversubscription) | 20 each | **0** |
| 2 | target test alone, concurrent with a full repo-wide `go test ./...` | 60 cluster / 40 ra | **0** |
| 3 | FULL package binary, every test in normal order, 24 busy loops | 6 each | **0** |

~100+ iterations of each. **Neither flake reproduced.** That does not refute the
issue — the rate may be below 1-in-100 — but it means "timing-sensitive" is an
unconfirmed hypothesis, and any fix has to be justified by READING the test
rather than by inheriting the premise.

### Two method errors, both caught before they became claims

- Shapes 1 and 2 ran the target test **alone**, next to load. That deletes the
  exact confound the difference is made of: "passes alone / fails in the suite"
  differs by *the rest of the package running first*, and an isolation re-run
  cannot see it by construction. Shape 3 is the corrected experiment.
- Shape 3's first attempt reported **96 failures** in `pkg/cluster`. All of them
  were mine: I ran the prebuilt test binary from the repo root, so every
  AST/source-scanning cell failed to find its files (`go test` sets CWD to the
  package directory; running the binary does not). Re-run with `cd pkg/cluster`
  first: zero. 96 fabricated failures produced entirely by the harness.

## What was fixed: `TestStartHeartbeatSingleStartRuns`

Independent of whether it is the one that fired, it carried a readable defect:

```go
time.Sleep(2 * DefaultHeartbeatInterval)
if got := s.sent.Load(); got == 0 { t.Error("sender emitted no heartbeats") }
```

Nothing is being waited FOR. The sleep is a guess at scheduler latency, and it
silently converts the claim under test — *"a single StartHeartbeat leaves a LIVE
sender"* — into *"the goroutine was scheduled AND emitted within 400ms"*, which
is a claim about the machine wearing the words of a claim about the code.

Replaced with `waitForSenderProgress`: wait for the condition on a 30s budget,
and DUMP every goroutine when it expires. Same shape, same budget and the same
dump idiom as `waitForTeardownProgress` (#7970) already in this package —
whose comment already says *read the dump, do not re-run*, because the wait
cannot separate a STARVED goroutine from a BLOCKED one and the stack can.

The new form is not weaker: it asserts liveness, which is what the test's name
and body claim. Punctuality is a different assertion and this test never made
it — it only appeared to.

**Mutation:** `s.sent.Add(1)` → no-op at the sole call site in `heartbeat.go`.
The mutant BUILDS (`go build` — not `go vet`), and the cell reds with the
diagnostic and the goroutine dump rather than silently. Restore verified
byte-identical (`diff -q`).

## What was NOT fixed, deliberately: `TestRestartTimeoutNoGoodbyeNoReplacement`

It races a graceful `Withdraw` against a wedged restart **on purpose** — the
race is the subject (#5094). A plausible mechanism exists: nothing orders the
`Withdraw` against the 150 ms join timeout, so under load it can land after
`Apply` has returned and change which path emits the goodbye, and the test's own
#8031 comment already records that the aggregate count "cannot separate the
timeout path emitted from the reclaimer's legitimate #5094 goodbye observed
early".

I did not observe it. Rewriting a deliberate concurrency test against an
unobserved mechanism is how a test gets narrowed into passing, so it is left
alone with the mechanism written down. It needs the reproduction I do not have.

## A REAL red found while doing this, and it is the issue's own thesis

`origin/master` carried an **un-gofmt'd file** —
`pkg/logging/audit_write_offload_9025_test.go`, from `7d17fa542` — so
`TestTreeIsGofmtClean` (`cmd/cli`) was a hard red on every repo-wide gate, for
every lane.

It is the most flake-shaped red imaginable: a package nobody touched, failing a
gate. My own first reading was wrong — "my edit raced the background gate in the
same worktree", the self-inflicted shape the issue describes — and I checked
before claiming: `git show origin/master:<path> | gofmt -l` flags the COMMITTED
content. Fixed here (`gofmt -w`, pure alignment, nothing semantic); afterwards
`gofmt -l ./pkg ./cmd ./test` is empty and both packages are green.

That #9110's investigation turned up a real red being mistaken for noise is the
issue's thesis demonstrated rather than argued.

## Item 3, landed as documentation rather than left in the tracker

`docs/engineering-style.md` §"Time in tests" gains clause **4 (sleep-then-assert)**
and a new subsection **"Before you call a red a flake, DIFF — do not re-run"**:
the package-order confound and how to reproduce it (including the CWD trap that
cost me 96 phantom failures), shared resources, unsound matches, the tree
changing under a background gate — and the case this rule exists to prevent,
that a red in a package your diff never touched can simply be REAL. The
non-reproduction is recorded there too, explicitly as "not a licence to close".

Item 2 (mark them as known-flaky) is deliberately NOT done: a marker that lets a
red be dismissed is a guard satisfiable by explaining reds away, which is the
behaviour the issue is trying to stop.
