# #9020 — an unrepresentable flexible-match-range shipped as a defaulted live match

- **Timestamp**: 2026-09-06
  - **Layer question, answered by measurement before choosing**: the strict
    commit gate ALREADY rejects every unrepresentable form, so no new
    commit-time gate is needed. The defect is reachable only on the tolerant
    load / peer-sync path (#1960) — the path that cannot reject — so the remedy
    belongs in the snapshot builder, failing closed.
  - **The nftables sibling was already right**: `daemon_nft.go:2248` and
    `daemon_nft_netlink.go:231` check BOTH `FlexMatchRangeNames > 1` and
    `len(UnknownFlexMatch) > 0`. The userspace builder checked only the first.
    This adds the second condition to the existing fail-closed channel rather
    than inventing one.
  - **Reproduced with a live control** (GOOD ships `offset:4 value:4660`):

    ```
    byte-offset 999      -> offset:0   enforces at offset 0, not 999
    match-value 0xZZZZ   -> value:0    enforces "equals zero"
    match-start payload  -> offset:4   evaluated at the layer-3 base
    ```
  - **Renamed the sentinel** `unrepresentable-multi-range` → `unrepresentable`.
    It reaches `show firewall ... effective`, and it now covers two causes —
    telling an operator with ONE range that their term names several is the
    misdirecting-diagnostic shape (#8992, #9006, #9023). The exact string
    carries no wire contract: the Rust side matches `layer-3`/`layer-4` and
    treats everything else as Unsupported.
  - **Fixture note, because it cost four attempts**: the compiler expects a
    nested `range <name>` level. Without it nothing compiles and every row
    reads `flexMatch=nil`, which is indistinguishable from "no defect". The
    liveness control is what exposed that.
