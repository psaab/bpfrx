# #9091 — instance-name containers accept an unknown keyword at commit

## What landed: the ratchet branch of the closure condition

The issue offers two closures — drive the 102 down with each newly-strict
container justified, **or** ratchet the population so a new instance-name
container cannot be added silently. This is the second.

It is deliberately NOT a fix, and the issue says why: making the walk descend
strictly turns every one of these containers strict at once, so every config
that commits today with a typo in one starts failing at commit. That is
asymmetric — `Store.Commit` takes the strict path while `Store.Load` (boot from
the persisted DB) and `Store.SyncApply` (HA config sync) take
`compileTreeLenient` and downgrade the identical violation to a warning, so a
config that stopped committing would still boot, warn, and silently truncate.
The remedy is per-container `closedWorld` opt-in, worked down with evidence.

## The number is a DIFFERENT measurement from the issue's 102

Stated plainly because conflating the two would misreport the state.

- **102** is the set that fails open END TO END at `configstore.CheckText`.
- **156** (this ratchet) is the SCHEMA-SIDE set: containers with
  `args>=1 && len(children)>0 && wildcard==nil` not covered by an armed
  `closedWorld` subtree.

156 is a strict SUPERSET. The issue's own correction records the same gap in
the other direction: 246 schema-blind collapsed to 205 end-to-end, because a
later compiler gate catches some of them (`applications application`, `chassis
cluster redundancy-group`). **Schema blindness is an upper bound on fail-open,
not the fail-open set** — a walk result is a claim about the walk.

Bounding the superset is nonetheless correct for the property being protected:
a new instance-name container enters this set whether or not some later
compiler gate happens to catch it, so the superset cannot miss one.

**The end-to-end 102 is NOT ratcheted, and that is a limitation not a
completion.** A `CheckText`-driven census needs a fixture builder that
synthesises an instance-name token per container, and a typed key validator
would reject a synthetic token for the WRONG reason — the container would score
REJECTED because its name was invalid, not because its body was checked, which
under-reports blindness. That is the #2419 census's `xpfarg` hazard. Building
one soundly is real work and is left named rather than silently skipped; a
follow-up issue carries the remediation so the reason to look again survives
this close.

## Instrument

Three precautions, each borrowed from `inert_validator_ratchet_test.go` for a
reason that has bitten this campaign:

- **path-keyed `seen`** — a node-keyed walk plus a path filter is
  non-deterministic under Go's randomised map order and gives a different count
  per run while looking stable within one run;
- **`groups` skipped at the root** — the mirror re-hosts the SAME schema node
  objects and would double every hit (#8921), the correction that took the
  issue's own figure from 205 to 102;
- **depth cap**.

Measured **stable at 156 blind / 7 armed over five consecutive runs**.

**Cross-checked against a different instrument.** #9091 classified six of these
containers by measuring commit behaviour end-to-end at `CheckText`. This
schema-side walk agrees with all six, in both directions:
`security ike gateway`, `security ipsec vpn`, `system login class` blind;
`protocols rip group` (armed by #9206) and `security ike proposal` armed; and
`security flow tcp-session` (args==0) not a candidate at all. Two instruments
built on different evidence agreeing is a cross-check, not a restatement.

## The control runs in BOTH directions

A ratchet that goes green because its population emptied is indistinguishable
from one that went green because it stopped looking, and a count assertion
alone cannot tell those apart — break the predicate and the number simply
changes, which reads as news about the schema rather than about the instrument.

So `TestInstanceNameBlindInstrumentStillDiscriminates9091` pins known-blind
paths as blind AND known-armed paths as armed, fails outright if either side of
the enumeration is empty, and asserts the two sets partition. Direction 2 is
load-bearing: a predicate that classified EVERYTHING as blind passes direction 1
completely.

The count assertion is an EQUALITY, not a ceiling. A drop fails too — a ceiling
left above reality stops being a ratchet, because it silently re-admits every
container between the two numbers.

## Mutation matrix

M1 was void on its first attempt: the splice's locator did not match, the edit
was never applied, and the run reported **0 failures** — which reads exactly
like a surviving mutant. It was redone with the mutation confirmed by grep
rather than by exit status.

| # | Mutant | Applied | Result | Killed by |
|---|--------|---------|--------|-----------|
| M1 | SCHEMA: arm `/system/login/class` (models the real remedy) | verified | **KILLED** | both cells — "SHRANK to 155 (ceiling 156)" + "no longer classified blind" |
| M2 | INSTRUMENT: drop `closedWorld` inheritance | yes | **KILLED** | ratchet |
| M3 | INSTRUMENT: classify everything blind | yes | **KILLED** | both |
| M4 | INSTRUMENT: stop skipping the `groups` rehost (#8921) | yes | **KILLED** | ratchet |
| M5 | INSTRUMENT: drop the `args>=1` arm | yes | **KILLED** | both |
| M6 | INSTRUMENT: enumerate nothing ("stopped looking") | yes | **KILLED** | both |

Four of the six mutate the INSTRUMENT rather than the schema, which is the
point: for a ratchet, the instrument breaking and the defect being fixed produce
the same green, so the mutants worth running are the ones that break the
instrument. **M6 is the one a bare count cannot catch** — it is killed only by
the emptiness guard in the control.

M1 is the remedy column and shows the ratchet behaving correctly under a real
fix rather than only under a regression: arming one container fails the build
until the ceiling is lowered and the control's known-blind list is updated in
the same change.
