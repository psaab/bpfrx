## The state before

`export_owner_rg_sessions` is asked with a ~60-byte request and answered with
the owner-RG session set. `max = 0` was the ONLY complete request a caller
could make, because a capped export truncates and since #5085 the receiver
reconciles authoritatively against the delimited window and DELETES every
eligible session missing from it. So the single knob the call exposed had
exactly one safe setting and one catastrophic one, and every caller passed 0.

The unbounded answer is bounded only by `MaxControlResponseBytes` (64 MiB).
Crossing it truncates the response, `doBulkSync` fails closed, and the HA cold
prime fails — permanently, on every attempt, on a busy cluster. #9322 made that
failure DIAGNOSABLE (it used to be reported as "the helper rejected it before
replying"); it did not make it not happen.

## Why "raise the cap" is refuted, re-measured at this head

The issue's worst-case delta was 1424 bytes. Re-derived here by reflection over
`SessionDeltaInfo` — every string field a full-width IPv6 literal, every
numeric at its type maximum — it is now **1492 bytes**: the wire schema has
grown since the issue was filed, which is exactly why the cell derives it
instead of pinning the number.

`workers x DEFAULT_MAX_SESSIONS(131072) x 1492 B`:

| workers | theoretical max | vs the 64 MiB cap | cap crossed at |
|---:|---:|---:|---:|
| 1 | 186 MiB | 2.9x | 44,979 sessions/worker |
| 4 | 746 MiB | 12x | 11,244 |
| 6 (loss cluster VF queues) | 1119 MiB | 17x | 7,496 |
| 16 | 2985 MiB | 47x | 2,811 |

That is not a number, it is a number PER BOX, scaling with a runtime quantity
whose only source is `ProcessStatus.Workers` — reported by the helper. Sizing an
allocation bound from a value the bounded party supplies is not a bound, and any
fixed constant large enough for a 16-worker box reopens the case #9003 closed.

## The fix

**The primitive already existed and was discarded.**
`drain_session_deltas_fair` computes `overflow = budget == 0 && any binding has
pending`, and the owner-RG call site threw it into `_overflow`. That is the
entire reason paging was not expressible: without it a caller cannot tell a
complete capped answer from a truncated one.

1. `drain_session_deltas_from_live` returns the overflow bit;
   `OwnerRgExportWait::wait_and_collect` returns `(deltas, more)`, taking the
   verdict from the LAST internal 1024-batch only — an intermediate batch
   reports overflow on every batch of a large drain and says nothing about the
   state after the loop.
2. `ControlResponse.session_export_more` carries it (additive, `omitempty`,
   #1961 skew-safe).
3. `SessionExportRequest.continuation` drains the REMAINDER of an open window:
   no kick, no export sequence, no ack-wait. This is the half `max` alone
   cannot express — an ordinary second call re-runs phase 1 and stacks another
   full set on the remainder, so the caller would assemble one window out of
   two instants. That is a different bug from truncation, not a smaller one.
4. `Manager.ExportOwnerRGSessionsPaged` pages to completion under ONE hold of
   the manager lock, bounded by `maxOwnerRGExportPages` and failing CLOSED past
   it.
5. `ProcessStatus.session_export_paging_protocol_version` gates it. A helper
   without the contract honours `max` by TRUNCATING and reports no more-bit, so
   it still gets the unbounded request.

### Three decisions worth stating

**The manager lock is held across every page.** The per-binding delta buffers
this export drains are the SAME buffers the incremental `drain_session_deltas`
verb drains. An interleaved incremental drain between two pages would steal part
of the window, and a window missing sessions is what makes the peer delete live
ones. Serializing the whole sequence is what makes the pages add up to the
single-shot answer.

**The version gate is explicit rather than probed**, because the ambiguous case
is unresolvable by observation: an answer of exactly `max` deltas with `more`
false is EITHER a new helper whose page consumed the window exactly OR an old
helper that dropped the remainder — and the probe that separates them (send a
continuation) is itself unsafe on the old helper, which ignores the unknown
field and runs a second full export.

**The daemon's `max` parameter is gone.** `userspaceSessionExporter` no longer
takes one. The safe value depends on the helper's worker count and on whether
the helper pages at all, and both are facts the Manager holds and the daemon
does not.

## The adjacent finding, fixed here because paging needs it

`controlRoundtripDeadline` sizes the round trip off the REQUEST BODY. This
verb's body is ~60 bytes, so it got `controlBaseDeadline` (3 s) while the helper
spends up to `OWNER_RG_EXPORT_ACK_WAIT` (15 s) waiting for worker acks before
writing its first byte. That is #4036's failure shape — "Go timed out and
reported failure while the helper was doing the work" — moved from the
request-size axis to the WORK axis, where #4036's per-mebibyte fix cannot reach
it because there are no mebibytes to scale on.

It is not optional alongside paging: an export that times out at 3 s is not an
export, so fixing the size bound while leaving the time bound would have shipped
a fix that cannot run.

`controlVerbDeadlineFloors9344` raises a FLOOR for named verbs. It does not
raise `controlMaxDeadline`, and the floor (18 s) is far below the #7675
REACHABLE bound (67 s, from a 64 MiB apply), so what a stop can be holding is
unchanged and #8526's shutdown census is untouched — `armControlIO` is still the
single site. A cell asserts both of those, and asserts that the floor does NOT
leak to `status` / `apply_snapshot` / `drain_session_deltas`, whose
responsiveness the #182 contention discipline depends on.

The 15 s is now a NAMED Rust constant and the Go side READS it out of the
helper source rather than restating it.

## A prior decision that spoke, and what happened to it

`TestUserspaceBulkSnapshotGathersUnboundedTableTruth6031` asserted `max == 0` on
the exporter call, with the reason "a capped export truncates the authoritative
window and the peer DELETES the remainder". That is correct and it is why this
issue exists. The assertion could not survive as written, because the parameter
it names no longer exists at that layer — so the cell's INTENT was moved rather
than deleted: the daemon-side assertion is now structural (there is no cap to
get wrong), and the behavioural half lives in the Manager cells above, where the
completeness decision actually is. Deleting it and calling the suite green would
have removed the only record of why the knob was dangerous.

### M3: the bit was computed correctly and never reached the wire

Deleting the handler's single `response.session_export_more = more;` left the
ENTIRE suite green — Go and Rust. The Rust cells drive `wait_and_collect`
directly; the Go cells drive a fake helper that scripts the bit itself. Nothing
connected the two, so the one line that puts the bit on the wire was free to
delete. That is the "bind the WIRING, not the function it calls" shape exactly,
and it is the more dangerous half of this change: with the bit missing the Go
caller reads `more = false` on page 1 and hands the peer a window truncated at
8192 sessions — silently, which is worse than the loud 64 MiB failure this issue
is about.

Closed with two control-socket-level cells in `server/tests.rs` that drive
`run_request` end to end, plus a `test_seed_binding_session_deltas` hook so a
dispatcher-level test can produce a capped window at all. The second cell is the
negative half: without it, `session_export_more = true` unconditionally would
pass the first.

### M7: the floor was correct and unreachable

`TestExportOwnerRGSessionsGetsAWorkDeadlineFloor9344` calls `controlWorkDeadline`
directly, so swapping the CALL SITE in `requestDetailedLocked` back to
`controlRoundtripDeadline` left it green. The sizing function was right and
nothing observed what the socket actually got.

Closed by recording the armed value (`Manager.lastArmedControlDeadline`, set
inside `armControlIO`) and asserting it after a real round trip — with `status`
as the control arm in the same run, because a change that armed the floor on
EVERY request would otherwise pass, and that is not a smaller mistake: it slows
the 1/s status poll and every session install sharing the socket.

A behavioural alternative (a helper that sleeps past the base deadline) would
have worked and would have been timing-dependent; this is exact.

### M6 was VOID first

Replacing the fail-closed return with `return all, status, nil` left `fmt`
unused and the package did not build. A mutant that does not build is VOID, not
survived — it was rebuilt with a use of the now-dead symbols and then scored.
