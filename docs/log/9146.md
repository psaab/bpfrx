# #9146 — the HA session-sync DELETE wire carried no routing domain

Filed **UNRESOLVED / NEEDS_VALIDATION**. The first deliverable is the measurement
that resolves it, not a fix.

## The measurement that resolves it

The validator established everything except one link and said so:

> For the refusal to fire, the standby helper must hold **two synced sessions
> with the same 5-tuple in two different non-zero routing domains**. … the only
> route I can see is *alternation* … I did not demonstrate that.

It is simpler than alternation, and it is now measured.

**(1) Install and delete disagree by construction.** Driving the real
`buildSessionSyncRequestV4`:

```
upsert tenant A: 10.0.0.5:1234->10.0.0.9:443/6 routing_domain=100007
upsert tenant B: 10.0.0.5:1234->10.0.0.9:443/6 routing_domain=100008
DELETE         : 10.0.0.5:1234->10.0.0.9:443/6 routing_domain=0
install/delete AGREE on the 5-tuple:      true
install/delete AGREE on routing_domain:   false
```

**(2) Swapping the tenant behind one bare 5-tuple emits NO retraction.** Driving
the real `mirrorSessionV4` twice against a recording session socket:

```
wire[0]: op=upsert routing_domain=100007
wire[1]: op=upsert routing_domain=100008
deletes emitted when the bare mirror row swapped tenants: 0
```

The Go mirror is bare-keyed so it remembers one row — but nothing retracts the
row the STANDBY already holds, and the standby keys synced sessions BY domain.
That last fact is already proven in-tree by the #8636 fixture
`state_holding_the_same_tuple_in(&[100_007, 100_008])`, which asserts
`synced_key_count == 4` (two tenants × forward+reverse).

**(3) The helper then refuses.** Already pinned in-tree by
`an_ambiguous_bare_tuple_delete_is_refused_and_touches_nothing_8636`. The Rust
cell the issue proposed as check (1) did not need writing — it exists and is
green.

**Verdict: MATERIAL, not NEG.** No alternation is required; two tenants sharing a
5-tuple is the ordinary case for overlapping VRF address space and is exactly the
#8636 fixture. The consequence half of the issue stands as written: #8636's
acceptance — *"a refused delete leaks for ONE PACKET, not until idle timeout"*,
because #8356 re-derives zone policy on the established-session hit path — was
written for the operator `clear security flow session` caller. A synced session
on a STANDBY receives no packets, so nothing re-judges it; it leaks to idle
timeout and is promoted on failover.

## The fix

The issue's own cheap repair: the value is already fetched at the delete site for
its `ReverseKey` and its domain was discarded. `deleteScopeVal` now carries just
that domain onto the delete request, so the exact delete lands and the ambiguity
probe never runs. A default-instance session still sends domain 0 —
byte-identical to before — which is what the second acceptance criterion asks.

`DeleteSessionV6` had the identical defect and is fixed in the same change;
leaving it would have been a partial fix by family.

## Scope: what is NOT fixed, and why

The **batch** path (`BatchDeleteSessions{,V6}` → `deleteHelperSessionsV4/V6`)
still sends a bare delete. This is the higher-volume path — measured:
`pkg/conntrack/gc.go:335` and `pkg/daemon/daemon_policy_invalidate.go:542` both
use `DeleteBatchKnownV4`, while the singular `DeleteSession` serves the CLI/gRPC
filtered clears. The values DO exist at `DeleteBatchKnownV4`
(`SessionEntryV4{Key, Value}`) but `batchDeleteV4` strips them to keys before
`s.dp.BatchDeleteSessions`, so carrying the domain means changing the `DataPlane`
interface (or adding an optional one) and touching `batchDeleteV4`'s #5448
one-at-a-time retry logic.

That is not deferred for size but for **validation reach**: every BPF-backed test
in `pkg/dataplane/userspace` skips in this environment (`RemoveMemlock:
operation not permitted` — 54 skipped cells), so an interface change on the
highest-volume session-delete path could not be exercised here at all. Shipping
the riskiest part of the change with the weakest validation is worse than a
scoped fix plus a filed remainder carrying the measurement that shows it matters
MORE than the half fixed here.

`ClearAllSessions` is deliberately left bare: it has no values by construction
and is exactly the caller #8636's refusal was designed for.

### M5, and why the seam was extracted

M5 survived, and it is **not** a privilege artifact: at the time, **no test in
`pkg/dataplane/userspace` called `Manager.DeleteSession` at all**. The userspace
dataplane's per-session delete had no cell whatsoever, so a mutation deleting its
entire helper-sync contribution passed the suite.

The first mutation run had the same shape for a different reason and was
corrected before scoring: the cells drove `syncSessionV4Locked` directly, so M1
also survived. `syncDeleteV4Locked` was extracted precisely so the scope
derivation and both sends could be DRIVEN without BPF; M1–M4 then killed.

`TestDeleteSessionItselfNamesTheDomainOnTheWire9146` closes M5, but it needs real
BPF maps and therefore SKIPS without CAP_BPF — like the 54 other BPF-gated cells
here. It binds on a privileged host; locally it is a VOID, not a pass, and is
recorded that way rather than counted as a kill.
