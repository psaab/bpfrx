# #9163 — the retained-pool index remap was a nested linear scan on snapshot apply

## Defect, re-measured at the base commit

`userspace-dp/src/nat/source/mod.rs::retained_pool_index_map` asked
`prev.addresses_v4.iter().position(|a| a == addr)` once per NEW pool address,
and the same shape again for v6. That is O(n·m) over the pool-address count.

The cardinality comes from real limits, not a guess: `MAX_POOL_PREFIX_HOSTS`
= 65,536 per prefix member (`nat/source/expand.rs`), aggregate
`max_addresses = 16 * MAX_POOL_PREFIX_HOSTS` = 1,048,576, and that aggregate
is a SUM — one pool may hold the whole budget, which the Go compiler admits
(`MaxSourceNATAggregatePoolAddresses`, `pkg/config/compiler_validate_strict_nat.go`).

The harm is where it runs. `reseed_retained_pool` <- `resolve_pool_allocators`
<- `parse_source_nat_rules_with_previous` <- snapshot apply, under the same
`state` mutex that serializes the control socket. `update_ha_state` is the only
refresher of the helper's 10 s per-RG forwarding lease and is sent on a 3 s
cadence, so it queues behind the apply, and `is_forwarding_active` is consulted
per packet.

**Measured** (standalone `rustc -O`, the same loop shape, prev fully retained
plus one added address):

| n = m | nested scan | hash index |
|---|---|---|
| 4,096 | 3.96 ms | 0.73 ms |
| 16,384 | 91.3 ms | 4.5 ms |
| **65,536** | **1.218 s** | **17.8 ms** |

(The "hash index" column is `std::collections::HashMap` with SipHash;
production uses `FxHashMap`, which is faster still.)

Static re-verification at the base commit: the `position(|a| a == addr)` inner
scan was present for both families, and `MAX_POOL_PREFIX_HOSTS` was still
65,536 — so the issue's cardinality argument was unchanged.

## Fix

`first_index_by_address` builds an `FxHashMap<Addr, usize>` over the previous
list once; the remap probes it. `or_insert` is the whole of the equivalence:
`position()` returns the FIRST match, so a previous list holding one address
twice always resolved to its lower index, and a bare `insert` would record the
LAST occurrence and quietly move which previous slot a duplicated address
carries its live port ownership from.

`retained_pool_index_map` now takes the previous lists as SLICES rather than a
`&PreviousPool`. The NAT64 wrapper had been synthesising a whole `PreviousPool`
— cloning the previous address vector and constructing a throwaway
`PortAllocator` — to reach one formula that read neither. Slices also make the
v6 arm reachable from a test, which the module-private `PreviousPool` did not.

The load-bearing cell is a BOUND that reds on the old algorithm, not a timing
assertion tuned to the new one: 250 ms sits ~50x above the fix and ~5x below
the revert, and the in-cell control makes the second half of that sentence a
measurement rather than a claim.

### The BOUND cell's own positive control, checked in both directions

The bound cell asserts BOTH that the fix finishes inside 250 ms and that the
nested-scan oracle, timed over the same inputs in the same run, does NOT. The
second half is what stops a vacuous green on a fast machine, and a control that
can never fire is not a control — so it was made to fire:

| Check | Edit | Result |
|---|---|---|
| MPC | `const N: usize = 65_536` -> `4_096` in the cell itself | **the control FIRED**, with its own message: `POSITIVE CONTROL FAILED: the pre-#9163 nested scan finished 7.657992ms over 4096 addresses, inside the 250ms bound this cell asserts. ... raise N, do not relax the bound` |

At n = 4,096 the nested scan takes ~4 ms (measured standalone above), which is
inside the 250 ms bound — so the control fires and the cell fails with
`POSITIVE CONTROL FAILED: ... raise N, do not relax the bound`. At n = 65,536 it
takes ~1.2 s and the control passes. Both directions observed.

## Documentation

No separate module doc exists for the retained-pool remap — `userspace-dp/src/FEATURES.md`
has no #6765 entry and there is no `nat/README.md`. The contract lives in the
function's own doc comments, which is where the complexity rationale, the
`or_insert` equivalence argument and the slice-signature rationale were written
in this change.
