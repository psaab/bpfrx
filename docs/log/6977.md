# #6977 — pkg/api tests observing async state without an attributable edge

- **Timestamp**: 2026-08-28
  - **Action**: Made the mutation gate's waiter edge attributable by
    construction (a caller-read BASELINE, not a bare global `> 0`), and made
    `p.done` mean "the lookup finished AND its slot is back" by registering the
    two defers in `connContext` the other way round.
  - **Class A (the substantive one)**: `mutationBodyWaitersInFlight` is
    process-global, and `waitForMutationBodyWaiter` accepted any value above
    zero. Two shapes satisfy that with a park the calling case did not create:
    a case returning with a request still parked (a later case, not necessarily
    the next in source under `-shuffle`, takes it), and a case that parks TWICE
    — `parkFlood` in `authz_bodybudget_customclass_6954_test.go`, called twice
    in one case, is the second. Every call site avoided the first by calling
    `waitForGateQuiescent` beforehand, which works; it is a convention living
    in a different statement, sometimes a different function, from the wait
    that depends on it. `waitForNewMutationBodyWaiter(t, baseline)` is
    attributable by construction: a leftover park raises the baseline too.
  - **Class B was already fixed at master, and is left alone.**
    `TestPeerIdentityIsResolvedAtAccept_5561` now reads its counts through
    `waitForPeerLookupsToFinish` (count AND zero pool occupancy) with a
    `waitSlots(t, 0, ...)` precondition — #6645 r22 finding 3, landed after
    #6977 was filed. The issue's cited line numbers no longer point at the
    defect it describes. Verified by reading the current call sites, not by
    trusting the issue.
  - **Class C**: `close(p.done)` ran BEFORE the admission token was returned
    (defers are LIFO and it was registered second), so a caller joining on
    `p.done` returned while the token was still out. Swapped. The receive
    cannot block — the goroutine's own token is in the buffer.
  - **A census point**: `waitForMutationBodyWaiter` had 6 call sites, one of
    which (`parkFlood`, added by #6954 after #6977 was filed) did not establish
    the precondition itself and relied on both its callers doing so. The
    issue named three affected observers; the population had grown.
