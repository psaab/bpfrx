# 6988 — `nat/source.rs` split into a module directory

## A premise in the dispatch, measured and refuted

The task came with an urgency argument: *"every branch that touches that file now
risks `TestTouchedFileCrossedModularityThreshold`."* **That is false, and it is
worth stating because it changes why this refactor is worth doing.**

The gate fires on a CROSSING — `base < floor && head >= floor`
(`pkg/refactoraudit/audit_touched_test.go:89`) — and there are exactly two
floors, 1500 `[WATCH]` and 2000 `[REFACTOR]`
(`audit_canary_test.go:25-26`). `source.rs` was already at **3315** at the merge
base, above both. No further crossing is possible, so the gate cannot fire for
this file again.

Measured rather than reasoned about, with a paired cell:

| cell | edit | gate |
|---|---|---|
| subject | `source.rs` 3315 → 3317 (append 2 lines) | **PASS** |
| positive control | `pkg/ddns/manager.go` 1957 → 2017 (crosses 2000) | **FAIL**, naming the file |

The control is what makes the subject's PASS readable: it proves the harness sees
uncommitted working-tree edits (`refactoring-audit-touched.sh:105` diffs
`--name-only` against the merge base) and does fire. Without it, "the gate did not
fire" would be indistinguishable from "the harness did not run".

Consequence: the `docs/refactoring-audit-accepted.txt` escape hatch is also
unavailable here — that file accepts a *crossing*, and no crossing can occur. The
split therefore stands on its merits (3315 lines, `[REFACTOR]` tier, a real
project rule), not on gate pressure.

## The decision, from the numbers

`source.rs` is 3315 lines with **zero inline tests** — the test split already
happened (13 sibling `tests_*.rs` in `nat/`), so there is nothing to harvest
there. 42.8% is comment, which is documentation of behaviour, not filler.

The largest single item is `match_source_nat_result_for_tuple` at **672 lines,
20% of the file** — so this is not the "one cohesive function that genuinely
belongs in one place" case from `docs/refactoring-audit.md`'s *When NOT to
refactor*.

Candidates ranked by the only metric that matters for a code-motion split —
**lines moved per visibility widening required**:

| cluster | lines | widenings | taken |
|---|---|---|---|
| `match_rules` (match pipeline) | 747 | 0 | ✅ |
| `synced` (HA synced reservation) | 515 | 0 | ✅ |
| `release` (release / rollback) | 257 | 0 | ✅ |
| `expand` (pool address expansion) | 174 | 0 (one respelling) | ✅ |
| `failure` (per-rule failure taxonomy) | 157 | 2 | ✅ |
| `nat64_ports` (NAT64 port lifecycle) | 140 | 0 | ✅ |
| **`resolve` (pending-allocator pass)** | **360** | **17** | ❌ **declined** |
| `budget` (aggregate accounting) | 81 | 1 | ❌ declined (couples to `resolve`) |

**1990 lines moved for 2 widenings.** `source/mod.rs` goes 3315 → **1367**, below
the 1500 `[WATCH]` floor.

Most candidates cost zero because of a Rust rule worth stating: a PRIVATE item is
visible to its own module **and that module's descendants**. Everything that
stayed in `mod.rs` and is called from a submodule — `SourceNatRule::matches`,
`matches_ignoring_scope`, `address_has_draining_pool_occupancy`,
`parse_match_prefix`, `port_in_ranges`, `nets_match_v4/v6` — needed no edit at
all.

## The declined seam, and why declining it is the right call

The pending-allocator resolution pass is the seam the issue named first. Moving
it costs **seventeen** visibility widenings, including making `PreviousPool` and
`PendingPoolAllocator` and all six of their fields `pub(super)` — because
`parse_source_nat_rules_inner`, which stays behind, CONSTRUCTS both.

That is the test the brief set: *a cluster that scatters a property across two
files is not a seam*. Here the property is "how a pending pool allocator is
seeded, charged and resolved", and splitting it would put the construction on one
side of a file boundary and the consumption on the other, with nine newly-public
fields as the interface. It stays with the parse pipeline it is part of, together
with the aggregate-budget cluster that shares
`SourceNatAggregateUse::saturating_with` with it.

## The one non-obvious edit — a preservation, not a change

`expand_pool_address` was `pub(super)` inside `nat::source`, i.e. visible in
`nat`, which is how `tests_aggregate_budget.rs:68` reaches it. Moved one level
deeper, the SAME keyword means `pub(in crate::nat::source)` — **narrower** — and
it broke that caller with `E0603` on the first build.

It is now spelled `pub(in crate::nat)`: exactly the visibility the pre-split file
had, written absolutely instead of relatively. The caution is recorded in
`nat/mod.rs`, because the next person to move a `pub(super)` item deeper will hit
it.

## Two machine checks instead of asking a reviewer to read 1990 moved lines

A behaviour change hidden in a motion diff is invisible, and the reviewer's only
defence is otherwise the author's word. These replace that word:

**1. Byte-exact reconstruction.** `scripts/verify-nat-source-split-6988.py`
rebuilds the pre-split `source.rs` from the six submodules plus the residual
`mod.rs`, un-applies the three enumerated edits, and compares against
`git show origin/master:...`. It PASSES at 3316 lines. A reordered statement, a
changed literal, a dropped comment or a lost blank line fails it, with a diff.

The explanatory lines the split adds are tagged `// #6988-note:` so the verifier
strips them deterministically. An earlier draft matched them by comment prefix and
missed two — the check caught its own weakness, which is the argument for tagging.

**2. Identical compiler diagnostics.** 168 warnings at master, 168 here, **zero
added and zero removed**, diffed as sorted sets with the source path normalised
(the file name changes, the diagnostics do not). A motion that altered behaviour
would be unlikely to leave that set untouched.

That second check also caught a false negative in my own work: an earlier
comparison appeared to show a NEW `private_interfaces` warning, which turned out
to be a cache-served `cargo build` ("Finished in 0.08s") that never re-emitted
master's warnings. The set diff, forced to recompile, showed them equal.

## Merging live work into a split file — the modify/delete conflict

Master landed #7858 (`carry_renamed_pool_reservations`, #6979 F6) in
`nat/source.rs` while this branch was open. The merge is a **modify/delete**:
this branch deleted the file, master modified it.

**It produces ZERO conflict markers**, so a marker sweep reports clean and any
"take one side" resolution silently drops the other. The reliable signal is the
STAGE LISTING:

```
$ git ls-files -u
100644 95869a1b4 1  userspace-dp/src/nat/source.rs   <- base
100644 a95386b3c 3  userspace-dp/src/nat/source.rs   <- theirs (origin/master)
```

Stages **1 and 3, no stage 2** — ours (the deletion) has no blob, which is what
says "we deleted, they modified". Git leaves theirs in the tree.

**Every one of master's hunks landed inside the DECLINED seam.** The new function
sits immediately after `reseed_retained_pool`, and its three call sites are
inside `resolve_pool_allocators` — the pending-allocator cluster this split
deliberately kept whole. Not one hunk crossed a seam boundary. That is empirical
confirmation of the decline: the property master had just extended lives entirely
inside the cluster that was not cut.

**Resolved by regeneration, not by hand-merging.** The seams were re-derived by
CONTENT — match each seam's first and last line in the new file and require the
span length to be preserved — which also PROVES master did not touch any moved
text (the derivation asserts `old[a:b] == new[a':b']` per seam and would fail
otherwise). Then `source/mod.rs` is rebuilt as "theirs minus the seam ranges,
plus the banner". The submodules are untouched because their text is untouched.

**The verifier is what makes this checkable rather than argued.** It compares
against `origin/master`, so after the merge it is comparing against the file that
NOW CONTAINS #7858. It passes at 3415 lines with the same three allowed edits —
which is a byte-exact proof that the carry survived, and strictly stronger than
`grep carry_renamed_pool_reservations`.

**And then a mutation, because present is not live.** Neutralising the carried
function with an early return reds exactly two tests:

```
nat::tests_pool::renamed_pool_carries_live_reservations_6979
nat::tests_pool::rename_onto_a_new_pool_name_carries_live_reservations_6979
```

Those are precisely the two #7858 records as RED at master (the reuse branch and
the fresh-allocator branch, which the resolver reaches separately). Its third
test, `coexisting_pools_sharing_an_address_do_not_cross_pollinate_6979`, stays
green — also as #7858 states, because it guards the fix's over-reach rather than
the original defect. The carried code is on both live paths, and its over-reach
control still guards.

**One self-inflicted hazard, recorded because it nearly cost the resolution.**
Running that mutation mid-merge and then `git checkout -- <path>` restored from
the INDEX — which held this branch's PRE-merge `mod.rs`, not the resolution —
silently eating it. The resolution had to be regenerated. The rule is the one
already in the project's habits and I broke it: **stage or commit the resolution
before mutating anything**. A merge in progress makes `git checkout --` restore
to a different baseline than the one you think you are on.
