# #6905 — neg_neigh overflow cleared the whole suppression cache

- **Timestamp**: 2026-08-27
  - **Action**: replaced the wholesale `clear()` on overflow with a bounded
    reclaim — expired entries first, else the single oldest.
  - **Reachability, measured** (the issue does not state it): the cap is
    `MAX_NEG_NEIGH_CACHE = 256`, and the constant's own comment says why —
    "a /24 scan touches 254 distinct dsts; 256 covers a full subnet sweep". So
    the overflow needs one subnet sweep **plus two other dead hosts**. This is
    not an exotic worst case; it is a /24 scan with anything else going on.
    For contrast the downstream cap is `MAX_PENDING_NEIGH = 4096`, 16x larger,
    so the suppression cache saturates long before the queue it protects does.
  - **Cost, measured, because the parent asked whether the obvious fix is worth
    it on a hot path**:
    - `neg_neigh_record` — where eviction happens — is called once per
      `(egress_ifindex, next_hop)` per pending-neighbour TIMEOUT window
      (`neighbor_dispatch.rs:251`), **not per packet**. It is the COLD path.
    - `neg_neigh_active` — the gate — is the per-packet path.
    - That asymmetry is the whole answer on policy: **LRU is the wrong
      instrument** because it pays bookkeeping on every HIT (hot) to improve a
      decision made only on RECORD (cold).
    - And the cost objection to a scanning reclaim mostly dissolves: `clear()`
      is already **O(capacity)**, not O(1). A one-pass retain is the same order
      of work choosing a better victim, still allocation-free.
  - **The issue's recommended fix is WRONG here, and this is the finding.** It
    says "cheapest correct option is to refuse the new key when at capacity (the
    pending-neighbour path already takes exactly this approach, so the codebase
    has precedent)". The precedent does not transfer: **this cache has no
    background prune.** TTL is enforced lazily in `neg_neigh_active`, on access.
    A scan records each hop once and never looks it up again, so those entries
    expire *unobserved* and are never pruned. Refuse-at-capacity would therefore
    fill with stale keys and stay full — wedging suppression permanently for
    every NEW dead host, which is strictly worse than the wholesale clear it
    replaces, and silent: `len()` looks healthy and no counter moves. Hence
    expired-first reclaim, with `sustained_scan_does_not_wedge_suppression_6905`
    as the control for exactly that failure.
  - **Deleted a test that pinned the implementation.**
    `overflow_clears_then_reinserts_new_key` asserted `len() == 1` after
    overflow — true only for a wholesale clear, so it would have had to be
    deleted to land ANY fix. That is a test blocking the change it exists to
    guide. Replaced with the property: an unrelated hop's suppression SURVIVES
    another hop's overflow, which reds for wholesale clear and passes for any
    bounded policy (LRU, oldest-first, random victim) without dictating one.
  - **Determinism note**: the surviving hop is recorded LAST so it is not the
    oldest. Under an age-ordered victim the eviction is then deterministic; a
    fixture that let the victim be arbitrary could not name a survivor.
  - **Two mutation cells survived the first matrix, and one was serious.**
    - **M4 (remove the fallback eviction entirely) red NOTHING.** Every
      assertion in the suite was a LOWER bound on what SURVIVES an overflow, so
      "evict nothing and grow forever" satisfied all of them — in a cache whose
      only job is to be bounded. Fixed with an explicit upper bound plus a
      sustained-insert loop.
    - **M2 (drop the expired-first pass) red nothing either**, and chasing it
      produced an honest correction rather than a patch. The pass is NOT
      load-bearing for victim selection: with a single clock, "expired" means
      "inserted before now - TTL", which is a PREFIX of the age order, so
      evict-oldest already evicts an expired entry whenever one exists and no
      fixture can separate the orderings. What the pass actually buys is
      AMORTIZATION — without it every new key at capacity runs another O(len)
      scan to free one slot; with it, one scan reclaims the whole dead
      generation. Bound as that, and
      `overflow_reclaims_expired_before_live_6905`'s doc corrected to say what
      it can and cannot distinguish rather than leaving it claiming more than
      it tests.
