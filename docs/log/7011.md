# #7011 — retire the hijacked-connection drain exception

- **Timestamp**: 2026-08-28
  - **Action**: `drainLeg` now closes hijacked connections, so its guarantee —
    "nothing this leg accepted is still being served" — carries no "modulo
    hijacked connections" qualifier in any of the three places it is stated.
    `TestNoHijackerInThisPackage_6827` is DELETED rather than re-keyed.
  - **Why deleted, not re-keyed.** The enumeration was defeated three times:
    `golang.org/x/net/websocket` (round 8), `golang.org/x/net/http2/h2c` (round
    9), and `net/rpc` — a STANDARD LIBRARY hijacker. The last one is decisive:
    the hijacker set is a function of the TOOLCHAIN, not of `go.mod`, so the
    corpus the map was derived over moves with nothing in the repository
    changing. The issue's own `go list -deps` fallback would have missed
    `net/rpc` too unless written to include the stdlib.
  - **Mechanism**: `http.Server.ConnState` fires with `StateHijacked` and hands
    over the `net.Conn` at the moment the server loses track of it.
    `trackHijackedConns` installs the hook in both leg constructors; `drainLeg`
    closes what the tracker recorded, on BOTH the graceful and the deadline
    path (a `Shutdown` that returned nil still left a hijacked conn open), and
    releases the registry entry so a rebind does not leak one per leg.
  - **What is NOT claimed**: the connection is closed, not the goroutine the
    hijacking handler started. Nothing can join that — the handler owns it and
    exposes no handle. The guarantee is about what is still being SERVED, and a
    closed conn serves nothing, which is the standard `Close` already meets for
    the non-hijacked in-flight case.
  - **Cost, stated**: `ConnState` is never called again for a hijacked
    connection, so a handler that hijacks and then closes leaves a tracker entry
    until the leg drains. The map grows with the number of hijacks a leg serves
    rather than with the number live at any moment. This package has no hijacker
    today, so it stays empty; a future high-volume hijacker needs a liveness
    signal, and the source comment says so at the place to start.
  - **The tests install a REAL hijacking handler**, which is the point: a case
    that only re-asserted "no hijacker is reachable" would be the same
    unmaintainable claim in a different file. A wiring cell separately requires
    both production leg constructors to install the hook, since the behavioural
    cells drive `trackHijackedConns` directly and would pass against a
    production leg that never called it.
