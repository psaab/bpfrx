# 9071 — two of five insert paths never bumped the insert generation

- **Timestamp**: 2026-09-06
- **Action**: bump `insert_generation` from the two bulk paths, and correct the
  rationale that said only the STATIC map was uncovered.
- **File(s)**: `userspace-dp/src/afxdp/sharded_neighbor.rs`,
  `userspace-dp/src/afxdp/neigh_schedule.rs`,
  `userspace-dp/src/afxdp/sharded_neighbor_tests.rs`.

The three per-key insert paths bumped `insert_generation`; the two **bulk**
paths bumped only the shard epoch. The consumer is #7156's poll-loop gate — a
full resolution pass runs only when
`neigh_generation != binding.last_neigh_generation` — so a neighbour learned by
the netlink bulk sync or the #1787 RX source-MAC transit learn never woke that
pass, and its buffered packet waited for the ≤50 ms recheck backstop.

**The epoch and the generation answer different questions**: the epoch
invalidates cached flows resolved to one shard; the generation tells the poll
loop a resolution pass is worth running at all. Neither substitutes for the
other.

## The larger half is the false rationale

`neigh_schedule.rs` said the recheck "covers **the one case** that gate cannot
see: the STATIC `forwarding.neighbors` map." There were **two dynamic cases** it
also could not see. A reader tuning `RESOLUTION_RECHECK_INTERVAL_NS` upward on
the strength of that sentence would have converted a bounded 50 ms delay on two
live paths into a real drop. Corrected, and the static map is now genuinely the
remaining case.

Severity is Low as filed, and the issue's two refutations are kept: the packet is
**not** dropped (`next_due_for_pending` arms every key at ≤50 ms against an
800 ms–2 s pending timeout), and this is **not** the primary resolution path
(that is `insert_if_changed`, which always bumped).

## The condition took two attempts, and the wrong one was subtle

My first version reused the epoch's `changed_shards` set. **That was wrong**:
`changed_shards` marks a key whose **MAC changed**, and a brand-new key has no
prior MAC to differ from — so a freshly resolved neighbour, *the exact case the
poll loop is waiting for*, would not have bumped. The condition is "did this
call install anything".

Before that I bumped **unconditionally**, and the narrowness cell caught it: an
empty netlink sync would fire the gate every sweep, which is #7156's
optimisation removed while looking like a fix. **A counter that advances on
every call carries the same information as one that never advances.**
