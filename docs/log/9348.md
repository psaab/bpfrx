# #9348 — cluster mode dropped the family-level Kea scalars

Self-filed during #9141. The filing named two dropped fields; the measurement at
fix time found **six**.

## Measured at HEAD (cd7b29bb4)

```
v4 SocketType    src="udp" filtered=""
v4 ExpiredLeases src=true  filtered=false
v6 SocketType    src="udp" filtered=""
v6 ExpiredLeases src=true  filtered=false
DynamicDNS       src=true  filtered=false
DynamicDNSv6     src=true  filtered=false
```

The issue named only the v4 pair. The v6 family and the two `DHCPServerConfig`
DDNS pointers were dropped by the same code for the same reason — which is the
point: the defect is **reconstruct-by-enumeration**, so its blast radius is
"every field the author did not name", not a fixed list.

## Severity, split

- **The Kea scalars are the defect.** A clustered node rendered Kea without
  `expired-leases-processing` (#1387 — Kea falls back to its built-in
  reclamation defaults) and without `dhcp-socket-type` (#7318 — Kea falls back
  to `raw`), while a standalone node rendered both from the same committed
  config. #7318 exists because `raw` does not work on some substrates, so on a
  cluster that leaf read as applied and was not.
- **The DDNS pair is harmless**, audited rather than assumed: this result reaches
  only `dhcpserver.Manager` (the Kea render), and the DDNS policy is read
  straight off the ACTIVE config by
  `ddns.Manager.ReconcileScoped(ctx, &cfg.System.DHCPServer, opts)`.
  `pkg/dhcpserver` contains no non-test reference to `DynamicDNS` at all.

## The fix

Copy the source and swap only what the function narrows, at BOTH levels — the
same shape #9141 used for `resolveDHCPRethInterfaces`. The copy is the guard: a
field added to either struct is carried by construction.

Behaviour change worth stating plainly: clustered nodes now render
`dhcp-socket-type` and `expired-leases-processing` where they previously did
not. That is the point of the fix, but it does change the generated Kea config
on a clustered box whose operator set either leaf.

## Mutation table

Each mutant confirmed to build AND test-build; bounded at 300s / `-timeout 180s`;
a non-finishing run or one with no pass/fail actions is VOID.

| # | mutation | result |
|---|----------|--------|
| M1 | rebuild the v4 family field-by-field | **KILLED** |
| M2 | drop the outer struct copy (`var result config.DHCPServerConfig`) | **KILLED** |
| M3 | rebuild the v6 family field-by-field | **KILLED** |
| M4 | sever the WIRING — `desiredClusterDHCPConfig` stops delegating | **SURVIVED, then KILLED** |

Escapes: none. Voids: none.

**M4 is the one that mattered.** Every other cell calls
`filterDHCPConfigForMasterRGs` directly, so all of them stay green if
`desiredClusterDHCPConfig` — the single entry point the commit path, both RG
transition edges and the #6535 converger all use — stops calling it. A scalar
assertion cannot see that either, because the *unfiltered* config carries the
scalars too. The observable that separates delegating from not is the RETH name
resolution: a delegating call yields `ge-0-0-1.0` where the authored config says
`reth1.0`. `TestDesiredClusterDHCPConfigDelegatesToTheFilter9348` was added for
exactly that and kills M4.
