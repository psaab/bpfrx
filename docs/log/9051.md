# 9051 — a stream outlives its own authorization verdict

- **Timestamp**: 2026-09-06
- **Action**: re-authorize long-lived streams on both surfaces, at the same
  choke point that makes the initial decision.
- **File(s)**: `pkg/grpcapi/authz_stream_reauth_9051.go` (new),
  `pkg/grpcapi/authz.go`, `pkg/api/authz_stream_reauth_9051.go` (new),
  `pkg/api/authz.go`, plus a test file per package.

## The defect

Both streaming surfaces adjudicated ONCE, at open, then handed the stream to a
handler that loops until the client disconnects or xpfd restarts. A principal
demoted or deleted mid-stream kept its `PermView`-tier feed — POLICY_DENY /
SCREEN_DROP records, log lines, interface counters — for the life of the
connection. Unary RPCs on the SAME connection were already re-adjudicated every
call, so the gap was stream-only.

## The rationale it hollowed

`readAuthz`'s own doc justified the single pass:

> A GET has no body to withhold: the handler is entered immediately, so there is
> no window between the verdict and the action for a revocation to fall into.

SSE is a GET whose handler runs **indefinitely** — precisely the window that
sentence says cannot exist — and both SSE routes sit behind that gate. The
one-pass design was justified by a property server-sent events do not have.

## Why the choke point and not the handlers' loops

The issue suggested re-checking on each loop's existing tick. That covers the
four streams that exist and silently omits the fifth: a new streaming RPC or SSE
route would get its OPEN adjudicated and its CONTINUATION adjudicated by
nothing, and nothing about adding one would prompt the author to remember.

Putting it in `principalStreamInterceptor` and `readAuthz` makes the two
decisions impossible to separate, and no handler needs to know it exists —
they already all select on their context.

The gRPC path returns the AUTHZ error rather than `context.Canceled`, because a
bare cancellation is indistinguishable from an ordinary shutdown and the client
must be able to tell it was revoked. On the REST side the response is already
committed to `text/event-stream`, so there is no status left to send and the
`slog.Warn` is the record.

## Validation

Four cells, two per surface, and the second of each pair is the one that keeps
the fix honest:

- **Termination** — with a REFERENCE ARM asserting the stream was ADMITTED
  first. Without it, a fix that refused every stream at open would satisfy the
  termination assertion while deleting the feature.
- **Narrowness** — an authorized principal's stream survives 20 re-auth
  intervals, and an ordinary client hangup still ends it with no revocation
  error. Without this row, "terminate the stream" is satisfied by terminating
  every stream.

Three mutants, each killed:

| mutant | result |
|---|---|
| gRPC interceptor stops re-authorizing (`return handler(srv, ss)`) | killed |
| `readAuthz` stops re-authorizing | killed |
| cancel unconditionally instead of on a denial | killed by the narrowness row |
