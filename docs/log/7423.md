# #7423 — counters: the four remaining #6566 rows

Four `show` surfaces that printed a number or a status an operator could not
distinguish from a measurement. All four are render-layer honesty defects: the
underlying state was correct in every case, and the fix is what the surface
claims about it.

## Row 3 — NAT `Translation hits` lacked an armed gate

- **Action**: gate the per-rule NAT translation-hit read on the same `armed`
  predicate the session scan in the same function already used.
- **File(s)**: `pkg/natshow/source.go`, `pkg/natshow/dest.go`,
  `pkg/natshow/natshow.go`
- **Why the `err == nil` guard did not cover it**: `Manager.ReadNATRuleCounter`
  is a map read that returns `(offset, nil)` unconditionally — it has no error
  path at all. The guard is not dead code (other implementations of the
  interface do error) but it cannot fire for the production Manager, so an
  unarmed dataplane rendered a confident `Translation hits: 0`. The REST
  sibling already refuses instead (#5046).
- Unarmed now renders `n/a (dataplane not armed)` from one shared constant, so
  the hits row and the session row cannot drift into describing the same
  condition differently.

## Row 4 — `Number of sessions` is a zone-pair aggregate printed per rule

- **Action**: move the count out of the per-rule loop to rule-set scope and
  relabel it as the zone-pair aggregate it is.
- **File(s)**: `pkg/natshow/source.go`, `pkg/natshow/dest.go`
- The scan keys on the session's ingress/egress zone ids, so the number is a
  zone-pair total. Printed once per rule, five rules over four hundred sessions
  printed `400` five times and summing the column gave five times the truth.
- Junos reports this per rule (`docs/junos-cli-reference.md`), and xpf cannot:
  a session carries zone ids and no rule identity, so there is nothing to
  attribute with. The number is real; it was labelled with the wrong noun.

## Row 5 — DDNS rendered a write-ahead record as `published`

- **Action**: narrow the owned arm on `PublishPending`, and report the last
  CONFIRMED address rather than the desired one.
- **File(s)**: `pkg/ddns/surface_a.go`
- **The ordering framing is a trap.** The obvious fix — moving the `lastErr`
  arm above `isOwned` — would make a healthy settled scope that once hit a
  transient error report `error` while its RR is live. Narrowing on the pending
  bit fixes both halves, because a failing re-publish leaves the bit set.
- **What the address column means during pending is `last confirmed`, not
  `what is live`,** and the two differ unknowably: per the #5334 analysis in
  `pkg/ddns/README.md` a pending record has the byte-identical shape for a
  window where the prior value is still live and one where the new value
  already landed. `withdrawOwnedLocked` deletes BOTH candidates for that
  reason. No single address can be asserted live, so the field is documented as
  last-confirmed and paired with `State: pending`.
- The first cut guarded the substitution with `PriorAddrText != ""`, which fell
  back to the unconfirmed address for a FIRST publish — the one case where the
  claim is least supportable. Fixed, with its own cell.

## Row 6 — `show security alg` fabricated eight `Enabled` rows

- **Action**: extract `renderALG`, delete the twelve hard-coded rows, report
  the four modeled ALGs by what they do, and render configured-but-unmodeled
  protos as `configured (not implemented)`.
- **File(s)**: `pkg/cli/cli_show_security_objects.go`
- **Origin**: the sixteen rows were cloned from the real-vSRX capture in
  `docs/junos-cli-reference.md`, sample VALUES included. A capture records what
  another box printed; rendering it as local state is the defect. The capture
  is left intact and an xpf-divergence note added beside it.
- Nothing in the dataplane does data-channel pinholing — the ALG bits reach one
  consumer, `alg_type_for_session`, which tags the conntrack row. So `Enabled`
  overstated three of the four, and TFTP's wire bit is `#[allow(dead_code)]`
  with no consumer at all.
- **Deleting the ghost rows alone would have introduced the opposite defect**:
  `security alg h323` is accepted at commit and recorded in `UnsupportedProtos`
  (#4232), so it can be in the running config. Printing only the four would
  make a configured stanza invisible on the surface an operator checks.
- **Row 6 is a THREE-surface defect, not a CLI one.** The issue names the CLI's
  fabricated rows, and only the CLI had those. But gRPC (`showAlg`) and REST
  (`showTextHandler`, topic `alg`) both printed `enabled` for the same four
  ALGs. Fixing only the CLI would have left the three surfaces describing the
  same four ALGs differently — the divergence
  `flow_tcp_timeouts_6539.go`'s header calls always-a-bug and never legitimate.
  All three now route through one authority, `pkg/config/alg_status_7423.go`,
  which owns the wording, the proto set and the render order; layout stays
  per-surface. Each surface has its own tests: a shared helper is not evidence
  that a caller reaches it, which is the same gap row 4 had internally (its
  first tests drove only `RenderSourceRuleDetail` while `dest.go` carried the
  identical fix untested).
