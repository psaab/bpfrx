# #7212 — revalidate established sessions against a changed static input filter

- **Timestamp**: 2026-08-30 (`fix/7212-static-filter-revalidation`)
- **Action**: lazy per-tuple revalidation of an established session's interface
  INPUT filter, stamped by config generation; the #5858 commit advisory deleted.

## Why

A purely STATIC address/protocol/port `then discard` attached or tightened after
a session was created was never rechecked, so that flow forwarded until it idled
out. The session-hit fast path re-evaluated an input filter only when its verdict
genuinely varies per packet (#1430 DSCP / #2362 per-packet L4), and the rotation
purge is gated on the same predicate, so a static filter change matched neither.

The obvious symmetry — an interface-keyed clear, mirroring the policy
invalidation — was rejected in #5858 and is not re-proposed: it drops PERMITTED
flows, and a purged permitted SNAT flow reinstalls on a DIFFERENT translated port.

## Mechanism

For a static filter the verdict is a pure function of `(ingress interface,
family, 5-tuple)`, all constant for the life of one direction of a session. Each
session entry is stamped with the config generation its verdict was computed
under; on a hit whose stamp predates the live snapshot the verdict is re-derived
ONCE, side-effect free, the entry re-stamped, and the session revoked only if the
verdict is now DENY.
