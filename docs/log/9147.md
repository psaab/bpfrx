## Why this lands while the issue is filed UNRESOLVED

The issue is UNRESOLVED because whether Route 53 echoes AAAA values verbatim or
normalized **cannot be observed from inside the repo**, and it gated the fix on
that answer. **The fix does not depend on it**, for two reasons:

- **Comparing IP values byte-exactly is wrong on its face.** Two spellings of one
  address are one address, whatever any particular server echoes back.
- **The repo already holds this position.** `wireRRClaim` (`pkg/ddns/state.go`)
  normalizes rdata through `netip` *"so the two ownership surfaces ... compare
  EQUAL for the same address even if their textual forms differ (e.g. an IPv6
  address written expanded vs compressed)"*. That is this exact argument, already
  made and already shipped, on a path reaching the same data. This one did not
  use it. A cell now pins the two normalizations to agree — two that disagree
  would be worse than one that is missing.

If Route 53 *does* normalize on storage, this is **inert**, not wrong: every
value read back is already canonical and the key equals the string. So the
unmeasurable premise decides whether the defect is **reachable today**, not
whether the comparison is **correct**.

The reachable arm, restated: AWS's own "Supported DNS record types" page gives
the AAAA example in expanded form, so an operator pre-seeding the FQDN by
following that documentation produces a string that can never byte-equal what
xpf writes — and `mergeUpsertValues` then puts both into one ChangeBatch. Its own
comment says *"Route 53 rejects a duplicate value in one RRset"*, so the publish
400s every tick and the record never converges.

## Key-only, deliberately

The normalized form is **never emitted** for a value xpf does not own. Rewriting
a foreign member's spelling on write-back would edit someone else's record to
suit our comparison — the same sole-delete-authority boundary `DeleteLease`'s doc
comment draws. Output keeps the ORIGINAL string, and a cell asserts the *live*
spelling survives a merge. The issue notes the originating report's `canonicalIP`
normalized the output too; that is narrowed here.

## Not carried

The report's "stale AAAA leaked forever" arm is **not** claimed. A leaked record
implies a successful publish, which implies xpf's canonical value is present and
`removeValue` finds it — the issue's own refutation, kept.
