# 7051 — `FragAuthority.routing_table`, an inert dimension the doc still claimed

## The issue's literal premise is REFUTED

#7051 states that

```diff
-        routing_table: meta.routing_table,
+        routing_table: 0,
```

"stays green". Measured on the full binary, no `-run` filter,
`-- --test-threads=1`:

| cell | rc | collected | named |
|---|---|---|---|
| `routing_table: meta.routing_table` -> `0` | **101** | 4821 | `tests_nat64_tunnel::nat64_frag_authority_dimensions_are_threaded_end_to_end_5798` |

A witness exists. The mutation does not stay green.

## The substance holds anyway — and more sharply than reported

That witness feeds a **fabricated** `routing_table: 1` through a meta production
pins to `0`. What it binds is that the field participates in the key's
*equality*, not that a routing instance ever reaches the key. It is exactly the
shape of test that reads as coverage while binding nothing reachable.

**#6927 r2 already knew this**, and says so at the test site: the case is
labelled `"FABRICATED input — inert in production"`, both literal-zero assignment
sites are named, and it records that real VRF discrimination is carried by
`ingress_ifindex`.

So the tree disagreed with itself. The *test* site disclosed the inertness in
full; `nat64.rs` still presented the field as a live key dimension. **That
inconsistency is the defect, and it is in the doc, not the code** — which is also
why the issue's "count four dimensions and get three" complaint is right even
though its measurement is wrong.

## The asymmetry the old wording hid

The old paragraph swept both fields into one sentence — `zone` and
`routing_table` "are carried explicitly because the enforcement arm reads them
directly" — with a parenthetical that justifies only `zone`. The justification
cannot extend, and the difference is visible in one function:

```rust
// prerouting_ingress_scope
let zone_name = zone_override.and_then(...)          // override consulted FIRST
    .or_else(|| forwarding.ifindex_to_zone_id.get(&logical_ifindex)...)

let routing_instance = forwarding
    .ifindex_to_routing_instance
    .get(&logical_ifindex)                            // no override, ever
```

There is **no routing-instance override anywhere on the path**, and
`ifindex_to_routing_instance` is built one entry per interface
(`forwarding_build/interfaces.rs:122`). So the VRF is a **pure function of the
logical unit**, which the key already carries in `ingress_ifindex` +
`ingress_vlan_id`.

The consequence is stronger than "inert today": **even populated correctly the
field could not separate two authorities that the interface identity does not
already separate.** A "VRF-only" fixture is impossible to construct through
production — varying the routing instance necessarily varies the interface — and
that impossibility is the argument, not a gap in the fixtures.

## Kept, not dropped

The issue offers dropping the field. #6927 r2 made the opposite call knowingly,
with a stated trigger for revisiting. Reversing a deliberate, documented decision
needs a defect it causes, and it causes none:

- **Safe by direction.** A stamped value can only make the key FINER. A finer key
  is a MISS, which falls through to the full enforcement arm — fail-closed by the
  same construction the whole authority design rests on. It can never produce a
  false inherit.
- Dropping it would also mean editing the #6927 r2 case out of a test whose whole
  purpose is to enumerate the dimensions, for no behavioural gain.

What was wrong was the description. The description is what changed.

## A doc claim owes a guard, because this one rots silently

Stamp the field and nothing fails — the key just gets finer. So the claim is
CHECKED rather than asserted in prose, by
`frag_authority_routing_table_is_inert_in_production_7051`, which covers both
assignment sites in the two different ways they can be covered:

- the in-crate `Default`, **by value**;
- the shim writer, **by source** — `userspace-xdp` is a separate crate compiled
  into a BPF object, so there is no value to read from here. Scanning its source
  is what the Go/Rust pool-reason lockstep already does for the same reason.

A red there is **not a defect**: it means the field became live, and the test's
own doc names the follow-up #6927 r2 wrote down (relabel the fabricated case,
drive it from a real ingress, correct the "three dimensions" wording).

### The guard caught its own weakness twice before it was right

Recorded because both drafts would have shipped a guard that reports the wrong
thing:

1. The first matched the shim's `routing_table: u32,` **field declaration** as a
   stamp, and reported the field LIVE against a shim that only declares it.
2. The second counted `mem::offset_of!(UserspaceDpMeta, routing_table)` — an ABI
   assert that is neither a declaration nor a stamp.

It now discriminates on `routing_table:` *with the colon*, minus the `u32`
declaration. It also asserts non-vacuity on **both** halves: no mentions at all
means the field was renamed and the scan is hunting a name that does not exist,
which is not evidence of inertness.

The second cell is the one that matters for a source-scanning guard: a renamed
field makes the scan match nothing, and an "all matches are zero" check over an
empty set passes for free. The non-vacuity assertion is what turns that into a
red.
