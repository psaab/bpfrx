## The question

Option 2 ("skip the mirror walk when the dataplane streams authoritative
deltas") is costed in the issue as *"removes the backstop entirely, so a dropped
delta is never recovered"*. If the delta stream had a recovery path of its own,
that cost would be overstated and the owed cluster measurement might not be
load-bearing for choosing it.

## The answer: the cost is UNDERSTATED

The delta stream has no recovery path of its own for a daemon→peer drop. **The
sweep is that recovery path.**

1. Both producers share one bounded `sendCh`. The delta stream reaches the wire
   via `queueUserspaceSessionDeltas` → `queueDeltaSink.openV4` →
   `QueueSessionV4` → `queueMessage`; the sweep calls the same `queueMessage`.
2. `queueMessage`'s overflow branch arms `syncBackfillNeeded` and logs
   "enabling sweep replay". The counter the issue says to measure
   (`stats.Errors`) and the sweep it proposes to delete are two halves of one
   mechanism.
3. `syncBackfillNeeded` has exactly three consumers, all in the sweep.
   (Positive control: the same search shape returns 35 test references and the
   arm/declaration sites for the sibling flag `forceResync`.)
4. The recovery works by refusing to advance the window: on overflow `syncSweep`
   returns before `s.lastSweepTime = now`, so the next sweep re-walks the
   identical `Created >= threshold` window and re-sends what was dropped.
5. The helper's `FullResync` is a DIFFERENT failure domain — helper→daemon loss
   when the replay buffer is trimmed past the daemon's ack. By the time a delta
   reaches `queueMessage` the daemon has already consumed and acked it.

## Two stale comments, both load-bearing for the issue's own options

- `SessionSyncSweepProfile` said *"Keep a periodic refresh for long-lived
  flows"*. The sweep does not and structurally cannot: `Created >= threshold`
  sends only sessions created SINCE the last sweep, and `sync_conn_sweep.go`
  says so itself — *"every session that existed before the sweep started is
  permanently invisible to it"*. Option 3 cites that sentence as its
  justification, so option 3 is not "narrow the walk to its stated purpose" but
  "build a refresh capability the sweep never had".
- `sync_conn_sweep.go` said the backfill flag *"holds the sweep at the 1s active
  cadence"*. That is the eBPF default; under userspace the profile makes it 15s.

This is the third time in this campaign a stale comment has propagated into a
decision. Both are corrected with the measurement recorded beside them.

## The implementation trap

The issue says `SessionSyncSweepProfile` "already identifies that case". It
does — but `enabled` is not a disable switch. `sweepIntervalsForDataPlane` uses
it only to decide whether to adopt the profile's intervals, and `false` falls
through to the 1s/10s DEFAULTS. Implementing option 2 by returning `false` would
run the sweep at 1s instead of 15s: 15x more duplication, silently, and the
opposite of the intent. Recorded at the definition site.

## The guard that was missing

`syncBackfillNeeded` had **zero** test references while `forceResync` had 35.
The recovery path that makes option 2 unsafe was entirely unguarded — someone
implementing option 2 would have deleted it with a green suite. Two cells added:
one pinning the arm + the held window + the replay, one pinning that a DELTA
dropped on the shared queue arms the SWEEP's replay (the cell that actually
decides option 2).

**The first draft of those cells was vacuous and a mutation caught it.** The
fixture used `now` for both `lastSweepTime` and `Created`, so a mutation letting
the sweep advance the window on overflow ESCAPED — advancing to `now` is
indistinguishable from holding at `now`, and a session with `Created == now`
still satisfies the advanced filter. The fixture now opens the window strictly
behind the sweep's clock, which is what makes both assertions able to fail. That
is the "never let a fixture use the value the bug falls back to" shape.

## What remains cluster-blocked

Choosing between option 1 and a redesigned option 3 is still a volume question
and the `SessionsSent`/`Errors` run stands. One note for whoever runs it: the
metric is **not linear in connection rate**. An overflowing sweep does not
advance `lastSweepTime`, so the next sweep replays the same window — grown by
everything created meanwhile — while the arm holds it at the active cadence.
Pressure feeds pressure, so sampling one "realistic" rate can land below the
knee and report a clean `Errors == 0` that says nothing about the rate just
above it. The run should bracket the overflow threshold rather than sample one
point, and record `queue_len`/`queue_cap` from the warn line alongside the
counters.
