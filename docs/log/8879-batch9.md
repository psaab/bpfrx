## The fail-open is a CLASS, not a one-off

Batch 6 found that `routing-options forwarding-table` elision dropped the export
leaf *before* its dangling-reference check ran, so a typo'd policy name
committed clean. I recorded it as the worst shape found and moved on.

A second instance turned up in this batch, and only because a fixture of mine
happened to name an RPM probe that did not exist:

    braced,  undefined rpm-probe  ->  REJECTED at commit  (correct)
    elided,  undefined rpm-probe  ->  COMMITTED CLEAN     (fail-open)

`services ip-monitoring` drives probe-driven WAN failover. A silently dropped
policy means **failover never arms, and the operator is never told the probe
name was wrong** — arguably worse than the forwarding-table case.

Two independent instances in the two batches that looked. The guard is
therefore now a TABLE rather than a single case, because a single-case cell
keeps reading as an oddity while a table reads as a class. The shape to look
for: *a container whose child carries a cross-reference that strict commit
validates.* Anyone extending this work should assume more exist.

## Two fixtures repaired before use — both my fault, not the code's

- `security ssh-known-hosts` with a bare `host` compiled to **zero hosts on both
  arms**: a host with no key is not stored. That is a dead comparison that would
  have read as "no drop" and cleared a pair that does drop.
- `services ip-monitoring` needs BOTH a defined rpm probe and a `then
  preferred-route`; without them the braced reference did not compile at all —
  the unanswerable third state again.

Both were caught by reading the measured VALUES rather than the pass/fail.
