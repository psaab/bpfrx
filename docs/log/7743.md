# 7743 — reap/delete map-fd fixture: decision and single-source fix

## Question the issue asked

> Decide whether a map-fd fixture is worth building for
> `delete_session_map_entry_for_removed_session_with_origin`, and say why
> either way.

## Decision: NO map-fd fixture. Measured reasons below.

### 1. The prescribed part-2 property is already bound, purely

The prescribed cell was *"two sessions, reap one, assert the other
survives"*. The set of map keys a reap touches is computed by
`for_each_session_map_redirect_key` from **this session's own key + NAT
decision** — it has no mechanism to reach another session's key. Two
sessions collide only if NAT allocated them the same
(address, port) tuple, which is an invariant of the NAT allocator, not
of this code. A disjointness assertion here would be
mutation-insensitive: there is no guard to delete that would change the
outcome. The key set itself is already asserted at
`bpf_map_tests.rs` (`session_map_redirect_keys_for_forward_session_include_nat_aliases`,
`session_map_redirect_keys_for_kernel_local_synced_session_delete_superset`)
with no map required.

### 2. What a real map WOULD have caught was the key ENCODING — and that
is bindable without a map

`delete_bpf_conntrack_entry` is fd-guarded (`if conntrack_v4_fd >= 0`),
so the `-1` fds every existing fixture passes make it a silent no-op.
The only property a real fd adds is *"the syscall was issued with these
exact key bytes"*. That is a publish/refresh/delete **agreement**
property, and it was genuinely unbound — see the two findings below.

### 3. Cost

A real map needs `CAP_BPF` (verified in #6923: unprivileged
`BPF_MAP_CREATE` -> EPERM on this host, `unprivileged_bpf_disabled=2`),
so the cell would be SKIP-gated on any unprivileged machine — a weaker
guard than a pure test for the same property.

## Findings fixed in this change

### F1 — the branch a fixture would have discriminated is vacuous

`delete_session_map_entry_for_removed_session_with_origin` read:

    delete_session_map_redirect_for_session(..);
    if uses_kernel_local_session_map_entry(..) {
        delete_bpf_conntrack_entry(v4, v6, key);
        return;
    }
    delete_bpf_conntrack_entry(v4, v6, key);

Both arms call the same function with the same arguments. `git log -L`
shows it has been that way since it was introduced (`580439fa2`,
#1572) and in the pre-split file before it — the arms have **never**
differed. No fixture can bind a discriminator that does not
discriminate.

Collapsed. This is behaviour-preserving, and the delete was already
correct for both cases: the kernel-local publish writes its entry under
the same `session_map_key` derivation (only the map VALUE differs,
`USERSPACE_SESSION_ACTION_PASS_TO_KERNEL`), and a BPF delete addresses
the row by KEY.

### F2 — eight hand-rolled copies of the conntrack key encoding, zero
production coverage

The conntrack map is written by three operations that must address the
same row byte-for-byte: publish (`publish_conntrack`), refresh (the
lookup + `BPF_EXIST` update), and delete. Each hand-rolled the key
literal — 8 sites — repeating `.to_be()` on both ports and `pad: [0;3]`
as an assumption. If any drifts, publish writes a row delete can never
remove: a permanent conntrack leak, and **no behavioural test fails**.

The test that looked like it covered this,
`bpf_conntrack_key_port_byte_order`, built the struct literal INLINE in
the test body. It called no production code, so it asserted only that
`u16::to_be` works; reverting the production encoding left it green.

Fixed by single-sourcing into `bpf_session_key_v4` / `bpf_session_key_v6`
(divergence here is always a bug, so single-source rather than
bind-two-copies), retargeting the byte-order test at the builder, adding
the v6 twin, and adding an anti-drift source scan that fails if a ninth
hand-rolled literal appears.
