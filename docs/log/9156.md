## V020: the fix

`hoistAndSplitRun8939` at BOTH tunnel readers
(`compiler_interfaces.go` interface-level and unit-level).

The choice of remedy was measured, not picked by family. Three exist in this
tree and which one works depends on the shape `SetPath` built:

- `tunnel` **already declares `packedStatements: true`** and still loses,
  because that flag splits a packed tail on ONE node's `Keys` and SetPath builds
  this as a nested CHAIN — `[keepalive-retry 5] > [destination 10.0.0.2]`. The
  issue names this trap and it is real; adding the flag is not the fix.
- `expandFlatRun` alone handles the chain and the packed tail but leaves a
  CONTAINER leaf's subtree alone, so `tunnel routing-instance destination VR1
  source 10.0.0.1` would still lose the source: `source` sits two levels down
  under `routing-instance`.
- `hoistAndSplitRun8939` covers both, and lifts the nested `source` precisely
  because it is UNAMBIGUOUSLY foreign — legal in `tunnel`, illegal under
  `routing-instance`. That bound is what stops it turning a leaf's VALUE into a
  statement.

## V020's second half: one endpoint predicate, not two that disagree

The routing side and the dataplane side each had their own endpoint screen and
they did not agree:

```
EmitTunnelEndpointNames (what the DATAPLANE learns)
  Mode != "wireguard" && (Source == "" || Destination == "")  -> skip

collectAppliedTunnels (what the ROUTING side creates)
  Source != "" || Mode == "wireguard"                          -> apply
  ...and its per-UNIT loop screened NOTHING AT ALL.
```

So variant B — source, no destination — passed the routing gate and failed the
dataplane one: the TUN is created, brought up and given its configured
addresses, while the dataplane holds no endpoint for it. An operator can zone
it, route into it, and every packet disappears.

`pkg/routing/tunnel.go` HAS a correct guard for this
(`localIP == nil || remoteIP == nil` -> warn and refuse) and it is **dead
code**: its own comment records that the daemon always sets AnchorOnly, and
`dataplane.EffectiveType("")` is `TypeUserspace` on every box, so `Apply` always
dispatches to `applyAnchorLocked`, which has no endpoint check at all.

`config.TunnelHasUsableEndpoints` is now the single predicate, used by the
emitter and by both arms of `collectAppliedTunnels`, and the drop is WARNED
rather than silent. It is deliberately the STRICTER of the two, because the
emitter's is the one that decides whether the tunnel can carry traffic —
creating a device the dataplane cannot forward through is the failure, not the
remedy. WireGuard stays exempt for the reason #1432/#1736 record.

Blast radius checked against the shipped corpus: `docs/ha-cluster-userspace.conf`
and its siblings all write both endpoints, so nothing in-tree stops being
applied.

## The umbrella this issue owns

### The gate the #2419 gate cannot express

`schema_spelling_differential_gate_test.go` is the #2419 gate and its unit is
*(one leaf, TWO VALUES)* across five spellings. This class is *(one container,
TWO DIFFERENT LEAVES)* on one line. Different axis, structurally blind — its
green says nothing here, which is how the class reached 26 containers with a
green suite.

`TestLeafRunDifferentialGate9156` is the missing axis. For every container
holding an untyped admission head alongside ≥2 childless leaves it compiles the
leaves on ONE line and on SEPARATE lines and requires the compiled `Config` to
match. **The separate-lines form is the oracle** — two spellings agreeing tells
you nothing about which is right.

**It compares on the LENIENT path, deliberately.** A census that compiles
strictly loses a row exactly where a validator rejects its synthesized value, so
it goes blind at the GATED sites — the ones a reader is most likely to have
skipped. Per #1960 the lenient path is what `Load` and `SyncApply` take, so a
strict rejection does not mean the loss cannot happen; it means it happens on
boot and HA sync instead of at commit.

### M1's first survival was the gate's, not the fix's

M1 killed the two tunnel cells immediately, but it did NOT red
`TestLeafRunDifferentialGate9156` or its Discriminates control. That is the more
important result: the gate could not see the defect it was built for.

The reason is the axis. The braced and flat-set spellings of the SAME statement
build DIFFERENT ASTs:

```
braced    tunnel { keepalive-retry 5 destination 10.0.0.2; }
          -> [keepalive-retry 5 destination 10.0.0.2]        PACKED KEYS
flat-set  set … tunnel keepalive-retry 5 destination 10.0.0.2
          -> [keepalive-retry 5] > [destination 10.0.0.2]    NESTED CHAIN
```

The first version of the gate rendered only the braced form, so its 26 findings
were the packed-tail axis and it was structurally blind to the nested-chain axis
— which is the one #9156 is about. A gate blind to its own subject is the
"fixture chosen to discriminate question A is VACUOUS for question B" shape, and
only the mutation exposed it.

**The gate now drives both axes and labels every row.** That immediately found a
container the braced-only version could not see:

```
security log stream xpfarg [port -> category]  {flat}
```

which corrects the issue's own probe table — it recorded `security log stream`
as "recovered", and it is, on the BRACED axis, while still losing on the
flat-set one. One row moves the other way (`system ntp server` differs only when
braced), so the two axes are genuinely independent and neither subsumes the
other. 27 rows: 25 both, 1 flat-only, 1 braced-only.

Re-scored, M1 now makes the gate report
`interfaces xpfname tunnel [keepalive-retry -> destination] {flat}` as an
unrecorded difference.

### M7: the ratchet could be disarmed without a red

Making the gate accept every difference as recorded left the whole suite green.
`TestLeafRunRegisterIsNotVacuous9156` checked the register's SIZE, which says
nothing about whether the register is CONSULTED.

Closed by extracting the ratchet DECISION (`ratchetLeafRunDiffers9156`) so a
cell can hand it a fabricated input and read the verdict back: one unregistered
and one registered difference must return exactly the unregistered one, and an
empty difference set must report every registered row as stale. "Make a
surviving guard exercisable rather than excused" is the remedy that applied.

### M3 is the one that justifies the remedy choice

`expandFlatRun` instead of `hoistAndSplitRun8939` kills **only** the
routing-instance cell — every other tunnel arm stays green. That is the
measurement behind picking the stronger helper: the difference between the two
is exactly one shape, the run nested two levels down under a container leaf, and
without that cell the weaker remedy would have looked sufficient.
