# #8882 — a typo'd top-level stanza commits clean and discards everything under it

- **Timestamp**: 2026-09-05
  - **Action**: added a commit-time gate rejecting an unmodeled TOP-LEVEL
    stanza. `securty { zones { security-zone z1 { } } }` compiled clean,
    schema-validated clean, and yielded `zones=0` — the keyword resolves to no
    schema node, so the walk never descends and the whole stanza is discarded.
  - **NOT `setSchema.closedWorld`**, which is the obvious fix and is wrong: the
    flag inherits (`childClosed := closed || childSchema.closedWorld`), so
    arming it at the root closes every subtree, and the schema does not model
    the tree exhaustively. Measured: **9 of the 10 shipped and example configs
    rejected** (`chassis cluster redundancy-group interface-monitor`,
    `system services dhcp-local-server ... pool`, `family inet6 dhcpv6`,
    `security flow tcp-mss all-tcp`). The gate closes ONE level and inherits
    nothing; a cell asserts that it does not inherit.
  - **Load-path premise, asserted rather than described**: the safety argument
    is NOT "the load path does not validate" — it does. `compileTreeLenient`
    schema-validates and downgrades to a warning (#1319 PR 2), so the
    no-blackout property rests on that downgrade continuing to exist.
    `TestLoadDowngradesUnknownTopLevelStanza8882` reds if it ever stops.
  - **Corrected a false comment** in `schema_validators.go` which claimed
    `compileTreeLenient` "does not schema-validate at all". True when written,
    hollowed by a later change, nothing re-checked it — and then cited as
    authority by two agents in one day to argue a new gate could not affect the
    load path.
