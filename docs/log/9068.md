# #9068 — one parser, two exec channels

Filed as **UNRESOLVED (reachability)**, not as a confirmed defect. This closes it
by removing the question rather than answering it, which the issue itself names
as the cheaper and strictly better option.

## What was established

**One parser, two channels.** `GetSAStatus` used a stdout-only buffer with the
explicit comment *"the parser needs stdout alone"*. `liveConnNames` routed
through `runSwanctl` → `CombinedOutput` — stderr folded in — on the
security-critical TEARDOWN path. Its in-place justification, *"parseSAOutput
ignores any unrecognized stderr lines CombinedOutput may fold in"*, was
**asserted, never tested**.

The issue's executed tolerance matrix on `parseSAOutput`:

| injected | result |
|---|---|
| a whole stderr line before the IKE header | name preserved |
| a stderr line containing `": #"` | a SPURIOUS extra name (harmless — not in `removedSet`) |
| CRLF | tolerated |
| **a mid-line splice into the IKE header** | **the real name is LOST** |

So the justification is true for whole lines and false in the one direction that
matters.

**Why a lost name is a fail-open.** `terminateRemovedConns` iterates
`for name := range live`, so a removed connection absent from `live` is neither
terminated nor entered into `pendingTerminate` — and `prevConnNames` has already
advanced past it, so the teardown-debt record #6542 exists to keep is never
created. A deleted VPN's SA keeps forwarding under an unloaded configuration,
with no retry and no debt.

## What was NOT established, and why the fix does not depend on it

Whether a mid-line splice can actually occur: stdout to a pipe is
block-buffered, stderr unbuffered, so it needs a listing large enough to force a
mid-stream flush plus a concurrent stderr write — and whether
`swanctl --list-sas` writes to stderr at all on a *successful* listing is
unknown.

Giving the parser the same stdout-only channel its sibling already uses costs
less than the experiment and its correctness does not depend on the outcome.
**Which of the two was right** was the question worth answering first, and the
answer was in the code: `GetSAStatus`'s own comment.

## Fix

`runSwanctlSplit` returns stdout and stderr separately. `liveConnNames` uses it
and puts **stderr alone** in its error, matching `GetSAStatus`. `GetSAStatus`
was refactored onto the same helper rather than keeping its inline copy — two
spellings of one exec discipline is how the divergence happened, and there is
now one.

The NON-parsed calls (`--load-all`, `--terminate --ike`) deliberately keep
`CombinedOutput`: their only consumer is an error message, and folding stderr in
is what makes it useful. The wiring guard asserts that split.

`scSplit` falls back to the legacy combined seam and treats its output as
stdout, so **every pre-#9068 test double keeps working** — a double returns
canned listing text with no stderr to fold. Without that fallback the change
would have silently stopped every existing double from reaching the parsed call,
and those cells would have passed while exercising nothing.

M4 was **void on its first attempt** — dropping `errOut` from the error string
left it declared-and-not-used, which does not compile and emits no `--- FAIL`.
Re-run with the variable kept referenced so the mutant builds; it then kills.

M3 is the one that would have been easy to skip. The fallback looks like
politeness toward old tests; it is load-bearing, because without it the entire
pre-existing double population goes inert *silently* — every one of those cells
still passes.

## The gate caught a cross-package guard

`go test ./...` (in full, per the #9246 blast-radius rule) failed in
**`pkg/cli`**, not `pkg/ipsec`:
`TestEveryCommandOutputDisplaySiteIsSanitizedOrDeclared6584` scans
`../ipsec/manager.go` by content and requires every `exec` fork on a display
path to sanitize or be **declared**. My new `runSwanctlSplit` was an undeclared
fork.

A package-scoped gate could not have seen it — the guard lives in a package the
diff never touched. Declared with a reason that is specific and true: the
exposure is unchanged from `runSwanctl`, because `GetSAStatus` still sanitizes
its rows at ingest and both callers escape stderr into their error path;
splitting the streams changed which buffer the parser reads, not whether raw
output reaches a terminal. The guard checks its entries for staleness in BOTH
directions, so a vague entry would be a liability.
