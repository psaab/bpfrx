# #7080 / #7081 / #7082 / #7084 — the four surfaces #6847 left behind

#6847 made `class-of-service classifiers inet-precedence` a **live**
behavior-aggregate classifier: it compiles, crosses the wire as
`inet_precedence_classifiers`, and the dataplane selects the egress queue and
loss-priority from the top 3 bits of the DS field. Four surfaces around it were
not extended with it. All four were filed from #6877's review as non-blocking.

The common thread is worth naming: **the enforced classifier was the one the
operator could not inspect, could not have a dangling reference reported for,
and could not be warned about when it blackholed** — while the two *inert*
classifier families beside it had all three.

## #7084 — the code-point grammar

Decimal `0..7` only, so both spellings Junos actually uses were rejected.

**Three-bit binary needs no table and can only widen.** `000` and `001` mean 0
and 1 under either reading; `010`/`011`/`100`/`101`/`110`/`111` read as decimal
are 10/11/100/101/110/111, every one already out of range. So no token that
compiles today changes meaning — the change is strictly "configs that were
refused now commit".

**The aliases are a transcribed table, and that is recorded at the table.** They
are the RFC 791 IP-precedence names — which `cs0`..`cs7` in `coSDSCPValues` are
the DSCP encoding of (precedence << 3). #7084 enumerated **seven** and omitted
the value-0 name; `routine` is included because a table missing an entry rejects
a legal config, which is the defect being fixed.

The risk asymmetry is what makes adding an entry on a transcription safe:

| outcome | consequence |
|---|---|
| an alias Junos does not use | **inert** — nobody types it |
| a **missing** alias | refuses a legal config — the defect being fixed |
| a **mis-mapped** alias | the only dangerous one |

and the 1..7 mappings are corroborated by the issue's independently written
list, so the dangerous column is the one with two agreeing sources.

## #7081 — the undefined-reference warning, and which field means "defined"

Every other CoS binding a unit can carry drew one. This was the only one that
committed silently.

**Definedness is read from `INetPrecedenceClassifiers`, the NAME list — not from
`INetPrecedenceClassifierDefs`.** `Defs` is populated only
`if len(classifier.Entries) > 0`, so a classifier defined with an empty or
wholly-rejected body is absent from it while being perfectly well defined.
Keying on `Defs` would report *"references undefined … classifier"* for a
classifier the operator can see in their own config — a confident wrong name,
which is worse than the silence being fixed.

Cell **M4** binds that choice: switching the check to `Defs` reds
`TestDefinedINetPrecedenceClassifierDoesNotWarn_7081` and nothing else.

## #7082 — the T-4 blackhole warning

`classOfServiceClassifierQueueWarnings`' own doc comment promises the model
mirrors `build_cos_iface_config` *"exactly so the warning fires iff the
dataplane would have blackholed the code-point"*. With only the dscp and
ieee-802.1 arms, that sentence was **false** for every unit whose blackholing
classifier was the inet-precedence one.

`Defs` **is** the right source here, unlike #7081, because this arm needs the
ENTRIES to know which forwarding-classes are mapped. A classifier with no
entries maps no code-point and can blackhole nothing — which is exactly the nil
case the function already returns on.

## #7080 — the three operational surfaces

1. `show class-of-service classifier` rendered an enforced classifier as
   **"No class-of-service classifiers configured"**.
2. The `type` filter offered no value that could name it — and the formatter had
   no arm for it either, so the two halves had to move together.
3. `show class-of-service interface` printed the two bindings that are **not**
   steering traffic and omitted the one that is.

The `cos_summary` golden gains exactly **one** line and no other byte moves.
Classified before regenerating — a golden accepted without classifying its diff
launders a behaviour change.

## Two method notes

**M2 was a VOID cell on the first attempt.** Deleting the warning arm left
`"slices" imported and not used` — a build break, `ran=0`, which reports
identically to a clean run in any harness that only reads the failure count. Re-
run as `if false && …`, it reds 1.

**One of my own tests was wrong and would have passed against unfixed code.**
The #7082 cell originally asserted the warning text contained
`forwarding-class "VOICE"`, and passed — against a fixture that declared
forwarding-classes with a syntax that did not define them, so it was matching
the **undefined-class** warning rather than the blackhole one. The fixture now
uses `forwarding-classes queue <n> <name>` and carries a materialized-class
control, so warning unconditionally cannot satisfy it either.
