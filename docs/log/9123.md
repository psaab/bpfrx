# 9123 — the SNMPv1 agent-addr, and a comment that cited the opposite rule

- **Timestamp**: 2026-09-06
- **Action**: populate the v1 Trap-PDU `agent-addr` from the source address the
  trap will actually leave from, and correct the miscitation that justified the
  hardcode.
- **File(s)**: `pkg/snmp/agent_addr_9123.go` (new), `pkg/snmp/traps.go`,
  `pkg/snmp/agent_addr_9123_test.go` (new),
  `pkg/snmp/traps_version_3948_test.go` (call-site arity).

## The miscitation is the load-bearing part

`traps.go` said *"agent-addr is 0.0.0.0, per the RFC 2576 §3.1 SNMPv2->SNMPv1
mapping for a standard generic trap."* RFC 3584 (obsoleting 2576) puts that
translation in **§3.2** — §3.1 is the other direction — and its normative text is:

> If the translation occurs within a notification originator application, and
> the notification is to be sent over IP, the SNMPv1 agent-addr parameter SHALL
> be set to the IP address of the SNMP entity in which the notification
> originator resides. If the notification is to be sent over some other
> transport, the SNMPv1 agent-addr parameter SHALL be set to 0.0.0.0.

xpf is a notification originator sending over IP, so **the cited authority
required the opposite of what the code did.**

Consequence kept narrow: many receivers (net-snmp's `snmptrapd` among them) fall
back to the UDP source, so "the trap is dropped as malformed" is not established
and is not claimed. What is established is attribution — a receiver keying its
inventory on `agent-addr` files every link-up/down against node `0.0.0.0`.

No configured value was being discarded: `config.SNMPTrapGroup` carries only
Name, Targets, Version, Categories, and no `trap-options source-address` leaf
exists. Adding that Junos-parity leaf is a config-schema change with its own
blast radius and is deliberately not folded in.

## Two fixture defects this produced, both worth recording

**1. A flaky red I nearly shipped.** The first version located the agent-addr
with `bytes.IndexByte(pkt, tagIPAddress)`. `tagIPAddress` is `0x40`, and the
**v2c PDU carries a randomized request-id** — so roughly one full-package run in
three contained a `0x40` byte inside an integer and the check reported an
IpAddress TLV that did not exist. It passed alone and failed ~1 run in 3. A
flaky red is worse than no cell: it teaches everyone to re-run. Replaced with a
structural BER walk; six consecutive full-package runs clean.

**2. "Byte-identical" was the wrong control.** The v2c comparison first asserted
two builds were byte-identical. They are not, and not because of the change: the
PDU carries a random request-id, so it reported a difference for every target
including the empty one. The assertion is now the invariant that matters — v2c
carries no IpAddress TLV and its length does not vary with the target — plus a
reference arm proving the **v1** packet *does* vary, without which the v2c rows
are satisfied by a build that ignores the target entirely.

The walker's first version refused long-form BER lengths rather than guessing,
which is why the v2c message (`30 81 81`) produced a clear message instead of a
misparse. A decoder that guesses a length is a byte scan's unsoundness wearing a
parser's clothes.

## A guard made exercisable rather than excused

`net.IP` may hold an IPv4 address in a 4-byte **or** a 16-byte v4-mapped form,
and indexing the first four bytes of the mapped form yields `0.0.0.0` — the very
value this change exists to stop emitting. Inline as `ua.IP.To4()`, a mutation
removing that guard **survived**, because this platform returns the 4-byte form.

Split out as `ipv4Bytes9123` it can be driven with both forms directly and the
mutant dies. Whether a guard is reachable through its only caller today is a
different question from whether it is correct.
