# #9007 — a duplicate BGP neighbor address across two groups committed clean and rendered twice

- **Timestamp**: 2026-09-05
  - **Action**: rejected one BGP neighbor address appearing in two DIFFERENT
    `protocols bgp group` blocks within a single BGP instance, strict at
    commit and downgraded to a warning on the tolerant load / peer-sync
    paths.

    Re-verified at `2f80dc085` rather than inherited: the issue was probed at
    `9bb0e8f11`, and #9182 (the #8939 BGP flat-run series) landed on
    `compiler_protocols.go` in between. It still reproduced exactly.
    `configstore.CheckText` — the REAL commit gate — returned ACCEPTED with
    **0 warnings**, compiling two neighbors on one address (`peer-as`
    65002/65003, hold-time 90/30, secrets A/B), and `generateProtocols`
    rendered two `remote-as`, two `timers`, two divergent `password` lines
    and two `peer 192.0.2.1` BFD blocks.

    The password line is the sharp edge: the other divergences are
    misconfigurations an operator can eventually observe, but one of two
    secrets is selected by render order, silently, while `show` keeps
    reporting both groups as authored.

    **The first version of this fix was wrong, and an existing cell caught
    it.** The gate was keyed on the address alone and paired with a
    first-wins dedup at the renderer's `validNeighbors` construction.
    `TestSlotEscapeTable` went red with `configured in more than one group
    (G and G)` — the same group name twice. The compiler emits one
    `*BGPNeighbor` PER AST NODE, and a single authored neighbor can occupy
    several nodes: `set protocols bgp group G neighbor X` followed by `set
    protocols bgp group G neighbor X import PS` — ordinary flat-set
    authoring, and the shape the slot-escape fixtures themselves use —
    yields TWO entries for one peer, both in group G, one carrying the
    import policy.

    Measured against the pristine renderer, that shape emits a redundant but
    CORRECT stanza: a repeated `remote-as` line (which FRR accepts) plus the
    `activate` and `route-map … in` that only the second entry carries. The
    first-wins dedup DROPPED that second entry, silently deleting the
    route-map — a regression the symptom-shaped fix would have shipped. So
    the render dedup was reverted entirely and the gate narrowed to
    DIFFERENT groups. The renderer is deliberately left alone; the commit
    gate is the defense and the tolerant path warns.

    Scope: the gate partitions by BGP INSTANCE. The same neighbor address in
    two routing instances is legitimate (separate VRFs peering with one
    address is ordinary), so duplicates are sought only WITHIN one
    `BGPConfig`.

    Five PRODUCTION mutants, all killed, one per assertion arm: M9 (same-group
    repeats no longer exempt) reds the same-group control AND both
    slot-escape fixtures — the arm that proves the narrowing is load-bearing;
    M2 (gate unwired) reds the strict arm in both packages; M3 (lenient flag
    off) reds the #1960 no-new-rejection arm; M4 (instance partition
    collapsed) reds the cross-instance control; M5 (diagnostic drops the
    group names) reds the message arm. M4 first appeared to SURVIVE — the
    patch script had aborted on a non-unique anchor and left the file
    unwritten, and the result grep matched only `_test.go:` lines so a
    no-op run and a clean pass were indistinguishable. Re-applied scoped to
    the one function, it dies on the cross-instance control.

    The per-AST-node duplication is a separate, broader defect (it makes a
    plain two-line authoring sequence render a redundant `remote-as`); filed
    on its own rather than folded in here.
