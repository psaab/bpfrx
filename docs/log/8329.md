# 8329 — a source-NAT rule naming an undefined pool reported as armed

- **Timestamp**: 2026-09-02
  - **Action**: Verified the premises, then fixed by DELETION.
    `SourceNATRuleNotInstalledReason` short-circuited on a map miss and
    returned `""` (armed) for a rule naming an undefined pool, while the
    builder marks exactly that rule unusable with the token
    `missing_pool` (`nat_source.go:98-102`).
    The fix removes the early return, because the correct answer was
    already available: `SourceNATPoolUnusableReason` returns
    `"missing_pool"` for a nil pool, and a map miss yields exactly that
    nil. The short-circuit discarded a verdict the predicate was about
    to give, in favour of the one value meaning "nothing is wrong". So
    the renderer and the builder now share both the decision and the
    token rather than only the intent.
    Reachability asserted IN THE TEST, not in prose: `CompileConfig`
    (strict) refuses an undefined pool reference, so the branch is
    unreachable there and a strict fixture would pass on the broken code
    by never entering the state. The fixture compiles through
    `CompileConfigLenient` — the stored-config load and HA peer-sync
    path, i.e. a node that booted from disk or took a config from its
    peer, which is where a config arrives without strict re-validation.
    Three mutations, three cells, three diagnostics: restoring the early
    return reds the primary cell; dropping the empty-pool-name guard
    reds the interface-mode control (confirming that arm is load-bearing
    — conflating them would disarm every interface-mode rule, a far
    larger population); returning `missing_pool` unconditionally reds
    the defined-pool control.
    No separate doc file describes this composition — its module
    documentation is the file's own header comment, which this change
    extends with the reachability argument.
