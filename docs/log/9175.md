# #9175 — `appliedDigest` was never invalidated, so a promote/fail/re-promote flap read as converged

Base: `239440c36471fe3e25f09440e228bcb72052e710` (`origin/master`).

## Re-verified at the base commit

The issue's own three-step sequence, driven through the REAL daemon apply path
(`pkg/daemon/applied_digest_failed_apply_9175_test.go`) rather than through the
store API, because the defect is that nothing CALLED an invalidator:

```
FAIL TestPromotionFlapDoesNotFalselyConverge9175
FAIL TestFailedApplyClearsTheAppliedMarker9175
PASS TestSuccessfulApplyKeepsTheAppliedMarker9175       (control)
PASS TestCapturedDigestStampSurvivesASuccessfulApply9175 (control)
PASS TestFailedApplyWithNoStoreDoesNotPanic9175          (control)
```

| step | active | `ActiveApplied()` at base | |
|---|---|---|---|
| 1 | A | `true` | A applied |
| 2 | B | `false` | B promoted, apply failed — conservative, CORRECT |
| 3 | A | **`true`** | A re-promoted, apply ALSO failed — **falsely converged** |

Source confirmation at the same commit: `MarkActiveApplied` (`store.go:917`) and
`MarkAppliedDigest` (`store.go:972`) were the digest's ONLY writers, and the only
clear was the `active == nil` arm inside `MarkActiveApplied`. Nothing unrecorded
a success.

The field comment (`store.go:373-374`) asserted the invariant the defect
violates: *"a stale value can only make the shortcut MORE conservative … never
falsely converged"*. That is true for a FORWARD sequence — every promotion moves
the active text away from the stamped digest — and false for RE-PROMOTION of a
text that already applied once in this process, because the leftover digest
matches the active text again.

Distinct from what `TestActiveApplied_TracksPromotionVsApply` (#4957) covers:
that cell marks B applied before re-promoting A, so the marker has MOVED and the
check is correct. The defect needs B's apply to FAIL, which is the row no
existing cell drives.

## Remedy

`Store.InvalidateAppliedDigest()` clears the marker, and `applyConfigLocked`
calls it from a deferred close over a NAMED return:

```go
func (d *Daemon) applyConfigLocked(ctx context.Context, cfg *config.Config) (retErr error) {
	defer func() {
		if retErr != nil && d.store != nil {
			d.store.InvalidateAppliedDigest()
		}
	}()
```

**Why there and not at each caller's failure branch.** `applyConfigLocked` is
the single choke point every apply in the daemon goes through — the
boot/background path (`applyConfigUnderSem`), the feed publication path
(`applyActiveConfigResult`), the commit path (`applyAndSyncCommitted`), the peer
config-sync path (`syncAndApply`) and the commit-confirmed auto-rollback. Putting
the clear in the callers is four sites today and a fifth silently missing
tomorrow; putting it in the deferred close covers every early return inside the
function too — the #2926 context abort, the factory-reset refusal, the test seam
— without anyone having to remember.

**Why the clear is unconditional** rather than keyed to the failing text: the
failing path does not always hold a digest (a context abort bails before any
capture), and being wrong in THAT direction is the falsely-converged state this
exists to prevent. Being wrong in the other direction costs one idempotent
re-apply — the same cost #4957's shortcut avoids, and the correct side to be
wrong on.

## A prior decision spoke, and was answered rather than edited

`pkg/refactoraudit.TestEveryAppliedMarkerSiteIsClassified7343` red on the new
`s.appliedDigest = ""` assignment: *"an unreconciled count means a marker is in
the tree with nothing checking it"*. That registry is keyed on
(file, statement, count) deliberately, and the correct response is to CLASSIFY
the new site, not to loosen the count. The `pkg/configstore/store.go` entry now
declares 2 and its `Why` records what the second one is — a zero-reset, the safe
direction, and the thing that makes the existing caller contract sufficient.
