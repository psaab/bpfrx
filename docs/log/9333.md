# #9333 — an undecodable varbind was SKIPPED, so a GET got a noError response with fewer varbinds than it asked for

- **Timestamp**: 2026-09-06
  - **Action**: made every malformed-varbind shape in `decodePDUFields` an
    ERROR, so the whole PDU is discarded instead of answered with a short
    variable-bindings list.
  - **File(s)**: `pkg/snmp/agent_ber.go`,
    `pkg/snmp/ber_oid_subid_bound_9133_test.go` (the #9133 pin, updated
    deliberately), `pkg/snmp/README.md`

  - **The decision the issue asked for, and the RFC's view.** Three remedies
    were on the table: drop the varbind, return `genErr`, or return the varbind
    with an error status. The standards settle it. A varbind this loop cannot
    decode makes the message unparseable, and RFC 1157 §4.1 and RFC 3416 §4.1
    both say an unparseable message is DISCARDED — there is no "malformed
    varbind" response in either. `genErr` and a per-varbind exception both
    presuppose a decoded OID to name, and the whole problem is that there is
    not one. RFC 1157 §4.1.2's arity requirement is what rules out the fourth
    option, silently answering short.

    Consistency confirms it: `decodePDUFields` ALREADY returns an error for a
    malformed request-id, error-status, error-index or varbind-list header, and
    every caller turns that into a dropped datagram. The six varbind arms were
    the only inconsistent ones in the function.

  - **Six arms, not five.** The filing said five `continue`s; there are five
    `continue`s AND a `break`, and the `break` is the worst of them: it dropped
    that varbind and every one after it, so the response could be short by an
    arbitrary number rather than by one.

  - **What is NOT changed, and it is asserted twice.** A varbind carrying no
    value TLV at all (`SEQUENCE { OID }`, 5 bytes) is well-formed, reaches none
    of the six arms, and is still accepted with its OID delivered. #6551's
    densest-packing bound depends on it
    (`TestWireVarbindByteFloors_6551`), and a gate that rejected it would be
    levelling down rather than fixing anything — so
    `TestEveryMalformedVarbindShapeIsAnError9333` carries it as an explicit
    reference arm too.

  - **My own #9133 pin fired, and it was updated rather than deleted — which is
    what its own failure message demanded.** It pinned the SKIP behaviour and
    said: "if that is now the behaviour, this pin is stale and the arity concern
    is resolved — update it deliberately rather than deleting it." Both of its
    vectors are kept, and so is the split between them: `truncated-continuation`
    reaches this path at master too, while `overflowing-subidentifier` reaches it
    only because of #9133's decoder bound. That split is what made
    "pre-existing" a measured claim rather than an argument, and it is still
    worth keeping now the remedy has landed.

  - **The positive control the discard assertion needs.** "No response" is
    satisfied by an agent that answers nothing, so the cell first drives the
    SAME two-varbind shape with both OIDs well-formed and asserts a response
    carrying TWO varbinds. Without it the discard arms would pass against a
    broken agent.

  - **Mutation table** (`go test -count=1 -timeout 900s ./pkg/snmp/`; each
    mutant confirmed BUILT and APPLIED before scoring). Two of the seven
    survived, for DIFFERENT reasons, and separating them is the point:

    | # | mutation | result |
    |---|---|---|
    | U1 | short body `continue`s again | KILLED |
    | U2 | wrong first tag `continue`s again | KILLED |
    | U3 | truncated OID value `continue`s again | KILLED |
    | U4 | undecodable OID `continue`s again | KILLED (5 cells, incl. both end-to-end vectors) |
    | U5 | unreadable length `break`s again | **SURVIVED — proved UNREACHABLE** |
    | U6 | OID length-decode error `continue`s again | **SURVIVED, then KILLED** — a gap in my table, not in the code |
    | U7 | OVER-REACH: the value-less varbind rejected too | KILLED (5 cells, incl. the shipped `TestWireVarbindByteFloors_6551`) |

    **U5 is unreachable BY CONSTRUCTION, and the proof is in the code rather
    than in a fixture.** `berDecodeHeader` (called on the same slice, just
    above) and `berEncodedLen` compute the SAME quantity from the SAME bytes,
    and the header's check is strictly stronger: if it succeeded then
    `1+lenBytes+length <= len(remaining)`, which is exactly what
    `berEncodedLen` returns. No input can make the guard fire. The arm is kept —
    and kept as an ERROR rather than the original `break` — because the two
    functions are only equivalent while they stay in lockstep, and a `break`
    degrades silently if they ever diverge while an error degrades into the
    discard the rest of the loop already performs.

    **U6 survived for the opposite reason and was a real gap.** My table's
    "OID value truncated" case used length `0x7f` — a VALID short length that
    overruns the body — which hits the truncation arm, not the length-DECODE
    arm. Three vectors that `berDecodeLength` itself refuses (`0x80`,
    numBytes 0; `0x85`, numBytes 5; `0x82` with the length bytes truncated)
    reach it, and were added.

    I nearly recorded both survivals as the same verdict. They are not: one is a
    proof about the code, the other was an absence in the test.

    **U7 is the levelling-down guard.** It reds the SHIPPED
    `TestWireVarbindByteFloors_6551` as well as my own reference arm, which is
    what says the value-less acceptance is a contract rather than an accident.
