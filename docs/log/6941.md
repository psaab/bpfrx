**The routing half is confirmed**: routing does create `wg0` from the
interface-level record. The issue's characterisation of the unit device as "the
mode-independent tuntap anchor" is **wrong in the general case** — a unit tunnel
under an interface-level WG *inherits* `mode wireguard` unless overridden, and
the mode-WG branch returns before the anchor branch, so `wg0u3` is normally a
second persistent WG TUN, not a tuntap anchor. It is an anchor only when the
unit explicitly overrides the mode (e.g. `mode gre`).

## Which side is wrong — the question the issue asks

`ep.Tunnel.Name` and `TunnelNameMap[ep.Name]` were compared across six tunnel
shapes (interface-level GRE, per-unit GRE, interface-level GRE + unit tunnel,
interface-level WG plain, interface-level WG + unit tunnel, IPIP). They
**agree in every shape except the divergent one**.

But "make the endpoint use `tunnel.Name`" is NOT a safe fix, and the reason is
the fact that settles the question: **the unit's ADDRESSES are on the unit
device too**. `wg0.3`'s `10.66.3.1/24` lands on `wg0u3`; `wg0` carries none.
So the dataplane is INTERNALLY CONSISTENT — endpoint device == address device
== `wg0u3` — and forcing the endpoint onto `wg0` would attach the WireGuard
engine to an addressless device. That is a fix matched to the symptom's shape
that breaks the datapath.

**Conclusion: the dataplane side is not wrong.** What is anomalous is that
routing materialises `wg0` from the interface-level record while no emitted
endpoint binds to it — an orphan device — and #6861 already documents the
dataplane's resolution as the production authority for endpoint→device binding
(`compiler_validate_strict_tunnel_ipip.go`, `emittedTunnelDeviceNames`).

## The larger defect found while settling it

The root is that `EmitTunnelEndpointNames` emits an endpoint whose **key** comes
from one object (the lowest unit) and whose **payload** comes from another (the
interface-level tunnel). The device divergence is one consequence. The other is
worse and is not in the issue:

For the supported per-unit-peer shape (`tunnel_perunit_deepcopy_test.go:123`,
interface-level WG peers plus per-unit peers), measured:

```
iface.Tunnel  peers=1 [cccc]
unit 1 tunnel peers=2 [cccc aaaa]
unit 2 tunnel peers=2 [cccc bbbb]
ENDPOINT ref="gr-0/0/0.1" tunnel.Name="gr-0-0-0" peers=1 [cccc]
```

`pkg/dataplane/userspace/tunnels.go:142` is the ONLY path from config to the
dataplane for WG peers, and it reads the endpoint's `TunnelConfig`. So the
per-unit peers **never reach the dataplane**. #3898 deep-copies per-unit
`WgPeers` precisely so each unit owns its own set; nothing then consumes them.
The pattern is tested at the config layer and non-functional at the runtime
layer, and it fails silently — the tunnel comes up and only the
interface-level peers can handshake.

## Not done

No fix in this pass. A device-only change is refuted above; the coherent repair
is a peer-set decision (merge every unit's peers into the single
interface-level endpoint, or reject the shape), which is a design change to
WireGuard per-unit semantics rather than an agreement patch, and is larger than
this issue as filed.
