## The defect

The #8965 preflight exists to stop an operator stranding a running cluster by
changing its control endpoint. It **passed the deletion case**:

```go
if want == "" || have == "" || want == have { return nil }
```

`have != "" && want == ""` was admitted. The comment's justification — *"unset
on either side means there is no live endpoint to strand"* — is true for
`have == ""`, an **addition** where the heartbeat has not started, and **false**
for `want == ""`, a **deletion**, where the live endpoint being stranded is
precisely the one being removed. Two of the four combinations were decided by a
sentence that covered one of them.

## Severity is set by the fabric, not by the deletion

- **With a fabric configured**, `clusterSyncTransport` falls back to it, so the
  config push still has a transport and the deletion propagates. The heartbeat
  dies on both nodes — what the operator asked for — and there is no partition.
- **On a control-link-only cluster** (which the strict compiler gate accepts)
  there is no fallback: no heartbeat **and** no sync transport. That is exactly
  #8965's apply-then-push partition, and it is durable because the peer never
  learns why. Reachable with `delete chassis cluster peer-address` + `commit`.

## The remedy

`controlEndpointDecision8965` is now total over the four combinations, with the
fabric fallback passed in as a third argument. That argument is not decoration:
whether a fallback exists is a property of the **candidate config**, not of the
two addresses, so the decision could not stay a two-string function *and* be
total.

### The predicate mirrors the sync-START condition, not the transport label

`fabricFallbackConfigured9178` requires `FabricInterface != "" &&
FabricPeerAddress != ""` — the condition `daemon_ha_sync.go:890` actually gates
the sync goroutine on.

This was found by the acceptance cell, not by reading. The first version of that
cell derived the runtime's answer from `clusterSyncTransport`'s **label**
(`transport == "fabric" && peer != ""`) and RED on the `FabricInterface == "",
FabricPeerAddress != ""` row. The label is not the answer: `clusterSyncTransport`
returns `"fabric"` whenever the control link is incomplete — *including when the
fabric is incomplete too* — so a gate reading it would have reported a transport
that never starts, and admitted a deletion into a config with no sync at all.
The cell was correcting me, not the code.

## Acceptance table

`TestControlEndpointDecisionIsTotal9178` enumerates all four `(have, want)`
combinations × the two topology columns the issue asked for (control-link-only
and fabric-configured) — ten rows. A gate that returns nil for two of four
inputs is the defect, so the enumeration is the test.

The load-bearing rows are the two that must still be **ALLOWED**: `deletion with
a fabric fallback`, and the unchanged/addition rows. Without them, "refuse every
deletion" satisfies the refusal rows and breaks a legitimate operation —
consistency achieved by levelling down.

| Cell | Asserts |
|---|---|
| `TestControlEndpointDecisionIsTotal9178` | the ten-row enumeration |
| `TestDeleteRefusalNamesTheRemedy9178` | the refusal names the procedure, and is NOT the move text — whose remedy ("set the new address on BOTH nodes") is meaningless when there is no new address, and would send an operator looking for a value that does not exist |
| `TestFabricPredicateMatchesTheRuntimeFallback9178` | the commit-time predicate and the runtime start condition agree on all four fabric shapes |
| `TestThePreflightPassesTheFabricColumn9178` | **binds the wiring**: the other cells call the decision directly, so they stay green if the preflight stops passing the column — it would pass the zero value, refusing every deletion including the safe one |

### One existing row was corrected, not deleted

`{"candidate leaves it unset", "10.99.0.2", "", false}` in the #8965 table
scored the deletion as allowed, quoting the justification above. That is the
defect, expressed as a test. The row now carries the fabric column and splits in
two; the rest of the #8965 table is unchanged, because the rest of its reasoning
is still correct.
