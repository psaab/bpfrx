# #9067 — a TTL-only DDNS change never propagated

## Two defects, different permanence

**Cloudflare (permanent).** `UpsertLease` returned on a CONTENT match alone, so
a TTL-only edit was never written. Every later refresh — including the
operator's explicit `request system dynamic-dns update` force latch — re-entered
the same early return. `cfRecord.TTL` was already parsed: the datum was
available and simply unread.

**Change detection (delay, all backends).** `changed := addr != rt.lastAddr`
did not treat a TTL edit as a change, so nothing republished promptly on ANY
backend — including Route 53, whose own backend comparison is correct.
Convergence waited for the forced-refresh floor, 24h by default.

Both defeat the same operator intent, which is what makes the delay a defect and
not merely a latency: a shorter TTL is bought precisely so a change propagates
soon. Waiting a day for the TTL itself to land inverts it, and the harm arrives
later — at the planned renumber the shorter TTL was bought for.

It is silent throughout: no error, no warning, and `show` reports the CONFIGURED
TTL.

## Census first, per the dispatch

Eight backends. Only **two** do a read-compare-skip at all:

- `backend_route53.go` — `live.found && live.ttl == ttl && sameValueSet(...)`.
  Correct, and the model for the fix.
- `backend_cloudflare.go` — content only. The defect.

The other six (`bind`, `duckdns`, `dyndns2`, `generic`, `http`, `rfc2136`) do no
live-state read before writing, so the TTL rides the wire op every time and none
can exhibit this. Checked by reading each `UpsertLease`, not inferred from the
TTL mention count — `rfc2136` mentions TTL fourteen times and always sends.

So the class has exactly two members and one is already right. That is worth
recording: the shape "three do X and one does not" was not what this turned out
to be.

## Fix

**Cloudflare:** compare TTL alongside content. A content match with a differing
TTL records that row's id and PATCHes it — falling through to the POST would
create a DUPLICATE at the name, which is worse than the un-propagated TTL.

**Change detection:** `surfaceAState.lastTTL` records the TTL of the last
successful publish; a delta marks the scope changed.

Two details are load-bearing and both were mistakes I made first:

1. **Compare the NORMALISED TTL.** `TTL <= 0` means "use `defaultDDNSTTL`", and
   the publish normalises it that way. My first version compared the raw field,
   which would miss an explicit→unset edit and invent a change on
   unset→explicit-default. `normalizeDDNSTTL` is shared with the publish path so
   the two cannot disagree about what the TTL IS — two spellings of one
   normalisation is exactly how a comparison ends up checking a property the
   system does not act on.
2. **Store the NORMALISED TTL.** `lastTTL == 0` means "not published in this
   process" and suppresses the comparison, so a scope re-adopted after restart
   (the durable store records the address, not the TTL) is not republished
   spuriously. Storing a raw 0 for a scope published with the leaf unset is
   indistinguishable from "never published" and disables the comparison for that
   scope **permanently** — re-entering #9067 through the fix.

## Mutation matrix

| # | Mutant | Result | Killed by |
|---|--------|--------|-----------|
| M1 | Cloudflare: content-only early return | **KILLED (2)** | `…TTLOnlyChangePropagates`, `…LeavesForeignRowAlone` |
| M2 | Cloudflare: drop the early return entirely | **KILLED** | `…UnchangedContentAndTTLStillSkips` |

| M4 | the FAKE stops applying the PATCH TTL | **KILLED (2)** | both Cloudflare TTL cells |
| M5 | revert the change-detection delta | **KILLED** | `…TTLOnlyChangeRepublishesPromptly` |
| M6 | `changed = true` unconditionally | **KILLED (2)** | `…UnchangedTTLStillSkips`, `…ComparisonIsNormalized` |
| M7 | compare the RAW TTL | **KILLED** | `…ComparisonIsNormalized` |
| M8 | store the RAW TTL on publish | **SURVIVED → then KILLED** | `…UnsetThenExplicitTTLRepublishes` |

**M4 is a mutant of the FIXTURE, and it belongs in the matrix.** The fake's
PATCH handler dropped the TTL, so my first run failed against a *correct* fix —
the cell was measuring the fake. Had the assertion been weaker it would have
passed while proving nothing. Mutating the fixture is how that stays true.

**M8 is the finding.** Storing the raw TTL survived every cell I had, because
each of them published with an explicit non-zero TTL where raw and normalised
coincide. The case it breaks is the most ordinary edit there is: a scope that
never set a TTL, then does. That cell now exists.

M2 and M6 are the over-broad-fix detectors in each half — a fix that simply
wrote every time would satisfy every positive cell while turning an idempotent
no-op path into unconditional provider traffic, and on a rate-limited API into
failures.
