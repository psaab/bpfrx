# #7758 — RFC 6040 §4.1 ingress on the WG host-originated encap path

- **Timestamp**: 2026-09-03
- **Action**: Made `wg_control::encap_and_send` copy the inner DS byte onto the
  outer header, matching the transit encap path and GRE. Corrected the docs that
  reported the encap direction as simply DONE.
- **File(s)**: `userspace-dp/src/afxdp/coordinator/wg_control/{sock,dispatch,attempt}.rs`,
  `userspace-dp/src/afxdp/coordinator/wg_control/wg_control_tests.rs`,
  `userspace-dp/src/afxdp/wg/{mod,tests}.rs` (test-fixture visibility),
  `userspace-dp/src/afxdp/wg/dscp.rs` (module doc),
  `docs/wireguard-interop.md`.

## The finding was a boundary error, and it is worth recording as a method note

The issue said WireGuard "implements only the decap half". I verified that inside
`wg_control/` — the directory the issue names — and it held: the §4.2 decap
combine is live there and the send path ends at a bare `send_to`.

It is false anyway. **WireGuard has TWO encap paths**, and the transit one
(`frame/wg.rs:516`) has copied the inner DS byte since #2303, using the same
`gre::inner_tos_byte` helper GRE uses.

Every check inside the named boundary was sound, and none of them could see that
the boundary was wrong. Positive controls do not help here either: a control
proves the PATTERN can match, and says nothing about whether the CORPUS is right.

The cheap counter-check is to **search for the MECHANISM across the whole crate
before accepting a scoped absence** — one `grep -rn inner_tos_byte userspace-dp/`
or `grep -rn '#2303'` returns `frame/wg.rs` immediately, where a scoped search
for the feature's absence in `wg_control/` never can.

## What was actually wrong

The two WG encap paths disagreed. The transit path (inner arriving on AF_XDP)
copied; the host-originated path (inner read from the wgN TUN) did not. So the
same inner marking produced a different outer DSCP depending on which path a
packet took — an internal routing detail no operator can see, while a downstream
classifier sees WG traffic marked or unmarked accordingly.

That restates the harm without the deployment survey the original framing needed:
it is an internal inconsistency provable from the tree, not a question about
whether anyone classifies on WG outer DSCP.

## Shape

`wg_send_to` takes the outer TOS as an explicit `Option<u8>`. `None` is the
pre-existing `send_to` path byte-for-byte; `Some` goes through `sendmsg` with
`IP_TOS` / `IPV6_TCLASS` ancillary data, per-datagram because the value is the
inner packet's and varies per packet.

**The cmsg level follows the destination's WIRE family, not the socket family.**
A v4-mapped destination on the dual-stack AF_INET6 socket emits an IPv4 datagram
and takes `IP_TOS` — mirroring the receive side, whose own doc says `IP_RECVTOS`
"governs both native v4 and the v4-mapped datagrams the dual-stack v6 socket
delivers". This was NOT taken on trust: the test asserts the DS byte as RECEIVED
on a loopback round trip, so a wrong level choice reds rather than silently
sending unmarked.

**Exemptions are explicit at the call site.** Handshake initiation, handshake
response, cookie reply and keepalive carry no inner packet, so they pass `None`.
The parameter is explicit rather than defaulted so a NEW send site has to decide
instead of inheriting either answer.

**No fallback on cmsg rejection.** An error returns and the existing caller
counts `transport_send_errors` and records a tunnel exception carrying the errno,
so a rejecting kernel is diagnosable as `wg_socket_send:EINVAL`. A silent fall
back to an unmarked send would be a safety net no test can reach — a claim
written into inert code — on a path whose sockopts have been stable for two
decades and whose kernel floor is 6.18.

## Validation

Two cells, both mutation-verified, and each mutation reds ONLY its own cell:

| mutation | expected red | result |
|---|---|---|
| `encap_and_send` passes `None` (the pre-#7758 tree) | the copy cell | RED |
| a keepalive passes `Some(0xB8)` | the exemption cell | RED |

The copy cell asserts the DS byte **as received on the wire** rather than the
helper's return value — the helper was never the missing part, and a cell calling
`inner_tos_byte` directly would have stayed green through the entire defect. Its
second assertion pins the AGREEMENT between the two paths
(`got == inner_tos_byte(&inner, AF_INET)`) rather than a literal, so it still
fails if either path later changes what it means by the inner DS byte.

The exemption cell drives the real `send_keepalive`, not `wg_send_to`, because
the claim is about the call site's choice.

the same rustfmt-diff count as master (the tree at large is not rustfmt-clean and
was left alone).
