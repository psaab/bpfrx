# 9047 — the rate drops userspace silently while the totals include it

## What the external review got right, and the one thing it got wrong

The dismissal read:

> Counters are cumulative; the both-samples gate is fresh-series spike
> suppression — treating a missing side as zero would attribute the full
> cumulative to one window. **No coherent distinct fix exists.**

The first half is correct and is preserved here — `TestDroppedComponentIsNotFoldedInAsZero9047`
pins it, and the mutant that folds the missing side in as zero reds two cells.
Auditing a dismissal is what found the rest.

"No coherent distinct fix exists" is false, and the file itself says so. #7422
row 10 already decided that a counter group which could not be contributed must
carry a NOTE rather than silently render 0, "a value indistinguishable from a
genuinely idle interface" — and it fixed the two sibling groups ON THE STRENGTH
of the userspace group already having one. The RATE path then went on dropping
that same group silently. The third option is neither "add the cumulative" nor
"drop it silently": it is drop it and say so.

## Why the two gates are NOT reconciled to match

`displayTrafficCounters` gates on `curr` alone; `snapshotTrafficDeltas` gates on
both. In any window where prev lacks a source and curr has one, the TOTAL
includes userspace bytes while the RATE does not.

They answer different questions and are both right. A total is a single-sample
fact and is correct to include userspace as soon as curr has it. A rate needs
two samples and cannot be computed without both. Forcing the total to drop
userspace whenever prev lacked a source would make the TOTAL wrong in order to
fix a cosmetic disagreement — a worse trade. The honest reconciliation is to
report the disagreement, which is what the flag does.

## The false-positive the note has to avoid

Reporting whenever the gate declines would put a permanent note on every
kernel-only interface — one that has no userspace source to drop and never will.
A note that fires on every window is one operators learn to skip, which disarms
it for the window that matters. So the flag is raised only when `curr` HAS a
userspace source and `prev` does not: a real gap, not a permanent state.
`TestNoNoteWhenTheInterfaceHasNoUserspaceAtAll9047` pins that, and the
report-always mutant reds it.

## When the gap actually occurs

`hasUserspaceTrafficSource` is false at the first sample after helper start,
after a helper restart, and whenever the status read failed — that path sets
`Userspace` to a struct carrying only a `StatusNote`, with no bindings and no
counters, so the gate declines. None of those is rare, and all three are exactly
when an operator is watching `monitor interface`.

## Mutation matrix

    never report the drop (pre-#9047)     -> "dropped from the rate and NOT reported"
    report ALWAYS on decline              -> "kernel-only interface reported"
    fold the missing side in as zero      -> 2 cells red (the spike the dismissal warned of)
