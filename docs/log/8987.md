# #8987 — a live control-INTERFACE move partitions the cluster, ungated

Split out of #8965, which fixed the peer-ADDRESS half and recorded this one as
uncovered — *"exactly the kind of half nobody re-opens"*.

## The defect

`applyConfigLocked`'s step 20 stops cluster comms and restarts them on the new
control interface; only then does the push to the peer run, over a transport
just rebuilt somewhere the peer is not listening.

Nothing heals it, and each link in that chain was checked rather than assumed:
`QueueConfig` no-ops on a nil connection so the push fails **silently** rather
than erroring the commit; the #5863 reconciler returns early on
`!syncPeerConnected`; that flag is set in exactly one place (the session-sync
connect callback), so it cannot bootstrap a mismatch in which nothing is
connected; heartbeats carry no config. Both nodes end up durably configured, so
retry and reboot **reproduce** the split rather than repair it.

## Why #8965 could not fix it, and what changed

#8965 stated the blocker precisely: the manager kept no RUNNING value for
`control-interface`, so a gate would have compared **config to config** —
unable to distinguish "the operator is changing it" from "this is what it
already was", and liable to fire on a peer-synced text.

`StartHeartbeat` never received the interface. `startHeartbeatWithRetry`
resolves it to a local IP (`resolveClusterInterfaceAddr`) and passes only the
IP, so the manager recorded `hbLocalAddr` / `hbPeerAddr` / `hbVRFDevice` and no
interface name.

The interface is now the fourth `StartHeartbeat` argument, recorded as
`hbControlIface` beside the other three and carried across `RestartHeartbeat`.
Making it a **parameter** rather than a setter is deliberate: a setter is a step
someone can forget, and the value would then silently describe a different
heartbeat than `hbLocalAddr` does.

### Two plausible wrong sources, both rejected with a reason

- **`m.controlInterface`** — also an interface name, right there, and wrong:
  `UpdateConfig` overwrites it on every config apply, so it tracks the config.
  A gate reading it compares the candidate against itself. This is the mutant
  that survived the first matrix (M2) — see below.
- **`hbLocalAddr`** — usually moves when the interface does, but an operator who
  moves the control link to another interface and carries the same address
  across leaves it unchanged. A gate keyed on it waves through exactly the move
  that partitions the cluster.

## Peer-sync safety was MEASURED, not inherited

#8965's argument does not transfer, and assuming it did was the trap #8987
names for this path. #8965 is safe because `PeerAddress` is **per-node**: each
node's config names the other's address, so a synced text compiles to the local
node's own value.

`control-interface` is safe for a **different and stronger** reason, read off
the shipped cluster config rather than reasoned about: in
`docs/ha-cluster-userspace.conf`, `peer-address` sits INSIDE `groups node0` /
`groups node1` (lines 9, 38) while `control-interface em0` sits OUTSIDE them
(line 73) — it is one shared value, so a synced text carries the identical
string and the comparison is trivially equal. Both leaves are read by the same
`nodeVal` call in the same container (`compiler_system.go`), so a config that
DOES scope it per node still expands for the local node exactly as
`peer-address` does. The property holds either way; the reason differs.

## All three apply paths

`commitAndApply`, `syncAndApply` and `commitConfirmedAndApply` all reach
`applyConfigLocked`. The gate is wired at each, beside its #8965 sibling.

### M2 is the finding

M2 is the plausible wrong gate — the one #8965 explicitly declined to ship — and
**it survived the first matrix.** The cell that describes that mistake by name,
`TestRunningControlInterfaceIsTheHeartbeatsNotTheConfigs8987`, asks the Manager
for both values and then calls `controlInterfaceDecision8987` itself. It proves
the accessor is right and the decision is right while **never exercising the
wiring between them**, so swapping the preflight to the wrong accessor left it
green.

That is the same failure #8965's own split-seam comment warns about — "a seam
that bypasses the thing under test is worse than no seam, because it reads as
coverage" — arriving one level up. The fix is a cell that drives the real
preflight with a real `Manager` whose running and config-tracked interfaces
**disagree**, which is also the exact live state at commit time: `UpdateConfig`
has taken the candidate's value while the heartbeat is still bound where it was.
It carries a both-directions control so it cannot be satisfied by a gate that
always refuses.

M5 is the over-broad-fix detector: a "fix" refusing every candidate would
satisfy the refusal cells, and reds only because the peer-sync no-op is asserted
separately.

M4's guard uses the **#8965 sibling as its control**: it asserts the address
gate is wired at exactly three functions before checking the interface gate is
wired at the same three. Without that, the cell could not distinguish "the
interface gate is missing from `syncAndApply`" from "`syncAndApply` was renamed".

## Docs

`docs/ha-no-hitless-restart.md` carried a parenthetical — *"Fabric /
heartbeat-transport / control-interface identity IS reconciled live … so only
the node-id / cluster-id identity is boot-baked"* — that was true and reassuring
for the wrong reason. Being reconcilable live is precisely what makes the
control tuple dangerous. Corrected in place, with a new section documenting both
gates, the no-healing chain, and the two different peer-sync arguments.
