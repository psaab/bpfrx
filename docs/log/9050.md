# 9050 — the render belt deferred auth-token safety to a gate the lenient path downgrades

- **Timestamp**: 2026-09-06
- **Action**: give the FRR render path its own auth-token check, and omit rather
  than emit a secret that is not a single vtysh token.
- **File(s)**: `pkg/frr/auth_token_9050.go` (new),
  `pkg/frr/protocols_render.go` (8 emit sites),
  `pkg/frr/auth_token_9050_test.go` (new), `pkg/frr/frr_test.go` (one prior
  assertion revised).

## The seam, in the code's own comments

`frrTokenUnsafeIndex` (pkg/config) rejects `' '`, `'\t'`, `< 0x20`, `0x7f`.
`sanitizeFRRValue` rejects only `< 0x20` / `0x7f` — **and maps them to `' '`**.
Its own doc defers the whitespace case to "the commit gate", and
`compiler_uniformgates_log_feed_routing.go` downgrades exactly that gate to a
warning on the tolerant path. So on `Store.Load`, HA `Store.SyncApply`, or a
confirm-rollback recompile:

```
 neighbor 10.0.2.1 password my secret pass
```

A TAB is sharper still: `sanitizeFRRValue` converts it **into** a splitter, so
the belt manufactures the shape it exists to prevent. And the strict validator's
stated rationale — *"the render path strips control chars and the offending line
stays inert / single-line"* — is false for a literal space and false in the worse
direction for a tab.

A new commit cannot introduce this (`CheckText` and `Store.Commit` hard-reject);
the value must already be persisted — a pre-#2889 config, an older rollback slot,
or a peer on an older build.

## Why OMIT rather than emit

What FRR does with a split line was not measured and is not asserted. Both
possibilities are bad and they differ in **blast radius**: either it truncates to
the first token — a silently weakened secret — or vtysh refuses the line, which
by this repository's own precedent for a bad router-id **fails the whole
frr-reload**, taking down every routing protocol on the box rather than one
adjacency.

Omitting the single auth line confines the damage to one adjacency, which then
fails to authenticate loudly, in FRR's own logs, at the layer that owns that
decision. The neighbor itself is still configured — its own cell asserts that,
because dropping the whole neighbor would be a larger outage than the defect.

Not quoting it: whether vtysh accepts a quoted operand at each of the eight sites
is unmeasured, and guessing wrong reproduces the reload failure this avoids.

The warning names the protocol and the secret's length and **never the value** —
this is an auth secret and the log is not 0640.

## A prior decision, revised rather than deleted

`TestGenerateProtocols_NewlineFreeTextDoesNotInject` (#1798) required that the
sanitized password **was** emitted, as `password pw agentx`. That satisfied
#1798 — no injected line — while leaving a value vtysh reads as two tokens: the
belt collapsed a newline into a space and thereby manufactured, for an auth
secret, exactly the splittable line this issue is about.

For a description or an as-path regex a space is legitimate and that cell's other
assertion stands unchanged. For an auth secret it is not. The password assertion
is inverted, with the reasoning written into it.
