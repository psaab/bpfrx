# #8992 — a fully elided stanza could not be deleted, and the error named the wrong thing

- **Timestamp**: 2026-09-05
  - **Action**: made the delete path see a fully-elided stanza, bounded so a
    packed RUN is refused rather than whole-node deleted.

    ```
    system master-password pseudorandom-function hmac-sha2-256;
      -> ONE node, Keys = [system master-password pseudorandom-function hmac-sha2-256]

    delete system master-password
      -> path not found: container "system" does not exist
    ```

    `deletePath` descends by looking for a CONTAINER whose Keys equal the path
    segment. In the elided spelling `system` is not a container — it is the
    first token of a leaf carrying the whole statement — so the descent finds
    nothing and reports the container absent while `show configuration` renders
    it on screen.

    **Four of the five test rows are controls, and each rules out a different
    wrong explanation.** Fully braced and child-elided already worked, so it is
    neither "delete is broken" nor "elision breaks delete". The genuinely-absent
    case gives a DIFFERENT message, so it is not the generic not-found path.
    And the elided-beside-a-braced-sibling row is the one that placed the fix:
    the descent SUCCEEDS into the sibling and fails deeper, so the error changes
    to `no node matching "master-password"` and the elided node is never
    examined — a fix in the not-found branch would have missed it entirely.

    **THE BOUND IS THE POINT, because this is the delete path.** A node's Keys
    can carry a packed RUN of several statements. Removing the whole node to
    satisfy a delete of one would silently take the others — the #3846
    fail-wide. Splitting the run is `consumeNodeKeys` work #8932 records as
    unfinished. So a run is REFUSED, with a message naming the situation and the
    workaround rather than falling through to "container does not exist" (the
    #9006 misdirecting-diagnostic shape). Verified: the two-statement run is
    left intact and `host-name` survives.

    **MY FIRST FIXTURE WAS NOT A CONFIG, AND IT READ AS THE FIX NOT WORKING.**
    I probed with `system master-password ascii-text "x"`, but `master-password`
    declares only `pseudorandom-function` — so the schema walk stopped at an
    unknown token, the helper returned false for the right reason about the
    wrong input, and I measured "#8992 is still live" against an invalid
    fixture. Fourth instance this campaign of a synthetic config that is not a
    config; the others were in the #8939 generator.
