# 9157 — `tunnel keepalive-retry` is the only untyped leaf among four typed siblings

- **Timestamp**: 2026-09-07
- **Issue**: #9157 (finding key V022)
- **Base commit**: `566d132b0` (`origin/master` at the time of the re-measurement)

## Channel measured

The four config channels disagree, and the issue's own table labelled its
measurement "the strict commit gate" while the layer that actually discriminates
is the typed-leaf schema walk. Re-measured, per channel:

| channel | `keepalive-retry 99999999999` | CONTROL `keepalive 99999999999` |
|---|---|---|
| `config.SchemaValidate` | **accepted** | **REJECTED** — `integer out of range [0..32767]` |
| `configstore.CheckText` (operator commit path; runs the walk via `compileTreeStrict`) | **accepted**, `kar=99999999999` | **REJECTED**, same message |
| `config.CompileConfig` (STRICT compiler gates) | accepted | **also accepted** — this layer covers neither leaf, so a claim made here would have measured nothing |
| `config.CompileConfigLenient` | accepted, `kar=99999999999` | accepted |

So the discriminating channel is `SchemaValidate` (and `CheckText`, which runs
it). Naming `CompileConfig` would have been the wrong-instrument error: the
sibling that IS bounded is not rejected there either, so the "control" would have
agreed with the defect.

`schema_interfaces.go:540` was unchanged from the issue's quote.

**One claim in the issue's dependency chain was STALE and is corrected here.**
The archived `fable-review-161` note (cited in the tree) says the whole keepalive
engine is unreachable on the userspace dataplane, because the daemon sets
`AnchorOnly` for every tunnel and `applyAnchorLocked` never consults
`tc.Keepalive`. That was true when written and is not true now: **#4071 ported
the keepalive engine to the anchor path** (`pkg/routing/tunnel.go:444` and its
doc comment, `startKeepalive` at :591 and :799). So the consequence this issue
describes is reachable on the production dataplane, not only on the legacy
standalone-CLI branch. Had that note still held, the severity would have been
"an inert knob", which is a different issue.

## Remedy

`valueType: ValueInteger` + `validator: ValidateInteger(1, 255)` on
`keepalive-retry`, plus a rewritten leaf comment. 1..255 is Junos's own range for
this leaf; `ValidateIntegerMin` was rejected because an explicit ceiling is the
point, and `ValidateInteger(1, 0)` is the reversed-range trap #8358 already paid
for.

The bound is chosen for REACHABILITY, not for overflow. `keepaliveTick`
transitions the tunnel down at `state.Failures >= state.MaxRetries`; `Failures`
increments once per probe tick; `startKeepalive` normalizes only `<= 0 -> 3`. At
the ceiling the check is still reachable in 255 ticks — 42 minutes at a practical
10 s interval — where an unbounded count made it unreachable outright.

## What typing it COST, stated rather than absorbed

`validateModifierChild` rejects a flat run whose head leaf is TYPED, so
`keepalive-retry` was one of the `tunnel` container's two UNTYPED ADMISSION HEADS
(#9156 V020). Typing it means

```
set … tunnel keepalive-retry 5 source 10.0.0.1 destination 10.0.0.2
  before: accepted, and (since #9156) expanded correctly
  after : REJECTED — `tunnel keepalive-retry: unknown modifier "source"`
```

That is the only cell in the tree this change reds:
`TestTunnelFlatRunSurvivesAnUntypedHead9156`, all four arms.

**A PRIOR DECISION is speaking there, so it was read before being touched.**
#9156's rationale (`tunnel_flat_run_9156.go`) is that a run headed by an untyped
leaf must EXPAND rather than be swallowed, and its own doc names
`routing-instance` as the container's second untyped head. The cell's subject is
the expansion, not `keepalive-retry`; `routing-instance` is still untyped and
still an admission head (measured: all four arms pass unchanged with it as the
head). So the fixture was RE-POINTED rather than the arms deleted — deleting them
would have removed coverage while looking like a passing suite — and the head
that left is pinned in the other direction by
`TestKeepaliveRetryHeadIsRejectedOnceTyped9157`, which also asserts the surviving
head still works so "the run is rejected" cannot be confused with "the expansion
regressed".

The narrowing itself is defensible on its own terms: Junos does not accept several
statements on one `set` line, and the TYPED-head order
(`destination B keepalive-retry 5`) has always been rejected here — so the two
orders now agree instead of one being accepted and the other refused.
