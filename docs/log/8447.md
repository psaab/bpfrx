# #8447 — persistent-nat pool stops transit: the cause, and why it was invisible

- **Timestamp**: 2026-09-04
- **Action**: Diagnosed #8447 and fixed the observability defect underneath it.

  **The cause is not in NAT.** On a chassis cluster, a source rule pointing at a
  pool carrying `persistent-nat` sets `ForwardingSupported=false`
  (`capabilities.go`, `cfg.Chassis.Cluster != nil &&
  userspaceConfigUsesPersistentSourceNAT(cfg)`), which makes
  `disarmBeforeUnsupportedPublishLocked` send `set_forwarding_state{armed:false}`
  before the snapshot publish; `desiredForwardingArmedLocked` then keeps it
  disarmed and the 1 Hz reconcile short-circuits because desired == actual. The
  bindings stop counting RX, which is the reported `rx=0`.

  **That behaviour is documented and deliberate** — the closed #1449 admission
  boundary, written up in `docs/ha-failover-status.md` and
  `docs/userspace-dataplane-gaps.md`. So #8447 is an OBSERVABILITY defect, not a
  NAT defect: the config commits cleanly, nothing logs, there is no metric, and
  the only surface was `Forwarding supported: false` inside a `show` nobody runs
  when the symptom is "the link went down". Five rounds of cluster measurement
  went into rediscovering a documented contract.

  The smoking gun: `disarmBeforeUnsupportedPublishLocked` computed a `reason`
  and used it ONLY to decorate an error string on the FAILURE path. The success
  path — the one that actually stops traffic — emitted nothing. The fix is to
  log it, at WARN, with the unsupported reasons and the consequence.

  **A hypothesis I held and had to abandon.** The published table (rx, tx,
  sessions, every `cos_*`/`waterfill_*`/`binding_tx_*` at zero) comes entirely
  from one `curl -s --max-time 8 .../metrics`, and
  `test/incus/pnat-upstream-stage-8447.sh` prints only non-zero deltas with no
  emptiness guard — so an empty scrape produces a byte-identical table. That
  rival explanation is REFUTED by the newer `pnat-wedge-recovery-8447.sh`, whose
  `rx_now()` prints the literal `ABSENT` when the series is missing; the landed
  run reported numeric 6/0/0/6, never `RX-ABSENT`. The older harness's table is
  still not evidence on its own.

  Validation: 6-mutation table, all killed, no survivors. Two of my own harness
  errors are recorded because they are the interesting part: the mutation
  harness restores by `git checkout`, which DELETED the uncommitted production
  fix and produced a red baseline I nearly read as a pre-existing failure (the
  rule is to commit before running it); and the first M1 killed by COMPILE
  failure rather than behaviourally, which proves nothing, so it was rewritten
  to compile. `M6 gate drops the cluster condition` SURVIVED the first table —
  every cell covered only the cluster case, so the obvious "fix" of widening the
  gate would have turned a cluster-only outage into a standalone one. Bound now
  by an accept-side control.
