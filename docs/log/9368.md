## What was wrong

The doc block stated that over-subscription yields `Some(0)` and that this is
*"deliberately not `None`"*. The body 90 lines below returns **`None`**, and its
inline comment argues the opposite with the reason.

Provenance is exact: the doc came from `596969d30`, the original #6846
implementation, which did return `Some(0)`. `067d6b548` ("#6846 review F1-F4")
inverted the behaviour and correctly updated **both** the Rust body and the Go
advisory — missing only this block.

## Why it was worth fixing rather than tolerating

What the stale text asserted is not a harmless inaccuracy, it is **precisely the
fail-open a review had just removed**:

> at the call site a `Some(0)` becomes `guarantee_enabled = true` with
> `transmit_rate_bytes = 0`, so the queue is promoted into guarantee service AND
> read as uncapped by the token bucket — the inverse of the starved queue this
> was meant to produce

And it asserted it **emphatically**. That is the shape most likely to be
"restored" by someone making the body match its documentation. A false comment
that merely describes is a nuisance; one that argues for a specific removed
behaviour is a standing invitation to reintroduce it.

## Code changed: none — and that is the finding

The behaviour is already pinned by `over_subscription_is_unresolvable`
(`cos/remainder_temporal_tests_6846.rs`), whose own comment records that it
asserted `Some(0)` in an earlier revision and why the encoding was wrong. So the
#6846 review fix was complete in substance; **the documentation was the only
stale artifact**, and there was no second defect hiding behind it. Verified
rather than assumed.

The corrected doc now names that cell, so the prose and the guard read as one
statement and a future change has to move both.
