# #8061 — subnet-directed broadcast: verdict, not a fix

- **Timestamp**: 2026-09-03
- **Action**: Answered the issue's reachability question. The asymmetry is real,
  the consequence chain is not, and no product consumer is affected. Recorded the
  disposition where a dataplane reader will find it, and added the guard that
  makes the recording falsifiable. No production code changed.
- **File(s)**: `docs/host-inbound-multicast.md`,
  `userspace-dp/src/afxdp/tests_bind_forward.rs`.

## The issue honoured its own hedge, so the first deliverable was a verdict

Filed as "a latent asymmetry to check, not a confirmed defect". Three questions,
each closing the next if it lands negative.

**1. Does it resolve to `LocalDelivery`? No.** Six production sites return it;
none is reachable for this class. `fib.rs`'s arm gates on `owned_here`
(membership in `local_tables_v4` / `local_nat_any_table_v4`);
`forwarding/local_delivery.rs` gates on `iface.primary_v4 == Some(ip)`;
`poll_stages.rs`'s is the IPsec passthrough decision and is not address-derived.
Those membership sets are populated from each interface's HOST address
(`forwarding_build/interfaces.rs`, `local_v4.insert(v4.addr())`), so a directed
broadcast is never a member. The only residual is an operator configuring the
broadcast as a DNAT external.

**2. Is there a consumer? No.** The product's three `AF_PACKET` consumers each
take a different class: the DHCP client uses the limited broadcast (early
fallback), VRRP uses multicast (early fallback), and the HA ARP probe is
EtherType 0x0806 and never reaches the `AF_INET` arm.

**3. What is the repair? Does not arise** — and that was the expensive part. No
shim change, so no `make generate`, no pinned toolchain, no kernel-verifier gate.

## The context that reframed it

`family inet targeted-broadcast` is a REAL config leaf
(`schema_interfaces.go:178`) that is ACCEPTED-ONLY and not enforced (#4308), and
a commit-time advisory tells the operator so, guarded by
`TestInterfaceParityKnobsAdvisory_4308`. The dataplane's non-handling is not an
unnoticed asymmetry — it is the advertised state of a knob deliberately left
unimplemented.

## Reading turned into measurement

The verdict on question 1 rested on reading gates, which is exactly the shape
that has gone wrong repeatedly this week. So it is now a cell:
`subnet_directed_broadcast_is_never_locally_delivered_8061` builds a real
`ForwardingState` from a `192.168.1.1/24` snapshot and asserts the disposition
for `192.168.1.255`.

It carries its **positive control inside the cell**: the interface address is
asserted to resolve `LocalDelivery` FIRST, so the negative assertion cannot pass
merely because nothing in that state resolves locally.

Mutation-verified against the exact future hazard — adding the broadcast to
`local_v4` + `local_tables_v4` in the builder, which is the natural way someone
would implement #4308's dataplane half. It compiles (checked BEFORE reading the
verdict, since a build failure is a VOID rather than a red) and reds the cell.

## Method note

The first search for the issue's named identifiers (`should_fallback_early`,
`is_local_destination`, `userspace_local_v4`) returned nothing, because it was
scoped to `userspace-dp/` and the shim is a separate crate, `userspace-xdp/`.
That is the same boundary error as #7758 — verifying inside a boundary cannot
audit the boundary — caught here in one step by widening the corpus and
re-running with a positive control (`ForwardingDisposition`, 510 hits) that
proved the search worked.
