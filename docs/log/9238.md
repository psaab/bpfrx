# #9238 — the watermark ends up ahead of the image that boots

## Defect

`cmd_fetch` consults the anti-rollback watermark **twice**, with the same
comparison and opposite consequences.

- **Early** (before the download): `die` on `_ver_key(ver) < _ver_key(prev)`.
- **Late** (after verification): the same comparison used only as the condition
  for *writing* the watermark. When it failed, nothing happened — no die, no
  warning — and execution fell through to the incus alias import / libvirt
  golden replacement.

The late block re-reads `prev`, so it is the one place in the process holding
correct information about a concurrent advance, and it threw it away.

| | watermark | published alias |
|---|---|---|
| start | v0 | v0 |
| A verifies v1, passes the early check, stalls | v0 | v0 |
| B verifies v2, advances, publishes | **v2** | **v2** |
| A resumes, re-reads prev=v2, skips the write, **publishes** | v2 | **v1** |

Deploy only checks alias/golden *existence*, so v1 is then consumed as the
channel's stable identity with nothing dissenting. No forged signature and no
`--allow-rollback` is involved: both images are legitimately signed and the
ordering does all the work. The `--version`-less pointer flow makes it
reachable on ordinary channel rotation, or against a briefly-stale mirror.

The original comment above the block — *"advance the monotonic watermark only
AFTER a successful verify (so a failed/tampered fetch never moves it)"* — is
entirely about **not advancing** on a bad fetch. That reasoning is correct and
is retained. It simply never considered the watermark moving underneath a
**good** fetch, which is this case. `except OSError: pass` is correctly scoped
to the write I/O and was not the problem.

## Fix — two halves, neither sufficient alone

1. **The late comparison is a decision.** An inversion aborts *before* the
   alias import or the golden replacement, naming both versions so an operator
   sees a concurrent-fetch collision rather than a mystery.
2. **The publish is serialized.** A new `_watermark_lock` (exclusive flock on
   `<state>/xpf/.image-watermark.lock`, modelled on the existing `_golden_lock`)
   spans the late read, the comparison **and** the publish. Without it, half 1
   only narrows the window — check and publish are still two steps. Lock order
   is watermark-then-golden (`_install_libvirt_golden` takes `_golden_lock`
   inside this block); nothing takes them the other way round. Best-effort in
   the same sense as `_golden_lock`: a state dir that cannot be locked must not
   turn a first fetch on a fresh workstation into a hard failure, so the fetch
   proceeds and **says so** rather than letting an unserialized run look
   serialized.

## Cells

Hermetic: throwaway minisign keypair, `file://` base URL, private
`XDG_STATE_HOME`, `incus` stubbed. The concurrency is modelled by advancing the
watermark from inside `verify_image_artifact` — exactly the window between the
two checks — so the race is deterministic rather than hoped for. The primary
cell asserts the hook actually **fired**, so it cannot pass vacuously by simply
never setting up the race.

## Mutation matrix

Every mutant was confirmed to parse and RUN before being scored; a mutant that
does not run reports no failures and reads exactly like survival. M2 was void
on its first attempt (the dedent ran past the end of `cmd_fetch` into the next
class) and was re-run bounded to the function.

| # | Mutant | Ran | Result | Killed by |
|---|--------|-----|--------|-----------|
| M1 | revert half 1 — late compare back to a bookkeeping condition | yes | **KILLED** | `test_a_concurrent_advance_aborts_before_publishing`, `test_the_abort_names_both_versions` |
| M2 | revert half 2 — keep the abort, drop the lock | yes | **KILLED** | `test_the_publish_is_serialized_under_the_watermark_lock` **only** |
| M3 | weaken the abort to `<=` | yes | **KILLED** | `test_refetching_the_SAME_version_is_not_an_inversion` |
| M4 | strip the version names from the abort message | yes | **KILLED** | `test_the_abort_names_both_versions` |

M2 is the column that matters for the two-halves requirement: with the abort
still in place and only the lock removed, exactly one cell reds — the
serialization one. That is what shows the halves are bound **independently**
rather than one cell covering both and hiding a missing half.

M3 and M4 guard the two ways the abort could be wrong in the other direction:
firing on an equal re-fetch (the common case, must not abort) and firing
uselessly (an operator who cannot tell a collision from a corrupt watermark).
