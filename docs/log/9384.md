## The defect

`zone_policy_deny_on_session_hit` was handed `Some(metadata.ingress_zone)` as the
from-zone override. The override WINS over the live ingress map
(`forwarding/mod.rs`), which also made the ifindex argument beside it dead. So the
to-zone was resolved live and the from-zone came from the ENTRY, and the module
header's coverage claim — *"a commit that moves an interface BETWEEN ZONES is
caught; a commit that changes a ROUTE ... is NOT"* — was true of the EGRESS half
only.

An operator moving an interface OUT of a permitted zone to cut off access got the
new verdict for NEW flows while every live session kept being judged under the
zone it was admitted in, was stamped fresh, and kept forwarding. A
security-intent operation silently did not take effect on live traffic.

The generation question is not what was missing: every commit goes through
`Compile`, which takes its generation from `m.bumpGeneration()` unconditionally
(`pkg/dataplane/userspace/manager_compile.go`), so a zone-membership edit DOES
bump the generation and the re-derivation DOES run — with the stale from-zone.
Go's commit-time invalidation cannot cover it either: it compares policy
match/action text and referenced-object fingerprints
(`pkg/daemon/daemon_policy_invalidate.go`) and never diffs zone MEMBERSHIP.

## Why the shipped cells could not see it

`metadata(is_reverse)` hard-codes `ingress_zone: TEST_LAN_ZONE_ID` AND leaves
`reth1.0` in `lan` in the snapshot. Entry zone and live interface zone were never
allowed to DISAGREE, so the override was unobservable.

## The two things that keep this from being a revoke storm

1. **FABRIC INGRESS keeps the entry's zone.** A fabric-punted packet arrives on
   the fabric link from the peer, so its arrival zone is structurally not the
   flow's. The discriminator is the PACKET's fabric ingress (`packet_fabric_ingress`,
   threaded from the call site), NOT the session's `metadata.fabric_ingress`: the
   latter says the session was INSTALLED from a fabric punt, which tells you
   nothing about where THIS packet arrived, so a session whose later packets
   arrive locally should be judged on where they arrived.

   This is load-bearing on the SHIPPED config, not hypothetical.
   `docs/ha-cluster-userspace.conf` puts `fab0` in the `control` zone, and
   `ifindex_to_zone_id` PROPAGATES a zoned child's zone onto its parent
   (#921/#3618) — so a fabric arrival on `ge-0-0-0` resolves live to `control`,
   which nothing permits to `wan`. Without the exemption, every established
   cross-chassis session is revoked on the first packet after any commit: TCP
   death on VRRP failback, which the fabric redirect exists to prevent.
2. **#9383:** the live resolution goes through `resolve_ingress_logical_ifindex`.
   Keying `ifindex_to_zone_id` on the raw physical index would reintroduce the
   logical-vs-physical defect on a trunk, and this is the site that would turn it
   from a mis-attribution into a revocation. That is why #9383 landed first.

## The residual, stated as a decision

An interface moved out of EVERY zone resolves to the unknown-zone sentinel 0 and
takes the pre-existing `from_id == 0` DECLINE arm rather than revoking. That arm
exists because a zone lookup failure is not a verdict, and revoking on one is the
mass-teardown risk (#6722's MAC-less egress is the reachable case). An ingress in
no zone is also not an ordinary configuration. Closing the residual would mean
distinguishing "deliberately unzoned" from "no ledger row yet", which the snapshot
does not express. Pinned by
`an_ingress_moved_to_no_zone_declines_rather_than_revoking_9384`, which is a
CHANGE DETECTOR rather than a defect guard — and the log says which it is.

Row 2 is what stops the fix degenerating into "revoke on any disagreement": the
interface moved and the zones disagree exactly as in row 1, but the zone it moved
INTO is permitted. Row 3 stops "always revoke". Row 4 proves the harness can see a
revocation for this zone pair at all, so row 1's `revoked == 1` is not something
else in the fixture firing. Row 6 is the correctness control and its fixture
detail is load-bearing: the fabric PARENT is given a zone, because an UNZONED
parent would make the cell pass either way via the pre-existing `from_id == 0`
decline — a cell that cannot distinguish the exemption from the decline.

The `dmz -> wan` permit that `policy_deny_snapshot` ships with had to be REMOVED
from this fixture. With it, moving `reth1.0` into `dmz` lands in a permitted zone
and the move is unobservable — the fixture would have sampled only the passing
point of the axis it varies.

## The #9381 relay question, settled by measurement and landing here

A concern was relayed on #9381 that the defect might be wider than its title —
that `set security policies default-policy reject` could make the whole revoke arm
inert appliance-wide — with the counter-intuition that under default-reject one
would expect OVER-revocation rather than inertness. Both halves are right about
different tenses, and two cells land with this change (same file, same fixture
helpers) rather than as a fourth round-trip:

- `default_policy` is parsed by the SAME `parse_action` a rule's action is, so
  `"reject"` becomes `state.default_action` and every flow matching no rule gets a
  REJECT verdict — reached by the implicit-default exit, a DIFFERENT code path from
  `try_match_rule`.
- PRE-#9381 (`!matches!(.., Deny)`) all of those sessions took the PERMIT exit and
  were STAMPED. On a default-reject box that is the entire default-verdict
  population — strictly wider than #9381's title, which named only a rule narrowed
  `permit` -> `reject`.
- POST-#9381 they revoke exactly as under default-DENY, which is the correct
  verdict and is the over-revocation the counter-intuition expected.

| snapshot | expect | pre-#9381 |
| --- | --- | --- |
| `default_policy: "reject"`, NO `lan -> wan` rule | revoked 1, 0 left | **revoked 0** |
| `default_policy: "reject"` + a `lan -> wan` permit — the control | revoked 0, 1 left | revoked 0 |

The control is load-bearing: without it, `revoked == 1` is satisfied by a box that
revokes whenever the DEFAULT ACTION is non-permit regardless of whether a rule
admits the flow, which would tear down every permitted session on a default-reject
appliance. So the concern is a larger consequence of the SAME one-token defect,
already closed, and needs no new issue — the only real gap was that #9381's cells
sampled the terminal-action axis through an explicit RULE only.
