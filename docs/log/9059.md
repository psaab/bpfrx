# 9059 — the fabric allowlist admitted a method that multiplexes 127 topics

- **Timestamp**: 2026-09-06
- **Action**: gate `ShowText` on the fabric listener by request TOPIC, the way
  its sibling `SystemAction` is already gated by request ACTION.
- **File(s)**: `pkg/grpcapi/fabric_showtext_topic_9059.go` (new),
  `pkg/grpcapi/server.go`,
  `pkg/grpcapi/server_fabric_allowlist_4122_test.go` (one prior list revised,
  two cells added).

## The file already made this argument, four lines above

On `SystemAction`:

> deliberately absent: it multiplexes fabric-safe cross-node cluster-failover
> with destructive node actions (zeroize/reboot/halt/power-off) under ONE gRPC
> method, so a method-name allowlist that included it would still expose
> zeroize. It is gated separately, by request-action.

`ShowText` sat in the same map with no equivalent gate. It multiplexes ~127
topics, so allowlisting the name admitted `route-all`, `security-log`,
`commit-history`, the `nat-*-detail` topics and the `test-policy:` policy
simulator — while **both** peer-proxy call sites send exactly one topic,
`"chassis-forwarding"`.

The allowlist's own comment says each entry is "a method the local node actually
proxies". True at method granularity; false at topic granularity.

## Why an explicit topic list rather than reusing the pricing table

The loopback chain already prices every topic
(`TestEveryShowTextTopicHasAPermission_5278` keeps it exhaustive), and the fabric
listener deliberately shares no interceptor with it. But that table prices a
topic **for a principal** — "may this login class read this". The fabric listener
has no principal, and its question is narrower: **"does this node ever ASK a peer
for this"**. Reusing a permission tier would admit every topic at or below
whatever tier the fabric was deemed to hold — the method-granularity mistake
again, one level down.

## Severity kept as filed

Medium. The marginal disclosure is **runtime** state, not configuration: the peer
already receives the entire active config text through config sync. And the
reachable population is bounded — the peer chassis, a token-replay attacker
inside the documented 30-90 s window, or a legacy in-place-upgraded unkeyed
cluster (a new unkeyed `chassis cluster` is hard-rejected at commit since #6611).

## A prior list revised, not deleted

`TestFabricAllowlistUnary_AllowsProxiedReadMonitorRPCs` passes a **nil** request
and asserts admission **by name**. That is the right shape for a method that does
one thing and the wrong shape for one that multiplexes. `ShowText` moves out of
that list and into a request-content case, mirroring
`TestFabricAllowlistUnary_SystemActionNestedGate` exactly.

## The cell for the opposite failure

`TestFabricShowTextAllowlistCoversEveryProxiedTopic_9059` reads the two
peer-proxy call sites' **source** and requires every literal topic to be
allowlisted. The failure it prevents is quieter than #9059's: someone adds a
second proxied topic, the fabric gate refuses it, and the feature silently does
not work across the cluster. It carries a positive control — if the pattern
matches nothing it fails rather than reporting a clean board — and an upper bound,
so the allowlist cannot grow entries nothing proxies.
