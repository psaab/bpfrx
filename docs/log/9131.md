# #9131 — the address-only persistent SNAT allocator refused instead of probing a sibling pool address

- **Timestamp**: 2026-09-06
  - **Action**: `reserve_address_only_persistent` now probes the remaining pool
    addresses on a reverse-identity collision when — and only when — the lease
    is FRESH and the pool is not `address-persistent`.
  - **File(s)**: `userspace-dp/src/nat/allocator.rs`,
    `userspace-dp/src/nat/tests_addr_only_sibling_9131.rs` (new),
    `userspace-dp/src/nat/mod.rs`,
    `docs/userspace-dataplane-architecture.md`,
    `docs/userspace-dataplane-gaps.md`

    The collision check returned `AllocatorExhausted` without ever looking at
    another pool address, while the sibling `reserve_address_only_roundrobin`
    does `continue` on the identical condition ("This address's reverse
    identity is owned by a DIFFERENT flow for this remote — try the next
    sibling instead of dropping"). For a port-less protocol (GRE 47 / ESP 50 /
    ICMP) the identity degenerates to `(proto, translated_ip, 0, dst_ip, 0)`,
    so two tunnels from different subscribers to the SAME popular remote
    collide the moment they land on one pool address.

    **The refusal is not the defect and is deliberately kept for the two
    PINNED cases**; only the missing retry was wrong. The originating report
    asked for a blanket fallback, which would break both of them:
      * `address_persistent` — the address is `sticky_pool_index(src_ip)`, a
        pure function of the source. Rotating breaks the contract the operator
        configured, and the roundrobin sibling likewise sets
        `address_attempts = 1` there.
      * an EXISTING lease (`reusing`) — the address is pinned by
        `persistent-nat` for the permit scope's lifetime, and two flows sharing
        one public reverse identity are genuinely ambiguous on the return path.

  - **Reachability of the `reusing` + collision arm, which is not obvious.**
    It needs two DIFFERENT flow keys that produce the SAME reverse identity AND
    the SAME persistent-lease key. `AddressOnlyReverseKey` carries no routing
    scope and `PersistentSourceKey` carries none either, while
    `SourceNatFlowKey` does — so two flows identical except for
    `routing_scope` are exactly that shape. That is how
    `a_reused_lease_collision_still_exhausts_9131` reaches the arm without
    manufacturing anything.

    **N1 is the fixture check that matters.** It restores master's behaviour
    exactly, and exactly three cells go red — the three that assert the
    fallback. The three narrowing guards stay GREEN under it, which is what
    makes them guards rather than restatements of the fix.

    **N2 is the finding the issue does not contain.** The originating report's
    blanket fallback does not merely over-reach in theory: it reds three
    SHIPPED #8132 HA cells about an address-only client keeping its public
    address across a failover. Those cells were already in the tree and nobody
    had to write them for this.

    N5's first construction asserted a single call site and aborted — there are
    TWO (`match_rules.rs:773` v4, `:902` v6). Scored only after mutating both.

    **The end-to-end cell needed a second assertion to be a WIRING binder.**
    On its first form it did NOT red under N5: with the persistent branch
    disabled the flows fall through to `reserve_address_only_roundrobin`, which
    ALSO probes siblings, so every assertion about the two addresses still
    passed. It was bound to the fallback BEHAVIOUR and blind to which function
    produced it. Asserting that each subscriber holds an address-only
    persistent LEASE — which the round-robin path never creates — is what makes
    it discriminate; it now reds under both N1 and N5.
