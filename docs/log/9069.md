# #9069 — the NAT64 ICMPv6 arm diverged from the declared checksum SSOT

## The defect

`recompute_l4_checksum_after_nat64_v4_to_v6`'s `PROTO_ICMPV6` arm wrote `sum`
raw, while its own `PROTO_UDP` sibling ten lines above canonicalised zero to
`0xFFFF`, and while `adjust_zero_checksum_illegal`
(`afxdp/frame/checksum.rs`, #1839) — this codebase's **declared single source of
truth** — says V6 zero is illegal for UDP *and ICMPv6*. The afxdp-side
`recompute_l4_checksum_ipv6` canonicalises its ICMPv6 arm. The NAT64 translator
diverged from the rule its sibling path enforces.

The zero is **producible**, not theoretical: the issue brute-forced two payload
bytes of a real Echo Reply until the pseudo-header checksum folded to zero and
confirmed `0x0000` was written.

## What this is NOT, because the source finding's consequence was refuted

The originating report cited RFC 4443 §2.3 and RFC 8200 §8.1 for a mandatory
all-ones substitution on ICMPv6. **That rule is UDP-specific in RFC 8200 §8.1,
and RFC 4443 §2.3 contains no such sentence.** A `0x0000` ICMPv6 checksum
verifies correctly at a compliant receiver — there is no "no checksum" sentinel
for ICMPv6 — so "dropped by compliant hosts" does not follow.

What survives is an **internal SSOT divergence**, which is a real contract
violation. Severity Low, and the cells assert consistency rather than wire
correctness. Recording this matters: a fix justified by a non-existent RFC rule
would be the same defect class as the one it fixes.

## Fix — one rule, not a per-arm matrix

The issue's dedup note asks that this and its #8869 sibling "ride on one fix that
routes every recompute arm through `adjust_zero_checksum_illegal` rather than
re-implementing the matrix per call site". That is what landed.

`canonicalize_zero_checksum(sum, protocol, family)` consults the SSOT, and all
four NAT64 arms (v4→v6 TCP/UDP/ICMPv6, v6→v4 UDP) go through it. The two
hand-rolled `if sum == 0 { 0xFFFF }` fixups in production are gone.

`adjust_zero_checksum_illegal` and `ChecksumFamily` were `pub(in
crate::afxdp::frame)`. **That visibility is why a second implementation grew
outside the module and then diverged** — the rule was unreachable from the
translator, so the translator restated it, and a restatement is free to drift.
Both are now `pub(crate)`.

Correctness of the non-covered pairs falls out of the rule rather than being
re-argued: `adjust_zero_checksum_illegal` returns false for TCP in both families
(a computed TCP `0x0000` is legal on the wire — the reason the sibling finding
GEMINI-050-009 was refuted) and for V4 ICMP (no pseudo-header, no sentinel).

### Three simultaneous FALSE survivors — a new void mechanism

M2, M4 and M5 all reported **survived** on the first run. None of them had been
applied: my `perl` patterns were written with `\t` indentation, correct for Go
and **wrong for space-indented Rust**, so nothing matched.

Three at once is what makes this dangerous. One survivor prompts suspicion; three
prompts a conclusion — "my controls are inadequate" or, worse, "the SSOT check is
not load-bearing". Both would have been wrong, and both point at weakening the
work rather than fixing the harness.

Re-run with an **applied-check per mutant** (assert the replacement count before
scoring), all five kill. This is the sixth distinct void mechanism this session,
after: orphaned imports, a dedent past a function end, a locator that did not
match, a method that does not exist, a splice landing on the wrong function, and
a runner whose error grep meant the opposite in the other language.

M5 mutates the FIXTURE: the brute-force helper derives the zero-folding tail for
*this* packet rather than copying the issue's `(0xa1, 0x2a)`, which was found for
a different one. A hard-coded tail would leave the checksum non-zero and the
canonicalisation never exercised — the cell would pass while testing nothing.

## Docs

No documentation file changed, and the reason is not that it was skipped: the
zero-checksum rule is documented in `adjust_zero_checksum_illegal`'s own doc
comment, which is the SSOT, and that comment already enumerated the matrix
including the TCP exclusion. It now also records why it is crate-visible. Neither
`userspace-dp/README.md` nor `docs/userspace-dataplane-architecture.md` has a
checksum-rule section to fall out of date.
