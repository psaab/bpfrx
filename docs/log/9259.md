# 9259 — absence of a barrier is not proof of fencing (the final link of #9036)

## What was left

#9036's chain was: *the barrier is gone → the wait returns nil → nil means
applied*. PR #9247 removed ONE way for the barrier to be gone (supersede, now
resolved with `ErrFailoverSuperseded`). The final link — **absence of a barrier
read as proof of fencing** — was untouched, and two routes still reached it:

1. **NeverArmed** — a `(rgID, reqID)` for which no barrier was ever registered.
2. **VerdictConsumed** — the first waiter deletes the entry after reading it,
   deliberately, so a later wait cannot re-read a stale verdict (#6177). A
   second wait then found an empty slot.

Both returned `nil`, and `sync_failover.go` sends `failoverAckApplied` EXACTLY
when the wait returns nil. So the peer promoted on no evidence of a fence.

## Baseline checked BEFORE changing the default

Changing `nil` → error is only safe if `b == nil` is not the normal path.
Verified rather than assumed:

- `handleRemoteFailover` calls `WaitFailoverApplied` only after
  `OnRemoteFailover` returned nil — the error path sends its ack and returns at
  `sync_failover.go:434`, so no wait runs.
- That handler ARMS the barrier before `ManualFailover` and disarms only on the
  error path, where it returns the error and again no wait runs.
- The supersede path deliberately leaves a FAILED barrier rather than none, so
  it is unaffected.

On every path that reaches the wait for a live request, a barrier is armed.
`b == nil` is reached only by the two abnormal routes above.

## The fix

Both routes now return an error, so the ack downgrades to `failed` and the peer
HOLDS. The trade is deliberate and asymmetric: holding costs a failover attempt,
while the previous default cost the one-owner-per-RG property (#5640).

They are distinguished — `ErrFailoverNeverArmed` vs `ErrFailoverVerdictConsumed`
— because they send an operator to different places: a stale/duplicate request
id versus a retry racing its own first attempt. Distinguishing them needs a
record of consumed requests, kept in a ledger bounded at `failoverConsumedCap`
with oldest-out eviction. **An eviction degrades the DIAGNOSTIC, never the
safety property**: an evicted key reports as never-armed, which is still an
error and still downgrades the ack — the more conservative of the two readings.
Pinned by its own cell, because a bounded structure silently changing an
operator-facing reason is what gets discovered during an outage.

## Two existing cells redded, and neither was stale

Both were read before either was touched, and in both the property the cell
actually pins SURVIVES — only an incidental half changed.

**`TestFailoverActuation_UnarmedRGIsNoop`.** Its rationale read "resolving is a
no-op **and** a wait returns immediately with no error", as if the second
followed from the first. It does not, and they have different subjects: *"every
ordinary demotion"* is true of RESOLVING and false of WAITING — an ordinary
local demotion never calls `waitFailoverActuated` at all. **Split**: the
resolve-side no-op is kept and now asserted directly (no barrier is created);
the wait-side half is inverted into a named sibling with the reason attached.

**`TestFailoverActuationBarrier_DisarmedRequestReportsNoFence`.** Its own
comment says *"the handler is not on the ack path here"* and its subject is that
the wait must return IMMEDIATELY rather than burn the full timeout. The `want
nil` was incidental to that. **The timing assertion is kept verbatim**; only the
value changed.

This is the "when a fix reds an existing cell, a prior decision is speaking"
rule, and in both cases the prior decision was right about something else.
