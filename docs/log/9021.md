# #9021 — the synced NAT64 import never asked the peer-ownership question

## The asymmetry

Four arms reserve a NAT64/SNAT translated identity. Three ask whether a PEER
allocator already owns it:

- local NAT64 mint → `nat64_refuse_if_peer_owns`
- both SNAT synced arms → `peer_owns_wire_identity`
- **HA-synced NAT64 import → nothing**, on either of its two routes.

It returned `reserve_nat64_pool_port` directly. The refusal was not one level
down: that function ends at `allocator.reserve_flow`, and `PortAllocator`
carries no `PoolAddressOwners` logic at all — so nothing on the path could have
asked.

## Consequence

A peer-synced import reserves against the NAT64 prefix's **own** bitmap only. A
`Nat64Prefix`'s allocator is keyed by `(prefix_bytes, pool_v4)` while a
source-NAT pool's is keyed by pool NAME — two independent bitmaps over one
address. With a live local source-NAT flow holding `(X, P)`, the import
succeeded, `reserve_synced_nat64_allocation` returned true, the coordinator
published, and the reverse (1:N) index carried **two live flows on one
translated identity** — the split #8115 R2/R3 closed for the other three.

The consumers make it worse rather than better: the coordinator
(`afxdp/ha/session_import.rs`) uses the returned bool as its **only** refusal
point, and the worker twin (`upsert_synced.rs`) **discards** it. Nothing
downstream re-checks, so the bool has to be right here.

## Fix

`reserve_synced_nat64_port_unless_peer_owns` — reserve, then apply the existing
`nat64_refuse_if_peer_owns`, which does its own `rollback_flow` (not
`release_flow`: the activation is being WITHDRAWN, and the deterministic arm's
block port must go back through `free_no_recycle` rather than onto a recycle
ring the deterministic mapping never draws from).

**One helper, not a copy per route**, for the reason `nat64_refuse_if_peer_owns`
itself gives: the two routes differ in how they CHOOSE the prefix, not in what
makes the tuple a duplicate, and a duplicated check is free to drift — a drifted
copy still answers, just about a different question.

**Both routes needed it.** The `match_ipv6_dest` narrowed arm and the fallback
pool scan are separate `return`s. Wiring only the narrowed one would be the
partial-fix shape on the path that exists precisely for when narrowing fails
(a v4-keyed or prefix-less key: config drift between nodes, an old peer).

## Cells

Four, on the real `build_forwarding_state` path — the #8115 R3 harness, which
exists because a cell that hand-builds a `PoolAddressOwners` would prove the
query works and stay green with the registration deleted.

- narrowed route refused when a source pool owns the identity;
- fallback-scan route refused (v4-keyed key, so it cannot narrow);
- **control**: an unowned identity is still RESERVED;
- **control**: disjoint pools are unaffected.

The first control is load-bearing. A "fix" that refused every synced import
satisfies both defect cells while breaking HA session sync entirely — the
standby would reserve nothing and a post-failover local flow could reuse a live
translated identity, which is the #4512 defect this whole path exists to
prevent.

## Mutation matrix

| # | Mutant | Result | Killed by |
|---|--------|--------|-----------|
| M1 | revert the NARROWED route | **KILLED** | the narrowed cell, alone |
| M2 | revert the FALLBACK SCAN only | **KILLED** | the fallback cell, alone |
| M3 | refuse EVERY synced import | **KILLED (2)** | both controls, alone |

Each mutant reds a disjoint set, which is what shows the two routes are bound
**independently** and that the fix is not over-broad.

### The void-detector was wrong, in the opposite direction from usual

My first run scored **all three mutants as VOID**. The detector grepped
`^error` — and `cargo test` prints `error: test failed, to rerun pass ...`
when a test **FAILS**. So it was reading every KILL as a build failure: the
exact inverse of the Go failure mode, where a build failure reads as a survival.

Both directions are wrong and both are silent. The detector now keys on
`error[E….]` / `could not compile`, and I gave **the detector itself a
two-direction positive control** before trusting it: a deliberate type error
reads VOID, a deliberate assertion break reads KILLED. An instrument used to
adjudicate mutants needs adjudicating first.
