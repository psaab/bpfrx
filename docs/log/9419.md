# #9419 — SYN-cookie validated-client whitelist: ephemeral-port key + single-use lookup

## Summary

The challenge-and-reset design's own recovery step (step 6 of the algorithm in
`docs/syn-cookie-flood-protection.md`, "client retransmits SYN -> passes as
validated") was unreachable. Two independent reasons, both of which had to be
fixed:

1. the whitelist key carried the client's **ephemeral source port**
   (`SynCookieTuple`), and
2. the lookup was a single-use `take_valid` that removed the entry on a hit.

Step 5 answers a valid cookie ACK with a RST addressed to the client at its
exact `RCV.NXT`, which aborts the just-ESTABLISHED socket with `ECONNRESET`. No
TCP stack retransmits a SYN from that state — the application calls
`connect()` again, on a NEW ephemeral port. That reconnect missed the
port-scoped whitelist, was challenged, and was reset again. While an attacker
held a zone over its SYN-flood attack threshold (Junos default 200 SYN/s), every
legitimate TCP client to that zone looped on `ECONNRESET`.

The RST itself is the documented design and is unchanged.

## Change

- **`userspace-dp/src/screen/syncookie.rs`**
  - New `SynCookieClientKey { src_ip, dst_ip, dst_port }` — the whitelist key.
    Deliberately distinct from `SynCookieTuple`, which stays the **cookie MAC**
    key (the MAC must bind the full 4-tuple; the whitelist must not).
  - `SynCookieValidatedKey.tuple` -> `.client`; `key_hash` drops `src_port`.
  - `take_valid` -> `contains_valid`: a hit no longer removes the entry.
    Renamed rather than edited in place so any caller still assuming
    consume-on-hit fails to compile (BIND THE WIRING). An expired entry is
    still reclaimed on the lookup that observes its expiry.
  - `debug_set_index` takes the client key.
  - Module doc updated.
- **`userspace-dp/src/screen/mod.rs`** — the two call sites: the PHASE-0
  validated-cache consume in `check_packet_with_zone_id_opts` now peeks a
  client key; `validate_syn_cookie_ack_on_session_miss` inserts a client key
  while still validating the MAC over the full tuple.
- **`userspace-dp/src/afxdp/frame/tcp.rs`** — corrected the
  `build_syn_cookie_ack_rst_frame` doc comment, which asserted a "mirrors the
  eBPF behavior" equivalence that did not hold while the key was narrower than
  the eBPF ancestor's.
- **`docs/syn-cookie-flood-protection.md`** — algorithm step 5/6 reworded to
  "whitelist the CLIENT" / "client reconnects", plus a new "Whitelist scope and
  lifetime (#9419)" section stating the key, the TTL bound, the #2446
  generation bound, and what the pre-#9419 shape did.

Bounds retained after removing the single-use bound: the one-cookie-epoch TTL
(64 s, refreshed per validation) and the #2446 per-zone profile generation.

## Cells re-anchored (prior decisions, not stale tests)

Three shipped cells asserted the single-use property directly. Each was
re-anchored, keeping the half that is still true, rather than deleted:

- `screen::tests::syn_cookie_ack_validation_marks_next_syn_bypass_without_session_creation`
  — `len() == 0` / "validated tuple is single-use" -> `len() == 1` with the
  reason recorded inline.
- `screen::tests::syn_cookie_validated_syn_bypasses_flood_gate_and_passes` and
  `screen::tests::syn_cookie_validated_cache_hit_within_same_generation` — same
  trailing `len() == 0` assertion.
- `afxdp::poll_stages::tests::session_miss_ack_stage_invokes_syn_cookie_runtime_validation`
  — its trailing "validated SYN-cookie bypass must be single-use" assertion is
  replaced by the two claims that survive: the validated client's reconnect IS
  admitted, and a DIFFERENT source is still challenged. The assertion this cell
  actually exists for (the poll stage invokes cookie validation) is untouched.

The unit-level cache cells (`..._is_bounded`, `..._index_is_keyed`,
`..._generation_is_keyed`, `..._refresh_extends_ttl`,
`..._expires_on_ttl_boundary`) previously obtained key distinctness by varying
`src_port`. Under the new key that would have inserted the SAME entry N times
and the cells would have measured nothing — they now vary `dst_port`.

## New cells

- `syn_cookie_retry_from_new_ephemeral_port_bypasses_9419` — step 6 in the only
  shape it can occur in.
- `syn_cookie_repeated_reconnects_from_validated_client_bypass_9419` — five
  successive reconnects, each on its own port, all admitted within the TTL.
- `syn_cookie_whitelist_does_not_widen_past_the_validated_client_9419` —
  NEGATIVE CONTROL with a positive control at the same instant: a different
  source IP and a different destination service are still challenged. Without
  it, "always return true" passes the two cells above.
- `syn_cookie_whitelist_stops_bypassing_after_ttl_9419` — the TTL is what
  bounds the whitelist now that a hit does not consume it.
