# 9335 — my own #9123 cell was flaky at 1.2%, and it is the error I documented

- **Timestamp**: 2026-09-06
- **Action**: replace a packet-LENGTH identity assertion with a structural BER
  signature that is invariant to the randomized request-id.
- **File(s)**: `pkg/snmp/agent_addr_9123_test.go`.

## The defect is mine, and it is the second instance of one error

`TestV2cTrapIsUnaffectedByTheTargetMove9123` asserted that the v2c packet
**length** is identical across three targets. The v2c PDU carries a **randomized
request-id**, and a BER INTEGER is minimal-width — a request-id that fits in one
byte encodes shorter than one needing three. So the length varies **by chance**,
with nothing about the target having changed.

The cell's own comment, three lines above the defect, says:

> Byte-identity was my first attempt and it was simply wrong: the v2c PDU carries
> a RANDOMIZED request-id … It reported a difference for every target including
> the empty one, which is what showed it was measuring the randomness rather than
> the change.

**And then I asserted a length identity that measures exactly that same
randomness.** Writing the lesson down did not stop me reproducing it one level
lower, where the hit rate was low enough to survive review.

## A low-rate flake is worse than a loud one

Measured, with a positive control on the repair itself:

| assertion | failures / 20,000 |
|---|---|
| length identity (as shipped) | **240 (1.2%)** |
| structural signature (this change) | **0** |

Independently measured at 1.08% by another lane, which is how it surfaced.

At that rate it passes every time its author runs it and fails for someone else,
weeks later, in an unrelated package — where the honest reading ("my change did
this") is wrong and the cheap reading ("re-run it") is how a suite stops being
believed. It reds `go test ./...` for every lane.

## The replacement, and what it costs

`berShape9335` renders the tag tree with every leaf's bytes included **except**
INTEGERs, whose value is discarded. That is the field the randomness lives in,
and discarding it is a real loss of strength — so
`TestTheShapeSignatureDiscriminates9335` pins that the signature still
distinguishes linkUp from linkDown, and that it is stable across repeated builds
of the same trap. **A summarising comparison that discards too much passes
trivially**, so the discarding has to be shown to still discriminate.

The rule this generalises to, which is not "avoid byte comparison": **any
assertion over data containing a random field is unsound unless the assertion is
invariant to that field — and length is a function of the field, not an escape
from it.**
