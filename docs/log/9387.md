## The defect

`pkg/config/schema_security.go`'s `setSchema` entry for
`security policies policy-rematch` carried

```go
desc: "Re-evaluate in-progress sessions on policy change (accepted-only; unenforced)"
```

`desc` is the text `?` completion puts in front of an operator. The knob is
ENFORCED: `changedPolicyRuntimeIDs` (`pkg/daemon/daemon_policy_invalidate.go`)
gates on `newCfg.Security.PolicyRematch` and clears the sessions of every
surviving policy whose match or action changed, plus — with `extensive` — the
sessions of an UNCHANGED policy whose referenced address-book / application
object definition changed (#8993's `PolicyResolvedFingerprints` arm).

The doctrine was already written down three files over, in the commit that
REMOVED the matching advisory (`pkg/config/compiler_validate_warn.go`):

> **NO ADVISORY IS EMITTED FOR EITHER KNOB NOW.** Leaving the old one would tell
> an operator a capability is missing when it exists -- the failure this campaign
> catalogued on #8942 -- and would do it **in operator-facing text** rather than
> in a comment.

The `?` help is operator-facing text saying exactly that. Two non-operator-facing
comments carried the same stale claim and are corrected too
(`types_security.go`: "xpf does not yet perform any session invalidation on
commit (tracked as the enforcement feature #4234)" and "commit emits an
accepted-only advisory" — both false).

## Why it is not cosmetic

`policy-rematch` is **off by default** — no defaulting code, the zero value IS the
default, matching Junos where it is opt-in. So on a stock box the commit-time
invalidation does not run at all, and it is the only commit-time mitigation for
the #9381 `permit` -> `reject` revocation gap. An operator who types `?`, is told
the knob does nothing, and therefore does not set it, has neither mechanism.

## The census, and why the predicate the issue proposed is WRONG

#9387 suggested a "more durable" guard: *fail when a `setSchema` `desc` contains
an accepted-only/unenforced phrase whose referenced issue is CLOSED.* The census
run for this change **refutes that predicate**:

| site | claim | referenced issue | state | claim true? |
| --- | --- | --- | --- | --- |
| `schema_interfaces.go` (`unnumbered-address`, `gratuitous-arp-reply`, ...) | "accepted-only, not yet enforced — #4308" | #4308 | **closed** | **yes** |
| `schema_routing.go` (`forward-only`, `relay-agent-option`) | "accepted-only; always inserted — #4309" | #4309 | **closed** | **yes** |
| `schema_security.go` (`tcp-session strict-syn-check`) | "accepted-only" | #8296 | closed | **yes** |
| `schema_security.go` (`policy-rematch`) | "accepted-only; unenforced" | #4233/#4234/#8993 | closed | **NO** |

#4308 and #4309 closed on ADDING a commit advisory, not on enforcing the knob, so
their descs are accurate and the issue being closed changed nothing about them.
A closed tracking issue is therefore not the discriminator, and neither is the
phrase: **44** `desc` strings across `pkg/config/schema*.go` carry one.

The real discriminator is whether an ENFORCEMENT PATH READS THE FIELD. For
`strict-syn-check` the answer is no — `StrictSynCheck` is read only by the
compiler that sets it and by `compiler_validate_warn.go`, which emits the
matching advisory — so its desc is true. For `PolicyRematch` the answer is yes,
and that is why this one was stale.

Three rows audited by hand; the other 41 were NOT, and this log says so rather
than asserting 44 verdicts the change did not earn.

## The guard, and why it lives in `pkg/daemon`

`pkg/daemon/policy_rematch_help_claim_9387_test.go` states the contract in ONE
cell with both halves, because neither half alone is the contract:

- **Half 1 (behavioural)**: `changedPolicyRuntimeIDs` really does report a policy
  whose action changed when the knob is SET, and really does report nothing when
  it is UNSET. This is what makes "unenforced" a false statement.
- **Half 2 (operator-facing)**: given half 1, neither the leaf's `?` help nor its
  `extensive` sub-token's help may assert the capability is missing.

It is in `pkg/daemon` because that is where `changedPolicyRuntimeIDs` lives; a
guard in `pkg/config` could only assert the absence of a phrase, which is
satisfiable by rewording and says nothing about whether the capability exists. And
it reads the text through `config.CompleteSetPathWithValues` — the function the
CLI's `?` handler calls — so it reads the bytes an operator is actually shown,
and a renamed or moved leaf fails the explicit non-vacuity check instead of
passing for free. An EMPTY desc also fails: a guard against a false claim must
not be satisfiable by saying nothing.

The second cell pins the earned, narrow property: **nothing under
`security policies` advertises itself as unenforced** (count 0). Not a 44-row
whole-schema allowlist, for the reason above.
