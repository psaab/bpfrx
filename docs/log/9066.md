# 9066 — the demote-failure path dropped the frontier, and the comment saying that was safe was false

## The instruction that shaped this

> When a comment asserts safety and the code does not deliver it, fix BOTH; a
> corrected comment on uncorrected code is the worse outcome.

Both are fixed here. The comment is not merely deleted — it is replaced with
the measurement that refutes it, so the next reader inherits the number rather
than a new assertion to trust.

## The false justification, and exactly how false

`cos_classify.rs` said:

> The failure-rollback path (`cos_queue_restore_front`) is round-trip neutral
> per #913 §3.7 and stays correct without snapshot/restore.

**True for a single bucket, false for several.** The issue's measurement, three
flows x two packets at vtime 5000, forced down the Local-head `else` arm:

| bucket | pre head | post head | delta |
|---|---|---|---|
| 0 | 6500 | 10700 | **+4200** |
| 1 | 5900 | 8600 | **+2700** |
| 2 | 6200 | 9500 | **+3300** |

Each bucket's frontier comes back inflated by the bytes of the OTHER buckets
drained ahead of its own last item.

## What it is, kept apart from what it is not

Not "corrupt scheduler state" or "permanently lost state": vtime round-trips
exactly and relative order among restored buckets is preserved. What it IS: a
new flow arriving right after a failed demote anchors at `vtime + bytes` and is
served ahead of the entire restored backlog — the temporal-inversion class
**#926**, fixed on the success path and left open on the failure path.

Reachability is high: `cos_queue_accepts_prepared` refuses Prepared once the
queue holds any Local item, so the first drained Local trips the `else` arm on
every subsequent demote.

## The fix

`restore_flow_fair_frontier` extracted and called on **all three exits** —
success and both failures — rather than patched into two of them. Extracting it
is what makes the paths unable to drift again; the defect was precisely that
two exits and one exit disagreed while a comment explained why that was fine.

## The cell, and why the existing one could not see this

Acceptance asked for "a multi-bucket demote-failure cell asserting each bucket's
post-restore `head_finish` equals its pre value; a single-bucket cell (which
already exists) cannot see this."

`demote_failure_preserves_mqfq_frontier_across_buckets_9066` is the failure-path
sibling of the existing multi-bucket SUCCESS cell, using the same fixture. Two
deliberate choices:

- It triggers the failure with a **Local item in the queue** — the COMMON
  trigger. The source finding named the rarer `clone_prepared_request_for_cos`
  failure and treated the Local-head arm as an aside; it is the other way round.
- It asserts its own **fixture** before its subject: both buckets must hash
  differently (else the cell degenerates into the single-bucket case it exists
  to distinguish itself from), both must carry a non-zero frontier (else the
  assertions compare zero to zero and pass whatever the code does), and the
  demote must actually **fail** (else every assertion is measuring the success
  path that was already correct).

## Mutation matrix

| # | Mutation | Verdict |
|---|---|---|
| M1 | drop the restore on the non-Prepared exit | **FAIL** — with the inflation message |
| M2 | neuter `restore_flow_fair_frontier` entirely | **FAIL** |

Both mutants BUILD; restore verified byte-identical.

## Validation

Full Rust suite: rc=0, 11 test binaries green (5425 tests in the main one).

No `make test-failover` and no `go test ./...`: this is dataplane TX scheduling
in `userspace-dp`, touching no Go package and nothing in cluster, VRRP,
session-sync or failover. Stated rather than silently skipped.

## Not folded in

The issue suggests folding in GEMINI-050-013 (NAT64 ICMPv6 zero-checksum
canonicalization) as "a one-line consistency fix in the same subsystem family".
Left alone: it has its own issue, it is a different defect with its own
acceptance, and bundling an unrelated one-liner into a fairness fix makes both
harder to revert.
