# #9392 — `recycle_scan_pops` had no production reader, so the recycled phase had no signal

## Defect, re-verified at the base commit (`c525bb966`, `origin/master`)

```
$ grep -rn "recycle_scan_pops" userspace-dp/src/
allocator.rs:910    recycle_scan_pops: AtomicU64,          <- preceded by #[cfg(test)]
allocator.rs:928            recycle_scan_pops: AtomicU64::new(0),
allocator.rs:1100           self.recycle_scan_pops.fetch_add(1, Ordering::Relaxed);
allocator.rs:1633   pub(super) fn debug_recycle_scan_pops(&self, addr_index: usize) -> u64 {
tests_pool.rs: 8 call sites, all tests
```

Every reference outside the declaration is a test. `grep -rn recycle_scan pkg/`
returns nothing, so there is no Go-side consumer and no operator surface. A
release build does not even compile the counter.

What that costs is specific. #9327 measured on this tree that the recycled phase
of `PortAllocator::claim` does NOT amortize — retained tokens are pushed to the
BACK of the per-address FIFO, so K out-of-band-occupied tokens ahead of F free
ones cost `(K+F)/F` pops per claim, degrading to `K+1` as `F -> 1`, i.e. worst
exactly as an address approaches exhaustion. #9327 corrected the in-code comment
that claimed otherwise and deliberately did NOT bound the walk, because a bare
scan budget cannot distinguish "scanned enough" from "genuinely full" and `None`
on budget exhaustion turns a slow allocation into a spuriously dropped NAT
translation. It left the REACHABILITY question open: does a production pool ever
get to K-large / F-small? The counter that would answer it could not be asked.

## The remedy

1. `recycle_scan_pops` leaves `#[cfg(test)]`.
2. **A denominator is added**, because the promoted counter alone answers
   nothing: a large cumulative pop count is equally consistent with a busy pool
   doing cheap walks and an idle one doing pathological ones, and that
   distinction IS the question. `recycle_scan_walks` counts recycled-phase FIFO
   walks, incremented once per walk AFTER the `occupied >= range`
   short-circuit — a short-circuited claim walks nothing, and counting it would
   add denominator without numerator, pulling pops/scan toward zero on exactly
   the most exhausted pools.
3. Both are summed per POOL into `PortAllocatorSnapshot` ->
   `SourceNatPoolStatus` (Rust) -> `SourceNATPoolStatus` (Go) and rendered by
   `show security nat source pool <name>`:
   `Recycled-scan pops: 128 over 8 scans (16.00 per scan)`.
4. ADD, never redefine: two NEW keys, `serde(default)` / `omitempty`. The helper
   and the daemon roll independently.

### Hot-path cost

The increment is NOT per pop. `claim` accumulates in a local `u64` and does ONE
`Relaxed` `fetch_add` after the walk, so a healthy single-pop claim pays one
relaxed RMW (plus the one for the walk counter) on a line it already owns — the
walk runs under the `recycle` mutex — and the pathological walk pays the same
one rather than K of them. That is strictly cheaper than the `#[cfg(test)]`
shape it replaces.

### Render gate

The line is gated on `RecycleScanWalksTotal > 0`, never on the pop count. An
older helper omits both keys and they decode 0; a pool whose recycled phase has
not run reports 0 honestly. Printing a ratio from a zero denominator would state
a measurement nobody made — the fabricated healthy zero this exact view has
already had refused out of it twice (#7473 for a disarmed pool, #8606 for a pool
the helper has no entry for).

## Not fixed, deliberately

The BOUNDING question stays open and this change does not touch it, per #9392's
own instruction. A bare scan budget cannot tell "scanned enough" from "genuinely
full"; `occupied == range` is the existing exact discriminator and a budget is
not one. This issue ships the instrument that would justify a bound; it does not
ship the bound.

No Prometheus series was added. #9392 asks for "a Prometheus series or a `show`
line" and names `show security nat source pool` as the natural home; adding both
would double the wiring for one signal, and the `show` line sits beside the
utilisation the cliff is a function of, which the metric would not.
