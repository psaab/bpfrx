# #9324 — ConfigTarget's proto3 zero value is CANDIDATE

## Measured at HEAD (3c4d3bfa8), independently of the issue's own run

With a session holding a staged, uncommitted edit:

```
REST show no ?target         -> "... security-zone SECRET-WIP-ZONE ..."
REST show ?target=active     -> "system { host-name COMMITTED-ACTIVE; }"
REST show ?target=candidate  -> "... security-zone SECRET-WIP-ZONE ..."
REST compare (no selector)   -> "+ security-zone SECRET-WIP-ZONE"
restReadPermissions[GET /api/v1/config/show]    = PermView
restReadPermissions[GET /api/v1/config/compare] = PermView
```

Two failure modes, not one. **Disclosure:** a view-only principal reads another
session's uncommitted topology, zones, policies and address books. **Silent wrong
answer:** on an idle box the same call returns an EMPTY string, so a
config-backup client written without `?target=active` archives either nothing or
somebody's draft and cannot tell which.

The two benign verdicts were audited rather than assumed — a benign verdict is
the one nobody re-checks. The census is now a GUARD
(`TestProtoEnumZeroValuesAreSentinelsOrAllowlisted9324`) so a new enum with a
non-sentinel zero must be allowlisted *with a reason*, which is the moment to ask
whether it is another `ConfigTarget`. Its scan carries a positive control (fewer
than five enums found = the scan is broken, not the file clean).

Also audited: `GET /api/v1/config/show-rollback`, which the issue flagged as "in
the same block". It reads the committed rollback ARCHIVE
(`ShowRollbackRedacted` → `rollbackEntry`), not `s.candidate`. Clean; stays
`PermView`.

## The fix, and why the two surfaces differ

The acceptance offers a choice: default to ACTIVE, or price CANDIDATE above
PermView. The right answer differs by surface, because only one of them can tell
"absent" from "explicit".

- **REST** — `?target` is a string. Absent now renders ACTIVE (matching
  `GET /api/v1/config/export`, which always has, and Junos operational
  `show configuration`); an unrecognised `?target` is a 400 rather than a
  fall-through, which was the same fail-open shape as the default itself.
- **gRPC** — proto3 cannot distinguish an omitted enum from an explicit zero, so
  "unset means ACTIVE" would also rewrite an **explicit** `CANDIDATE` request
  into an ACTIVE one, and `cmd/cli/show.go:420` sends exactly that for the
  config-mode view. Renumbering the enum to add an `UNSPECIFIED` sentinel is a
  wire REDEFINITION and a rolling-upgrade hazard. Fixed by PRICE only.

Both surfaces charge the same price: reading a candidate costs `PermConfig`, the
permission that lets you be in configuration mode at all. Enforcement is at the
two choke points that already adjudicate (`readAuthz`; the gRPC interceptor
beside `authorizeRPCConfigMutation`), not in handlers, so a new target-taking
route cannot be added with its read ungated.

`cmd/cli` sets the target EXPLICITLY at both of its call sites
(`ACTIVE` at show.go:111, `CANDIDATE` at :420), so no in-tree caller relies on
the old default.

## An existing cell reddened — split, not inverted

`TestReadOnlyClassIsAllowedAViewRPC_5278` went red. Its stated reason is still
true and still needed: *"the negative control for the case above. Without it, a
gate that denied EVERYTHING would pass every denial assertion in this file."*
What changed is which `ShowConfig` a read-only class is entitled to.

The assertion was SPLIT, keeping the still-true half verbatim: the control's
`ShowConfig` now names `Target: ACTIVE` and must still be ADMITTED, and a second
line asserts the bare `&pb.ShowConfigRequest{}` it used to send is now DENIED.
Both halves live beside each other so they cannot drift.

That split turned out to be load-bearing beyond bookkeeping: it is what kills
M4 (severing the gRPC wiring) and half of M5.
