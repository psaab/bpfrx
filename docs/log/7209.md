# 7209 — sync_session under the snapshot-wide ServerState mutex

- **Timestamp**: 2026-09-02
  - **Action**: Re-verified the central claim at `6a2e170d6` before
    scoping. **It is live and unmoved.** `handlers/mod.rs:130` takes the
    global lock; `sync_session` dispatches under it at `:262` and
    `apply_snapshot` at `:133`; `reconcile` is still `&mut self`
    (`reconcile/mod.rs:231-232`), so the `Arc<Coordinator>` option stays
    dead; `WORKER_STARTUP_BARRIER_TIMEOUT_NS` is still 10 s
    (`bringup.rs:41`).
    Lock graph, as asked: today BOTH paths take their inner locks UNDER
    the global mutex, which is why the arrangement is safe-but-slow —
    the global lock serialises them, so there is no ordering hazard to
    invert. `upsert_synced_session(&self)` takes
    `workers.records_snapshot()` plus an ArcSwap load; `apply_snapshot`
    takes the same `workers` mutably through `reconcile`. Moving
    `sync_session` off the global mutex gives `global -> inner` against
    `inner alone`, which is not an ABBA inversion **provided the
    off-lock path never needs the global mutex** — the hazard is not
    deadlock but the three worker-set decisions straddling a teardown,
    which is exactly the second instrument the spec comment names.
