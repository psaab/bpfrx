# #7174 C06 — journal rotation defers to an in-flight append

- **Timestamp**: 2026-09-02
  - **Action**: closed the rotation-unlink half of the row.
    `pkg/configstore/journal/journal.go` `Log` releases `j.mu` before its fsync
    (#4829), so a writer can be parked between its `f.Write` and its `f.Sync`
    while another writer rotates. The renames are harmless — a rename preserves
    the inode — but rotation also UNLINKS the oldest kept segment, and once
    that inode is gone the parked writer's fsync still succeeds and `Log` still
    returns nil. `maybeRotateLocked` now checks the inode it is about to
    destroy against a `Journal.inflight` registry and defers.
  - **File(s)**: pkg/configstore/journal/journal.go,
    pkg/configstore/journal/rotation_inflight_7174_test.go,
    pkg/configstore/README.md
  - **Decision note — the OTHER half of this row is deliberately unchanged.**
    C06 is written as one row but names two things: the off-lock fsync and the
    unguarded rotation unlink. The off-lock fsync is a reviewed choice, not an
    oversight — `journal.go` documents the durability contract it preserves
    ("Log returns success only after f.Sync ... succeed") and
    `TestTailNotBlockedByLogFsync` pins that a Tail does not stall behind a
    writer's fsync. Moving it back under `j.mu` would undo #4829. What the
    off-lock fsync DOES create is the in-flight window the unlink half needs
    guarding against, which is why the two belong in one row and only one of
    them is a code change.
  - **Severity note**: reaching the destroyed slot takes `maxSegments+1`
    rotations — three full segments of appends at the defaults — so this is an
    audit-integrity edge case rather than a routine loss. It is worth closing
    because of HOW it fails: the fsync on an unlinked inode SUCCEEDS, `Log`
    returns nil, `Store.journalLog` only warns on an error so it warns about
    nothing, and the audit record is simply absent. There is no signal anywhere.
  - **Starvation note**: deferring names ONE OLD inode, and later appends land
    on the current segment (a different inode), so nothing arriving afterwards
    can extend the deferral. The next append after that writer's fsync rotates;
    the cost is a current segment that overshoots the threshold by one record.
    The control test pins this — a guard that deferred forever would satisfy the
    main cell while silently disabling retention.
  - **Test note**: mutation-checked four ways. Removing the guard, removing the
    registration, and removing the release each red the correct cell; a guard
    that always defers reds the control plus four pre-existing rotation tests.
