# #9143 — every FRR vtysh shell-out except one branch was unbounded and uncancellable

## The "every X except one" verdict

**The ONE is right and was under-generalized; the ungated majority is the
outlier.** Establishing this before writing code mattered: a funnel applies
whatever it holds to every call site at once, so funnelling the WRONG behaviour
would have propagated a defect instead of a fix.

The evidence is not a judgement call. `pkg/diagcmd` already asserts the same
rule three separate times for this exact cost class:

| limiter | issue | what it bounds | why |
|---|---|---|---|
| `DefaultLimiter` | #5057 | REST + gRPC ping/traceroute | they fork a child; "a request flood cannot pin hundreds/thousands of PIDs/FDs/goroutines" |
| `SessionWalkLimiter` | #5433/#5708 | every full-table walk, both surfaces | per-bucket map locks |
| `SnapshotReadLimiter` | #8151 | snapshot copies | map-copy cost |

An FRR status read forks a `vtysh` child that runs for up to 15s. Same class as
a forking ping handler, and it was simply never gated. #6809 gated ONE branch of
ONE handler (`GET /api/v1/routing/bgp?type=routes`) for a STREAM-shaped cost
(memory + a held connection). Its admission reasoning was correct and general;
only its mechanism was stream-specific.

- **The source report undercounted**: it named `ospfHandler` only.
  `bgpHandler`'s DEFAULT branch (`GetBGPSummary`) is the same shape and equally

- **Sub-claim 3 (terminal-escape injection) is NEG** and was not acted on, per
  the issue: REST bodies are `json.Marshal`ed and `pkg/termsafe`'s package doc
  states sanitizing happens at the DISPLAY boundary only, so machine consumers
  get the raw value (#6468). Wrapping REST output would contradict a documented
  decision and corrupt values for scripted consumers.

### Two mutants that survived first — the finding, not a process note

- **M2** survived initially. Every pre-existing `pkg/frr` test injects a FAKE
  `frrExecutor`, so `realExecutor.Vtysh` — the only place the caller's context is
  composed with `vtyshTimeout` and handed to `exec.CommandContext`, i.e. the code
  that actually reaps the child — had **no coverage at all**. Reverting it to
  `context.Background()` left the entire suite green. Fixed by making the
  production path EXERCISABLE rather than excusing it: `vtyshBinary` is now a
  package var so a cell can point it at a controllable child, and
  `real_executor_ctx_9143_test.go` drives cancellation, a shorter caller
  deadline, and the unchanged 15s cap.
- **M7** survived initially for the same reason one layer over: the apply-path
  cell asserted through `RecordingExecutor`, so a mutation inside `realExecutor`
  was invisible. Rewritten to drive `realExecutor{}` directly, with a control
  asserting the OPERATIONAL path IS refused under the same saturation — without
  that control the apply-path assertion is vacuous.

### One scoring correction

M1's first run reported SURVIVED. That reading was **void, not a result**: the
`go test` process had been killed by a `pkill` while it ran, and a killed run
emits no `--- FAIL`, which reads exactly like a survival. The cell could also
HANG under that mutant (the over-cap read blocked on the fake executor), which
would have burned the budget of every later cell. Both were fixed before
scoring — the cells now bound the over-cap read with a 2s deadline and fail
fast, and the runner treats a non-finishing run, or one producing no test
actions, as VOID — and M1 was re-run and killed.

## By-product, fixed here

`SnapshotReadLimiter` (#8151) was never added to the metrics collector's limiter
list, so its refusals exported as a permanent 0 — the worst direction for #8312,
whose argument rests on a 0 being trustworthy, since an unregistered limiter is
indistinguishable from one that never refuses. The registry moved into
`pkg/diagcmd` beside the declarations; `snapshot_read` and `vtysh` are both
exported now; `TestAllLimitersIsExhaustive9143` fails when a limiter is declared
without being registered (source-scanned, with a positive control asserting the
scan itself found the limiters).

## Note on the branch mechanics

Two squash attempts produced a diff that REVERTED other lanes' merges, because
`git reset --soft origin/master` resolves a remote-tracking ref that is
repo-GLOBAL across worktrees — another lane's fetch moved it mid-operation. Both
were caught by reading `git diff --stat` before pushing (55 files / 1995
deletions where 34 / 184 was expected) and undone via reflog. The squash was
redone against a PINNED base SHA. Remote-tracking refs are shared state in a
multi-worktree checkout, exactly like `git stash`.
