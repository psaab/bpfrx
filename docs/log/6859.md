# #6859 — `then log` no longer forwards filter hits to syslog

- **Timestamp**: 2026-08-27
  - **Action**: routed `then log` away from the syslog fan-out (Junos parity)
    AND shipped the commit advisory that names each affected term, as one
    change. Measured first: xpf has no `show firewall log` (the local surface
    is `show security log`, reading the event buffer); the buffer/callbacks and
    the daemon log line are written BEFORE the syslog fan-out, so suppression
    costs no local visibility; and the `syslog` bit reaches the Rust
    `FirewallTermSnapshot` but `parse_term` never consumes it, so the decision
    has to be control-plane-side. Events carry `RuleID`/`TermID`, which the
    Rust side assigns as positional indices into the snapshot Go renders, so
    `FilterTermSyslogMap` PROJECTS the answer from that same snapshot rather
    than re-walking cfg — a divergence between the two orderings would
    mis-route silently in either direction. nil map = "never wired" (legacy
    fan-out); empty non-nil = "wired, no syslog terms".
  - **File(s)**: pkg/logging/ringbuf.go,
    pkg/dataplane/userspace/filter_term_syslog_6859.go,
    pkg/config/filter_log_syslog_6859.go, pkg/config/compiler_tailgates.go,
    pkg/daemon/daemon_system.go, pkg/logging/README.md, docs/feature-gaps.md
  - **Decision note**: the issue asked for a migration decision between
    release-note-only, a deprecation window, and a config opt-out. Settled as
    fix-plus-advisory in one change: a deprecation window needs a clock and
    this repo has no release cadence, so "then correct it later" would leave
    the known-wrong default indefinitely. The advisory carries the window's
    value — an operator told, at commit, which terms changed — without its
    delay. The opt-out was rejected: it would make a parity bug permanently
    configurable.
