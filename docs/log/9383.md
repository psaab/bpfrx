# 9383 — two `ifindex_to_zone_id` consumers read the RAW PHYSICAL ingress ifindex

- **Timestamp**: 2026-09-09
- **Action**: resolve the LOGICAL (VLAN unit) arrival ifindex at both sites;
  RE-ANCHOR the source-text guard that pinned the defective spelling; add the
  behavioural trunk pair
- **File(s)**: `userspace-dp/src/afxdp/session_glue/mod.rs`,
  `userspace-dp/src/afxdp/session_glue/tests.rs`,
  `userspace-dp/src/afxdp/poll_descriptor/mod.rs`, `userspace-dp/README.md`

## The defect

`ForwardingState::ifindex_to_zone_id` deliberately PROPAGATES a zoned child
unit's zone onto its parent's ifindex (#921/#3618,
`forwarding_build/interfaces.rs`) so untagged traffic on a trunk parent is
attributed to its unit's zone. The consequence is that the RAW PHYSICAL key and
the LOGICAL (VLAN unit) key can return **different answers** for the same frame.
Two consumers used the physical one while every zone / filter /
pre-routing-NAT admission site resolves the logical unit first (#3021/#5802):

| site | what the wrong answer costs |
| --- | --- |
| `session_glue/mod.rs` — the #7169 reverse-session synthesis | the match is admitted and `install_reverse_session_from_forward_match` MINTS a reverse session; reverse entries are exempt from zone-policy re-derivation by design (`policy_revalidation.rs` gate 1), so it then rides the established fast path with no further adjudication |
| `poll_descriptor/mod.rs` — the fabric zone stamp on the new-flow path | the id is encoded into the fabric redirect and therefore selects the **peer node's** ingress zone for the redirected packet |

The row shape is now pinned by its own cell
(`a_trunk_parent_carries_its_zoned_units_zone_while_a_sibling_has_none_9383`),
measured through `build_forwarding_state` on a trunk whose units each own a
netdev:

```
ifindex_to_zone_id[parent 41]        = Some(wan)   // propagated from unit 42
ifindex_to_zone_id[unzoned unit 43]  = None
resolve_ingress_logical_ifindex(41, vlan 80) = Some(43)
resolve_ingress_logical_ifindex(41, vlan 50) = Some(42)
```

The physical lookup answers `Zone(wan)` where the logical resolution answers
"unzoned". That is a different ANSWER, not a different spelling of the same one.

## The guard PINNED THE DEFECT, and it was fixed first

`session_glue/tests.rs` asserted the literal source substring
`ifindex_to_zone_id.get(&ingress_ifindex)` — the raw physical key — with the
message *"the main path must resolve the ARRIVAL interface to a zone. Without this
the reverse-canonical match is decided by tuple equality alone (#7169)"*. So the
CORRECT fix reddens that cell with a message saying the fix REOPENED the hole it
is closing, which is close to the strongest possible signal to stop and revert.

A literal-source assertion cannot distinguish "the call site changed because
someone broke it" from "the call site changed because someone FIXED it" — it only
knows the bytes moved. It is re-anchored to the two properties that really are
invariant: a zone IS resolved from the arrival, and it is resolved from the
LOGICAL unit (`resolve_ingress_logical_ifindex(` present AND
`ifindex_to_zone_id.get(&arrival_logical)` present — the second matters, because
resolving the logical index and then looking up the physical one anyway is the
defect with an extra line). Its failure messages now describe the real invariant.

The cell's own doc comment also claimed a behavioural cell was impractical
("would need to drive a ~20-argument function through a full session install").
That was an argument for not writing the cell that mattered, and it is replaced
by a pointer to the behavioural pair, which does exactly that.

## Why `.unwrap_or(physical)` and not fail-closed on an unresolved arrival

Every other site spells it `resolve_ingress_logical_ifindex(...).unwrap_or(physical)`
(`poll_descriptor/filter.rs`, `prerouting_scope.rs`, `poll_stages.rs`,
`neighbor_dispatch.rs`, `forwarding/mss.rs`, `forwarding/local_delivery.rs`). The
reason is in `prerouting_scope.rs`'s own comment: *"An untagged port has no
`(parent, vlan)` mapping, so it resolves logical == physical and the scope is
byte-identical to pre-#5802."* `populate_egress` inserts
`ingress_logical_ifindex[(bind_ifindex, vlan_id)]` for EVERY snapshot interface —
before the `src_mac` `continue`, so a MAC-less interface is included — so an
unresolved arrival means the interface is not in the snapshot at all, and the
zone lookup that follows then returns `None` and takes the pre-existing
fail-CLOSED arm (`ReverseIngress::Unzoned`). Matching the established spelling
keeps the change to the ONE case it is about: a tagged frame on a trunk.

Checked that GRE/WireGuard decap is unaffected: `logical_ingress.rs` builds the
inner meta with `ingress_ifindex = params.logical_ifindex` and
`ingress_vlan_id = 0`, and `ingress_logical_ifindex[(tunnel_ifindex, 0)]` exists
(a tunnel row has no parent, so it keys itself), so the resolution is the
identity and the tunnel's own zone is still what is read.

### The census found a THIRD site, and it is fixed here rather than filed

`forward_request.rs:520` — the filter-log `source-zone` attribution on the
forward-request / TX-selection path — read the raw physical index with no
resolution and no stated reason, while `ctx.meta.ingress_vlan_id` was already in
scope. Its cost is FORENSIC, not enforcement: a trunk-arriving frame's filter-log
record named the wrong source zone. It is fixed rather than filed because
censusing a site and then leaving it wrong is worse than not having looked — a
landed partial fix removes the reason anyone looks again. The severity difference
is recorded rather than smoothed over: the two adjudication sites are the reason
this issue exists; this one is a log-record correctness fix riding along because
the census found it and the remedy is three lines. It carries no dedicated cell —
the behavioural pair below covers the `session_glue` site, and the fix here is
the same one-line resolution applied to a log field. That gap is stated, not
hidden.

## The behavioural pair, and why it is a PAIR

The fixture is a trunk whose two units each own a netdev under one parent: unit 42
in `wan` (the zone the forward flow EGRESSES to, which is what #7169's arrival
check compares against) and unit 43 in NO zone. A forward NAT'd session is
pre-installed, and `find_forward_nat_match(reply_key).is_some()` is ASSERTED before
the drive — otherwise a "no reverse session" result says nothing about the zone
check, because an empty table produces the same observation.

The two cells differ in ONE byte of input: the arrival VLAN id.

| arrival | logical resolution | zone answer | expect | base (physical key) | branch |
| --- | --- | --- | --- | --- | --- |
| parent 41, vlan 80 | unit 43 | **unzoned** | no reverse session | **FAIL — a reverse session WAS installed** | PASS |
| parent 41, vlan 50 | unit 42 | `wan` | reverse session installed | PASS | PASS |

The second row is the load-bearing control. Without it, "no reverse session" is
indistinguishable from "the synthesis path was never reached" and from "the fix
broke reverse synthesis outright" — which would kill the reply of every NAT'd flow
in the box. It is also the reason the fix is not satisfiable by
`ReverseIngress::Unzoned` unconditionally.

## Mutation score 1/1, no survivor — AND the guard inversion is measured

The mutant restores the raw-physical key at the `session_glue` site, keeping the
resolution call so the mutant is the DEFECT and not merely a compile change
(`let _ = arrival_logical;` + `ifindex_to_zone_id.get(&ingress_ifindex)`).

- **APPLIED, by occurrence count in BOTH directions**:
  `ifindex_to_zone_id.get(&arrival_logical)` 1 -> 0 and
  `ifindex_to_zone_id.get(&ingress_ifindex)` 0 -> 1.
- **BUILDS**, bounded at `timeout 5400` (a `RUNEXIT=124` would score VOID), and
  collected **5586** test results — far above the >= 50 floor.
- **KILLED**, and by exactly two cells:
  - `a_reply_on_an_unzoned_trunk_unit_installs_no_reverse_session_9383`, on its
    `!resolved` assertion with the #9383 message — the behavioural half;
  - `the_main_path_passes_a_resolved_arrival_zone_7169`, the RE-ANCHORED guard, on
    *"the resolved LOGICAL ifindex must be what keys the zone ledger. Resolving it
    and then looking up the physical index anyway is the defect with an extra
    line"*.
- The zoned-sibling CONTROL and all four other #7169 cells stayed **green**, as did
  the rest of the crate (`5528 passed; 2 failed`).

**The guard inversion is the point of the second kill.** Before this change that
cell reddened on the FIX, with a message claiming the fix reopened the hole. It now
reds on the DEFECT. That is the difference between a test that agrees with the bug
and a test that catches it, and it is measured here rather than asserted.
