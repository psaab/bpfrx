# 9040 — the >16-queue cap, made audible

- **Timestamp**: 2026-09-06
- **Action**: make the per-interface RX-queue cap observable, and correct the
  operator doc that denies the cap exists.
- **File(s)**: `userspace-dp/src/server/helpers/planning.rs`,
  `pkg/api/metrics_degraded_path_9040.go` (new), `pkg/api/metrics.go`,
  `pkg/api/metrics_descriptors_global.go`, `pkg/api/metrics_degraded_path_9040_test.go`
  (new), `docs/afxdp-packet-processing.md`.

## What the defect actually is

`replan_bindings_from_candidates` caps an interface's bound RX queues at
`BINDING_QUEUES_PER_IFACE` (16) with a bare `.min()`. RSS is reshaped to fit the
bound set only on **`mlx5_core`** — `pkg/daemon/rss_indirection.go` guards on the
driver and skips everything else, silently. So on a virtio-net / i40e / ice /
bnxt NIC with more than 16 queues the hardware keeps hashing across all `Q`,
only 16 are bound, and transit landing on the rest takes
`drop_degraded_transit`: a steady loss of roughly `(Q-16)/Q` while the interface
reads up. There is no `ethtool -L` anywhere in the tree.

`computeWeightVector` is already driver-generic — it clamps `active` to
`min(queues, BindingQueuesPerIface)` for anything it is called on. The gap is
not the clamp; it is that the caller never reaches a non-mlx5 NIC.

## What this change does, and what it deliberately does not

The issue offers two remedies — refuse the plan (the doctrine its own slot-cap
sibling states: *"a partial plan is an availability failure indistinguishable
from healthy"*) or reshape RSS on the non-mlx5 path — and then says, of both:
**"whichever is chosen, the cap must not be silent."**

That second half is unconditional and lands here in full. The either/or does
not, and the reason is specific rather than caution: **`ethtool -X` indirection
support varies by driver.** Extending the reshape past the mlx5 guard would
issue a table write that i40e/ice/bnxt accept and virtio-net may not, into a
code path whose errors are deliberately swallowed (*"Never returns a non-nil
error — D3 regressions must not break interface bring-up"*). So the reshape
silently fixes some drivers and silently fails on others, which is the same
class of defect being fixed. Refusing the plan is the honest alternative and it
takes a working box offline. Choosing between them is a product decision, and it
is now the open question recorded on the issue with this evidence.

## What landed

- **The cap names itself at bring-up.** A warning naming the interface, both
  counts, why the rest is dropped, the reason string, the metric, and the
  operator remedy (`ethtool -L <iface> combined 16`).
- **`xpf_dataplane_degraded_path_total{reason=...}`.** `DegradedPathCounters`
  already existed on the helper status and reached only the status JSON and the
  `show` text render, so a box dropping transit was visible solely to an
  operator who already suspected it and knew which `show` to run.
- **The doc corrected.** `docs/afxdp-packet-processing.md` said the planner
  *"does not cap the queue count"* — false since #7497 — and offered
  `ethtool -L` as the remedy without saying what happens if you do not. It now
  states the cap, the mlx5-only reshape, the loss, the metric and the open
  question.

## The metric's sparseness is deliberate

The family is emitted only for reasons actually present, and only when a status
was read. Unlike the authz-denial or probe-skip counters, whose label sets are
enumerable and which therefore always emit including at zero, this map is
sparse: a reason that has never fired has no entry. Zero-filling would invent a
series whose absence is meaningful and would make "this box has never taken a
degraded drop" indistinguishable from "this reason exists in the code". Its own
cell pins that, and the zero-fill mutant reds it.

## Validation

Cells drive the collector's real `Describe`/`Collect` against a dataplane that
reports a status — never `emitDegradedPathCounters` directly, which would prove
the emitter works while leaving `Collect` free never to call it, reproducing the
original failure exactly.

| mutant | result |
|---|---|
| drop the `Collect` wiring | killed |
| drop the `Describe` wiring | killed |
| zero-fill an empty status instead of staying sparse | killed |
