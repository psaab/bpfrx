# 9057 — rotation had no persistence class, so four sites got it wrong the same way

## The instruction that shaped this

> This is your #9052 shape one level down: a durability CLASS with no row in the
> taxonomy, so nothing checks it. Expect the answer to be a taxonomy row plus a
> canary, not a one-site fix.

Exactly right, and the four sites are the evidence. They did not get it wrong
because four authors were careless — **the operation had no row in the #1894
taxonomy and no primitive in `pkg/fsatomic` to reach for, and the canary that
enforces the taxonomy only ever looked at `os.WriteFile`.** That is what a
missing class looks like from below: not one bug repeated, but the same gap
found four times.

## Baseline verified before anything was written

- Canary: **0** occurrences of `Rename` in `pkg/fsatomic/canary_test.go`;
  **8** of `WriteFile` (the positive control — the file IS being read).
- `pkg/fsatomic` exported surface: `MkdirAllDurable, Plain,
  SetAfterRenameSyncDirForTesting, SyncDir, WithOwner, WithPreserveExisting,
  WithResolveSymlinks, WriteFileAtomic, WriteFileDurable`. **No rotation
  primitive.**
- All four rotation sites present (line numbers had drifted from the issue).

## What landed

**The class.** A `DurableNamespace` row in `docs/engineering-style.md` and in
`pkg/fsatomic/README.md`, stating that the durable artifact is the DIRECTORY
ENTRY, not a file's contents, with the honest consequence bound: an unclean
shutdown only, losing the newest seconds of lines plus possibly the generation
numbering — **not** corruption, and no file contents destroyed.

**The primitive.** `fsatomic.RenameDurable`, whose doc says when NOT to use it:
a shift loop through it issues N directory fsyncs where one suffices. A
cross-directory move syncs BOTH directories, because syncing one of two looks
like a durable move and is half of one.

**The canary.** `TestNoUnsyncedRename`, keyed on the function's BEHAVIOUR — a
bare `os.Rename` is accepted in a function that also reaches `SyncDir` or
`RenameDurable`, which is what a correct rotation looks like (N renames into one
directory, then ONE `SyncDir`).

**Why behaviour and not a path allowlist**, which turned out to matter: my first
allowlist was a guess at nine function names for the `pkg/upgrade` staged
promotions. The canary's own fixture check (`allowedHits == 0`) caught that
**every one of them was wrong**, and the sweep then showed why it did not matter
— those sites already call `SyncDir` in-function, so the behaviour rule passes
them because they are correct. The allowlist shrank from nine invented entries
to **two real ones**. A path allowlist would have been nine wrong entries that
also silently stopped checking those functions.

**The four sites.** `journal.go` (move the `SyncDir` out from behind an early
return), `locallog.go`, `trace.go`, `monitor.go` (one `SyncDir` after the shift).
The error policy at each site MATCHES that site: the two log writers count and
log like their sibling shift failures; `monitor.go` returns, because every other
rotation failure there returns and a caller that keeps writing onto an
un-rotated file is what its rotate exists to prevent.

## The two allowlist entries, and why each is honest

- `configstore/journal::Journal.maybeRotateLocked` — the fsync is deliberately
  in the CALLER with `j.mu` RELEASED. Doing it in-function would reintroduce
  **#4829**, where a Tail reader blocks for the writer's entire fsync duration.
  A real constraint, found by reading the code rather than by assuming the
  canary was right. What keeps the exemption honest is the per-site cell below.
- `ddns::quarantineBadState` — a one-shot quarantine move, idempotent on retry;
  the namespace change is not the durable artifact.

## The per-site cell the acceptance names, and why it needs a seam

> per-site cells asserting `SyncDir` runs on the rotation path *including* when
> the preceding file sync fails (that is the `journal.go` shape and an
> outcome-only assertion cannot see it)

An fsync **leaves no artifact** — you cannot look at the filesystem afterwards
and tell whether a directory was synced. So the only way to assert it ran is to
observe the call, hence a `syncDir` seam mirroring the `syncFile` one beside it.
`TestJournalRotateSyncsDirEvenWhenFileSyncFails9057` injects a failing file sync
and requires the directory sync to still run **and** the file-sync error to
still be reported — running the dir sync must not SWALLOW the data-sync error.
Its control, `...ReportsDirSyncFailure9057`, requires the dir sync on the
HEALTHY path too, so a "fix" that ran it only on the error path fails.
