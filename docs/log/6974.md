# #6974 — the accept-time peer-lookup budget

- **Timestamp**: 2026-08-28
  - **The cap is NOT reverted.** The wedge it bounds is real:
    `localAddrsFn()` holds `localAddrCache.mu`, and a context cannot unblock a
    goroutine parked on a mutex, so admission control is the only lever.
  - **Which of the two costs is fixed**: *spent pre-authentication*, for the
    connections it can be fixed for. The budget is split by whether a connection
    can REACH the enumeration. `authz.couldBeLocal` short-circuits on loopback
    delivery and returns before `isLocalAddr`, so a loopback-delivered
    connection never takes the mutex and no longer spends the pool that defends
    the connections that can. On the default `127.0.0.1` posture that is every
    connection.
  - **Which is declined, with the reason**: *process-global → per-listener*.
    `localAddrCache.mu` is process-global, so under a real wedge every listener
    blocks on the same mutex whatever the partitioning is — per-listener pools
    would multiply the goroutine bound (the property the cap exists for) while
    buying no isolation. Partitioning by reachability of the mutex does buy it,
    because the two classes contend for different things. The third listed cost
    (denies rather than queues) is not removable: queuing IS the unbounded
    accumulation the cap prevents.
  - **The acquire did not move.** It is still taken at accept and still held
    across `s.lookupPeer` — the call that wedges. Moving it after authentication
    would move it past the thing it protects. What moved is only WHICH bounded
    pool a connection draws on.
  - **The predicate is single-sourced.** `authz.LoopbackDeliveryCannotEnumerate`
    is the exported form of `loopbackDelivery`, which `couldBeLocal` uses for the
    short-circuit. A second copy would agree until someone edited one of them,
    and the failure would be silent — connections that CAN wedge would stop
    spending the budget.
  - **Two accessors had to change or the fix would have weakened edges it did
    not intend to.** `PeerLookupSlotsInUseForTest` now returns the SUM of both
    pools: several cases use "zero slots in use" as a quiescence edge meaning
    "no lookup in flight anywhere", and a reading covering one pool would report
    quiescence with loopback lookups still running — the #6977 class of defect.
    `PeerLookupPoolForTest` lets a case saturating the budget fill the pool its
    own fixture will use rather than guessing.
  - **Three existing tests were re-decided**, each for a fixture reason rather
    than a property change: `TestPeerLookupSlotsAreReturned_5561` and
    `TestWedgedLookupsDoNotAccumulate_5561` fill pools, and their fixtures are
    on `127.0.0.1`, so they now fill the pool they actually use (the second
    fills both). `TestPeerDoneIsClosedAfterTheSlotIsReturned_6977` matched the
    deferred receive by the package variable's name; the operand is now the
    chosen pool, so the guard matches the set of pool names — it pins the defer
    ORDER, not the operand's spelling.
