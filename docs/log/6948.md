# #6948 — commit-time deletion-clear over-clears a session on a reused policy id

- **Timestamp**: 2026-08-27
  - **Action**: Runtime policy ids are positional, so deleting a policy renumbers
    every later one. The invalidation sweep computes its id set from the OLD
    config's numbering but runs after `applyConfigLocked` returns, while the
    dataplane admits under the NEW numbering from the moment the apply publishes
    it — so a session admitted in that window by a policy that inherited a
    deleted policy's id was swept although correctly permitted. Stamped
    `d.policyActivationSecs` immediately before the dataplane publishes
    (placement is the design: earlier would let genuinely-deleted-policy sessions
    escape the sweep, the stale-authorization direction), and the shared
    `clearSessionsForPolicyIDs` now skips rows `Created` strictly after it, for
    both address families.
  - **Correction to the issue**: it states the defect is "not fixable by refining
    the sweep predicate" because the row carries no config epoch or stable rule
    identity. True as far as it goes, but the row does carry `Created` — "seconds
    since boot" on the BPF side, `CLOCK_MONOTONIC` seconds on the Go side, the
    same clock — and the codebase already uses `Created >= threshold` as a
    before/after discriminator for the incremental sync sweep.
  - **Residual, not closed**: `Created` has one-second granularity, so a session
    created in the same integer second as the stamp is ambiguous and is still
    cleared (fail-safe: under-clear is a stale-authorization gap). This narrows
    the over-clear from the entire post-activation apply — tail included, easily
    seconds — to at most one second. Closing it fully still needs an admission
    fence or a stable admitting-rule identity on the row.
  - **Found by the matrix**: the first four cells all set `policyActivationSecs`
    directly, so deleting the production assignment in `applyConfigLocked` left
    every one of them green — the guard would have gone permanently inert with
    the whole file passing. Added a wiring cell that drives `applyConfigLocked`
    and asserts the stamp advanced.

- **Timestamp**: 2026-08-28 (round 2 — the residual, and a larger half the
  first round did not see)
  - **Action**: Replaced the post-apply session-table read with a
    PRE-PUBLICATION capture. `armPolicyInvalidationPlan(oldActive, compiled)`
    at the three commit-class apply call sites,
    `capturePolicyInvalidationLocked()` at the last statement before
    `rt.ApplyConfig` in `applyDataplaneAndHACore`, and the three clears delete
    from the capture's per-class buckets through one shared
    `deleteInvalidatedSessions`. An unarmed path (boot apply) still falls back
    to the legacy scan + `policyActivationSecs` guard.
  - **Why round 1 was not enough**: it treated the window as an ADMISSION race
    and guarded on `Created`. There is a second, larger writer. The helper's
    #3395 live-row refresh (`refresh_bpf_conntrack_last_seen`, driven from the
    worker loop: `CT_REFRESH_SLICE_BUDGET` 2048 slab slots per
    `CT_SLICE_INTERVAL_NS` 100ms, `CT_REFRESH_WINDOW_NS` 10s full-table target)
    re-resolves every forward row's `policy_id` from its bound rule handle
    against the CURRENT rule table and writes it into the same pinned conntrack
    map `BatchIterateSessions` enumerates. Between the snapshot swap and the
    sweep — the whole apply tail, seconds — established rows are re-stamped: a
    survivor that inherited a deleted id gets that id and is SWEPT, and the
    deleted policy's own rows get `DEFAULT_POLICY_SENTINEL_ID` and are MISSED.
    Both rows were created long before the commit, so `Created > activation`
    cannot see either.
  - **The in-tree premise that was false**: `deletedPolicyRuntimeIDs`' header
    said the clear "runs synchronously in the apply path (right after the
    dataplane ApplyConfig), before the next refresh tick". It runs after the
    whole of `applyConfigLocked`, `applyTailReconciles` included. That sentence
    is the stated reason the numeric-id diff is sound; corrected in place, with
    the old wording quoted so the moved premise is visible.
  - **Mechanism chosen, and the rivals**: capture-then-delete. (a) A pure
    reorder — sweeping before the publish — inverts the defect: the deleted
    policy is still live at that point, so an active flow re-establishes under
    it immediately. The capture is a READ, so it cannot re-admit. (b) Stable
    admitting-rule identity on the row and (c) a per-session policy-generation
    stamp both hold the property too, but need a helper change plus a
    session-listing wire field; the control plane can hold it alone, so it
    does.
  - **Property**: every session the commit-time invalidation deletes was
    OBSERVED carrying its target policy id under the OLD numbering. No session
    admitted under, or re-stamped to, the new numbering can enter the candidate
    set.
  - **Residual**: a session admitted by a to-be-deleted policy between the
    capture and the publish is not in the capture (stale authorization until
    idle timeout). That window is the `ApplyConfig` call itself, strictly
    inside round 1's window (which was the same gap plus everything after
    `activationSecs + 1s`).
  - **Found while writing the matrix**: PR #7803's body and this log both claim
    a fifth cell, `TestActivationStampIsWiredIntoTheApply6948`. It is not in the
    tree — commit `509e12f4b`, whose subject is "bind the #6948 activation
    stamp's wiring, not just its predicate", changed only `docs/log/6948.md`.
    So at master, deleting `d.policyActivationSecs = daemonMonotonicSeconds()`
    leaves the whole file green, which is exactly the escape that commit says it
    closed. This round binds its own wiring twice: behaviourally
    (`TestCommitApplyArmsThePolicyInvalidationPlan6948`, via the
    `applyBodyForTest` seam) and structurally
    (`TestCaptureRunsBeforeTheDataplanePublish6948`, an AST cell that parses
    with comments discarded and asserts the capture call precedes
    `ApplyConfig`).
