# 9145 — the allocate-path reuse returns never recorded a holder

- **Timestamp**: 2026-09-06
- **Action**: OR the caller's holder bit at the eight allocate-path
  idempotent-reuse returns; correct a rationale this change falsifies.
- **File(s)**: `userspace-dp/src/nat/allocator.rs`,
  `userspace-dp/src/nat/tests_pool.rs`.

## Landed as a BACKSTOP, and the reachability claim is retired

The mechanism was already EXECUTED on the issue: an idempotent-reuse return
hands back an existing translation **without taking a holder bit**, so a
worker-0 `release_flow` frees a `(pool_addr, port)` worker 1 still holds.

The issue's only demonstrated production route was **#9062** — two rule-sets
scoped to different routing instances sharing a pool, whose identical 5-tuples
collapsed onto one `live_by_flow` record. **#9062 is fixed**: `SourceNatFlowKey`
now carries `routing_scope`, so the two tenants no longer alias, and I verified
that in the current source rather than from the issue text.

So this lands on a **direction argument, not a reachability claim**: ORing on
reuse can only ever cause an UNDER-release, never an over-release, which is the
direction `drop_holder_locked`'s own doc explicitly prefers. Recorded plainly so
nobody later reads it as a live-defect fix.

## The census differs from the issue's, because the code moved under it

The issue counted five or six sites. There are **eight**, because #9130 split the
deterministic arms into a lock-free probe plus a locked path *earlier today*.
Three further `live_by_flow` sites were deliberately NOT touched —
`release_flow`, `retire_worker`, `rollback_flow` are release paths, where ORing a
holder in would be backwards.

## The mutation that found a real gap

`slot.holders = holder.bit()` — assignment instead of OR — **survived** the first
three cells. It drops the FIRST worker's bit on reuse, and those cells happen to
release in the order that hides it. Releasing the REUSING worker first makes the
difference observable: under assignment the mask empties immediately and frees a
translation worker 0 is still using.

**A bitmask that can be overwritten is a single-holder field wearing a mask's
shape**, and the cell that says so now exists.

## A rationale this change falsified

`tests_pool.rs` stated that *"two `allocate_source_for_worker` calls would NOT do
this — the live-hit path returns the existing translation without taking a second
bit"*. That was true when written, is the reason that cell uses the reserve path,
and is **quoted by #9145 itself as evidence**. It is now false. Marked historical
in place rather than deleted, because it still explains why that fixture is
shaped the way it is — an unmarked stale rationale becomes a false justification
that looks freshly confirmed by whatever is edited beside it.
