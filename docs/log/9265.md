- **Timestamp**: 2026-09-09
- **Issue**: #9265 (remediation branch of #9091's closure condition)
- **Base commit**: `098294d28` (origin/master)

## Channel measured

`configstore.CheckText` — i.e. `compileTreeStrict`: the typed-leaf
`SchemaValidate` on the apply-groups-expanded view, then the strict compile. That
is the operator commit path, and it is the channel #9091's 102-container headline
was measured on.

It is deliberately NOT the schema walk. #9091's ratchet enumerates the
SCHEMA-SIDE set, which is a strict superset of the fail-open set, and the whole
point of this issue is that driving remediation from the superset arms containers
that a later compiler gate already covers. Two of the eighteen containers
considered here are exactly that case, measured rather than assumed.

The lenient channel (`CompileConfigLenient` via `Store.Load` / `Store.SyncApply`)
is the reason the arming is done per container with evidence rather than in one
flip: `Store.Commit` is strict while those two are lenient (#1960), so a
container armed carelessly makes a config that stops committing but still boots,
warns and silently truncates.

## Selection criteria

**1. `closedWorld` INHERITS, so only ALL-TERMINAL containers are armed.**
`childClosed := closed || childSchema.closedWorld`, so arming a container closes
its whole subtree. Measured precedent, not theory: `docs/config-schema.md`'s
#9017 note records arming `firewall family` closing the entire filter grammar and
rejecting `from source-prefix-list trusted`, which is valid and shipped.

Censused over the blind population:

```
blind instance-name containers                          158
  all children TERMINAL  (inheritance reaches nothing)   63   <- armable
  at least one NESTED child                              95   <- needs a different approach
```

This batch takes 16 of the 63.

**3. Arming must not change any SPELLING's acceptance, and the container must
DECLARE every keyword it deliberately accepts.** This criterion does not come from
reasoning — it comes from `go test ./...` rejecting a first pass that armed
sixteen. Two containers were dropped:

- **`/snmp/community` fails twice.** #4306 S-5 deliberately ACCEPTS an undeclared
  `view` knob with an advisory (`TestSNMPInertKnobAdvisories`), and a closed world
  refuses it. And #9416's supported packed spelling
  `community <c> client-list-name <n> authorization read-only` puts a legal
  COMMUNITY-level keyword under the terminal `client-list-name` leaf via the
  flat-set chain, where the INHERITED closed world refuses it
  (`TestSNMPClientListFlatSetSpellings9416/reference_BEFORE_authorization`).
- **`/protocols/router-advertisement/interface/prefix`**: the packed flag spelling
  `prefix <p> no-autonomous no-onlink` is ACCEPTED today, and arming refuses it
  with "unknown configuration keyword \"no-onlink\" under closed-world subtree".

**THE ALL-TERMINAL CRITERION IS NOT SUFFICIENT, AND THAT IS THE LESSON.** It stops
arming from closing a declared sub-container, but a flat-set chain NESTS the next
statement under a TERMINAL leaf, so the inherited closed world refuses a sibling
that is legal one level up. Both dropped containers are all-terminal.

**My acceptance fixture could not see it**, and that is the sharper half: it used
the BRACED spelling only, which is a silent claim about which question it answered.
Every armed row now carries the PACKED spelling too, asserted as a fatal
precondition, and both declined containers keep a row whose `packed` line is the
FAIL-ON-REVERT guard for the decision not to arm them — verified by re-arming
`snmp community`, which reds the cell.

### The fixture hazard #9265 warned about, observed

Three of my first-pass fixtures were rejected for the WRONG reason — two chassis
cluster ones needed `authentication-key` and the VRRP one needed a prefix length
on `virtual-address`. Under-reporting blindness is exactly the `xpfarg` hazard
#9265 says any census here owes a control for: a container scores REJECTED
because its fixture was invalid, not because its body was checked. The rows above
are the corrected measurement; the `clean` column IS that control, asserted in
the test as a fatal precondition on every row.

## The SECOND ratchet this change moves, and what it exposed

`TestMultiLeafAbsorptionPopulation9206` tracks every `multi: true` leaf under a
`closedWorld: true` container. Arming brings seven more inside, so it moves
25 -> 39 absorbing / 20 -> 27 distinct (each new site has a `groups` rehost).

Its own failure text says to check whether the new absorption reaches the
COMPILER. Measured:

```
security nat proxy-arp interface <if> address   STRICT COMPILE REJECT
policy-options community <c> members    COMMITS -> Members:[65000:1 xpfbogus9206 v1]
system login class <c> permissions      COMMITS -> Permissions:[view xpfbogus9206 v1]
address-set <s> address (both books)    COMMITS -> Addresses:[a1 xpfbogus9206 v1]
address-set <s> address-set (global)    COMMITS
```

#9206's discriminator holds: the two that reject are the two whose value type has
a downstream validator.

**These four are PRE-EXISTING, and I measured that rather than assuming it.** On a
pristine `origin/master` worktree with no arming applied the compiled output is
BYTE-IDENTICAL, and all six spellings commit clean at `configstore.CheckText`
there too — including the bracketed-list form
(`members [ 65000:1 xpfbogus9206 v1 ]`), which is not a flat-run question at all.
Absorption is a property of the `multi` leaf and `SetPath`, not of `closedWorld`.
Arming only brought these containers inside the census's DEFINITION; before it the
same garbage was also accepted as a plain sibling statement, so arming is a strict
improvement that does not close the multi-leaf route.

Filed as **#9490** rather than fixed here — the remedy is a per-leaf validator for
`validateMultiValueLeaf` (#2497), a different change from arming a container's
keyword world, and `system login class permissions` needs its
`MappedPermissions` semantics settled before anyone picks a direction.

## The prior decision this change reds, and why it is re-anchored

`TestInstanceNameBlindInstrumentStillDiscriminates9091` pinned
`/system/login/class` as one of three known-BLIND witnesses. Arming it reds that
cell by design, and the cell's own failure text prescribes the move: *"Either it
was armed (then lower the ceiling and say so) or the instrument stopped detecting
blindness — and those two look identical in the count."*

So it moves to the known-ARMED direction rather than being deleted. Both
directions stay populated, and the entry is now the strongest in either, because
it is pinned by an end-to-end measurement in BOTH states (#9091 measured it
ACCEPTED, this change measured it REJECTED with the declared body still
committing). The two remaining blind witnesses are deep containers, so criterion
1 keeps them blind and makes them durable anchors.
