# #9170 — the printed install digest was re-hashed from the public file

## Defect

`xpf-deploy.py fetch --no-import` / `--qcow2-only` does not consume the image.
It verifies the downloaded qcow2 against the signed manifest and then prints a
one-liner for the operator to run **later**:

```
echo '<sha>  <out>/xpf-<ver>.qcow2' | sha256sum -c - && sudo install -m 0644 -D ...
```

`<sha>` came from `sign.sha256_file(qcow2_pub)` — a **second read of the same
public path, taken after the signature check had already finished**. So the
printed digest bound "the bytes in `--out` at print time", not "the bytes that
passed the signature".

The value that should have been printed had already been computed and thrown
away: `sign.verify_image_artifact` compares `sha256_file(path)` to the signed
manifest entry and then returns a bare `True`.

The window is not sub-millisecond. Between the verification read and the digest
read sit a complete `verify_manifest_map` → `verify_and_read` →
`verify_signature` → `subprocess.run(minisign)`, two `mkdtemp`/`rmtree` cycles
and the watermark `os.replace`. `--out` is the operator's own directory, and
`_verified_private_artifacts`' docstring says of it, three hundred lines up in
the same file: *"The public `--out` dir may be writable by another local
process."*

A local process that wins that window gets its bytes installed **and** gets the
operator's own `sha256sum -c` to bless them. That is the last integrity check
before `sudo install` puts an image on a firewall.

## The guard was vacuous

`test_xpf_deploy_golden_guard_8597.py:159` asserted

```python
self.assertIn("expected_sha", window,
              "the digest must be computed from the verified file, not "
              "left for the operator to look up")
```

The **message** names exactly the property the code lacked. The **predicate** is
a substring the defective code satisfies — `expected_sha` was present, it was
just derived from the wrong bytes. Run at the base commit
`2f4165461ab84f6118788f6089c39ae7da7c355c`, all four cells in that file pass
over the live defect.

## Remedy

1. `scripts/dist/sign.py` — `verify_image_artifact` returns the **signed
   digest** (`manifest[base]`) instead of `True`. All four existing call sites
   ignore the return value or `assertTrue` it; a hex string is truthy.
2. `scripts/deploy/xpf-deploy.py` — the verification loop keeps what each
   verification established (`verified_sha[w] = sign.verify_image_artifact(...)`)
   and the `--no-import` branch prints `verified_sha["qcow2"]`. The re-hash is
   gone: there is no second read of the public path at all.
3. `scripts/deploy/test_xpf_deploy_golden_guard_8597.py` — the vacuous
   `assertIn` keeps only the weak claim it can actually support (a digest is
   printed at all) and gains an `assertNotIn` on the re-hash spelling, with its
   own comment saying it is necessary and not sufficient and pointing at the
   behavioural guard.
4. `docs/distribution.md` — states that the printed digest is the signed one and
   why the two importing paths do not need it.

plus `git diff --quiet HEAD`, asserted after every cell. Every run bounded by a
300 s budget; a timeout scores VOID, not a kill. Failures are matched by NAME

No survivors. M4 is the one that matters for wiring: the helper is unchanged and
still called, and only the binding between its result and the printed value is
cut. A source-text assertion that `verify_image_artifact` appears in the file
cannot see it; the behavioural cells do.

Recorded rather than run: hashing the public file *immediately before* the
verify call is an equivalent mutant, not a survivor — `verify_image_artifact`
re-hashes and dies on any mismatch, so the two values can only differ in a run
that aborts.
