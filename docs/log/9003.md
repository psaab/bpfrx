# #9003 — helper control socket: default path, directory adoption, peer identity

## Summary

The daemon pushes the WireGuard local private key and every per-peer preshared
key in cleartext across the userspace-helper control socket. The compiled-in
default put that socket under `os.TempDir()`, `os.MkdirAll(dir, 0755)` adopted a
pre-existing directory of any owner, and neither end ever asked who the peer
was.

## Deliberate non-changes, and why

- **The arbitrary `control-socket` path is NOT rejected at commit.** A
  parse-time rejection of a path outside `/run/xpf` would break configs that
  commit and boot today, and #7139 already recorded that as needing its own
  #1960 no-brick analysis. The runtime trust check makes it unnecessary for the
  confidentiality property: an untrusted DIRECTORY is refused wherever it is.
- **`/tmp` itself still passes the directory check.** It is 1777 — world-writable
  AND sticky, root-owned — so a non-owner cannot rename or unlink our objects
  there. A deployment that committed `control-socket /tmp/xpf.sock` keeps
  working. What is refused is the SUBDIRECTORY shape (`/tmp/xpf-userspace-dp`),
  which is exactly the one an unprivileged user can own, and which the old
  default created.
- **`PrivateTmp=yes` was not added to the unit.** The issue itself calls it
  "cheap belt-and-braces but not the fix", and the repo ships no production unit
  (only `test/incus/xpfd.service`); the packaging unit is generated elsewhere.
  With the default off `/tmp` entirely, it would guard nothing that the
  directory + peer checks do not already guard.
- **`ValidateUnixSocketPath` is unchanged.** `configstore.CheckText` is the
  commit gate; adding a world-writable-directory rejection there would evaluate
  filesystem state at commit time, which is neither stable nor available on the
  peer during config sync.
