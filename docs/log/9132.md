# #9132 — a BARE routing-instance interface reference bound no addressed unit

- **Timestamp**: 2026-09-06
  - **Action**: added the missing bare→units fan-down to
    `buildInterfaceRouteTables` and `buildInterfaceRoutingInstances`, hoisting
    the rule into one shared `pkg/config` helper the zone binder uses too.
  - **File(s)**: `pkg/config/host_inbound_effective_view.go`,
    `pkg/dataplane/userspace/routes.go`,
    `pkg/dataplane/userspace/bare_ri_iface_fandown_9132_test.go` (new),
    `docs/config-schema.md`, `docs/userspace-dataplane-architecture.md`

    Both routing binders keyed a reference on
    `config.CanonicalInterfaceUnitRef(ifname)` alone. For a BARE `ge-0/0/0` that
    is the bare name, while the per-unit snapshot rows carrying the ADDRESSES
    are `ge-0/0/0.<unit>` — so the reference reached nothing addressed. The unit
    row fell back to `inet.0` with `RoutingInstance == ""`, which is precisely
    the field the Rust side derives the connected table from, so #2388's table
    scoping was rendered INERT rather than wrong.

  - **It is NOT the #9063 collapse, and the difference decides the fix.**
    #9063 was `logicalUnitDeviceKey` normalizing two DIFFERENT spellings onto
    ONE key, so the consumer could not tell a whole-device reference from a
    unit-0 one — an OVER-match, fixed by reading the RAW reference to recover
    the distinction. #9132 collapses nothing: `CanonicalInterfaceUnitRef` leaves
    `ge-0/0/0` and `ge-0/0/0.0` distinct (measured — it only folds the suffix
    through `CanonicalLogicalUnit` and returns a bare ref unchanged), and the
    bare key simply reaches no row — an UNDER-match, fixed by fanning DOWN.
    Same class (an interface reference whose key shape is held together by a
    note), opposite direction, opposite remedy. Filing it as "the same collapse
    at a third consumer" would have prescribed reading the raw reference, which
    fixes nothing here.

  - **What did NOT move into the shared helper, and why.** The zone binder also
    fans a UNIT reference UP to the base key. That is right for zones
    (host-inbound on the physical interface must resolve) and wrong for routing:
    the base snapshot row inherits the kernel netdev's addresses, which belong
    to unit 0, so binding the base from a `ge-0/0/0.1` reference would move unit
    0's prefix into unit 1's instance — #9063's hazard pointed the other way.
    Levelling the three binders to one behaviour would be consistency achieved
    in the wrong direction, so the fan-UP stays at the zone binder's own call
    site with a comment saying so, and the shared helper carries only the
    fan-down.

  - **An ordering rule the fan-down forces someone to choose.** Before #9132 a
    bare reference and an explicit unit reference could not collide — the bare
    one claimed only the bare key. Now they can. A single pass with plain
    assignment would resolve `ge-0/0/0` in tenant-a against `ge-0/0/0.1` in
    tenant-b by the order of `cfg.RoutingInstances`: deterministic (it is a
    slice, and MEASURED to be in authoring order, not sorted by name) but not a
    rule anyone chose. `forEachRoutingInstanceInterfaceKey` walks twice — pass 0
    binds the reference as written, pass 1 adds fanned units without overwriting
    — so the explicit unit always wins, whichever instance is authored first.

  - **The ordering cell was VACUOUS on its first form, and the mutation matrix
    is the only reason I know.** `TestExplicitUnitRefBeatsAFannedDownBareRef9132`
    originally varied the order of the two `set routing-instances <ri> interface
    …` lines and called the two arrangements "authoring orders". They are not:
    an instance's position in `cfg.RoutingInstances` is fixed by its FIRST
    mention, which is the `instance-type` line — identical in both sub-cases. So
    both produced the SAME slice order, and in that order (bare reference first)
    last-writer-wins happens to AGREE with the rule. The
    single-pass-last-writer-wins mutant P3 SURVIVED. The cell now varies the
    `instance-type` order, ASSERTS the resulting slice order so it cannot
    silently stop varying, and leads with the discriminating arrangement — the
    EXPLICIT unit reference in the EARLIER instance.

    That shape also yields a property worth stating: **pass 0 is byte-for-byte
    the pre-#9132 loop, so the change is PURELY ADDITIVE on these maps.**
    `TestBareRefFanDownIsPurelyAdditive9132` asserts it against the old loop
    re-implemented verbatim as the oracle, so it cannot drift into agreeing with
    the new code by paraphrase.
