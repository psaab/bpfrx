## The ratio was nearly meaningless until the decline was added

Batches 2 and 3 both drew candidates from the sweep's SILENT column. That column
is *defined* as "differs, and the operator is told nothing" — so an
admitted/declined ratio computed over it is close to 1 BY CONSTRUCTION, and
reporting 8/0 would have been reporting the selection rule, not a finding. The
ratio only carries information once candidates that can be declined are inside
the population.

## The decline, and why the obvious reason for it is wrong

`interfaces <name>` is the sweep's other CANDIDATE-DROP row, verdict
STRICT-REJECTS — which reads as "declined because the drop is loud". Measured,
that is not the case. With a hand-written leaf
(`unit 0 family inet address 10.9.9.1/24`), BOTH arms compile strictly clean and
both yield one interface.

**That row's gate verdict is a property of the single synthesized leaf the
sweep happened to pick, not of the pair.** A per-row verdict derived from one
synthesized leaf does not generalise to the pair it names — worth carrying back
to the sweep's owner, since every row in that table is derived the same way.

The true decline reason is structural and leaf-independent:
`compactNormalizeInScope` is keyed on a (container, head) pair of literal
keywords, and here the head is an operator-chosen INSTANCE NAME. There is no
string to admit. `TestInstanceNamePairCannotBeAdmitted8879` asserts the bound
(two arbitrary interface names must be treated identically, and neither in
scope) plus the corrected fact (the elided spelling is NOT refused), so a later
reader cannot re-derive the wrong reason from the sweep row.
