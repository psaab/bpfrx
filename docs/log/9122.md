# #9122 — a narrowed DHCPv6 group rendered subnet6 with no interface selector

## Defect

`generateKea6Config` states its own invariant and then breaks it three lines
later:

> Kea v6 subnet selection cannot fall back to address matching the way v4 can
> (clients talk from link-local source addresses), so subnet6 REQUIRES the
> interface selector — silently omitting it for a multi-interface group would
> orphan the subnet.

It enforces that with `if len(group.Interfaces) > 1 { return ... }` and then
calls `subnetInterface(group)`, which returns `""` **first** on
`MembersFiltered`. A group narrowed by the RG member filter presents a
*singleton* list, so the guard does not trip and the subnet renders
selector-less. Kea cannot select it for a link-local SOLICIT: a silent, total
DHCPv6 outage for that group, with no error anywhere.

**It is the steady state, not a failover transient.**
`filterDHCPConfigForMasterRGs` is driven by the 2 s periodic converger as well
as by RG edges, so a v6 group spanning two RGs in an active/active cluster
renders this way continuously on *both* nodes.

## Fix

Refuse the narrowed group, keeping #6520's do-not-cross-bind property by failing
LOUD on the family that has no address fallback.

**Its own message, not folded into the existing one.** The two causes are
different states with different remedies — "the runtime narrowed a group you
authored across RGs" versus "you authored this group too broadly" — and the
operator action differs accordingly. That is the #9073 lesson applied: distinct
states need distinct signals.

**The originating report's proposed fix is HARMFUL and is pinned against.** It
returns `group.Interfaces[0]` for a narrowed singleton, which binds the REMOVED
member's pool to the SURVIVOR's interface: precisely the cross-bind #6520 was
filed to stop, re-opened for v6. Kea would lease a foreign prefix on that link.
`TestV6FilteredGroupNeverCrossBindsToTheSurvivor9122` exists solely to make that
regression loud.

**The v4 path is untouched.** #6520's address-fallback remedy is valid there and
invalid only for v6, so a cell pins that v4 still suppresses-and-renders.

### M2 was applied to the WRONG FUNCTION first

`sub.Interface = subnetInterface(group)` appears **twice** — once in
`generateKea4Config` (line 1164) and once in `generateKea6Config` (1335). My
first M2 replaced the first occurrence, so it mutated the **v4** renderer while
claiming to test the v6 harmful-fix. Both cells red'd, which looked like a clean
kill and was the wrong attribution: the v4 cell was reporting a v4 cross-bind I
had introduced by accident.

Re-scoped to the `generateKea6Config` span with a count assertion, M2 reds the
two **v6** cells and leaves v4 alone — which is the result that actually means
what the row says. Same class as the #9009 splice, and the reason a matrix needs
the SITE verified and not just the edit.

M3 is the over-broad detector: a fix that refused every v6 group would satisfy
the subject cell while removing DHCPv6 entirely.

## A fixture defect caught by a panic

My first v6 fixture used `DHCPLocalServer` — the **v4** container.
`generateKea6Config` reads `DHCPv6LocalServer`, so it rendered nothing and
panicked on the nil. Loud, and therefore harmless; a fixture that had quietly
rendered an empty config would have made every cell pass while asking a
different question.
