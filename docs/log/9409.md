# 9409 — a forwarding instance's protocols rendered into the GLOBAL FRR instance

- **Timestamp**: 2026-09-07
- **Action**: reject `protocols` under `instance-type forwarding` at strict
  commit, warn on the tolerant path, and drop the stanza at the FRR assembler
  so the downgrade is inert rather than globally active.
- **File(s)**: `pkg/config/compiler_validate_strict_forwarding_protocols_9409.go`
  (new), `pkg/config/compiler_opts.go`,
  `pkg/config/compiler_uniformgates_routing_rib_rpm.go`,
  `pkg/daemon/daemon_ipmon.go`, `pkg/cli/apply.go`, `docs/multi-wan.md`,
  `pkg/frr/README.md`, plus two new test files.

## Re-measured at HEAD, all four channels plus the render

```
routing-instances { ISP-B { instance-type forwarding;
    protocols { ospf { area 0.0.0.0 { interface ge-0/0/1.0; } } } } }
  configstore.CheckText        ACCEPT
  config.CompileConfig         ACCEPT
  config.CompileConfigLenient  ACCEPT
  config.SchemaValidate        ACCEPT
  rendered -> TWO `router ospf` blocks, NEITHER with a `vrf` suffix
forwarding + isis -> a GLOBAL `router isis xpf`
forwarding + rip  -> a GLOBAL `router rip`
forwarding + bgp  -> `router bgp 65001` / ` neighbor 10.0.0.2 remote-as 65002`
                     under a SECOND global block — it JOINS THE GLOBAL AS
CONTROL virtual-router + ospf -> `router ospf vrf vrf-ISP-B`   (correct)
```

The control matters: this is specific to the forwarding TYPE, not to
per-instance protocols in general, so the remedy must not remove the feature.

## Severity: I re-derived it and agree with Medium

The filing already graded this Medium against the source report's High, and
the reasoning holds up:

- **Reachability requires a non-Junos authoring act.** Junos `instance-type
  forwarding` takes `routing-options`, not `protocols`, so a config migrated
  from a vSRX cannot contain it — it would not have committed there.
- **No shipped or test config composes it.** `test/incus/fbf-two-upstream-config.set`
  is statics-only; `docs/multi-wan.md`'s recipe is statics-only.
- **The consequence when reached is genuinely bad** — an IGP in the global
  routing context with its routes in the main table while the FBF table stays
  empty, and a BGP neighbor attached to the global AS, all silently.

Bad consequence × authoring path the product's own documentation never
describes = Medium. It would be High if any shipped config composed the two.

## The remedy is two halves and the second is what makes the first safe

`validateForwardingInstanceProtocolsStrict` rejects at commit / commit-check,
naming the instance AND the protocol — mirroring the #5830 per-instance
next-table rejection. `opts.lenientForwardingInstanceProtocols` downgrades it
to a warning on the tolerant load / peer-sync paths so a box already carrying
the config still boots (#1960).

That downgrade is only defensible because `assembleFRRConfig` now NILs a
forwarding instance's protocol pointers. Every other lenient gate in that
uniform block cites an "and the applier keeps it inert" clause; without the
drop, this one would have had none — the leniently-loaded config would boot and
quietly rewrite the global routing table, which is the defect. `pkg/cli/apply.go`
(the legacy standalone path, which builds its own InstanceConfig) drops them
too.

The RENDERER is deliberately left alone. Nothing in `pkg/frr` can distinguish
"the master table" from "a forwarding instance's own table" through one empty
string; the discriminator only exists at the assembler, which is where the fix
belongs.

The compiler still COMPILES the protocols into the tolerant config. Erasing
them there would make `show configuration` disagree with what was committed —
the drop is a render decision, not a config-model one.

## Validation

- `go test ./...` — full tree, green.
- Controls carried in the same table as the rejections: a statics-only
  forwarding instance still commits (the documented FBF recipe), and a
  `virtual-router` with the same protocols still commits and still renders
  `router ospf vrf vrf-ISP-B`. A gate that also rejected those would be #9409
  "fixed" by deleting the feature.
- `TestGlobalProtocolsRenderExactlyOnce9409` asserts the acceptance criterion
  on the RENDERED managed section, with two positive controls in the same
  render (the global BGP neighbor and the global OSPF activation must still be
  there) so the counts cannot pass by everything vanishing, plus the
  forwarding instance's statics still rendering into `table <id>`.
- Mutation results are in the PR body.

**No cluster smoke was run, and none would have been evidence.** No shipped or
test config in the tree composes `protocols` with `instance-type forwarding` —
that absence is part of the severity argument above, and it is the same reason
a green smoke could not have reached this code.
