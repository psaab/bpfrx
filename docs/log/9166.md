## Half one — the failure was invisible

Three surfaces, all silent, and the failure produced the **same observation as
"flow export is not configured"** on every one:

- `FlowExportError()` had zero production readers (only a `_test.go` call site);
- the `xpf_flow_export_collector_*` family is *"omitted entirely … when no flow
  export is configured (empty slice)"* — and an empty slice is exactly what a
  failed build produces;
- `show` renders the configuration as present, because the config **is** present.

The triggering fault is ordinary: a collector hostname unresolvable at boot, or
a pinned source-address bind attempted before the interface is up. NetFlow is
frequently the only record of what traversed the box, and its absence looks
exactly like a deployment where it was never turned on — which is why nobody
investigates.

### The remedy, and why it needs a denominator

`flowexport.BuildState{Family, ConfiguredGroups, BuildFailed}`, emitted as
`xpf_flowexport_configured_groups{family}` + `xpf_flowexport_build_failed{family}`,
**for both families on every scrape, including at zero**:

| observation | meaning |
|---|---|
| `configured=0, failed=0` | not configured |
| `configured>0, failed=0` | configured and healthy |
| `configured>0, failed=1` | configured, and the build FAILED |

Two decisions that carry the fix:

1. **The configured count is recorded before the hash gate.** The count of
   RUNNING exporters cannot stand in for it — on a build failure with nothing
   previously running it is also 0, which is precisely the not-configured
   reading the fix exists to separate.
2. **Emitting only the failure would not have worked.** It would leave
   not-configured and healthy both as "the series is absent", and absence is
   also what a scrape that never reached the code looks like — the same
   ambiguity in a new place.

## Half two — nothing retried until the next commit

`reconcileFlowExporters` runs only from the apply tail
(`daemon_apply_tail.go:259`) and the boot block (`daemon_run.go:370,384`), so
the retry cadence was **"the next commit"**, which on a stable box is never —
while both faults the #3742 design cites clear on their own minutes later.

`armFlowExportRetry` starts a single-flight loop that re-reconciles every 30s
against the **live active config**. Reading the live config, not the config
captured at failure, means a commit that removes flow export converges the loop
instead of resurrecting deleted config — the reason `activeConfigForRebind`
exists (#4899). The loop is cancelled and JOINED at shutdown under a bounded
timeout: a late tick must not reconcile against a torn-down subsystem, and an
unbounded join could push the stop past the systemd `TimeoutStopSec` and get the
process SIGKILLed before the HA takeover fence runs (the #6397 shape).

The arm is placed in `reconcileFlowExporters`, **outside both reconcile
mutexes** — the loop's tick re-enters `reconcileFlowExporters`, which takes
them.

## What was NOT changed, deliberately

- **`d.flowHashSet = false` on the failure path.** The finding narrates
  withholding the hash as the defect. It is the **fix**: without it the next
  commit is hash-gated into a permanently dead family. Recorded so a later pass
  does not "fix" it.
- **`dialCollectors` still fails the group on a dial error**, and the
  build-before-swap still keeps the old exporters running. Those are the #3742
  availability design; this change makes that design *observable and
  self-healing*, it does not weaken it.

### Three of these were SURVIVORS first, and each one changed the code

**F and G survived the first matrix.** G is the wiring: nothing tested that
`reconcileFlowExporters` arms the retry at all, because every retry cell drove
`tryFlowExportRetry`/`armFlowExportRetry` directly. The retry existed on paper.
`TestAFailedReconcileArmsTheRetry9166` now drives the real reconcile with an
unassignable pinned source-address — the same fault class the issue names — and
`TestASuccessfulReconcileDoesNotArmTheRetry9166` is its control, without which
"arm unconditionally" satisfies it and every healthy box runs a pointless 30s
reconcile forever.

F survived for a different reason: the convergence check was **redundant**, and
a second guard caught the mutation. Removing the redundancy exposed a real race
— re-deriving convergence from the error fields loses a commit-path failure that
lands between a tick's reconcile and its disarm, because that reconcile's arm
finds the loop already `active` and no-ops. One `pending` flag, updated under one
mutex, is now the single decision point.

**H survived a second matrix** — a genuine survival, confirmed with 2535 tests
executing rather than inferred from a killed run. The single-flight guard was
not exercisable: one loop and one loop per failing commit are the same
observation from outside, because the harm (each extra loop overwrites
`cancel`, so earlier ones outlive shutdown's cancel and are only reaped by the
bounded `wg.Wait`) surfaces as a 3s stall in the stop sequence, not as state a
cell can read. `loopStarts` makes it exercisable rather than excused, and K
scores the sibling guard the same way.

### A note on scoring

The first matrix was killed mid-run (exit 144, environmental). Two rows had
printed `SURVIVED no test failed` — which, from a run that collected nothing, is
**VOID, not survived**. The re-run asserts that ≥50 tests actually executed
before scoring, so a killed or empty run can no longer be recorded as a
survival. H turned out to be a real survivor; the other did not.
