## The design question: what does the allowlist mean?

Two candidate sets, and the choice is not cosmetic.

- **{gre, ip6gre, wireguard}** — "modes the dataplane carries". Makes #4785's
  `ipip` rejection one case of a general rule, which is what the issue asks for,
  but preempts #4785's diagnostic for an explicitly-typed `mode ipip`.
- **{gre, ip6gre, wireguard, ipip}** — "modes the system recognises". Leaves
  #4785's endpoint-naming diagnostic in place for every ipip route.

Decided by **measurement, not preference**: with the strict set in place,
`pkg/configstore` is fully green — every #4785 test, including the #1960
no-brick pair and the peer-effective gate, still passes. The strict set costs
nothing, because #4785's gate keys on the EFFECTIVE mode of an emitted endpoint,
and its most important case is the one the leaf can never see: an `ip-*`
interface with **no `mode` statement at all**, which the parser defaults to
`ipip`. The two mechanisms are complementary, not competing.

## The allowlist is a mirror, and the agreement is what is asserted

The SSOT is `tunnel_mode_kind` in the Rust dataplane. `TunnelModeNames` in
`pkg/config` mirrors it. The two are in different languages so neither can
import the other, so the drift guard parses the Rust match arms and asserts
equality — never a literal on either side, because a literal encodes which copy
is trusted and the defect class here is exactly the two drifting apart. Same
shape as `MasterPasswordPRFNames` against `configstore.prfHash`.

The parser has its own **non-vacuity floor**: a regex that stopped matching
would hand back an empty set, and "the Go list equals the empty set" is a
comparison that proves nothing while looking like a clean pass.

## #1960 no-brick, measured rather than assumed

`compileTreeLenient` — what `Store.Load` and `Store.SyncApply` use — does **not
call `schemaValidateExpandedTreeForNode` at all**, so a leaf validator cannot
reach the boot path. That is a structural answer, but structure read from source
is a belief, so it is bound as a test at the STORE ingress, not at the
validator: `Store.Load` must boot a persisted `mode banana` config AND preserve
the stanza verbatim, while the strict path rejects the same text. Both halves,
because a validator that accepted everything would satisfy the boot half alone.

## A negative cell needs a positive control

Every row of `TestTunnelModeRejectsUnknownValues_6924` is the SAME config with
`source` and `destination` present, differing ONLY in the mode token — so a
missing sibling or a stanza typo cannot be what rejects a row. The accepted rows
(`gre`, `ip6gre`, `wireguard`) are the control: without them a validator that
refused every value would satisfy every rejection row and break every tunnel on
the box. The rejection assertion also requires the error to NAME the offending
mode, so an unrelated complaint cannot pass the row.

## The side finding: a fixture that used the value the bug falls back to

Adding the validator reds `TestCompactBlockEquivalenceInventory2419`:

> `testdata/compact_block_divergences_2419.txt` lists "interfaces xpfname tunnel
> mode" as compact-blind, but it now compiles equivalently.

It does not. The #2419 census synthesises probe values from `valueExamples[0]`
and `[1]`. With `{"gre", "ip6gre"}` the probe writes `tunnel mode gre` compactly;
the compact spelling **drops** the value and `Mode` falls back to the parser's
default — which is `"gre"`. Dropped value and fallback become identical, the
divergence reads as EQUIVALENT, and the entry looks stale.

Probed directly: with `gre` first the census state for the site is
`"equivalent"`; with `ip6gre` first it is `"divergent"`, `checked` unchanged at
546 either way (so this is not the cell draining into a skip bucket — it is the
cell answering wrongly). Examples are therefore ordered `ip6gre, gre`, with the
reason recorded at the leaf. A fixture must never use the value the bug falls
back to.

Had this gone the other way — removing the inventory line because the test said
to — #2419 would have lost a live divergence to a stale-allowlist entry, which
is the exact failure that test exists to prevent.
