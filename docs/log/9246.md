# 9246 — a bracketed zone list drops the rule it was attached to

## The mechanism, dumped rather than inferred

`set security policies from-zone trust to-zone [ untrust dmz ] policy p1 ...`
lexes to:

    [security]
      [policies]
        [from-zone trust to-zone untrust]     <- the 4-key HIERARCHICAL shape
          [dmz policy p1 then permit]          <- the whole rule absorbed as key tokens

The bracket strips to a 4-key node, so the compiler takes the hierarchical
branch and builds `trust->untrust`. `FindChildren("policy")` then matches
nothing, because the only child is named `dmz`. The rule is not misplaced or
half-applied — it is absorbed into a key list and exists nowhere.

`from-zone` collapses differently and was NOT measured on the issue:

    [from-zone trust dmz to-zone]              <- keys SHIFT
      [untrust policy p1 then permit]

so `Keys[3]` is the literal string `"to-zone"`. That is caught today only by
accident, as an undefined zone named "to-zone" — loud, but blaming the wrong
thing and telling the operator to define a zone rather than remove a bracket.

## Why reject rather than expand

Junos accepts no bracketed list on `from-zone`/`to-zone`; a policy context is
ONE zone pair. Expanding would invent a semantics the platform does not have,
and would owe an answer to a question this is not the change to decide: what a
single policy NAME means once it exists in several contexts. Rejecting is
smaller, matches the platform, and restores the operator's ability to see the
problem.

## Where the check lives, and why not in the strict validator

By the time the config is compiled the residue is GONE: the pair looks like an
ordinary context that happens to carry no policies, which is also what a
legitimately empty context looks like. So the defect is captured where the AST
is still visible (`compiler_security_policy.go`) and recorded on
`SecurityConfig.MalformedZonePairs` — the same record-at-compile /
reject-in-a-strict-gate shape as `ScreenProfile.UnknownLeaves`.

It runs BEFORE the undefined-zone gate so the from-zone form is named correctly
rather than surfacing as a zone called "to-zone", and it carries the same #1960
lenient downgrade as its neighbour: `Store.Load` and peer sync warn instead of
refusing, so a config an older binary accepted still boots.

## Two false positives, found by running the suite rather than reasoning

The first detector flagged "any child of a hierarchical pair that is not
`policy`". That is wrong twice over, and neither case was visible from the
mechanism:

  - `inactive: policy p1 ...` is a SUPPORTED Junos spelling (#2008 H1). The
    marker is a statement PREFIX, so the node's first key is `inactive:` and
    `policy` follows -- byte-identical to the absorbed shape. Refusing it
    rejected a spelling the product accepts, and the repo's own
    TestInactive_UpgradeEquivalence caught it.
  - the #2419 census synthesises placeholder paths like
    `from-zone xpfarg xpfarg xpfarg policy ...`, which are not configs.

So the test narrowed to the ABSORBED-RULE signature: a child whose first key is
not `policy` and is not the parser's `inactiveMarker`, but which carries
`policy` LATER in the same key list. Both conditions together are what separate
absorbed tokens from every legitimate child.

Adding a struct field also perturbed the #4406 goldens with
`"MalformedZonePairs": null` on every case. It is a compile-time DIAGNOSTIC, not
semantic content, so it carries `json:"-"` -- otherwise it would shift every
fixture and every ConfigFingerprint comparison the elision censuses run, for a
field that is nil in every valid config.

## Scope: from-zone is deliberately left alone

`from-zone [ trust dmz ]` collapses the other way, shifting the keys so that
Keys[3] becomes the literal string "to-zone" -- and it is ALREADY refused, as an
undefined zone named "to-zone". That message blames the wrong thing, but it is
LOUD, and the silent to-zone case is the defect. Widening the detector to cover
it also flags the census placeholders above, which is a real cost for a message
improvement. `TestBracketedFromZoneIsStillRefused9246` pins the OUTCOME rather
than the wording, so it stays green if someone improves that message later.

## Mutation matrix, including the call site

    remove the gate from uniformgates (WIRING)   -> 2 cells red, "committed clean"
    neuter the detector, call site intact        -> 3 cells red, "committed clean"
    drop the inactive: exemption                 -> TestInactive_UpgradeEquivalence reds
    record the defect but do NOT skip the build  -> SURVIVED at first

The last one is the useful entry. Recording without skipping is invisible to
every strict-path cell, because the gate refuses either way — but on the
TOLERANT path it leaves a phantom `trust->untrust` context carrying zero
policies, which an operator would see in `show security policies` next to a
warning about the rule they actually wrote.
`TestMalformedPairLeavesNoPhantomContext9246` was added for it, and the mutant
now reds with "phantom context trust->untrust".

## Controls

Two, and both are load-bearing. `TestPlainZonePairStillCompiles9246` asserts the
ordinary spelling still compiles AND still carries its policy — a gate that
refused everything would satisfy both defect cells, and `policies=1` is the half
that catches a gate admitting the context while dropping the rule, which is the
defect itself. `TestSeparateStatementsPerZoneStillWork9246` asserts the
per-zone spelling the error message recommends still produces two contexts,
because refusing it would make the message a lie.
