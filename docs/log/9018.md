# #9018 — the AF_XDP worker discarded the proven peer identity on two authenticated decap arms

- **Timestamp**: 2026-09-06
  - **Action**: matched `try_decap`'s error instead of `.ok()?`-ing it, so
    `DecapError::Keepalive(pk)` and `DecapError::MalformedInner(pk)` reach the
    same `note_worker_observed_endpoint` the success arm uses. The frame is
    still declined: neither arm carries a deliverable inner packet, so the "no
    TUN write" contract is unchanged.

    **Severity, measured, because the recovery path bounds it.** The identity
    itself is NOT recoverable at that site — `.ok()?` returned `None` and the
    frame continued as opaque outer UDP, so nothing downstream ever saw the
    pubkey. But the CONSEQUENCE self-heals: handshake records (types 1/2/3) are
    still steered to the kernel by
    `wg_steer_to_kernel_on_port_match(local_destination, is_transport_data) =
    local_destination && !is_transport_data`, and the socket path learns the
    endpoint from them. `REJECT_AFTER_TIME_NS` is 180s and `REKEY_AFTER_TIME_NS`
    120s, so the roaming stall is bounded at roughly 120-180s — degraded, not an
    outage. `docs/wireguard-interop.md` had already reached that same bound for
    the pre-#7230 socket-path version of this defect.

    **One correction to the framing.** The report ties the identity to the
    Keepalive/MalformedInner COUNTERS. Those do not need it: `count_decap_err`
    matches `DecapError::Keepalive(_)` / `MalformedInner(_)` and bumps a single
    engine-wide counter, discarding the key. The identity is needed for ENDPOINT
    LEARNING, which is what actually broke.

    **A hollowed doc claim, found on the way.** `docs/wireguard-interop.md` says
    "Endpoint learning for authenticated datagrams now holds on any interface
    for both the keepalive and malformed-inner arms." That was true of the
    SOCKET path when written, and #8274 step 3 hollowed it by moving
    transport-data decap into the worker — where `.ok()?` discarded exactly the
    two arms #7230/#7686 had just created. Nothing re-checked the sentence.
    Corrected in the same change.

    Also corrected: `decap.rs`'s `inner.is_empty()` branch is UNREACHABLE
    (`try_decap` returns `Err(Keepalive(..))` before it can produce an `Ok` with
    a zero-length plaintext) and carried a comment saying the control thread's
    endpoint learning "still wants it" — describing, on dead code, the very work
    the `.ok()?` above was throwing away. The branch stays as a defensive guard;
    the claim is gone.

    NOT changed: `note_authenticated_recv` still clears `t7_armed_send_ns` from
    a received keepalive. The report suggests not clearing it when the endpoint
    could not be applied — but with the endpoint now applied, "the session is
    alive" is accurate, and the no-reply reinit arm is not the right mechanism
    to compensate for a stale endpoint. Changing T7 is a protocol-timing change
    with a much wider blast radius than this fix.

    Four PRODUCTION mutants killed, one per arm: M1 (revert to `.ok()?`) reds
    both roam cells; M2b (an AEAD FAILURE reported as an identity-carrying
    `MalformedInner`) reds the unauthenticated CONTROL — the arm that makes the
    other two safe rather than merely convenient; M3 (only `Keepalive` matched)
    reds the malformed-inner cell; M4 (recording `dst_port` instead of
    `src_port`) reds both, which is why the fixture roams the PORT as well as
    the address. A fifth attempt was recorded VOID, not survived: it called a
    `single_peer_pubkey` helper that #7686 deleted, so it never compiled — a
    filtered result line made that look identical to a clean pass until it was
    re-run unfiltered.
