# #9367 — a panicked worker's V_min slot was never vacated

## Defect, re-verified at the base commit (`c525bb966`, `origin/master`)

`PaddedVtimeSlot::{publish, vacate, read}`
(`userspace-dp/src/afxdp/types/shared_cos_lease/vtime.rs`) has **no TTL,
generation, epoch or liveness input**. `participating_v_min_snapshot` counts
every non-sentinel peer slot and takes the MIN; `read()` returns `None` only
for the `NOT_PARTICIPATING` sentinel.

Exactly two production `vacate()` call sites exist, and BOTH are executed by
the owning worker:

- `cos/queue_ops/accounting.rs` — this worker's last flow bucket on the queue
  drained;
- `worker/cos/mod.rs` — binding reset / HA demotion.

A worker that exits by PANIC executes neither. `spawn_supervised_worker`
(`coordinator/supervisor.rs`) catches the unwind, records a message, sets
`runtime_atomics.dead = true`, and lets the thread exit. Nothing respawns it.
The floor `Arc` survives, because `coordinator/cos_leases.rs` reuses an
existing floor while `f.slots.len() == num_workers` and a panic does not change
`num_workers`.

The sweep that should own this ALREADY EXISTS and skipped it:
`retire_worker_holders_where` (`coordinator/status.rs`) walks every `.dead`
worker under a one-shot `holders_retired` CAS and reclaimed **NAT holder bits
only** — #7092 fixed that class for NAT and did not enroll V_min.

Static re-verification at the base commit: `grep -rn 'vacate()' userspace-dp/src`
returns the two worker-side sites and the test-side calls, and
`retire_worker_holders_where` touched only `iface_nat_allocators`,
`retire_worker_from_pool_rules` and `nat64`.

## Consequence, and its size

`cos_queue_v_min_continue` compares `queue_vtime <= v_min + lag`. The dead
worker's `queue_vtime` is frozen while survivors' advance, so the check fails
permanently. After `V_MIN_CONSECUTIVE_SKIP_HARD_CAP` failures the worker
force-continues but HALVES its suspension window toward
`V_MIN_SUSPENSION_MIN_BATCHES`, and the window is restored to full ONLY on a
PASSING check. With the frontier pinned there is never a passing check, so the
window decays 1000 -> 64 and sticks. Steady state is 8 throttled + 64
suspended: **the fairness brake is off for 64/72 = 88.9% of drain
opportunities** on that exact class.

That is a standing ~11% drain-opportunity tax, not a collapse — and it is
ADDITIVE to the RX capacity the panic already cost, on a box that is already
visibly degraded (`xpf_userspace_worker_dead`, a `PanicMessage` status field).
Severity LOW-MEDIUM, recorded as such.

**It is not "for the life of the process".** A coordinator teardown discards
the map; a worker-count change fails the floor-reuse filter and builds a fresh
all-sentinel floor; removing and re-adding the exact queue drops the key. Under
unchanged operation none of those happen, so the poison can last indefinitely.

## Fix

`Coordinator::vacate_worker_v_min_slots(worker_id)`, called from
`retire_worker_holders_where` under the SAME one-shot `holders_retired` CAS —
the #7092 shape applied to the second structure of the same kind.

Single-writer is preserved, not waived: the sweep runs only for a worker the
supervisor already marked `dead`, so the owning writer has exited and this is
the only writer left. The floors map is read through `load_full()`, so a
concurrent reconcile store cannot tear the walk, and a floor built afterwards
starts all-sentinel.

It returns the number of slots that were actually participating, so the log
line means "a pinned frontier was released" rather than "the sweep ran".

## What I inherited vs what I changed

A previous lane died on a spend limit leaving `/var/tmp/wt-9367` with 4 modified
files and this log. Read before reuse. The production change
(`vacate_worker_v_min_slots` + its call site), both READMEs and two of the three
cells are INHERITED and sound; rebased from `4467d86c5` onto `c525bb966`.

Two corrections, both found by reading rather than assuming:

**1. The wiring cell was FAILING, and the reason matters more than the fix.**
The dead lane left `/var/tmp/wt-9367-test.log` and `-probe.log` — a dead run's
measurements, not citable as mine, but a pointer. They record
`refresh_status_vacates_a_dead_workers_v_min_slot_9367` red with
`left: Some(4242), right: None`, and the probe log narrows it to `PROBE-post
floors`: the floors map was EMPTY after `refresh_status`. (Both logs checked for
`no space left on device` first — zero hits, so they are a real failure and not
a disk void.)

Cause: `refresh_status`'s FIRST statement is `refresh_bindings`, which runs
`refresh_cos_owner_worker_map_from_binding_statuses` ->
`refresh_cos_runtime_maps` and REBUILDS `cos.queue_vtime_floors` from the plan.
A hand-stored floor for a queue the plan does not contain is discarded before
the sweep ever walks the map. The cell now builds the floor through the
production allocator (`exact_queue_forwarding_fixture`, rate raised to 500 MB/s
because the fixture's 50 MB/s is BELOW `COS_SHARED_EXACT_MIN_RATE_BYTES` =
2.5 Gb/s — caught by the cell's own fixture assertion rather than by a silent
pass on an empty map), and it asserts `Arc::ptr_eq` on the floor across the
tick.

That identity check is the substantive finding. A rebuilt floor is all-sentinel,
so `slots[N].read() == None` is bit-identical to the vacate having worked: the
obvious assertion is vacuous unless the floor is known to be the SAME Arc the
poisoned value was published into. The reuse filter
(`slots.len() == num_workers`, `cos_leases.rs`) is what keeps it alive, and a
panic does not change `num_workers` — which is also why the defect persists in
production.

**2. The vacate was ungated, and its own doc comment was false for a sibling
call site.** The inherited prose said the single-writer contract holds "because
the sweep runs only for a worker the supervisor already marked dead". That is
true of `retire_dead_worker_holders` and FALSE of `retire_all_worker_holders`,
which passes `|_| true` and runs in `stop_inner` BEFORE `workers.stop_and_clear`
— i.e. while those workers are still running. An ungated vacate there races a
live `publish()` on a slot documented single-writer, and buys nothing, because
the same teardown stores an empty floors map a few statements later. The vacate
is now gated on `atomics.dead`, the comment says why the gate is load-bearing
rather than belt-and-braces, and a third cell pins it.
