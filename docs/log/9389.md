# 9389 — my own #9062 split the allocator, and the overlap guard was right

- **Timestamp**: 2026-09-06
- **Action**: remove `from_routing_instance` from `SourceNatPoolAllocatorKey`;
  invert the #9062 cell that asserted the split.
- **File(s)**: `userspace-dp/src/nat/source/mod.rs`,
  `userspace-dp/src/nat/tests_scope.rs`,
  `userspace-dp/src/nat/tests_pool_overlap_6979.rs`.

## The error is in my own comment, and it names both halves

#9062's rationale, written by me:

> a port handed to one tenant was unavailable to the other **and** — with the
> flow key also domain-blind — the second tenant's identical 5-tuple was
> answered with the first's translation.

Two claims. **Only the second is a defect.**

- *"A port handed to one tenant was unavailable to the other"* is a shared pool
  **working correctly**. A pool is a finite set of wire identities; one
  `(address, port)` backs exactly one flow, whatever routing instance the traffic
  came from. "Unavailable to the other" is what a shared resource means.
- *"The second tenant's identical 5-tuple was answered with the first's
  translation"* was the real defect, and `SourceNatFlowKey::routing_scope` closes
  it **alone**. With distinct flow keys the two tenants hold two `live_by_flow`
  records and draw two DIFFERENT ports from the one allocator.

I fixed the second and also "fixed" the first, which needed no fixing.

## What the extra split cost

Two pointer-distinct `PortAllocator`s over identical addresses, either able to
mint the same `(addr, port)` for a different tenant. `same_allocator` is
`Arc::ptr_eq`, so the #6979/#8115 overlap index read them as **hostile peers** and
refused every mint whose candidate the other held — `PoolPeerAddressOverlap`,
rolled back into a dropped packet. Measured: five consecutive refusals for the
second instance on a pool with free capacity.

**The guard was right and the split was wrong.**

## What the split did not buy

`pool_addresses_v4`/`_v6` were already in the key, so two genuinely different
pools sharing a NAME across instances were always discriminated by the addresses
they hand out. The routing instance added no discrimination that was not already
there — pinned by `same_pool_name_different_addresses_stays_independent_9389`.

## The general shape

**A change that splits a shared object changes every identity test that object
participates in.** I reasoned about the key's *contents* — which values must
distinguish two flows — and never about the pointer identity of the thing now
being duplicated. `NatScopeCtx`'s own #9062 comment draws the distinction I then
failed to apply: *"The instance NAMES scope which RULE matches; this scopes the
flow's IDENTITY. They are different questions."* The allocator is neither — it is
the shared resource both questions are asked about.

## A cell of mine asserted the error, and is inverted rather than deleted

`source_nat_allocator_key_separates_routing_instances_9062` asserted the split,
with a comment calling the shared-pool behaviour "a quieter defect". It is now
`..._ignores_routing_instances_9389`, asserting the opposite, and the old wording
is quoted in place so the correction is legible rather than silent. Its reference
arm — the same rule in the same instance must still share — is kept verbatim.

**Why it did not catch the regression when it landed:** it was the cell that
*encoded* it. And `two_rules_naming_one_pool_are_not_peers_6979`, which asserts
exactly the invariant #9062 broke, stayed green throughout — its fixture leaves
`from_routing_instance` empty, so both rules built the same key and the split
never happened in it. **A fixture that cannot express the distinguishing field
cannot observe a defect keyed on it.**

## A fixture error of my own, worth recording

My first version of the new cells used the file's `mint()` helper, whose
`NatScopeCtx::default()` has an empty `ingress_routing_instance` — so a rule
carrying `from_routing_instance` never MATCHED and both cells failed at the first
mint. Written the other way round, as an assertion that something does *not*
happen, that fixture would have **passed**, for the reason that the rule never ran.
