## The mistake I made, and what caught it

I wrote the attribution test with a plain AH-bearing IPv6 frame. It passed. Then
I mutated arm E's guard order to check it actually bound, and **the swap escaped
at 4818 passed / 0 failed** (4816 + my two new tests).

On a frame only ONE predicate matches, `if A {a} else if B {b}` and
`if B {b} else if A {a}` record the identical counter — the order swap is a
no-op. And I had written a *precondition* asserting the frame was NOT a
fragment, which is precisely the condition that made the ordering unobservable.
I had proved my own cell vacuous and read it as a precondition.

Nothing about the passing test could have revealed this. Only running the
mutation did.

The discriminating fixture matches BOTH: `IPv6 → Fragment header (non-first) →
AH → TCP`. It is an ext-header reject (#5625) AND a fragment drop (#2562), so the
two orders record different counters. The precondition now asserts both
predicates true with the reason spelled out, so a future fixture cannot quietly
lose the discrimination. Re-measured: the arm E swap now **REDs**
`nat64_build_none_attributes_exthdr_before_fragment_6922` by name.

## The arm D escape is not "untested" — it is UNREACHABLE

Arm D sits lexically inside `if can_rewrite_in_place { ... }`, and

```rust
let can_rewrite_in_place = target_binding.umem.allocation_ptr() == ingress_umem_ptr
    && !is_nat64
    && ...
```

`is_nat64` is bound once at `:726` and never shadowed or reassigned (every
mention between it and arm D's end was enumerated). So inside arm D, `is_nat64`
is provably **false**: its `if is_nat64 { ... }` attribution block, and the
`build_nat64_forwarded_frame` call it guards, can never run.

That is worse than the duplication the issue describes. The **authoritative**
guard-order rationale lives in the DEAD copy, and the LIVE copy carries a comment
pointing at it — *"same SSOT predicates + translator-order rationale as the
direct/in-place copy path above"*. A reader auditing the NAT64 attribution finds
a cross-reference to a comment attached to unreachable code.

`nat64_never_reaches_the_in_place_rewrite_path_6922` pins the invariant the
deadness rests on. It **strips comments first** — the paragraphs above and in
`mod.rs` discuss `!is_nat64` at length, and a scan a doc comment can satisfy is
not a scan of the code — and fails loudly if the binding cannot be found at all.

## Part 2 — the collapse (next)

The single-source case, per the standing discriminator: **single-source**, not
bind-with-an-agreement-test. Arm D and arm E are the same copy fallback, for the
same frame, with the same attribution semantics; the only legitimate difference
is the enclosing match syntax. A NAT64 drop attributed differently depending on
whether the in-place rewrite returned `None` or direct-TX was unavailable is
always wrong — an operator's counters would classify the same packet by an
unrelated TX-path condition. That is the "divergence is always a bug" side of the
line.

The helper will take the ~11 inputs the issue predicts. Rather than ship a
rule-violating signature silently, the immutable subset goes into a by-reference
context struct (stack-only, so the no-allocation hot-path invariant is
untouched), leaving the three `&mut` and the flow key.
