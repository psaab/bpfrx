# #6929 — unbounded per-worker WorkerCommand queues

- **Timestamp**: 2026-08-28
  - **Producer/consumer relationship established FIRST — this is corrective,
    not defensive, but not for the reason the issue gives.** The issue lists "a
    consumer slower than a sustained producer" among the causes. That one is
    false: the worker drain takes the WHOLE deque in one `core::mem::take`
    (`session_glue/mod.rs:710`), so no sustained producer can outpace it — every
    poll empties the queue.
  - **The real mechanism is a consumer that STOPPED, and it is reachable.**
    `spawn_supervised_worker` catches a `worker_loop` panic, sets
    `runtime_atomics.dead = true` and lets the thread exit; the worker RECORD is
    never removed (nothing calls `records.remove`); and every producer fans out
    with `for rec in self.workers.records.values()` and **no `dead` check**. The
    `dead` flag is read only by `coordinator/status.rs`, for diagnostics. So
    after any worker panic the queues grow without bound until OOM.
  - **The issue's site list is a FLOOR, not a census.** It names 5 producers.
    The actual population is **16 push sites across 8 files**, counted
    mechanically over comment-stripped sources rather than by eye — an earlier
    draft of this log and of the commit message said "twelve", which was my own
    miscount, and is corrected here rather than restated. The unit matters and
    is stated for that reason: 16 is *call sites*, 8 is *files*; several sites
    are forward/reverse pairs inside one producer function, so a count of
    "producers" is a third and smaller number depending on where you draw the
    boundary. The breakdown, so the total is checkable by addition instead of
    trusted:

    | file | push sites |
    |---|---|
    | `ha/session_import.rs` | 4 |
    | `ha/state.rs` | 3 |
    | `shared_ops.rs` | 2 |
    | `tunnel.rs` | 2 |
    | `session_glue/mod.rs` | 2 |
    | `cos/cross_binding.rs` | 1 |
    | `tx/drain/mod.rs` | 1 |
    | `ha/export.rs` | 1 |
    | **total** | **16** |

    Bounding only the five the issue lists would have left the hazard open at
    the rest. All 16 now route through `worker_queue::push_bounded`.
  - **The wiring is bound by a source-level agreement test, because the four
    behavioural cells cannot see it.** All four exercise `push_bounded`
    directly, so reverting any producer to a bare `push_back` leaves every one
    of them green — they assert a property of the helper, not of the call
    sites. `worker_queue_6929_every_production_producer_routes_through_push_bounded`
    walks `src/afxdp`, blanks comments and string literals, and flags any
    `push_back` whose balanced-paren argument mentions `WorkerCommand`. Details
    that are load-bearing rather than incidental:
      - **Comments are blanked** so the guard cannot be satisfied by the doc
        comment on `push_bounded`, which names `push_back` in prose.
      - **String literals are blanked** so a literal containing `//` cannot
        silently blind the rest of a line.
      - **The argument is captured by walking parens, not to end-of-line**, so
        the multi-line pushes in `ha/state.rs` and `ha/session_import.rs` are
        visible; a line-oriented grep would miss exactly those.
      - **Test fixtures are excluded on purpose.** `session_glue/tests.rs` and
        `newflow_contention_tests.rs` hand-seed a queue to drive the CONSUMER
        (23 bare pushes); routing those through the cap would change what they
        exercise.
      - **The absence assertion is guarded against passing vacuously.** A
        detector that reaches nothing satisfies "no violations" perfectly, so
        the test also asserts it read >= 200 production files, that the fixture
        exclusion matched >= 2 (not everything), and that it found >= 12
        `push_bounded` call sites. A second test proves the detector produces
        the finding it claims is absent, on a sample where a commented push, a
        block-commented push, a push inside a string, a `push_bounded` call and
        an unrelated `push_back` must all be ignored and exactly one real
        multi-line push found.
  - **Cap = 4096**, mirroring `MAX_PENDING_SESSION_DELTAS` — the sibling bound
    this codebase already applies to the same class of producer-side deque. Two
    different ceilings for two per-worker backlogs would be a number an operator
    has to look up rather than know.
  - **Refuses the NEWEST rather than evicting the oldest.** The queue carries
    ordered state transitions (`UpsertSynced` then `DeleteSynced` for one key),
    so dropping from the front would apply a delete whose matching upsert was
    discarded — inverting the worker's view of that key rather than merely
    making it stale. Same choice `push_session_delta` makes.
  - **New counter, checked against the existing one first.**
    `WORKER_COMMAND_QUEUE_POISON_RECOVERIES` already exists but describes the
    OPPOSITE outcome: a poison recovery keeps the committed prefix and loses
    nothing, while a capacity drop discards a command. Folding them would tell
    an operator "something happened to the queue" while hiding whether anything
    was lost, and the two have opposite remediations. A dedicated cell asserts
    a capacity drop does not move the poison counter.
  - **Cells push PAST the cap.** A survives-assertion on a capacity is
    structurally a floor — pushing N and checking they arrive passes identically
    with no bound at all. Each cell fills to exactly the cap (asserting every one
    is accepted, so the fix is not "refuse everything"), then pushes one more and
    asserts refusal AND the counter moving.
  - **The counter was unreadable by anyone but the tests, which undercut the
    entire reason for having a separate one.** The first cut added
    `WORKER_COMMAND_QUEUE_DROPS` and asserted on it directly from the cells. The
    argument for keeping it separate from the poison counter is that an OPERATOR
    must be able to tell "a queue recovered, nothing lost" from "a command was
    discarded" — and nothing outside the test binary could read it. Wired the
    full path its sibling already had: `coordinator/status.rs` accessor →
    `server/helpers/status.rs` assignment → `ProcessStatus` serde field →
    Go `ProcessStatus` → `prometheus.Desc` + collect, as
    `xpf_userspace_worker_command_queue_drops_total`.
    - The existing **#6641 status-wiring guard** already requires every
      Coordinator `*_total()` accessor to be assigned into `ProcessStatus`, so
      the Rust-side populate line is bound by a guard that predates this change
      and would have caught its omission. Not re-implemented.
    - The **exhaustive `ProcessStatus` literal** in `server/lifecycle.rs` failed
      to compile until the new field was added — a compile-time invariant doing
      exactly its job.
    - The wire fixture `tests/fixtures/protocol_wire_v1.json` was regenerated,
      and the diff CLASSIFIED rather than trusted: exactly one key added
      (`process_status.worker_command_queue_drops`, value 0), zero removed, zero
      changed. A regenerated golden greens the suite either way, so the
      classification is the evidence, not the regen.
    - `pkg/api/metrics_test.go` gives the drop counter the fixture value **9**
      against the poison counter's **2**, deliberately different, so a collector
      that wired one Desc to the other field fails instead of matching by
      coincidence. The 45→46 emitted-metric count guard was bumped with its
      reason recorded in the comment chain.
  - **Cross-language wire key bound by AGREEMENT, not a literal.** Mirrors the
    #6842 guard: the Rust key is read from the `#[serde(rename)]` attribute, the
    Go key by reflection off the struct tag, and the test asserts they agree —
    a literal would encode which spelling is trusted. This counter needs the
    guard more than most: both planes default the field, so a key mismatch never
    fails a decode, it reads 0 forever, and 0 is the EXPECTED value here. The
    broken wire is therefore indistinguishable from a healthy firewall on every
    operator surface, and stays that way until the exact condition the counter
    exists to report actually occurs. The test also asserts decoding the drops
    key does NOT move the poison counter, since a tag aliasing one onto the
    other would satisfy every other assertion.
  - **Two assertions are NOT guards and are labelled as such.** Both wire
    tests assert that decoding/serializing the drops key does not move the
    poison counter. No cell in either matrix armed those lines: Y3 (the Go
    poison tag aliased onto the drops key) reds the DECODE assertion instead,
    because `encoding/json` ignores a tag name claimed by two fields at the
    same depth, so neither field is set; Y2 reds the serialize assertion for
    the same structural reason. They are defence-in-depth, not verified
    guards, and are not counted as coverage. The anti-folding property that
    IS armed is Y4 — the collector reading the poison field into the drops
    descriptor — which is the site where folding could actually occur.
  - **File(s)**: userspace-dp/src/afxdp/worker_queue.rs (+ tests),
    ha/session_import.rs, ha/export.rs, ha/state.rs, cos/cross_binding.rs,
    shared_ops.rs, session_glue/mod.rs, tunnel.rs, tx/drain/mod.rs
  - **Not done**: the loss-of-sync latch the issue's title also names. The
    `push_session_delta` precedent latches `delta_loss_pending` so the owning
    worker forces a full owner-RG resync — but that latch is per-BINDING state
    reached from the worker, and the WorkerCommand producers are coordinator-side
    with no equivalent handle. Wiring one is a separate change with its own
    ordering questions; the drop counter makes the loss visible in the meantime.
