# #6842 — PPTP (RFC 2637) GRE: the version field as a decap discriminator

- **Timestamp**: 2026-08-27
  - **Action**: landed the unblocked half of #6842. The full issue asks for a
    stateful PPTP control-channel ALG on TCP 1723 that learns the
    `(peer A call-id, peer B call-id)` tuple and installs it as a GRE data
    channel association; that needs the typed `TunnelDiscriminator` on
    `SessionKey`, which #7188 owns and which does not exist on master
    (`grep -rn TunnelDiscriminator userspace-dp/src/` returns nothing).
    Building it here would invent the discriminator substrate as a side
    effect, which is the scope explosion the #5804 split was made to prevent.
    The blocked remainder is filed as #7699.

  - **Action**: added the discriminator-symmetry taxonomy to
    `docs/userspace-native-gre-plan.md` §6e after the parent raised the
    #6837 adjudication. The proposed route there — put a GRE call-ID in
    the `SessionKey` and fix #6837's aliasing as a side effect — is
    refuted by the authoritative text, not by opinion. RFC 2637 §4.1
    defines the Call ID as "the **Peer's** Call ID", so the two directions
    of one call carry different values and no reverse companion can pair
    them. RFC 4303 §2.1 puts the ESP SPI in the same class ("generated by
    the receiver"). RFC 2890 §2.1 puts the v0 GRE Key in the OPPOSITE
    class ("the same Key value" both directions), which is why #7188 can
    key on it and only on it. The generalisation boundary the parent asked
    for is therefore SYMMETRY, not protocol identity: an allowlist of
    symmetric discriminators.
  - **Measured**: RFCs downloaded and quoted from the raw text, not from a
    summariser. A WebFetch of RFC 2637 §4.1 returned a bit-layout that
    does not appear in the RFC and then asserted the Call ID is "the
    sender's own identifier, not the peer's" — the exact inverse of the
    normative sentence. `curl` + `sed` on rfc-editor.org/rfc/rfc2637.txt
    (132565 bytes, md5 e6fc552768a3bbc23ca6e2af6159c422) gives §4.1
    verbatim; RFC 4303 is md5 803d7b6619fe546e9bcfa430cc9df80a.
  - **File(s)**: docs/userspace-native-gre-plan.md, docs/log/6842.md

    What IS unblocked is acceptance criteria 1 and 4 at the only site in the
    dataplane that reads a 32-bit GRE Key today: the native decap parser.
    `try_native_gre_decap_from_frame` already refused a non-zero GRE version,
    but that line had NO test — deleting it made a crafted RFC 2637 version-1
    frame (Acknowledgment-Present bit set) parse with RFC 2890 offsets, which
    lands `inner_offset` on the peer-chosen Acknowledgment Number and promotes
    an attacker-authored IPv4 packet as the tunnel's decapsulated inner frame.
    Bound that with paired version-1 / version-0 cells, and made the refusal
    observable with a counter that fires only when the outer tuple names a
    configured GRE endpoint (so ordinary transit PPTP, which is forwarded
    rather than refused, is not counted).
