# #8892 — routing_domain added to snapshot v8 without a version bump

- **Timestamp**: 2026-09-05
  - **Action**: bumped the config-snapshot protocol version 8 → 9 on both
    planes (`ProtocolVersion`, `CONFIG_SNAPSHOT_PROTOCOL_VERSION`), so a helper
    built before `routing_domain` no longer advertises a matching version and
    is refused by the exact-equality gate instead of silently resolving every
    interface to domain 0.
  - **Why a bump and not a compatibility gate**: the gate is already exact
    equality and is the correct design; it simply did not fire because both
    sides said 8. The daemon and helper are a node-local pair over the control
    socket, deployed together, so a mismatch is same-node deploy skew, and the
    helper refuses the snapshot loudly (`unsupported snapshot protocol
    version`) rather than arming with weaker isolation. In an HA pair
    mid-upgrade each node runs its own matched pair; the cross-node config-sync
    wire carries its own version and is unaffected.
  - **ADD, never REDEFINE**: no field changed meaning; the version integer
    moved and one new test-side constant was introduced. The production floor
    `MinProtocolSecureTunnelRefusal = 7` is deliberately untouched — a v8
    helper still handles `secure_tunnel` correctly.
  - **The guard is a SHAPE pin, because a lockstep pin would not have caught
    this**: both sides stayed at 8 and therefore agreed. The drift was between
    the snapshot's shape and its version.
    `TestSnapshotShapeIsPinnedToProtocolVersion8892` digests the wire structs'
    exported fields and demands the version move when the digest does.
  - **Doc**: the version-contract section carried the rule that AUTHORISED the
    omission — "a field that is purely additive in meaning does not need a
    bump". An old reader ignoring `routing_domain` does enforce what it
    enforced before, so the rule said no bump. Corrected to two questions: does
    an old reader enforce what it enforced before, AND is that acceptable.
