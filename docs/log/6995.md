# 6995 — a rejected forwarding build left residue in two live counter stores

## Premise check first — one third of the issue was already fixed

Checked at `origin/master` (`20a6068b4`) before writing code.

**The residue premise HOLDS.** `build_fallible_forwarding_state` binds the
policy counters at `forwarding_build/mod.rs:452`
(`parse_policy_state_with_counters`) and the NAT counters at `:544`, `:549`,
`:550`, while the three fallible belts that can reject the build come **after**:
NPTv6 at `:584`, filter at `:635`, CoS at `:640`.

**The "also fix the claim" section is STALE.** The issue says
`forwarding_build/mod.rs:270-272` documents the inner builder as returning `Err`
*"having touched NO live shared state"*. That absolute is gone at master; the
comment now reads:

> That scope is exact, and it is narrower than "no live shared state". Two OTHER
> `Arc`-shared stores are mutated inside this function… tracked as #6995.

A later PR corrected it. Only the mechanism itself remained.

## The defect

Both production call sites pass the LIVE, `Arc`-shared stores.
`PolicyCounterStore::rule_hit_counter` GET-OR-CREATES a block per policy rule
plus the reserved default-policy id; `NatCounterStore::rule_counter`
GET-OR-INSERTS one per NAT rule from the source, static and destination
reconcilers. A build the late belts reject had already mutated both.

**The NAT half was operator-visible, and that is what lifts this above
tidiness.** `NatCounterStore::snapshots()` emits one row per stored id
*regardless of whether its packet/byte value is zero*, feeding
`server/helpers/status.rs` → `ProcessStatus.nat_rule_counters` → Go
`NATRuleCounters`. A refused commit put phantom NAT rule-counter rows on the
operator status surface — rows for a configuration never installed — until the
next successful commit evicted them.

The policy half is memory-only: `Coordinator::policy_rule_counters` reads the
PUBLISHED forwarding state, not the store. It still grows the registry by a block
per rejected commit.

## Rolled back, not deferred — and why the #6832 shape was unavailable

#6832 fixed the sibling ZONE-counter instance by DEFERRING the binding into
`attach_zone_counters`, an infallible step that runs only after `Ok`. That is not
available here: these handles are embedded in `PolicyState` and the NAT tables
**at construction**, so moving the binding would mean a second pass over
already-built structures.

The caller captures both registries before the fallible build and retains them
back on `Err`:

```rust
let policy_ids_before = policy_counters.tracked_rule_ids();
let nat_ids_before = nat_counters.tracked_ids();
let mut state = match build_fallible_forwarding_state(...) {
    Ok(state) => state,
    Err(err) => {
        policy_counters.retain_rule_ids(&policy_ids_before);
        nat_counters.reconcile_ids(&nat_ids_before);
        return Err(err);
    }
};
```

A retain to the pre-build set is exact: it evicts only ids this build created and
**cannot drop a row carrying live cumulative totals**. That direction is the one
that matters — destroying those is the #5716 defect, and cell P2 is the
over-correction that does it.

`PolicyCounterStore::tracked_rule_ids_for_test` becomes an **alias** of the new
production accessor rather than a second implementation, so the #6832-era tests
that call it keep guarding the same registry view the rollback uses.

## Two properties, bound separately

They are separable, so they are separate tests: a fix that filtered zero-valued
rows out of `snapshots()` would satisfy the SURFACE assertion while leaving the
STORE dirty (and would also hide legitimately-zero rows for rules that really are
installed).

Both stores are **SEEDED with a live id** before each rejected build. That is
what distinguishes a rollback from a `clear()`: an over-correction that empties
the store passes "the candidate id is absent" and fails "the running rule
survived".

The row table is restricted to the three belts BELOW the bindings. The #3719
duplicate-zone row the zone tests use rejects ABOVE them and would be green for
the wrong reason.

## The pre-existing test this fix was designed to contradict — and nearly missed

`rejected_build_leaves_the_zone_store_clean_against_live_sibling_stores` (#6832
fold r7) positively asserted that the #6995 residue IS present, and used its
presence to pin the relative ORDER of the policy parse, the NAT parse and the
belts. Its own comment said what should happen next:

> If a later change fixes #6995, this assertion is the one that says so out loud
> instead of going quietly stale.

It did exactly that. **And I nearly shipped without seeing it**: the three new
tests were run under a `-- 6995` filter, which is green. Only the unfiltered
suite shows the row the fix contradicts. A filtered run cannot see the test that
owns the property you just changed.

The predicates are **re-anchored, not deleted**. The ordering property is real
and still true — it is a property of the INNER builder, which does the
get-or-create and does not roll back, not of the caller that undoes it. The row
now runs them against `build_fallible_forwarding_state` on its own live-seeded
stores, and at the caller's layer asserts both sibling stores come back
UNCHANGED. Deleting them would have removed the only bind on the two parses'
relative order — the exact regression #6832 fold r7 exists to prevent, since an
earlier round let both predicates collapse into one expression no row could
contradict.

## Mutation matrix

Full binary, `--test-threads=1`, **no `-run` filter**, per-cell
`CARGO_TARGET_DIR` under `/var/tmp`. RED requires a **named** failure with
**tests-collected > 0**; 4730 collected in every cell.

| cell | mutation | result | named failure(s) |
|---|---|---|---|
| **P1** | drop the rollback entirely (revert #6995) | **RED** | all three new tests + the re-anchored #6832 row |
| **P2** | roll back with `clear()` instead of a retain to the captured set — the OVER-CORRECTION | **RED** | all three + the #6832 row |
| **P3** | roll back only the POLICY store, leaving the operator-visible NAT half | **RED** | the NAT store test, the NAT SURFACE test, the #6832 row — **the policy store test stays GREEN** |

**P3 is the localising cell.** It reds exactly the two NAT assertions and leaves
the policy one green, which is what says the three tests are three properties
rather than one restated. P1 and P2 red the same set from opposite directions —
too little cleanup and too much — so between them the retain is pinned as
necessary *and* bounded.

## Validation

- `cargo test --manifest-path userspace-dp/Cargo.toml --release --bins --
  --test-threads=1`: 4730 collected, **4728 passed / 0 failed / 2 ignored**.
- Cells P1-P3 above.
- No Go changes and no dataplane deploy lane applies: the change is
  helper-internal counter-store bookkeeping on the REJECT path, and no packet
  takes a different route. The fallible builder already writes into a local
  `ForwardingState::default()` dropped on `Err`, and `coord.forwarding` is
  assigned only after success, so no half-applied config was ever visible.
