# 9048 — the generation guards are REORDERING guards; the missing guard was on the other verb

## The instruction that shaped this

> A guard that falls through unconditionally is not a guard; establish what it
> was meant to compare before changing it, because "fall through" and "compare
> against the wrong side" have different fixes.

The answer is **neither of those two**. There is a third case, and it is the
one here: *the guard compares the right side of the right question — and the
question it asks is not the one the issue wants answered.*

`installGenGuardV4` / `deleteGenGuardV4` are per-key **reordering** guards for
ONE sender's stream (#2170): "is this delta older than the last one I applied
for this key?" `recvGenV4` is populated solely by `recordInstalledGenV4` —
prior PEER installs — so for a locally-created session `stored == 0`, which
means *"I have no ordering information"*, not *"this is safe"*. Refusing on
gen-0 would break every legitimate first install and every legacy sender; that
is exactly what the `incoming == 0` arms exist for. **Nothing is wrong with
these guards.** Ownership is a different question, with different inputs, and
it belongs at a different layer.

## The decisive check the issue named, followed to ground

> With both nodes primary and the sync link up, does an inbound peer install
> whose key names a live local session actually overwrite it end to end?
> `synced_entry_allows_local_replace` may itself decline the replace; it is the
> one link in the trace not followed to ground.

**It declines — for INSTALL.** `SessionTable::upsert_synced_with_origin`
(`userspace-dp/src/session/install.rs:342-348`):

```rust
// Reject peer data that would clobber a locally-owned session
// unless explicitly allowed (e.g. during HA activation).
if matches!(self.entry_by_key(&key), Some(existing) if !existing.origin.is_peer_synced())
    && !allow_replace_local
{ return false; }
```

with `allow_replace_local = synced_entry_allows_local_replace(ha_state,
entry.metadata.owner_rg_id, now_secs)`, which is FALSE exactly when the
incoming entry's owner RG is locally forwarding-active — the dual-primary case.

So the issue's headline ("a second primary overwrites and deletes freely") is
**refuted for the install half**, and its proposed fix — give the Go guards a
local-ownership predicate — is at the wrong layer: the predicate already exists
one layer down, where local origin and local HA state actually live.

## A claim of mine that my own mutation refuted before I published it

I searched for tests binding that guard, found only positive
`assert!(table.upsert_synced_with_origin(...))` call sites, and was about to
report "the only mechanism preventing dual-primary mutual overwrite is
**unpinned**".

Then I ran the mutation instead of trusting the grep. Deleting the guard reds
**two** cells:

- `session::tests::upsert_synced_does_not_clobber_live_local_session`
- `afxdp::session_glue::tests::apply_worker_commands_preserves_local_session_for_active_owner_rg`

My search was literal-only — it looked at lines *calling* the function with an
assertion, and both cells assert on TABLE STATE after the call instead. An
absence claim from a grep needs a positive control, and here the mutation was
the positive control. It cost one 90-second run to not publish a false claim.

## What actually survives: the DELETE half

`handle_delete_synced` (`session_glue/commands/delete_synced.rs`) called
`sessions.delete(&key)` **unconditionally** — no origin check, no HA predicate,
nothing. `SessionTable::delete` is a bare `remove_entry`. So:

| verb | ownership guard before #9048 | consequence in a dual-primary split |
|---|---|---|
| install | YES, and pinned by two cells | peer install refused; local session survives |
| delete | **NONE at any layer** | peer delete tears down a LIVE LOCAL session mid-flight |

The asymmetry was invisible because the two verbs are guarded in different
files at different layers, and the delete is the **more damaging** half: a
wrongful delete kills a live flow outright, where a wrongful install at least
leaves a session installed.

Reachability is the issue's own (narrower than the source report's): both nodes
primary for the same RG. The delta EMITTER is gated on `IsPrimaryForRGFn`, so
in normal operation exactly one node emits and the receiver's entries at those
keys carry a peer-synced origin — the guard is inert. In a split both nodes
forward the same flows, both create LOCAL sessions under the same 5-tuples, and
either node closing its copy syncs a delete that kills the other's live flow.

## What landed

`handle_delete_synced` now refuses when the existing entry is **local-origin
AND** its owner RG is **locally forwarding-active** — the delete-side mirror of
the install-side guard, with `ha_state`/`now_secs` threaded in from the
dispatch arm (both already in scope; the sibling `UpsertSynced` arm takes them).

Nothing below the guard runs on a refusal: not the NAT pool release, not the
session-map delete, and **not** the `deleted_keys` record. #6457 records that
key unconditionally so a stale flow-cache permit cannot outlive the table entry
it was seeded from; here the entry SURVIVES, so the permit is still backed and
invalidating it would be wrong in the one direction #6457 does not consider.

Refusing is the conservative side: a session that lingers until it ages out,
against a live flow torn down mid-transfer.

Observability: `PEER_DELETE_REFUSED_LOCAL_OWNED` → `ProcessStatus.
peer_delete_refused_local_owned` → Go `PeerDeleteRefusedLocalOwned`. The
refusal is silent by design (the condition produces one per closing flow, so a
log line would be a storm exactly when the cluster is already in trouble),
which makes the counter the ONLY surface reporting it. A nonzero value is a
**split-brain indicator**, not a tuning knob. The helper's `UNSURFACED`
allowlist guard (#6641/#7398) is what forced the field to be assigned rather
than computed and dropped.

Docs: the scope note now sits on the guards themselves
(`pkg/cluster/sync_conn_gen.go`) and in `pkg/cluster/README.md` beside the
#2170 entry, so the next reader does not re-derive this.

## What this issue should NOT be read as closing

The dual-primary CONDITION is untouched. `electSingleNode` still skips the
readiness gate on `peerEverSeen && !peerAlive`, and `peer-fencing` still
defaults off. This is a blast-radius reduction — the split no longer tears down
live flows through the sync channel — not a split-brain fix. The issue's own
question of whether `peer-fencing` should default on is unanswered and
deliberately left open.
