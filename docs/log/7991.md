## Premise, re-verified — and two corrections to the issue

**Confirmed.** `lenientVRFOverlapPBR: true` is still set in `lenientCompileOpts`
(`compiler_opts.go:2459`), so the tolerant load / peer-sync path still admits the
combination the strict path refuses. The condition is live on any box carrying a
config persisted before #7924, or one arriving by peer-sync.

**Correction 1 — #3718 has NO `show` surface.** The issue proposes "a metric plus
`show` state ... mirror `xpf_host_inbound_ambiguous_addresses`". Measured, #3718
has a metric and a state-transition log and nothing in `pkg/cli` or
`pkg/grpcapi`. So *mirroring* it means a metric, not a `show` command. Building
one here would be inventing a convention rather than following it — and the
issue's own argument is that the convention already exists and this case does not
follow it. A `show` surface for tolerant-admitted state may well be worth having,
but it should be added for both cases together, by someone deciding that on
purpose.

**Correction 2 — it is not "logged once at boot".** `applyConfigLocked` emits
`slog.Warn("config validation", ...)` for every `cfg.Warnings` entry
(`daemon_apply.go:382`) on *every* apply path — boot, commit and peer-sync. The
substance of the issue stands (there is no queryable state), but the log is more
present than "once at boot" suggests.

## What was built

A gauge, `xpf_vrf_overlap_pbr_admitted{instance_a,instance_b,prefix}`, mirroring
`xpf_host_inbound_ambiguous_addresses` in every respect that carries meaning:

- **config-derived**, so `Collect` calls it BEFORE the dataplane gate — the
  condition can be open on a degraded / config-only boot, which is exactly when
  an operator most needs to find it, and below the gate the series would vanish
  there;
- **not self-healing**, so the series stands until the config is fixed;
- **one SSOT with the commit gate.** `TolerantVRFOverlapAdmissions` runs the SAME
  detector `validateVRFOverlap` runs, leniently. It is not a second scan.

### Single-sourcing was the design constraint, not a nicety

The obvious implementation is a second scan for the metric. That is the shape
this campaign keeps finding broken: two detectors that agree today and drift
later, with nothing to notice. So `validateVRFOverlap` now returns structured
`VRFOverlapAdmission` findings alongside its warnings, **and the warning strings
are rendered from the findings** (`VRFOverlapAdmission.warning()`). One scan, one
set of detections, two renderings. The full `pkg/config` suite passes unchanged,
which is what proves the warning text survived byte-identical — #2387 and #7924
both pin it.

### Reported ONLY for the combination

Findings are cleared when no PBR `then routing-instance` term is present. Plain
VRF overlap commits on the strict path too, so it is not a *tolerant-admitted*
state, and a metric that fired on it would fire on legal configurations —
overlapping address space across VRFs is the primary reason VRFs exist. A metric
that fires on correct configs is one operators learn to ignore.

### The HELP text carries the severity

A metric whose meaning lives only in an issue is a metric nobody can act on, so
the descriptor says what firing means: sessions are keyed on the bare 5-tuple
with no routing-instance discriminator, the established-session fast path runs
before the PBR table override with no policy call, so a colliding 5-tuple in the
second instance is forwarded out the FIRST instance's egress with its NAT and
without policy adjudication.

## A stale doc corrected in the same change

`userspace-dp/src/afxdp/forwarding/README.md` still said the overlap case *"still
commits"*. That predates #7924, which made the narrow combination a strict-path
rejection. Updated to state the current split (plain overlap commits; the
combination is refused; the tolerant path still admits it, which is what the new
metric surfaces).

## Validation

`go test -count=1 ./...` green. Two new cells in `pkg/api`, whose fixture asserts
its own preconditions rather than assuming them: WITH the PBR term the strict
path must refuse and the tolerant path must accept; WITHOUT it both must accept.
If the #7924 gate ever stopped refusing, the test would otherwise still pass on a
metric that fires for a state nobody is in.
