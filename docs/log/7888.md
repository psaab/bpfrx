## The issue's premise was corrected before implementing

The issue said the runtime WARN "is still wrong for that state", reading
`references undefined screen profile`. The first review comment established that
it does not fire at all: the two Go sets are disjoint by construction, only the
undefined one was on the wire (`grep -c ScreenInert protocol.go` -> 0), so an
inert zone was in neither `zones` nor `missing_profile_refs` and fell out of
`missing_profile_verdict` as a bare `Pass`. There was no branch to correct —
writing the text branch first would have been a claim in unreachable code.

That surfaced the more serious half, which the issue did not name: the inert
state had no substituted conservative default either. Two configurations with
the identical consequence got different protection, and the one that looks MORE
correct to an operator got LESS.

## Posture

Settled on the issue before implementation: inert gets the SAME substituted
default as undefined. The decisive argument is that a legitimate opt-out already
exists and is not this one — a zone with NO `screen` statement passes silently,
which `missing_profile_verdict` documents as "a legitimate configuration, not a
fault". So preserving inert as an opt-out protects no real intent; it preserves
only the failure mode. The canonical way into the state is configuring a
MODIFIER (`alarm-without-drop`, a threshold) and believing it enabled a check.

This is a behaviour change on a fail-open path. The traffic it newly drops is
the threshold-free malformed-packet set — LAND, teardrop, winnuke, syn-fin,
no-flag, fin-no-ack, syn-frag, ping-death, source-route-option. The substitution
cannot synthesise a rate check here for the same structural reason it cannot for
an unresolved zone: rate checks need per-zone tracker state in `ZoneScreenState`,
and an inert zone publishes no snapshot, so no such state exists.

## Shape

Ordering was wire field first, then the WARN, with the skew test in the same
change.

- **Two maps, not one flag.** `missing_profile_refs` and `inert_profile_refs`
  stay separate, and `unresolved_screen_kind` reads the three states off
  membership — the legitimate silent `Pass` is "in NEITHER map". Merging them
  would make the two WARN texts undecidable where they are emitted, which is
  this issue's own defect one layer down.
- **ADD a field, never redefine one.** `screen_inert_profile_zones` is an
  additive sibling: `omitempty` on the Go side, `#[serde(default)]` on the Rust
  side. Both skew directions degrade to the pre-#7888 behaviour — an old helper
  ignores the field, an old Go binary leaves the set empty, and inert zones
  `Pass` exactly as before. In a rolling HA upgrade the two nodes run different
  binaries on one wire, and `serde(default)` cannot help when the OLDER binary
  is the sender.
- **`has_screen_state` had to learn the inert map.** An inert-only config has no
  `zones` entry and no missing ref, so without that arm the whole screen stage is
  skipped and the substitution is unreachable — the same all-or-nothing hole
  #6860 closed for undefined references.
- **The WARN texts are extracted into pure functions.** A property asserted only
  inside a formatting macro cannot be asserted at all, and this change turns on
  the two texts being tellable apart. They allocate only on the emit path, which
  is rate-limited to one per zone per second and already past a `zone.to_string()`.

## `ScreenInertDisposition` had to change too, and the guard caught it

The shipped constant read "so no screen checks are applied to this zone ...
pending the #5806 enforcement-posture decision". Both halves became false: the
dataplane now enforces the substituted default for the zone, and the posture is
no longer pending. Leaving it would have told an operator a zone is unprotected
while the dataplane drops LAND on it — the same class of false statement about
enforcement this issue exists to remove, pointing the other way.

`TestScreenUnresolvedDispositionHasOneSource` reddened on its own self-check,
which is the guard working. Its subject has now moved twice for one fact:
#7059 shared a tail because both states had the identical consequence; #7168
split it when only the undefined state gained the substituted default; #7888
re-shares it (`screenSubstitutedDefaultTail`) now that both have it. Writing the
sentence twice instead would let the nine substituted check names drift the first
time that set changes. `ScreenUnresolvedDisposition`'s VALUE is byte-unchanged by
the re-sourcing — verified by dumping the constant before and after.

The guard additionally asserts the two dispositions have NOT collapsed into one
message: sharing the consequence must not erase the diagnosis, because "define
the profile" and "add a check to it" are different remedies.

## The module split, and a process note

The feature pushed `screen/mod.rs` from 1455 to 1639 LOC, crossing the 1500
[WATCH] threshold that `pkg/refactoraudit` enforces against the author of the
growth. `docs/engineering-style.md` says to split and land the feature on the
smaller pieces rather than clean up afterwards, so the unresolved-screen
handling moved to `screen/unresolved.rs` in its own commit — a pure move, kept
separate so it reads apart from the behaviour change. `mod.rs` is now 1406 LOC,
below even its pre-feature size. As a CHILD module `unresolved` reaches
`ScreenState`'s private fields directly, so the split cost no visibility
widening; the two `pub(super)` markers it needed are narrowings, not widenings —
`super` is the screen module, exactly who could reach those items before.

Process note worth carrying: `cargo check` passed after the move, and the move
had in fact broken the TEST build (`screen/tests.rs` calls the two WARN-message
builders, and `use super::*` does not reach a sibling module's namespace). Only
the full `cargo test` surfaced it. A green `cargo check` is not evidence that a
refactor landed. The #7888 mutation was then re-run against the MOVED code and
still reds exactly the two verdict cells, so the guards did not go vacuous in
transit.

## Layering of the wiring cells

The Go and Rust wiring cells are deliberately at different layers: the Go cell
asserts on the built SNAPSHOT rather than on `buildScreenInertProfileRefs`, and
the Rust cell asserts on the built FORWARDING STATE rather than on
`build_screen_inert_profiles`. A cell that called either builder directly stays
green through the exact revert this issue is about — the builders were never the
broken part.
