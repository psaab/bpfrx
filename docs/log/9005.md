# #9005 — portEnd emitted a wrapped 0x0000 interval end at the top of the range

- **Timestamp**: 2026-09-05
  - **Action**: replaced `portEnd(hi) []byte` with `portNext(hi) ([]byte, bool)`
    and stopped emitting an end element for a range reaching 65535. The port
    twin of #8597, which reached the same conclusion for addresses and whose
    `prefixNext` has the identical `(value, ok)` shape — a caller cannot forget
    to check, and the two key types now answer the question the same way.
  - **Measured before**, on the EMITTED elements rather than the helper:

    ```
    ports 80/80 + 1024-65535  ->  [0050 0051!end 0400 0000!end]
                                                      ^^^^^^^^^ end marker at the
                                                      BOTTOM of the key space
    after                     ->  [0050 0051!end 0400]
    ```
  - **Reachability detail the fixture depends on**: a SINGLE port range compiles
    to an `expr.Range`, not a set, and emits no elements at all. The set path is
    taken only with two or more entries, so a one-range fixture measures
    nothing — the first version of this measurement returned `[]` for exactly
    that reason and would have read as "no defect".
  - **Validation**: restoring the wrapped end reds the golden cell with the
    bottom-of-key-space message. A non-vacuity cell asserts an ORDINARY range
    still gets its end, so the fix cannot pass by suppressing every end — which
    would open the interval to the top and match far more than configured.
  - **File(s)**: pkg/nftables/netlink_build.go,
    pkg/nftables/interval_set_port_top_of_range_9005_test.go
