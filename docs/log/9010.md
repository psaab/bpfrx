# #9010 — route-listener catch-up marked at gap OPEN, never after re-establishment

- **Timestamp**: 2026-09-05
  - **Action**: each fresh route subscription now issues a catch-up refresh
    right after it goes live (`routeListenerCatchUp`).
  - **The reader was established first**, per the dispatch: `loop.Mark()` sets
    `dirtySince`/`dirtyGen`, and the coalescer's run loop reads them to decide
    whether to ACTUATE. #8915 measured 0 actuations across 50 sweeps with no
    mark, 1 after a single mark, and the periodic-floor alternative was
    considered and declined there. So a missing mark is a missing FIB refresh,
    not a cosmetic omission.
  - **Why #8915 does not cover it**: it marks from the `ErrorCallback`, which
    exists only for a fault during a LIVE subscription. A subscribe that FAILS
    never installs a callback — the 2-second retry path marks nothing — and a
    subscription that simply ends returns before any error is raised. The
    subscription is opened `ListExisting:false`, so re-establishment replays
    nothing and the data gap stays open.
  - **The route listener was the outlier**: `docs/bugs.md` records the
    link-state listener doing exactly this since #3950 — "each fresh
    subscription runs `resyncLinkState` right after it goes live and emits
    catch-up traps for any transition missed during the overflow". The fix
    mirrors an established, documented pattern in the same daemon rather than
    inventing one.
  - **Validation**: the cell drives the function production calls (the #8915
    seam argument) and asserts the ACTUATION, not the counter — removing the
    mark while keeping the counter reds it. A non-vacuity sweep first proves
    the loop does not actuate unmarked. A nil-loop cell keeps the refresh
    helper from crashing the daemon it exists to help.

    pkg/daemon/route_listener_catchup_9010_test.go, docs/bugs.md
