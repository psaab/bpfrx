# #6889 — a dropped RG0 transition leaves the manager PRIMARY while the store stays read-only

- **Timestamp**: 2026-08-27
  - **Premise re-measured on master** (all three clauses hold): `Manager.sendEvent`
    is still non-blocking with a `default:` drop; `applyRG0OwnershipTransition`
    still has exactly ONE production caller, the event consumer at
    `daemon_ha.go:704`; both `SetClusterReadOnly` call sites live inside it. So
    the authority boundary for who may write config was driven only by a
    droppable channel.
  - **Action**: the gate is now re-derived from RG0's authoritative state on
    every `reconcileRGState` pass — the 2 s loop plus the event-drop nudge,
    which is already the dropped-event recovery path.
  - **It re-drives `applyRG0OwnershipTransition`, not `SetClusterReadOnly`.**
    The gate is not the handler's only consequence: promotion also reconciles
    config-sync to the peer, re-initiates synced IPsec SAs and nudges DHCP
    lease-sync; demotion CONFIRMS a pending commit-confirmed first (#4378) so
    its rollback timer cannot fire on the demoted standby and diverge from the
    peer. A dropped event skipped all of those. Setting the bit alone would fix
    the symptom the issue names and leave the rest silently unapplied.
  - **Silent wherever the event handler is silent**: only Primary / Secondary /
    SecondaryHold, because those are the only states the transition handler acts
    on. Inventing a gate decision for `StateLost` / `StateDisabled` would be new
    behaviour arriving through a recovery mechanism.
  - **Closes #6890 as a necessary consequence, measured and bound.** A first
    probe was WRONG in an instructive way: a cold-start RG0 is created
    `StateSecondary` (`group_state.go:30`) but a single-node fixture reads back
    **primary**, because `UpdateConfig` runs an election and a peerless node
    promotes itself. The real #6890 shape is a node whose peer WINS RG0 — it
    seats at `StateSecondary` and never crosses a transition edge, so the gate
    was never armed. Deriving from state arms it. This is not avoidable: a gate
    derived from RG0's authoritative state cannot preserve a hole that existed
    only because the edge was never taken. Bound by a cell so a later narrowing
    to promotion-only reds instead of being rediscovered from a REST session.
  - **File(s)**: pkg/daemon/daemon_ha.go, pkg/cluster/group_state.go (test seam),
    pkg/daemon/rg0_readonly_reconcile_6889_test.go, pkg/cluster/README.md
  - **Operator-facing change**: the recovery enumeration's row 2 escape hatch
    (REST into an unarmed standby) is CLOSED, and row 3 (controlled promotion)
    lost its event-delivery precondition, so it is now reliable rather than
    merely likely. One precondition remains — an ineligible secondary (zero
    weight, active upgrade hold) still does not promote. Rows 2 and 3 and the
    section's closing summary were updated together.

- **Timestamp**: 2026-08-27 (validation)
  - **Mutation matrix caught an escape in my own coverage.** Cell R3 replaced
    the reconcile's `applyRG0OwnershipTransition(rg0.State)` with a bare
    `SetClusterReadOnly(wantReadOnly)` and left all 3111 tests GREEN — every
    cell asserted the BIT, which is identical either way. Added a cell binding
    the decision through its safety-critical consequence: a pending
    commit-confirmed must be CONFIRMED on a reconcile-driven demotion (#4378),
    or its rollback timer fires on the demoted standby. R3b now reds it.
  - **Cell R5 is a genuine NO-OP, not an escape.** Making the `default:` arm
    want read-only cannot change behaviour, because the reconcile delegates to
    `applyRG0OwnershipTransition`, whose switch has no `StateLost` /
    `StateDisabled` case. The "silent where the handler is silent" rule is
    enforced structurally by the delegation, not merely by the `default: return`.
  - **A probe of mine lied and was corrected.** `cli -c 'configure'` reports
    "requires an interactive terminal (TTY)", so it never reaches the read-only
    gate — my first evidence pass grepped its output for "read-only" and
    reported "accepted (writable)" for BOTH a writable store and a probe that
    never got there. Re-measured from the daemon's own logs instead.
  - **Cluster validation**: `make cluster-deploy` (sha256-verified both nodes)
    then `make test-failover` → **14 passed, 0 failed**, 22.1 Gbps.
  - **The smoke exercised the path, and the evidence is stronger than expected.**
    The reconcile fired **3 times in one failover cycle** (fw0 ×2, fw1 ×1), every
    one of them `rg0_state=secondary store_read_only_was=false` — a node seated
    as RG0 secondary with a WRITABLE config store. The log order is decisive:
    `gate disagreed` precedes `became secondary for RG0`, so that transition log
    IS the reconcile re-driving the handler. **That is #6890 reproducing on real
    hardware on every node restart**, not a theoretical gap. No correction ran in
    the promotion direction and there was no flapping — 3 corrections across ~7
    transitions with the smoke fully green.
