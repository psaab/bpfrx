## Re-measured at HEAD

```
Kea derivation  group untagged -> ["ge-0-0-1.0"]     <- not a device
Kea derivation  group tagged   -> ["ge-0-0-1.80"]    <- unit 80, vlan-id 180
ResolveKernelIfName(reth1.0 )  = "ge-0-0-1"
ResolveKernelIfName(reth1.80)  = "ge-0-0-1.180"
rethInterfacesMatchingRG(all)  = ["ge-0-0-1" "ge-0-0-1.180"]
```

## The consequence the report did not name, and it is the worse one

The report framed this as "standalone names a phantom device, tagged units bind
the wrong VLAN". Both are real. The third is not in the report:
`rethInterfacesMatchingRG` — the set `filterDHCPConfigForMasterRGs` compares
against — has ALWAYS derived `<member>.<vlan-id>`. With the Kea side deriving
`<member>.<unit-number>`, a tagged group matched neither `masterIfaces` nor
`rgScoped`, so the #6520 arm "not RG-scoped implies node-local, always keep"
kept it. Measured before the fix, on a Daemon mastering NO redundancy group:

```
cluster filter  group tagged -> ["ge-0-0-1.80"]   (kept; should be dropped)
```

A redundancy-group-owned tagged segment is served on the backup node. That is
the #6520 failure mode the filter exists to prevent, reached through a name
mismatch instead of a mastership bug — and it is invisible in every existing
cell because they all use untagged units, where `stripUntaggedUnitSuffix`
(#4647) happens to paper over the difference.

`pkg/dhcpserver/README.md` carried the false half in prose: *"A TAGGED unit
(`reth1.100` → `ge-0-0-1.100`) is left intact and still matches only its VLAN
member."* It matched nothing. That sentence is corrected in this change.

## The test that pinned the defect

`dhcp_reth_resolve_nomutate_9141_test.go` asserted `"ge-0-0-1.0"` under the
label *"Positive control: the resolution still happens"*. The issue is right
that this pins the buggy output as intended output. Two things needed changing,
not one:

- the EXPECTATION, from `ge-0-0-1.0` to `ge-0-0-1`;
- the FIXTURE. `reth1` declared **no units**, so `ResolveKernelIfName` fell
  through to its verbatim arm and the cell could not have told the canonical
  resolver from the two-arm derivation it was pinning. Without declaring
  `unit 0` the whole suite stayed GREEN across this fix — the change would have
  looked untested by a test that names the exact function it changed. Every
  config that can actually serve DHCP declares the unit; that is where the
  address lives.

## The residual, said rather than guessed at

`ResolveKernelIfName` returns the reference verbatim when the ref names a unit
the config never declares — it cannot know what device was meant. A blanket
`.0` strip would close that but would also rewrite a legitimately dotted
DECLARED interface name (the #8994 case), so the residual is reported instead:
`validateDHCPServerInterfaceRefWarnings` warns at commit, for both families.
A group whose unit is undeclared has no address either, so Kea could not have
matched a subnet on it even with a perfect device name — it is a broken config,
and the operator should hear it at commit rather than find a segment that never
leases.

It reuses `declaredInterfaceIndex` / `unresolvedInterfaceRef`, the predicate
introduced for the #9405 protocol advisory and already shared with #9406.

## Validation

- `go test ./...` — full tree, green.
- `TestKeaAndRGSetsDeriveNamesIdentically9407` is the #8994-style agreement
  cell the issue asked for, aimed at the pair that actually has to agree: the
  Kea derivation and `rethInterfacesMatchingRG`. Comparing outcomes catches
  today's drift; comparing derivations over a corpus catches tomorrow's.
- Mutation results are in the PR body.

**No cluster smoke was run.** `docs/ha-cluster-userspace.conf` configures
`dhcp-local-server` on `reth1.0` only — an UNTAGGED unit, the one shape
`stripUntaggedUnitSuffix` already covered — so a green cluster run would say
nothing about the tagged defect that is the substance of this change.
