# 9120 — `FenceAckOK` promised more than the fence does

## What the issue asked

`FenceAckOK` promises the peer relinquished every redundancy group, but the
fence does not verify that. Find what the ACK actually proves, then either make
it prove what it says or rename it to what it proves. **Do not just widen the
comment.**

Acceptance: "a cell that fences a node whose cluster state still says Primary
and asserts the chosen invariant across the *next* reconcile pass — the existing
`TestFenceRearmsReconcileRetry` is the counter-cell it must be reconciled
against, not silently inverted."

## What was measured at head (004ab1d9a), before choosing a remedy

- **Timestamp**: 2026-09-06
- **Action**: read the four load-bearing claims rather than inheriting them.

1. `fenceAllRedundancyGroups` (`pkg/daemon/daemon_ha_sync.go:1139-1186`) does
   exactly two things per RG: `rt.HA().SetRGActive(ctx, rg.ID, false)` and
   `getOrCreateRGState(rg.ID).InvalidateApplied()`. **No VIP release.** No
   cluster-state change.
2. `pkg/cluster/sync_fence_ack_7147.go:34` claimed fenceAckOK means "the peer
   confirms it relinquished every RG it knows about, **which is the property a
   takeover gate should be built on**". That second clause is the load-bearing
   half — it invites a future gate to build on the stronger reading.
3. `TestFenceRearmsReconcileRetry` (#6530) **passes at head**: the reconcile
   after a fence re-drives `rg_active=true`. The revert is pinned as REQUIRED
   behaviour, not tolerated behaviour.
4. `resignRethRG` — the only VIP-release path — is called from
   `bootstrap.go:549` only. Never on the fence path.

So the ack's true guarantee is: *at the instant it replied, the peer had driven
`rg_active=false` for every RG in its live config.* A point-in-time DATAPLANE
SUPPRESSION receipt, durable for at most one reconcile interval.

## The reframing that decided the remedy

The issue offers (a) make the fence a cluster-state event with a bounded
self-clearing timer, or (b) narrow the documented meaning.

I initially read #6530 as "the fence gets undone, so option (a) would invert a
pinned test." That reading is wrong and it is worth writing down, because it
would have ruled out the better remedy for a bad reason.

`desired = clusterPri || allVrrpMaster` (`pkg/daemon/rg_state.go`). **The fence
changes NEITHER input.** So the state machine is not undoing a fence — it
correctly observes that desired is still true and retries an apply that, from
its point of view, spuriously reverted. #6530 exists to retry a FAILED apply; it
does not exist to undo a fence. A future option-(a) fence that clears
`clusterPri` would therefore NOT contradict #6530 — it removes the input that
keeps `desired` true, so there is nothing left to retry.

That makes (a) genuinely available. I did not take it here because it carries a
decision I should not make alone: an unbounded cluster-state fence converts a
lost sync channel into a **no-primary outage**, so (a) needs a bounded hold
duration, and picking that bound is a policy call. Reported to team-lead.

## What landed (remedy (b), done properly)

The issue says do not just widen the comment. So the narrowing is paired with a
cell that makes the narrowed claim FALSIFIABLE.

- **File**: `pkg/daemon/fence_ack_guarantee_9120_test.go` (new).
  `TestFenceAckProvesDataplaneSuppressionOnly9120` fences a node whose cluster
  state still says Primary and asserts, across the next reconcile pass:
  1. every live-config RG is driven false and `RGsFenced == RGsTotal` (what the
     ack REPORTS is true);
  2. `clusterPri` is unchanged — as a TRIPWIRE (`t.Log`), not an assertion,
     because a future strengthening must not red;
  3. no VIP resignation — same, tripwire;
  4. the next reconcile re-drives `rg_active=true`, asserted as the DURABILITY
     BOUND of the ack rather than as a defect.

  It is the counterpart of `TestFenceRearmsReconcileRetry`, not its inversion:
  both pass together, before and after.

- **Files**: `pkg/cluster/sync_fence_ack_7147.go` (`WHAT THE ACK MEANS HERE`
  paragraph, the `FenceAckOK` constant, `FenceResult`, `FenceAck.Confirmed`),
  `docs/ha-failover-status.md` (the confirmed-vs-fail-open table row an operator
  actually reads, plus a new "What a CONFIRMED fence does and does not give you"
  subsection), `pkg/cluster/README.md` (a bullet ahead of the existing
  partition-residual bullet — this is a SECOND, independent residual and was not
  covered by that one).

end and requires the counter to move, so the zero above it is a measurement
rather than a silence.
