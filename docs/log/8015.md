## Premise check at `origin/master` (`18ee99640`)

The issue's load-bearing sentence — "Rust synthesizes *and publishes* the
reverse companion on every non-reverse import" — holds, and it is stronger than
the body claims. `synthesized_synced_reverse_entry`
(`userspace-dp/src/afxdp/shared_ops.rs`) is TOTAL on forwards: its only `None`
arm is `if entry.metadata.is_reverse`. `upsert_synced_session` calls it
unconditionally for a non-reverse import and publishes the result through
`publish_shared_session` plus a per-worker `UpsertSynced` fan-out. The #5674
entry cap is sized at `2 * worker_count * DEFAULT_MAX_SESSIONS` *because* of
that, so the pairing is a load-bearing invariant rather than incidental
behaviour.

Re-measured rather than inherited: `upsert_synced_session_refuses_standalone_
reverse_8015` leg (a) asserts a forward-only import leaves `entries == 2` and
names the companion key. Breaking the synthesis (`return None`) reds it at
`left: 1, right: 2`.

## What the triage comments left open, and what closed it

The **older-helper** question (a rolling upgrade running a helper that does not
synthesize) does not apply: `mirrorSessionPairV4`/`V6` is on the LOCAL control
socket, reached from `SetSessionV4`, and nothing of it crosses the HA wire.
Daemon and helper resolve together (`process.go` joins the helper next to
`os.Args[0]`). Additionally: `synthesized_synced_reverse_entry` first appears
in `766946d25` (2026-03-16), which predates every helper any current install
can be carrying, so even the `exec.LookPath` fallback residual has no version
window to hit.

Two things I found that the issue does not say:

1. **`mirrorSessionPairV4`/`V6` is barely reachable in production.** Every
   caller of `Manager.SetSessionV4`/`V6` is inside `pkg/dataplane`:
   `dataPlaneSessionStore.restoreV4`/`restoreV6` (the #5305 rollback restore) and
   `putClusterSyncedV{4,6}Raw`'s non-installer fallback — which the userspace
   manager never takes, because `LegacyDataPlaneAdapter` implements
   `SetClusterSyncedSessionV4`/`V6`. So the only live path into the pair mirror
   is a cluster-synced install that failed partway and is being rolled back. That
   makes the change low-risk, and it also bounds what the #7179 orphan counter
   could ever have observed.
2. **`SessionPairOrphanedReverseTotal` had no production consumer.** It was
   exported "for the status/metrics surface" and nothing outside its own test
   file read it, so removing it changes no operator-visible surface.

## What landed

**Go.** `mirrorSessionPairV4`/`V6` → `mirrorSessionV4`/`V6`, one `upsert` each.
With one request the #5007 single-snapshot build and the #5698 contiguous
transmit are vacuous, so `syncSessionPairLocked`, `sessionPairMaxRequests`,
`sessionPairResult`, `sessionPairResult.orphanedReverse`,
`recordSessionPairResult`, the `sessionPairOrphanedReverse` counter and
`SessionPairOrphanedReverseTotal` are deleted; `sendSessionSyncBatch` returns a
plain `error` again.

**Rust.** `upsert_synced_session` returns the new
`SyncedImportOutcome::RejectedStandaloneReverse` (token `standalone-reverse`)
before any other decision when `entry.metadata.is_reverse`. The typed refusal is
the signal; no counter was added, because with the sender deleted and the peer
path excluded no shipped daemon can produce the condition and a permanently-zero
metric says nothing.

The `!entry.metadata.is_reverse` conditions further down `upsert_synced_session`
are now redundant with that early return and are kept deliberately, the same
posture as the #2170 delete-side generation guard whose own comment records that
nothing reaches it today. Weakening the early return then degrades to the
previous behaviour rather than to an unguarded publish.

## The one field where the two companions differ

The explicit reverse was never ADDITIVE. By the time it arrived the helper had
already published a companion for that forward, so the second request either
overwrote it — when `val.ReverseKey` and the helper's
`reverse_session_key(forward, nat)` name the same tuple, the ordinary case — or
published a THIRD entry if the two derivations ever disagreed. Stated
disjunctively on purpose: two independent derivations of "the reverse tuple"
agreeing is a claim I did not measure, and the conclusion does not need it.
Either way, deleting the request cannot leave the reply direction uncovered, and
the version that survives is the one resolved against live node-local state — so
every field difference is a behaviour change in the helper's favour.

`synthesized_synced_reverse_entry` inherits the forward's `nat64_reverse`, log
selection, `policy_id`, `inactivity_timeout_ns`, `policy_counter*` and
`fabric_ingress`, swaps the zones, and resolves `owner_rg_id` and the resolution
against live state — a superset of what `revVal := val` could carry. The one
field it does NOT inherit is `session_id`: it sets 0, where the Go copy carried
the forward's `RTFlowSessionID`.

Checked, and it is not a regression. RT_FLOW logging reads the session id from
the FORWARD key (`sessions.session_id_for(&flow.forward_key)` at every
`poll_descriptor` site), off the worker-local table, not off the shared synced
map's reverse row. And every PEER-synced companion has always been synthesized
with `session_id: 0` — the local mirror's was the only companion in the tree
that carried a non-zero one, on a path reachable solely from the #5305 rollback.

`cap_rejected_forward_leaves_no_orphan_reverse_8015` drives the historical
sequence end to end — fill the shared map to its 2N entry cap, offer a NEW
forward (cap-rejected), then offer the companion the old Go mirror sent right
behind it — and asserts the map is left EXACTLY as it was found. Its last leg
re-measures the third fact from the refiling that no later pass re-checked: a
forward delete takes its synthesized companion with it, leaving zero.

#310 is covered inside
`upsert_synced_session_refuses_standalone_reverse_8015`: no `update_ha_state`
runs in that cell, so the companion's `UpsertSynced` in the worker queue IS the
companion arriving before RG activation — strictly earlier than the deleted Go
pre-install could deliver it.

The Go cells assert the exact request SET, not the absence of a flag: "no
request carries `is_reverse`" would also pass for a mirror that emitted the
companion under the forward's own flag, or emitted nothing at all. The capture
harness was rewritten to keep draining for a settle window after the first
request — the old one blocked until it had TWO and fatalled otherwise, which
cannot express "exactly one" — and the first mutation is the positive control
that it still SEES a second request.

## Deleted guards, and where their subjects went

- `session_pair_transmit_5698_test.go` (contiguous pair transmit),
  `session_pair_orphan_7179_test.go` (orphaned-reverse classification and its
  wiring) and `manager_sessionsync_snapshot_5007_test.go` (forward and reverse
  resolved against one snapshot) all had the PAIR as their subject. There is no
  pair; the subjects are gone, not unguarded.
- `TestReverseCompanionCarriesNoIngressIdentityV4/V6_7917` guarded the Go
  companion's ingress identity. That companion is deleted, so the invariant was
  re-homed onto the Rust builder as
  `synthesized_synced_reverse_entry_carries_no_ingress_identity_7917` — with a
  fixture that gives the forward a NON-ZERO identity, because `test_metadata()`
  carries `ingress_ifindex: 0` and a companion that inherited it would have read
  0 and passed for the defect. Its forward-unchanged leg is the over-reach
  control the Go cell carried.
- `pkg/dataplane/session_reverse_companion.go` keeps
  `ResetUnobservedForReverseCompanion` and its census test although the change
  removes its only caller. The rule, and its pinned divergence from
  `ScrubNodeLocal`, is what stops a future node-local field from silently
  becoming a companion reset — the #7097 failure mode. The file now says so.

## Harm if this is wrong

The failure this could cause is a locally installed forward session whose reply
direction has no synced entry, which after a failover would drop the reply. Three
things bound it: `synthesized_synced_reverse_entry` is a total function on
forwards (read, not assumed), the Rust control leg measures `entries == 2` from a
forward-only import, and the Go path that lost a request is reachable only from
the #5305 rollback restore. The refusal half cannot harm a current daemon at all
— nothing in tree sends a standalone reverse — and under a skewed OLD daemon its
explicit reverse would simply be refused, leaving the helper's own companion in
place, which is the better entry.
