# 7990 — LANE-1 in-place rolling has no session-sync version check

Premise-checked at `origin/master` `e67d38dfa` in a worktree. I filed this issue
myself while costing #7160, so the first job was to re-establish it by predicate
rather than re-read my own message — a verification by the process that formed
the belief is not a verification.

## Premise, re-verified

- `SessionSyncWireVersion` has exactly one gating consumer: it is printed by
  `xpfd protocol-versions` (`cmd/xpfd/main.go:176`) into the image manifest and
  compared by `GateMixedBaseSwap` (`imageversions.go:169`). Nothing else gates on
  it anywhere in the tree.
- It is **not** on the heartbeat: `HeartbeatPacket` carries `SoftwareVersion` and
  `HAProtocolVersion` and nothing else version-shaped (`heartbeat.go:123-137`).
- `sync.go:26` states the session-sync frame header has **no on-wire version
  field**, so a changed layout cannot be negotiated per-message.
- The LANE-1 drain precheck (`kernel_drain.go`) called only
  `HAProtocolCompatible`, which `parseHAProtocolCompatible` implements by reading
  the two "HA protocol version" lines. Since #7925 those are a different counter
  from the sync wire, so a matching HA version says nothing about whether the
  peer can decode a session frame.

**And two false claims in the code itself**, which is worse than the missing
check because they are what a reader consults:

- `kernel_drain.go` refused with *"HA/session-sync protocol incompatible with
  peer"* — naming a property the check never looked at.
- `RollingCluster.HAProtocolCompatible`'s doc comment said *"the local and peer
  HA/session-sync protocol versions"*. Same overstatement.

## Choosing the channel — measured, not assumed

The brief asked for the cheapest honest channel, with the compatibility
consequence measured rather than assumed to be free. I evaluated two.

### The heartbeat — feasible, but the wrong choice

Its trailer discipline is real and I verified it in the parser rather than the
comment: `UnmarshalHeartbeat` reads the software-version length-prefixed field,
then `HAProtocolVersion`, then `return pkt, nil` — trailing bytes are ignored
(`heartbeat.go:366-381`). #6370 shipped an epoch section on exactly this basis
and recorded the result as *"Bidirectional compatibility with no
HAProtocolVersion bump"*.

But it also recorded the way that goes wrong: appending AFTER the auth trailer
*"failed review in #6370 — a v1 receiver looking for `XPFA` at len-52 found body
bytes, read the frame as unsigned, and an enforcing v1 peer rejected every frame,
splitting a keyed cluster mid-upgrade."*

And the epoch section is auth-only (`marshalHeartbeatAuthEpoch` returns early on
an empty key), so an unkeyed cluster would get no advertisement at all.

### `syncMsgPeerCapabilities` — the right one, and already argued

`sync_capabilities_6650.go:24-39` already wrote down why this channel beats the
heartbeat for exactly this kind of advertisement, and its three reasons apply
with more force to a version that describes the sync connection itself:

1. same connection as the thing being gated, so "peer reachable" and "peer
   version known" share one lifecycle;
2. the heartbeat is size-capped UDP with back-indexed tail sections, and the
   epoch section needs a PSK;
3. the sync wire has the precedent and the room — TCP, no size pressure, and
   `handleMessage`'s switch has no default arm with length-prefixed framing.

Verified in the reader rather than the comment (`sync_conn_read.go:647-666`):
*"a LONGER one is a newer peer with extra fields we skip"* is implemented as a
`len(payload) >= 3` guard for #7147's flags byte, with the #6650 field read from
`payload[:2]`. A 5-byte payload is therefore read correctly by a pre-#7990 peer.

**No version bump, and here that is forced rather than convenient**: bumping
`SessionSyncWireVersion` in order to advertise `SessionSyncWireVersion` would
make `GateMixedBaseSwap` — which compares it for exact equality — refuse session
sync across precisely the upgrade that first carries the field.

## The honest limitation, stated rather than hidden

A peer advertising nothing predates #7990, and `SessionSyncWireCompatible`
**permits** that case. Refusing would fire on every roll from the previous
release and on no real skew — the worst possible calibration.

So this gate **cannot protect the first roll that carries it.** It protects every
roll after, which is every roll that could actually move the constant (it has
never moved; #7160 is what would move it first). That is the dual-accept shape
#4107 and #4126 already used: accept both wire forms during the upgrade window,
enforce once both sides speak the new one.

## Design choices worth naming

- **The advertisement reads the compile-time constant**, not a settable field.
  #6650 needs a setter because the snapshot version is a runtime property; the
  wire version is not. No bring-up call to forget, and no way for the advertised
  value to disagree with the frames the process actually writes.
- **`PeerSessionSyncWireVersion() uint16` is on the `SyncStatsProvider`
  interface**, not reached by an optional type assertion. An assertion that
  silently fails renders no version and leaves the gate unable to fire — which is
  indistinguishable from a healthy pair. The compiler asks instead, and it
  immediately caught the one `RollingCluster` fake that needed updating.
- **0 renders as `unknown`, not `0`.** There is no valid wire version 0, so
  printing the number invites a reader — or a parser — to compare it as one.
- **The gate is NOT behind `allowMixedHA`.** That flag exists because the LANE-2
  mixed-base gate already validated the HA *window* and exact-equality would
  wrongly abort the second node. It says nothing about the session wire, which
  `GateMixedBaseSwap` checks for exact equality in both cases. Reusing it would
  silently disable this gate on the path that most needs it.
- **A transport error on the check fails the drain.** An unreadable status is not
  evidence of compatibility.

## A lock-graph check, because a new field is a change to the lock graph

`Manager.PeerSessionSyncWireVersion` takes `m.mu.RLock`. `FormatStatus` also
takes `m.mu.RLock` — a re-entrant RLock deadlocks if a writer is queued between
the two. Verified by line number rather than by reading the shape: the lock
region is `status.go:13-35` and the new call is at `:86`, outside it.

## The defect I built, and the test that failed to catch it

The brief warned that a version check which cannot fire because its channel is
absent would be another instance of the failure shape this change exists to
remove. It was, and I had written it.

The first version of the decision did:

```go
peer, ok := parsePeerSessionSyncWire(s)
if !ok {
    peer = 0 // -> PERMIT
}
```

`parsePeerSessionSyncWire` deliberately distinguishes "line absent" `(0,false)`
from "line present, unknown" `(0,true)` — I had even written a comment saying a
future caller might need to tell them apart — and then the only caller collapsed
them. Absence is a statement about the INSTRUMENT, not the peer: `FormatStatus`
renders the peer line unconditionally when the peer is alive, and
`DrainAndConfirm`'s `PeerAlive` precheck runs first, so by the time the gate runs
the line must be present. Its absence means the status could not be rendered or
parsed, and permitting on that is a gate that cannot fire.

Now an ERROR, not an incompatibility — "the check could not run" and "the peer is
incompatible" are different facts and only one is about the peer.

**Then the test I wrote for it did not catch the revert.** M8 (collapse absence
back into permit) scored **0 named FAIL**. The cell drove
`parsePeerSessionSyncWire` and `cluster.SessionSyncWireCompatible` directly —
both UNCHANGED by the defect, which lives between them. Bind the wiring, not the
functions it calls; I wrote a wiring test that tested neither side of the wire.

Fixed by splitting `sessionSyncWireVerdictFromStatus` out of the gRPC fetch so
the decision layer is drivable, and pointing the cell at it. Re-run:

| mutation | named FAILs |
|---|---|
| M8 absence permits (the reverted fix) | 1 — `AbsentStatusLineFailsRatherThanPermits7990` |
| M9 refuse everything (the paired direction) | 1 — same cell |

Both directions red the same cell, which is what makes it a paired proof rather
than a one-sided one: M8 alone would be satisfied by a gate that refuses
everything, and that gate would abort every roll from a pre-#7990 release.

One process note: M9's first form was `if true {`, which leaves `present`
unused — a **build break**, and my ad-hoc check counted its 0 named FAILs as an
escape. Re-run as `if !present || true {` so it compiles. A cell with no named
failing test is a void cell, not a red, and I nearly recorded the opposite.
