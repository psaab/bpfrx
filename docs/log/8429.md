# #8429 — single-rate policers enforced one eighth of the configured bandwidth

- **Timestamp**: 2026-09-03
- **Action**: Fixed the unit crossing at the single-rate policer's snapshot
  emitter, corrected a log key that named the same bytes value as bits, and
  bound the END-TO-END unit chain with a control on the leg that shares the
  parse.
- **File(s)**: `pkg/dataplane/userspace/filters.go`,
  `pkg/dataplane/compiler_filter.go`, plus one new test file.

## Direction confirmed from the body, not the comment

The brief said to verify which side is wrong before writing anything, because if
the comment were the stale thing the fix would invert. It is not:

```go
func parseBandwidthLimit(s string) uint64 {
	return parseScaledDecimalUnit(s) / 8
}
```

The function returns BYTES per second, exactly as its comment says. The defect
is downstream.

## The chain

    config `bandwidth-limit 8m`
      -> parseBandwidthLimit            = 1,000,000 BYTES/sec
      -> wire `bandwidth_bps`           = 1,000,000   <-- bytes in a bits field
      -> filter/compiler.rs  bps / 8    =   125,000 BYTES/sec

125,000 B/s = 1 Mbit/s for a configured 8 Mbit/s: **12.5%**, which the cell now
prints when it fails. With `then discard` this drops conforming customer traffic
and the policer counters attribute it to the customer.

## Fix at the single crossing emitter

`BandwidthBps: pol.BandwidthLimit * 8` in `buildPolicerSnapshots`. NOT by
removing the divisor from `parseBandwidthLimit`, which is shared: three-color
policers parse through the same function and are correct because they emit into
`committed_rate_bytes_per_sec`, a byte-NAMED field the helper does not re-divide.
The eBPF leg (`RateBytesSec`) is byte-named too. Only the single-rate userspace
leg crosses units.

No overflow: the value is `scaled/8` for a `scaled` that already fit a uint64.

## The second surface, found by looking before being told to

The brief asked whether any operator-visible surface renders the same field.
`pkg/dataplane/compiler_filter.go` logged `"rate_bps", pol.BandwidthLimit` — a
BYTES value under a bits key, on the eBPF leg whose ENFORCEMENT is correct. Only
the label lied, and it lied in the same direction as the real defect: an operator
reading that line to check a policer saw a rate 8x too low. Key corrected to
`rate_bytes_sec`.

Checked and clear: no `show` command and no Prometheus descriptor renders policer
bandwidth, and the only wire consumer of `bandwidth_bps` is
`filter/compiler.rs:488`. So there is no third surface and no second issue to
file.

## The guard binds the CHAIN, because neither side alone was wrong

Both sides were internally coherent — Go consistent in bytes, Rust consistent in
"divide a bps field by 8" — so a Go-side pin and a Rust-side pin both passed
while the product was wrong. The cell therefore asserts BOTH the wire value and
the result of applying the CONSUMER's formula to it, so a change on either side
that breaks the agreement fails here.

The three-color cell is a control in the strict sense: it must be UNCHANGED by
the fix. Mutation-verified as having power — applying the tempting repair
(dropping `/8` from the shared parse) reds it with "every three-color policer now
meters eight times its configured rate".

| mutation | red |
|---|---|
| revert the emitter to `pol.BandwidthLimit` | chain cell, both assertions; control green |
| drop `/8` from the shared `parseBandwidthLimit` | **control** cell (and the chain cell) |

## What is NOT claimed

No live traffic verification. The CoS smoke configures `class-of-service
scheduler-maps` (schedulers/shapers), not `firewall policer` single-rate
policers, so nothing in-tree exercises this path against real traffic. Building
one is a new harness and out of scope here; the unit chain and its two mutations
are the evidence, and the enforced-rate claim rests on reading
`filter/compiler.rs`'s formula rather than on measuring a meter.
