# #6949 — the JSON session-delta leg dropped the whole policy attribution

**Branch** `fix/6949-session-delta-policy-attribution` ·
**Base** `origin/master` · Refs #4626, #5865, #7194

## 1. The defect

A session delta leaves the helper on **two** wires:

| Leg | Producer | Driven by |
|-----|----------|-----------|
| binary `MSG_SESSION_OPEN` | `event_stream::codec::session_sync::encode_session_open` | the event stream (primary HA path) |
| JSON `SessionDeltaInfo` | `afxdp::session_delta::session_delta_info` | `drain_session_deltas` + `ExportOwnerRGSessions` |

They had diverged on five fields. The binary frame has carried, as trailing
length-gated fields:

| Field | Since | Binary offset | JSON leg before this change |
|-------|-------|---------------|------------------------------|
| `policy_id` | #3056 / #3301 | `[+0:+4]` | **absent** |
| `policy_counter_idx` | #3073 | `[+4:+8]` | **absent** |
| app inactivity timeout (seconds) | #3227 | `[+8:+12]` | **absent** |
| `nat64` | #4565 | `FLAG_NAT64`, flags bit `1<<5` | **absent** |
| `nat64_snat_v4` | #4565 | `[+12:+16]` | **absent** |

The Go consumer (`pkg/dataplane/userspace/protocol_ha.go`, `SessionDeltaInfo`)
declared and read all five **unconditionally**, on whichever leg delivered the
delta.

### Reachability — this is not an exotic fallback

`eventStreamFallbackLoop` (`pkg/daemon/daemon_ha_userspace_stream.go`) drains the
JSON leg every **100 ms** while the binary stream is down and every **5 s** even
while it is up. `ExportOwnerRGSessions(rgIDs, 0)` re-serializes the entire owned
session table through the same struct on **every** helper-requested FullResync. A
helper restart or an event-stream reconnect on any clustered node reaches it.

### Impact

Every session learned through the JSON leg imported `PolicyID = 0`,
`PolicyCounterIdx = 0`, no application timeout and no NAT64 pool source:

* **Attribution** — renders `unattributed` on `show security flow session`, REST
  and gRPC.
* **Invalidation** — exempt from the commit-time deletion-clear and the #4234
  policy-rematch, both of which skip id 0
  (`pkg/daemon/daemon_policy_invalidate.go`). A session the operator meant to
  drop keeps forwarding.
* **Counters** — no per-rule hit counter after a failover promotion (#3073).
* **Timeouts** — ages on the global per-protocol timeout, not the
  per-application one (#3227/#3301).
* **NAT64** — this one is not a mis-attribution. `snat_v4` is chosen by
  `allocate_source` and is **not** derivable from the synced forward v6 key
  (#4565), so a NAT64 session promoted from this leg cannot rebuild its reverse
  v4→v6 BIB at all: a translation failure after failover.
* **HA retroactive loss** — each reconciliation copy carries a fresh #2170
  install generation, so a later JSON copy can **overwrite an earlier, correct,
  event-derived copy on the peer** under latest-generation-wins. A correctly
  attributed session can lose its attribution retroactively.

### Why it survived four releases

A rendered `policy_id` of 0 displays as `unattributed` (#6851) — identical to a
session no policy admitted. Three states (*attributed to N*, *attributed to 0*,
*attribution dropped*) were crushed into two, so the failure mode was
indistinguishable from healthy on every operator surface.

And the one place an auditor would naturally look said it was fine:
`protocol_ha.go` claimed since #3301 that the policy fields were *"decoded from
the trailing fields of the binary open frame **AND mirrored on the JSON
RPC-fallback delta**"*. The second half had never been true.

## 2. The agreement mechanism: single-source, not a second copy

A divergence between the two producers is **always** a bug — they describe one
session for one peer. So the derivation is single-sourced rather than written
twice and held in agreement by a test:

```rust
// userspace-dp/src/session/sync_attribution.rs
pub(crate) struct SessionSyncAttribution {
    pub(crate) policy_id: u32,
    pub(crate) policy_counter_idx: u32,
    pub(crate) inactivity_timeout_secs: u32,
    pub(crate) nat64: bool,
    pub(crate) nat64_snat_v4: Option<Ipv4Addr>,
}
impl SessionSyncAttribution {
    pub(crate) fn from_session(decision: &SessionDecision, metadata: &SessionMetadata) -> Self
}
```

`from_session` also owns the two **non-trivial conversions** that would otherwise
have been a second divergence waiting to happen even after the fields were
added: the saturating ns→s timeout, and the `(nat64, rewrite_src)` pool-source
selection.

Both producers destructure it **exhaustively — no `..`**:

```rust
let SessionSyncAttribution {
    policy_id, policy_counter_idx, inactivity_timeout_secs, nat64, nat64_snat_v4,
} = SessionSyncAttribution::from_session(decision, metadata);
```

so a field added to the struct **fails to compile** until both legs carry it.
That is the structural guard, at compile time rather than in a text scan.

### Why not a cross-producer agreement test alone

Because a test that pinned the JSON producer to `policy_id: 7` would encode
*which side is believed correct*, and would pass even if the binary side were the
broken one. The one agreement assertion that survives is "the two legs describe
the same session", which is what
`session_delta_json_and_binary_agree_on_policy_attribution_6949` asserts — one
session, both wires, neither side pinned to a literal. It is kept **alongside**
the single-source seam: it is what catches a future producer that stops using the
helper, and the pre-existing binary-side codec tests (#3301/#4565) are the other
half — they pin the binary leg's own values, so a mutation inside the shared
helper (which moves both legs together and leaves the agreement test green) still
reds. See cell **M6**.

### The three-state fixture

The agreement fixture's `policy_id` is **4242, not 0**. A fixture whose correct
value is 0 cannot distinguish "attributed to policy 0" from "attribution
dropped" — the exact confusion that hid the defect.
`session_delta_info_zero_attribution_is_present_not_absent_6949` covers the third
state from the other side: a genuinely unattributed session must emit the keys
carrying an **explicit 0**, never an absent key.

## 6. Rolling-upgrade safety and what is NOT fixed here

Both sides are `serde(default)` / `omitempty`, so the change is additive in both
directions: an old helper omits the keys and they decode to `0`/`""`/`false` —
precisely the pre-#6949 behaviour of this leg — and an old daemon ignores keys it
does not know.

That means this issue's parity is true **only when both sides are new**. Making
it durable across a mixed-version cluster — fail-closed capability negotiation,
and the canonical-schema equivalence test that would have caught this whole class
— is out of scope here and tracked on **#7194**.

Also unchanged and still open: `afxdp/bpf_map/publish_conntrack.rs` hardcodes
`log_flags: 0` on the BPF mirror while the same rows carry a real `policy_id`
(noted on the issue as a likely latent defect of the same family). It is a
different producer with a different consumer and is left for its own change
rather than folded in here.

`docs/sync-protocol.md` needs no update: it documents the Go↔Go cluster wire,
which was never missing these fields.
