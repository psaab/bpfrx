# 6989 / 6985 / 6945 — `install_session_serializes_with_reconcile_removal`

Three issues, one root cause: the test's non-vacuity guard measures the
scheduler instead of the precondition it claims.

`afxdp::wg::engine::engine_internal_tests::install_session_serializes_with_reconcile_removal`
asserts `reconcile_iters >= 1` under the message *"reconcile loop must have
completed at least one full add/remove cycle"*, whose surrounding comment reads
*"we made progress on both sides — otherwise the test is not actually
exercising the race window"*.

- **#6989** — ~1-in-3 under `cargo test --release -- --test-threads=1`, measured
  at `78f1239f9`.
- **#6985** — under machine load; also observed exceeding libtest's 60s warning
  threshold without failing.
- **#6945 part 1** — 1-of-5 at master `a26509a6f` under full-suite load, 0-of-10
  isolated. (Part 2, `v8_epoch_seqlock_snapshot_never_tears_tag_grace`, is
  explicitly not characterised there and is tracked on #6991 / #7001. This
  branch does not touch it.)

## What the guard actually is

It is a **precondition guard, not the assertion**. The assertion this test
exists for is the orphan-demux post-condition swept by
`assert_no_orphan_demux_entries` — every entry in `sessions_by_local_index`
references a peer present in the published table. `reconcile_iters >= 1` and
`ok > 0` are the guards that say the race window was exercised at all.

Miscasting it as the assertion is why a red here was read as a correctness
claim. The message says "must have", which reads like a contract; it is a
setup check.

## The guard was wrong in BOTH directions

**Before #6633 — a false RED.** The reconciler thread is unbounded and the
installer thread is not. Under contention the installer could complete all 400
attempts and the main thread could store `stop` before thread B was scheduled
even once, so `reconcile_iters` was 0 and the test failed on a scheduling
artifact. That is what all three issues report.

**After #6633 — a vacuous GREEN.** #6633 (`0443ec6bb`, 2026-08-22) gave
`reconcile_churn_until` a do-while shape, so at least one cycle always
completes. All three issues were filed at commits that PRE-DATE it
(`78f1239f9`, `a26509a6f`, `e8c2403a5` — none has `0443ec6bb` as an ancestor),
so the reported red cannot reproduce at today's master. But `reconcile_iters >= 1`
is now satisfied by a reconciler that ran its single cycle entirely AFTER the
installer joined. That is **zero overlap** — precisely the case the guard was
written to catch — reported as healthy. The value it returns when the
precondition fails is now indistinguishable from the value it returns when the
precondition holds.

## Reproduction

`--test-threads=1`, subject test only, under 24 synthetic CPU spinners on top of
an ambient load average of ~20 on 16 cores.

| tree | shape | trials | FAIL |
|---|---|---|---|
| **pre-#6633 control** (`while !stop` restored on master) | the shape the issues were filed against | 20 | **1** |
| master `58ad6d553` | do-while (#6633) | 20 | 0 |
| this branch | do-while + progress rendezvous | 20 | 0 |

The pre-#6633 row is the **positive control**, and it is what makes the two
zeros readable: without it, "0-of-20" would be an unfalsifiable green from a
harness that might simply be unable to see the defect. The control failure is
the reported one, verbatim:

```
panicked at src/afxdp/wg/engine_tests.rs:1122:5:
reconcile loop must have completed at least one full add/remove cycle
```

Master does not reproduce because the assertion is unfalsifiable there, not
because the machine was quiet. Both facts are needed; either alone misleads.

## The fix

Wait on the **observable**, not on elapsed time.

1. `reconcile_churn_until` publishes its completed-cycle count to a shared
   `AtomicU32` after every cycle. The do-while shape is retained unchanged — it
   is what makes the count non-zero by construction; the counter is what makes
   it observable *while the loop is still running*, which the do-while cannot
   supply.
2. The installer thread calls `wait_for_first_reconcile_cycle` before its first
   install. Every install then races live churn — established, not hoped for.
3. The post-loop guard becomes `saw_cycles >= 1`: the count thread A observed
   BEFORE its first install.

The 60s deadline is a **liveness backstop against a microsecond operation**, and
the failure text says so in those words. This project has twice reddened master
by "fixing" a wall-clock flake with a tight bounded wait, which only moves the
sample; the deadline here is six orders of magnitude of headroom and must not be
raised in response to a red.

**Why a rendezvous is safe here, when #6633 judged one unsafe.** #6633 rejected
it on two grounds: it makes the bounded thread wait on the unbounded one, inside
a module with an open futex wedge (#6952), trading a false red for a possible
hang. Both are addressed, and the reasoning is recorded at the helper:

- No cycle in the wait-for graph. The reconciler loops until `stop`, which the
  MAIN thread sets only after joining the installer, and it takes no lock the
  waiting installer holds (the installer holds none while waiting). The awaited
  thread is always runnable.
- It is not a futex block. It is a bounded poll that panics BY NAME — the same
  idiom `run_bounded` uses for the #6952 sweep. A stall becomes a named
  assertion failure, never an rc=124 wedge.

#6952 itself merged (PR #7809) before this branch, so the wedge that grounded
the original objection is closed.

## Second defect, found by the mutation matrix

`run_bounded` decided "the body finished" from an `AtomicBool` the worker sets
AFTER calling the body, so a body that **panicked** left the flag false and the
caller waited out the full 30s before reporting the deadlock text. Cell M1
produced exactly that: the sweep's own assertion fired with the diagnosis a
reviewer needs —

```
after removing the only peer, no demux entries should remain;
found 126 — install/reconcile race left orphans
```

— and the caller buried it 30 seconds later under *"the worker thread is parked,
which for this body means a same-thread RwLock self-deadlock (#6952)"*. Wrong
defect, 60x the cost, and a cell scored on the named message would have
attributed a real serialization regression to #6952.

`run_bounded` now watches the join handle as well as the flag and
`resume_unwind`s the body's payload. A body that genuinely parks never finishes,
so the deadlock path is unchanged — cell M5 confirms it.

**M1 is the proof obligation**: the serialization property this test exists for

assertion mis-reported. M1-at-master shows the fix is not *sufficient on its
own* for the property, i.e. it did not become the only thing holding the test
up.

## `ok > 0` was measured, not assumed, and deliberately left alone

The other non-vacuity guard in this test, `ok > 0`, is the same shape of check
and could in principle flake the same way. It was measured rather than
reasoned about — a throwaway cell forcing `ok > iterations` so the panic
message reports the distribution:

| tree | `(ok, unknown, collision)` over 8 full-suite runs |
|---|---|
| master `58ad6d553` | 400/0/0 ×7, 389/11/0 |
| this branch | 400/0/0 ×5, 388/12/0, 387/13/0, 386/14/0 |

`ok` never approaches 0 — the margin is ~386 of 400 — so `ok > 0` is not a live
flake, and it is left untouched (narrow scope). The distributions also match
across the two trees, which is the check that the rendezvous did not *reduce*
interleaving while making the guard honest.
