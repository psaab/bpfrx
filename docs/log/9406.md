# 9406 — the DHCP relay bound the authored Junos reference, so it bound nothing

- **Timestamp**: 2026-09-07
- **Action**: resolve each relay group member to its Linux device before
  binding, keep the authored reference as the relay's identity, surface the
  bound device, and warn at commit when a member names nothing.
- **File(s)**: `pkg/dhcprelay/relay.go`, `pkg/dhcprelay/README.md`,
  `pkg/daemon/daemon_apply_tail.go`, `pkg/daemon/daemon_run.go`,
  `pkg/cli/show_services_dhcp.go`,
  `pkg/config/compiler_validate_warn_dhcprelay_iface_9406.go` (new),
  `pkg/config/compiler_validate_warn_protocol_iface_9405.go` (helper extracted),
  `pkg/config/compiler_validate_warn.go`, plus the three new test files.

## Is this #4049 again? Same class, different remedy — and I measured it

The brief asked whether #4049 (LLDP: `net.InterfaceByName` handed the Junos
slash name) is the same defect, and whether to reuse its remedy. It is the same
CLASS and the remedy does **not** transfer. Measured at HEAD:

```
LinuxIfName("ge-0/0/0.0")          = "ge-0-0-0.0"    <- the #4049 remedy alone
ResolveKernelIfName("ge-0/0/0.0")  = "ge-0-0-0"
ResolveKernelIfName("ge-0/0/0.80") = "ge-0-0-0.180"   (unit 80, vlan-id 180)
```

`ge-0-0-0.0` is not a device either. LLDP references are PHYSICAL interfaces,
so the slash→dash rewrite was sufficient there; a relay member is a LOGICAL
interface, so it needs the unit-0 collapse and the `.<vlan-id>` arm as well.
Reusing `LinuxIfName` here would have looked like a fix, passed a
dash-vs-slash test, and still bound nothing.

## The shape of the fix, and the trap in it

A relay now carries TWO names. `ifaceName` stays the authored reference and
remains the relay's IDENTITY — the Apply diff key, the Stats row, the #2456
master gate, and `relayInterfaceRG`, which parses it as a Junos unit ref.
`kernelName` is the resolved Linux device and is what every kernel-facing call
takes: `SO_BINDTODEVICE`, the giaddr lookup, the #2347 ifindex drift check, the
#2076 raw-L2 sender.

**The tempting one-line fix — resolve the desired-set KEY — silently breaks
HA.** `relayInterfaceRG` looks the base name up in `cfg.Interfaces.Interfaces`,
which is keyed by the AUTHORED name. A kernel name is not a key there, so every
RETH-owned segment would resolve to RG 0, the #2456 gate would read "not
RG-owned → always relay", and BOTH cluster nodes would relay the same client
broadcast upstream with different giaddrs. A test asserts the identity stays
the authored reference for exactly this reason.

`kernelName` is part of `relaySpec` rather than a field beside it: a `vlan-id`
retag changes the device to bind without changing any other field, and
`relaySpec.equal` is the only thing that decides whether the reconcile rebinds.

## One call site, not two

Boot (`daemon_run.go`) called `Manager.Apply` directly while the day-2 path went
through `reconcileDHCPRelay` — two places to remember the resolver, and the
BOOT one is the one that matters, because a box that boots with a relay already
configured never sees a commit. Boot now routes through `reconcileDHCPRelay`
(`d.daemonCtx` is set long before, and was the ctx it passed anyway), so there
is one site. `TestDHCPRelayApplyHasOneProductionCallSite9406` keeps it that way.

## Loudness

The runtime cannot report this failure: `resolveGIAddrWithRetry` is an unbounded
loop with one `slog.Warn` then `slog.Debug` forever and returns no error,
`"dhcp-relay: started"` is logged before any bind, and every `RelayStats`
counter is a forwarding counter. A relay bound to nothing is indistinguishable
from an idle segment. So `show services dhcp relay` now prints the bound device
beside the configured interface, and
`config.validateDHCPRelayInterfaceRefWarnings` warns at commit when a member
names no configured interface or unit — advisory, not a gate, per #1960.

The declared-interface index and the "why does this reference resolve to
nothing" predicate are shared with the #9405 protocol advisory
(`declaredInterfaceIndex` / `unresolvedInterfaceRef`) rather than written twice.
The shared index deliberately does NOT call `ResolveKernelIfName` per interface
— that rebuilds the tunnel-name map per call and made the tolerant compile
quadratic in #9405's first draft.

## Validation

- `go test ./...` — full tree, green.
- The load-bearing cell is `TestRelayBindsTheKernelDevice9406`: it records what
  the RUNTIME hands `SO_BINDTODEVICE`, the giaddr resolver and the ifindex
  drift check through the injected seams, and requires `ge-0-0-0.180` for an
  authored `ge-0/0/0.80`. A correct desired set that nothing reads is exactly
  the pre-#9406 defect, so asserting the desired set alone would not have been
  enough.
- Mutation results are in the PR body.

**No cluster smoke was run, and none would have been evidence.** There is no
`dhcp-relay` stanza in `test/incus/*.conf|*.set` or `docs/*.conf` at all, so no
smoke has ever bound a relay.
