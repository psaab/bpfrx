# #9142 — REST clear-sessions flattened the HA-delegated gRPC status to 500

## Summary

`POST /api/v1/security/sessions/clear` answered the SAME condition with two
different status classes depending only on whether an HA session service was
wired, and leaked the gRPC framing string into the REST JSON body.

`sessionWalkLimiter` is process-wide (`MaxConcurrentSessionWalks = 4`) and shared
by REST + gRPC session list/summary/clear, so ordinary `GET /security/sessions`
scrapes are what saturate it. On saturation:

- standalone (`clusterSessionFn` nil): the local fallback acquires the limiter
  itself and answers **429** (#5779);
- clustered: the handler delegates to the in-process `*grpcapi.Server`, whose
  `ClearSessions` refuses with `codes.ResourceExhausted` from that same limiter
  — and the handler flattened every delegate error to **500**.

## Measurements

- **Timestamp**: 2026-09-06
- **Action**: reproduce, at `origin/master` 444173473, driving the real
  `clearSessionsHandler` with a `ClusterSessionService` that returns canned
  errors:
  ```
  resource-exhausted  status=500 body={"success":false,"error":"rpc error: code = ResourceExhausted desc = session scan concurrency limit reached; retry shortly"}
  unavailable         status=500 body={"success":false,"error":"rpc error: code = Unavailable desc = dataplane not loaded"}
  internal            status=500 body={"success":false,"error":"rpc error: code = Internal desc = boom"}
  plain-error         status=500 body={"success":false,"error":"not a grpc status error"}
  ```
  After the fix:
  ```
  resource-exhausted  status=429 body={"success":false,"error":"session scan concurrency limit reached; retry shortly"}
  unavailable         status=503 body={"success":false,"error":"dataplane not loaded"}
  internal            status=500 body={"success":false,"error":"boom"}
  plain-error         status=500 body={"success":false,"error":"not a grpc status error"}
  ```
  Note the last row: `status.Convert` on a NON-status error yields
  `codes.Unknown` plus the error's own text, so the default 500 arm loses no
  information.

- **Action**: confirm the delegate really produces those codes rather than
  assuming it. `pkg/grpcapi/server_sessions.go` `ClearSessions` returns
  `codes.Unavailable` ("dataplane not loaded") and, on
  `sessionWalkLimiter.Acquire()` failure, `codes.ResourceExhausted` — the same
  limiter variable the REST fallback acquires.

- **Action**: class census — are the other REST→cluster delegation sites the
  same defect? There are three (`pkg/api/sessions.go`, the `include_peer`
  branches of the list, summary and zone-pair handlers). All three ALREADY
  classify, through `peerFetchErrorStatus` (#7294/#8308), which is the precedent
  this fix follows. They set `PeerError = err.Error()`, which does carry gRPC
  framing — but the gRPC side stamps the same field the same way
  (`peer_only_5968.go:97,112`, `server_sessions.go:724,732,763` all use
  `err.Error()`), so that is a consistent existing convention across both
  surfaces, on a field describing a genuinely remote call. Not the same defect,
  and changing it would make the two surfaces disagree. Left alone.
  **Clear-sessions was the only delegation site with an unclassified status.**
