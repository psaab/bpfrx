# #9349 — the applyServicesReconcile DHCP wiring was unguarded in both modes

Self-filed during #9141 as a coverage finding with a measurement, not a defect
report. This closes it.

## What was measured, in #9141 and re-measured here

Two mutations to `applyServicesReconcile`, each confirmed to BUILD, scored over
the WHOLE `pkg/daemon` suite:

| mutation | #9141 | after this change |
|---|---|---|
| `desired := cfg.System.DHCPServer` instead of `desiredStandaloneDHCPConfig(cfg)` | **SURVIVED** | **KILLED** |
| `dhcpCfg := &cfg.System.DHCPServer` instead of `d.desiredClusterDHCPConfig(cfg)` | **SURVIVED** | **KILLED** |

Each deletes an entire subsystem contribution:

- **Standalone** — Kea is handed RETH LOGICAL names (`reth1.0`), not kernel
  devices, so it cannot bind them and DHCP fails on every RETH-backed segment.
- **Clustered** — Kea is handed the unfiltered config, so BOTH nodes serve every
  group regardless of redundancy-group mastership: dual-DHCP, the exact failure
  the #1835 F3 / #6520 design exists to prevent.

## Why it was uncoverable

`Daemon.dhcpServer` was a concrete `*dhcpserver.Manager` with 14 call points and
UNEXPORTED test seams (`runSystemctl`, `unitActive`, `confPath4`/`confPath6`,
`warn`), so a `pkg/daemon` test could not build a harmless one. The functions
BELOW the call sites were well covered — #6520/#4647 on the filter, #9141 on the
resolver, #6535 on the converger — and none of them can see their caller not
calling them.

## The change

`dhcpApplier`, an interface covering exactly what the daemon calls (plus the
three read methods `pkg/grpcapi` needs and the converger's
`ApplyFailedForTesting`), with `var _ dhcpApplier = (*dhcpserver.Manager)(nil)`
so a signature drift is a compile error.

`pkg/grpcapi`'s `Config.DHCPServer` became a three-method `DHCPServerStatus`
interface in the same change. Leaving it concrete would have forced a type
assertion at the hand-off — reintroducing the coupling the change removes. Go
widens interface-to-interface when the method set is a superset, so the daemon's
field assigns straight into it.

The recording applier in the cell deliberately re-implements NOTHING. A fake that
supplied the derivation would be the only correct implementation in the test and
could not observe production failing to derive.

## Mutation table

Each mutant confirmed to build AND test-build; bounded at 300s / `-timeout 180s`;
a non-finishing run or one with no pass/fail actions is VOID.

| # | mutation | result |
|---|----------|--------|
| M1 | sever the STANDALONE derivation (survived in #9141) | **KILLED** |
| M2 | sever the CLUSTER derivation (survived in #9141) | **KILLED** |
| M3 | take the standalone branch in cluster mode | **KILLED** |
| M4 | skip the DHCP block entirely | **KILLED** (both cells) |

Escapes: none. Voids: none.

## Scope note

The issue also asked whether the RA and IPsec branches of the same function have
the same shape. They do — `d.ra` and `d.ipsec` are concrete managers reached from
`applyServicesReconcile` — but that was NOT measured here and is not claimed
fixed. This change makes only the DHCP branch drivable.
