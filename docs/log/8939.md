# #8939 — the flat-set chain is a COMPILER property, not a grammar defect

- **Timestamp**: 2026-09-05
  - **Action**: measured #8939's proposed remedy against the product and
    **refuted it**, then landed the differential instrument that produces the
    real population.

    The issue filed the over-deep flat-set chain as a GRAMMAR defect and
    proposed rejecting such a `set` command at parse time. Measured on the same
    grammar shape, one command each:

    ```
    applications application myapp protocol tcp destination-port 8080
       packed  proto="tcp" dport="8080"     <- compiler WALKS the chain (#6524)
       split   proto="tcp" dport="8080"

    interfaces gr-0/0/0 unit 0 tunnel source A destination B
       packed  src="10.0.0.1" dst=""        <- compiler does NOT walk
       split   src="10.0.0.1" dst="10.0.0.2"
    ```

    Identical nesting, opposite outcome. The discriminator is the CONTAINER'S
    COMPILER, so a parse-time rejection would reject a spelling that a large
    minority of containers handle CORRECTLY today — `applications` among them,
    which has a test file (`compiler_application_chained_leaves_6524_test.go`)
    devoted to the chained form working.

    Population, by compiling packed and split and comparing rather than by a
    schema predicate: **40 containers LOSE the second leaf, 41 WALK it**, 2
    vacuous, 50 unmeasured. All 40 losers lose the second leaf ENTIRELY — total
    silent loss, never partial corruption.

    Two controls make those numbers mean something. A **vacuity control** on the
    WALK side (both forms compiling to the empty config proves nothing) cut 43 to
    41. A **total-loss discriminator** on the LOSE side (does packed equal
    leaf-A-alone?) is immune to whether leaf B takes a value — which the schema
    cannot tell me, as `schemaNode` has no such field.

    The first predicate I wrote was a schema-shape one, and its own positive
    control killed it: it detected **2 of the 4 examples the issue itself
    names**, while flagging hundreds of working lines across the suite. Its
    "0 of 711 shipped set-lines affected" was a real measurement of a predicate
    that answered the wrong question. The differential instrument replaced it
    because it uses the compiler as the oracle rather than a claim about shape.

    Mutation: the fixture moves in BOTH directions (a dropped row reports
    `+ NEWLY LOSING (regression)`, an added row reports `- no longer losing
    (fixed)`), and — the one that matters — mutating PRODUCTION so
    `applicationDirectLeaves` returns only immediate children kills the WALK
    control and its vacuity check together.

    ## CORRECTION 1 — the reachability discriminator is LEAF-LEVEL, not container-level

    I reported that a flat run is operator-reachable where the schema walk
    cannot REACH the trailing tokens, and named two causes: an arg-modelled
    instance container, and an undeclared first keyword. **Incomplete, and the
    third cause is order-dependent within one container:**

    ```
    ike gateway:  address A external-interface E      ACCEPTED
    ike gateway:  version v2-only address A           SCHEMA-REJECT
    login class:  allow-commands "x" idle-timeout 30  ACCEPTED
    login class:  idle-timeout 30 allow-commands "x"  SCHEMA-REJECT
    ```

    > **A flat run is rejected iff the leaf it STARTS at declares a
    > type/validator.** A validated leaf routes to the typed-leaf branch, whose
    > modifier-child check rejects the trailing tokens. An untyped `args:1`
    > leaf falls through to the container branch, which by #3332's
    > compiler-faithful contract DELIBERATELY ignores leftover Keys.

    So "nothing under a named login class is validated at all" — which I wrote
    — is **FALSE**; `idle-timeout` is. What IS container-level is
    unknown-keyword blindness (`bogus-token 5` admits under `class` and under
    `user`), a genuinely separate property. I had conflated the two and told
    lane-8526 so while they were preparing to file a 102-container count of
    the second; correction sent before filing.

    ## CORRECTION 2 — my fix broke a leaf, and the SHIPPED gate caught it

    `expandFlatRun` hoisted EVERY child of a terminating leaf, reasoning that a
    leaf declaring no schema children can have no body. **False for a `multi`
    leaf, and #2419 had already said so**: in `permissions { view; configure; }`
    the children are VALUES. Hoisting them turned a READ leaf into an unread
    one — `system login class <*> permissions`, `A=keep B=inert C=keep D=keep
    E=keep F=drop`.

    **The loser fixture could not have caught this, and #9096 says why in a
    stronger form than I first wrote.** My first reading was that the row was
    already a loser, so it leaving reads as the fix working — true, but weaker
    than the real reason. The collector's eligibility test is
    `children == nil && wildcard == nil && !multi`: **a `multi` leaf is
    excluded by construction**, so `permissions` is inside the 63% #9096
    publishes as discarded before the census runs. The census could not have
    measured that leaf under ANY outcome — this is not a row that happened to
    hide a break, it is a leaf the instrument is definitionally blind to.
    `TestSchemaSpellingDifferentialGate` caught it because it reports
    PER-SPELLING verdicts over a DIFFERENT population, so "read here, inert
    there" is visible as a disagreement rather than as an aggregate.

    That makes it a direct instance of lane-8015's rule, arriving from the
    other side: *the ratchet guards the population; the population was
    filtered first.* Here the filter is `!multi` and the thing that fell
    through it is the leaf my own fix broke.

    > **An aggregate ratchet cannot see a fix that breaks a neighbour inside
    > the same row.** Only an instrument that keeps the dimensions separate
    > can.
