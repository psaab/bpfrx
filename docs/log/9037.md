# #9037 — binary rolling never called `SessionSyncWireCompatible`

- **Timestamp**: 2026-09-06 (lane-8388)
  - **Action**: wired the declared-but-uncalled gate into `runRollingWith`,
    between `HAProtocolCompatible` and `PeerTakeoverReady`, mirroring the
    `kernel_drain.go` sibling that had it all along.

    The interface DECLARED the method, the comment above the declaration said
    *"the session-sync half is SessionSyncWireCompatible below"*, and no line of
    `runRollingWith` called it. Whole-tree call sites before this change:

    ```
    kernel_drain.go:71   syncOK, syncWhy, err := cl.SessionSyncWireCompatible()  <- sibling
    cluster_cli.go:164   the implementation
    rolling.go:33        the interface DECLARATION only
    ```

    A drain hands the RGs to the peer. If the peer cannot decode this node's
    session frames, that handover drops every established flow **while
    heartbeat, election and failover all keep working** — the cluster looks
    healthy and the loss is discovered at the failover, not at the upgrade.

    ## BIND THE WIRING, NOT THE FUNCTION

    This issue IS that lesson: the function existed, was implemented, was
    tested and was CORRECT. Deleting its body proves nothing about a caller
    that never called it — a body-mutation would have been green throughout
    the entire life of the defect.

    ```
    M1  DELETE THE CALL SITE          call sites 1 -> 0, mutant COMPILES (rc=0)
        -> incompatible_wire_aborts_before_demoting      RED
           transport_error_aborts_before_demoting        RED
           compatible_wire_still_completes_the_roll      RED

    M2  over-broad fix: syncOK = false  mutant COMPILES (rc=0)
        -> compatible_wire_still_completes_the_roll      RED  (only)
    ```

    M1 reds all three because the healthy-path cell asserts
    `syncWireChecks > 0` — the gate must be CONSULTED even when it passes, so
    a build where it silently vanished on the happy path is caught too. M2
    reds only the healthy-path cell, which is the over-broad-fix detector: a
    "fix" that refused every roll would satisfy both abort cells.

    Both mutants were confirmed to COMPILE before being scored, and the restore
    was verified by READING the file back (grep counts), not by an exit status
    — a non-compiling mutant emits no `--- FAIL` and reads exactly like an
    escape, and `git checkout -- <file>` is a silent no-op on an untracked one.

    ## The assertion that makes it a gate rather than a report

    `if cl.forced` — ForceSecondary must NOT have been called. A check that
    runs after the demotion has already cut the connections it exists to
    protect, so "aborted" is not sufficient; it must abort with the demotion
    not performed.

    A transport FAILURE reading the peer's version aborts too: unknown is not
    compatible, and treating an unreachable peer as compatible fails open on
    exactly the path where the peer's state is unknown.
