# #9116 — TCP segmentation refused a FIN-bearing oversized segment

- **Timestamp**: 2026-09-06
  - **Action**: both segmentation admission gates now decline SYN and RST only;
    FIN is admitted and carried on the LAST segment, cleared on the others by
    the shared `finalize_tcp_segment_headers` beside the identical PSH rule.

    `(tcp_flags & (SYN | FIN | RST)) != 0 -> None` sent a FIN-bearing oversized
    datagram to `compute_forwarded_egress_ptb`. That returns PTB for IPv6 and
    for IPv4-with-DF, but `Forward` for **IPv4 with DF clear** — so the original
    oversized frame was submitted and dropped downstream, black-holing the
    connection close. There is no IPv4 transit fragmentation engine to catch it
    (grepped; the only fragmentation code is NAT64's).

    SYN and RST still decline: a SYN carries no bulk payload and its options are
    per-connection, and a payload-bearing RST is exotic — conservative stays
    right for both. FIN is different in kind: it is an ordinary data segment
    that also closes the sender's half.

    **Admitting FIN is only half the fix.** A FIN repeated on every segment
    would close the half-connection at the first one and leave the rest of the
    payload outside the sequence space the peer accepts. The clearing rule went
    into the shared oracle in the property harness as well as production, so
    EVERY property that segments a FIN-bearing frame checks the placement rather
    than only the cell that introduced it.

    **An existing property test reddened, and it was a prior decision speaking.**
    `segmentation_declines_syn_fin_rst` pinned the old contract rather than
    detecting a defect. It is narrowed to `segmentation_declines_syn_rst` — with
    the reason recorded at the site — and the FIN case is replaced by a stronger
    property that asserts the frame SEGMENTS and delegates flag placement to the
    shared oracle. That is a better cell than the one removed: it fails both if
    FIN is declined (the defect) and if FIN is smeared across segments (the
    obvious wrong fix).

    **Two gates needed two bindings.** A mutation restoring FIN to the
    PREPARED-TX gate compiled and survived the entire suite, because the
    property test only drives the copy-path builder. A dedicated cell now binds
    the prepared-TX twin.

    Four mutants, each verified to BUILD before scoring, each restore verified
    by reading the file back: restoring FIN to the copy-path decline set reds
    the FIN property; not clearing FIN on non-last segments reds it too, by a
    different assertion; removing the SYN/RST decline reds the narrowed decline
    property; restoring FIN to the prepared-TX decline set reds the new
    prepared-TX cell and nothing else.

    HA wire: nothing moves. No session key, no wire struct.
