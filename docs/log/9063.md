# 9063 — a unit-0 VRF member claimed every tagged sibling on its port

- **Timestamp**: 2026-09-06
- **Action**: let the two consumers tell a WHOLE-DEVICE reference from a UNIT-0
  reference, which the normalized key cannot express.
- **File(s)**: `pkg/daemon/daemon_run_routehelpers.go`,
  `pkg/daemon/vrf_unit0_prefix_claim_9063_test.go` (new).

## The key is right; the consumers were wrong

`logicalUnitDeviceKey` collapses a unit with no vlan-id and unit number 0 to the
bare base — **correctly**, because `ge-0-0-0` *is* the kernel device name for
that unit. So the key cannot be changed. What it cannot express is the
difference between:

```
routing-instances blue { interface ge-0/0/0;   }   # the PORT
routing-instances blue { interface ge-0/0/0.0; }   # one UNIT
```

Both normalize to `ge-0-0-0`, and the two mean different things to a base match.
The **raw reference** is where that distinction survives, and both consumers now
read it: the claim records whether it named the whole device, and
`collectPrefixesForInterface` expands to sub-units only for a bare reference.

## Consequence, narrowed as the issue narrowed it

For a **global-unicast** next-hop the missing entry is harmless — the render
emits a scopeless `ipv6 route <p> <gw>` and FRR resolves recursively. The harm
is real only for a **link-local** next-hop, where FRR rejects a scopeless route:
the static never installs and the prefix blackholes. Preconditions are routine —
a VRF member on unit 0, a tagged unit on the same port in the default table, and
a link-local IPv6 static next-hop.

## Two sites, and the second is invisible from the first

`collectPrefixesForInterface` pulls prefixes **into** the VRF pool for the same
collapsed key — the dual of the exclusion. **A mutation reverting only the
inclusion side survived every default-table cell**, because the tagged prefix is
still in the default pool either way. It needed a VRF-SCOPED route to observe:
with the sibling wrongly in the pool there are two link-local candidates, so the
VRF's own static route stops resolving too.

## Fixture notes, both of which cost a wrong result first

1. **A third IPv6 interface makes every arm read `""`.** The resolver returns
   nothing when the link-local candidate is ambiguous, so my first fixture — with
   a spare `ge-0/0/1` — failed its own positive control for a reason unrelated to
   the defect. One physical port and nothing else.
2. **The resolver keys VRF entries as `vrf-blue`, not `blue`.** Filtering on the
   instance name returned nothing and read exactly like the defect. The harness
   now takes any non-default table rather than restating the spelling.

Also: three earlier probes produced no output because they did not compile
(`Parse` returns `[]ParseError`, not `error`), and I read "no output" as "no
result". **A build failure and an empty result are different states**; check the
build.

## Validation

| mutant | result |

Every arm has a narrowness partner: a whole-device claim must still take the
port, and a tagged claim must still leave unit 0 — which is what makes the fix a
distinction rather than a deletion.
