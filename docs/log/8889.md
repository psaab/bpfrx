# #8889 — nested application-set expansion is quartic and re-runs per policy

- **Timestamp**: 2026-09-05
  - **Action**: memoised `expandAppSet` on `(name, depth)`, and shared ONE memo
    across the whole strict policy validation instead of expanding from scratch
    for every referencing policy. Collapses B⁴ to O(total).
  - **Why it matters**: `CommitCheck` holds the store's READ lock across the
    whole compile (`store_commit.go:70`), and `mu` is a `sync.RWMutex`, so a
    long read-hold blocks *writers* — Commit, Load and the HA `SyncApply` path
    queue behind it. Concurrent readers are unaffected; this needs
    configuration authority and nothing is mis-compiled.
  - **The key carries the DEPTH, deliberately.** A set that expands cleanly at
    depth 0 may exceed the cap of 3 when reached at depth 3, so a name-keyed
    memo would serve a shallow success into a deep context and silently satisfy
    the very guard that makes the cost bounded. `TestDepthCapStillRejects8889`
    asserts a warm memo does not license a deeper reuse.
  - **The depth cap is NOT the defect and was not touched.** It is a working
    guard, and it is what makes "quartic" a derivation rather than a guess.
  - **The guard asserts the CURVE, not a stopwatch**: expansion bodies must be
    bounded by 4 per set (one per `(set, depth)` pair) and bodies-per-set must
    not grow with breadth. Measured, with the naive count printed alongside:

    ```
    breadth= 4 sets= 16 memoised-bodies= 13 naive-bodies=   85
    breadth= 8 sets= 32 memoised-bodies= 25 naive-bodies=  585
    breadth=16 sets= 64 memoised-bodies= 49 naive-bodies= 4369
    ```
  - **File(s)**: pkg/config/predefined.go,
    pkg/config/compiler_validate_strict_policy.go,
    pkg/config/appset_expansion_curve_8889_test.go
