# #9236 — factory reset left a self-decrypting copy of the config DB

## Defect

`PerformZeroizeWipe` erases the live config DB key-first, then TLS material,
login accounts, the archive, BPF pins and networkd files. It had **no knowledge
of `/var/lib/xpf/versions`** — zero occurrences of `versions`, `upgrade` or
`dbsnap` — while knowing `/var/lib/xpf/provisioned-users` and
`/var/lib/xpf/archive`, which is what makes it an oversight rather than a
decision.

Three legs, each checked separately:

1. **The snapshot is a complete copy, key included.** `copyTree` is an
   unfiltered walk of `ConfigDBDir`, and `master.key` lives *inside* that
   directory. The snapshot holds the AES-GCM body and the key that opens it, in
   one place — the project's own threat model (`pkg/configstore/README.md`:
   *"copy `master.key` one directory over and decrypt"*).
2. **It survives a successful upgrade indefinitely.** `flip.go`'s GC keeps a
   snapshot while its version dir survives, and `protected[]` covers
   current/target/previous. After one successful upgrade the target *is*
   current, so it is protected twice over. Steady state, not a window.
3. **Reset reported success anyway** — an affirmative receipt at exactly the
   RMA / resale / re-tenanting boundary this control exists for.

## Censused, not reported

Rather than fixing only the named path, I censused where else a full DB copy
lands. The rollback path stages `.configdb.restore.partial` (the snapshot being
installed) and moves the live DB to `.configdb.old`. Both are complete copies
including `master.key`, and both sit **inside the directory zeroize already
enumerates** — the #5768 owned-name loop matches neither (not the live config,
not the rescue config, not a journal, not a numbered rollback slot, and
`isFsatomicTemp` requires `.tmp-`). The success path removes `.old`, but a
crash between the two renames is precisely the state `restoreDBSnapshot`'s
recovery branch is designed to find, so both can persist.

## Fix

`zeroizeUpgradeDBSnapshots(versionsDir)`, folded into `performZeroizeWipe` as a
security-critical leg whose first error is surfaced.

- **Lock first, fail busy.** The host-wide upgrade lock (`pkg/upgrade/lock`,
  which has no xpf dependencies, so no import cycle) is taken before any
  removal. A busy lock is a **failure**, not a skip: a cut running concurrently
  writes a fresh `.dbsnap` after the sweep has passed it, leaving the box
  factory-reset with a new copy of the DB it just erased — reported clean.
  Failing busy is recoverable; a silent half-erase is not. The lock is only
  taken when there is something to erase, so a never-upgraded box cannot be
  failed busy for nothing.
- **Key-first, reused not reinvented.** `zeroizeDBCopyDir` unlinks
  `master.key`, fsyncs the directory to make that unlink durable, then removes
  the body — the same #4576/#5197 discipline as the live path, and the same
  #9013 symlink refusal in both directions (a symlinked copy dir is refused
  entirely; a symlinked `master.key` still gets its body erased). The same
  helper serves the versions snapshots and the `.configdb` siblings, so the
  discipline has one source rather than three.
- **Never widen a RemoveAll.** The sweep matches only `.<x>.dbsnap` and
  `.<x>.dbsnap.partial`. `.<ver>.partial` is a staged copy of a VERSION
  directory — binaries — and version dirs plus `current` are the running
  system. A dotfile glob would erase the executable the box is about to boot.
  The `.configdb` siblings are matched by exact suffix, never a `.configdb*`
  prefix, which would re-include `.configdb` itself and bypass its symlink
  handling.
- **Every failure is INCOMPLETE.** Busy lock, unlink, fsync — all folded into
  the surfaced result.

and dropping only the call reds five named cells.

M3 deserves a note on how it is observed. Key-first is an ORDERING, and an
outcome assertion cannot see order — after a successful wipe everything is gone
either way. The cell instead seams `zeroizeSyncDir` and inspects the tree **at
the durability point**: `master.key` must already be absent and the body must
still be present. It also asserts the snapshot fsync happened at all, so
deleting the fsync fails loudly instead of leaving an ordering check that is
never reached.
