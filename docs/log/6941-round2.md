# #6941 round 2 — the device question, answered after #7786

- **Timestamp**: 2026-08-28
- **Action**: Resolved. A unit that stays on an interface-level
  `tunnel mode wireguard` now shares the interface device.

## What #7786 changed, and what it did not

Measured at `dec5c6aa9`, both shapes through the production builders:

| shape | endpoint binds | unit addresses on | peers |
|---|---|---|---|
| A: lowest unit carries the tunnel stanza | `wg0u3` | `wg0u3` | merged `[aaaa dddd]` |
| B: unit 0 plain, unit 3 carries it | `wg0` | `wg0` **and** `wg0u3` | merged `[aaaa dddd]` |

**#7786 did not move the device binding** — exactly as its PR asserted. What it
changed is that per-unit peers now INSTALL. That is what turned a latent
inconsistency into a reachable one, and shape B is where it shows: unit 3's peer
is installed on `wg0` while unit 3's address is on `wg0u3`, a device that
carries no endpoint at all. Before the merge that peer was discarded, so the
orphan device referenced nothing and the split was harmless.

So **#6941 is not moot**. The merge made it reachable and, in doing so, made it
answerable: once a unit's tunnel stanza means "contribute peers to the one
endpoint" rather than "define an endpoint", the unit has no need of a device of
its own.

## Why this is not either repair I refuted

The two repairs refuted in round 1 both edited the ENDPOINT's fields, and each
desynchronised something: `LinuxName` from `Ifindex` (breaking three
tombstone-respawn coherence gates), or `logical_ifindex` from everything that
keys on it (to-zone, route→tunnel binding, session identity). This change edits
neither. It moves the UNIT's device name at the compiler, so the unit's
addresses and the endpoint move together and the endpoint's two fields stay
co-sourced from one interface row — the invariant #7785 guards.

## Scope, and why the mode branch is load-bearing

Only a unit that stays on the interface's WireGuard mode shares the device. A
unit that overrides to `gre`/`ipip` keeps `uN`, because `collectAppliedTunnels`
submits a TunnelConfig per record and `pkg/routing/tunnel.go` keys its desired
set by Name: sharing a name across two different MODES would give routing one
device with two records taking different apply paths — a conflict, not the
benign same-name/same-mode sharing that key already relies on.

The first cut did NOT have that branch and reddened 9 tests. Narrowing it to
mode-inheriting units took that to 1. The count is the evidence that the branch
is the real boundary rather than a patch to quiet a failure.

## The one test that still red, and why it is the interesting one

`TestIpipAnchorEmittedClauseIsPointerKeyedNotNameKeyed_6861`. Its fixture
comment says it outright — *"Emitted, and its device DIVERGES from its record's
Name"* — and it built that divergence with
`gr-0/0/0 tunnel mode wireguard` + `gr-0/0/0 unit 1 tunnel mode wireguard`.
**#6861 constructed its pointer-vs-name discriminator on top of the #6941
divergence.** With the divergence gone the device set contains `gr-0-0-0`, the
device clause decides first, and the keying under test is never consulted — the
fixture's own precondition caught it.

Fixed by moving the LEVER, not the assertion: `unit 1 tunnel mode gre` still
produces a Name/device divergence (a mode-overriding unit keeps `uN`), so the
test goes on testing the keying. The reason is recorded in the fixture so the
next person does not restore `mode wireguard` and silently disarm it.

## Not done

The residual that is NOT this issue: a mode-overriding unit under an
interface-level WireGuard tunnel gets a device and no endpoint of its own,
because the WireGuard branch emits exactly one endpoint. That device is dead
config. It is the shape #6861's anchor advisory is about, it is still covered by
the #7785 co-sourcing guard's divergent fixture, and it is a separate question
from the one #6941 asks.
