```

           -> ACCEPTED  gw="G" ipsec-policy="P"  bind-interface="st0.1"
PACKED   gateway G ipsec-policy P bind-interface st0.1;
           -> ACCEPTED  gw="G" ipsec-policy=""   bind-interface=""
```

Still live after #9090, which fixed the sibling IPsec containers.

## Why the existing expandFlatRun call did not fix it

The call site has been there since #9090. **It could not cut.** `expandFlatRun`
segments at tokens the container declares as leaves, and
`security ipsec vpn <name>` declares neither `gateway` nor `ipsec-policy` in
`setSchema` — the compiler reads both, the schema knows neither. Measured:

```
DECLARED: [bind-interface df-bit establish-tunnels ike local-address
           local-identity manual pre-shared-key remote-identity
           traffic-selector vpn-monitor]     closedWorld=false
```

So the run started at an unrecognised head and passed through whole. **The
declaration is not decoration for the split; it is the split's only source of
cut points.**

`ipsecVPNRunSchema9088` augments a shallow copy with those two, rather than
editing `setSchema`. #9088 asks for the compiler walk and says explicitly not to
declare them in `setSchema` first; editing it changes run segmentation,
`SchemaValidate` admission and `?` completion at once, and only the first stops
the loss. Declaring them there is the right follow-up — it is what would make
completion offer `gateway` — with its own blast radius.

## The half the issue did not name, found by a cell rather than by reading

The issue asks for the compiler fix. With only that, `TestPacked…IsSubjectToTheBindInterfaceGate9088`
**still failed**, and the reason is the more serious half:

`validateSecureTunnelBindInterfaceAST` (#5297) walks the **AST**, not the
compiled config, with a bare `inst.node.FindChild("bind-interface")`. A packed
run buries that leaf inside a sibling's Keys, so the lookup returns nil and the
VPN is skipped entirely. `bind-interface ge-0/0/0` — which the gate rejects on
the split spelling — **committed clean when packed.**

So the loss did not merely discard a value; it removed a security gate's
*subject*. The VPN then commits with no XFRM device at all, which is precisely
the silent-tunnel-down condition #5297 was written to prevent. A cell that only
compares two compiled configs cannot see this, because both spellings are
"accepted" either way.

This is `ipsecTrafficSelectorSchema8939`'s recorded lesson pointed the other
way: there, fixing only the compiler would have left the packed spelling
*rejected*; here it left it *ungated*. Both follow from a gate and a compiler
disagreeing about where a run ends, which is why `findChildInRun9088` is a
shared helper rather than an inlined expansion.
